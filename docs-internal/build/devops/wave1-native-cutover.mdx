## Production hold

`productionPublicationPolicy` in `tuturuuu.ci.ts` admits Calendar frontend only.
Meet, Mail and Apps remain held. A production push reports **held for wave-1 cutover** in the planner log and
summary and selects no publisher for those apps. Manual planner dispatch and
package recovery honor the same hold. All four direct legacy Vercel publishers and
Meet's native frontend/realtime publisher check it before any production credential
use, including validation cache and public build configuration. A held direct
production Meet invocation skips validation and publication. PR/main build and
original/restored runtime validation continue. Native Calendar/Mail validation
uses fixture configuration and empty Turbo cache inputs on production; native
Apps validation uses no production secrets. Other apps' deployment selection is
unchanged. This allows ordinary fixes to ship without native cutover.

Meet keeps its existing frontend and realtime Worker versions. Calendar, Mail and
Apps keep their existing Vercel deployments and canonical domains. Retain disabled
Vercel Git deployment and current framework settings. Never bypass the native-source
Vercel guards. A held app has no new deployment marker; **Held** is not delivery.

The policy schema requires a record for every protected app with `state` and a
nonempty, single-line `reason`. A held record uses `state: 'held'`. An admitted
record uses `state: 'admitted'` and explicit `surfaces`: `['frontend']` for Calendar,
Mail and Apps, or `['frontend', 'realtime-do']` for Meet. Missing/empty/malformed
records, unexpected fields and unknown workflow names hold publication. Deleting
a hold never admits publication. Known unrelated publishers keep normal selection,
and Supabase production migration eligibility keeps its existing gates. Calendar's legacy
Vercel production target stays disabled even after native admission. The planner
selects Calendar's native workflow only; its legacy native-source guard remains
intact as a final refusal boundary. Root
`production-publication-policy.test.js` covers policy mutations, planner outcomes,
CLI outputs and the direct publishers' dependency on the policy job.
`production-publisher-secrets.test.js` parses all legacy/native workflow jobs and
checks secret-bearing environments and action inputs against admission, with a
negative control for independent Meet validation.

The hold applies to runs using this source. Rerunning an older workflow retains
its original source and cannot acquire a later policy. The release owner retains
custody of pre-hold runs and their resulting deployment baselines.

## Mail bridge request ordering

Mail checks host/path ownership and rejects mounted session-writing endpoints
before shared-origin routing, request preparation or bridge dispatch. The mount
resolver determines mounted versus root requests; session routes use the same
segment matching as the endpoint dispatcher, including repeated/trailing slashes.
Root-host session endpoints retain their existing behavior. Shared-origin routing
keeps its separate mode and readiness gates; bridge adoption does not admit traffic.

Every response retains Mail's response policy, and HTML responses also receive the
per-app document security headers. The focused
`apps/mail/src/runtime/mounted-session-endpoints.test.ts` suite checks ordering,
route variants, root and neighbouring-route controls, routing refusal and document
headers through the real bridge with fixture application/provider boundaries.

## Release gates

Each app needs its own reviewed admission PR and exact accepted production SHA.
Tests, types, lint, a real native build, sealed original/restored runtime acceptance
and transitive supplier checks qualify that source. Keep the production publisher
route-free; admission permits upload without moving canonical traffic. Review and
freeze the exact promotion range before production sync.

The production-first cutover sequence is:

1. Deploy the exact sealed production artifact privately with production runtime
   configuration. Workers.dev and version previews remain disabled. Smoke the
   candidate on an explicitly admitted temporary custom host after upload, then
   remove that domain before the canonical switch. Staging acceptance remains
   useful evidence but is not a flip prerequisite.
2. Capture the current DNS record, proxy flag, TTL, every zone route, immutable
   Vercel fallback and old/new Worker versions. Rehearse the exact rollback and
   measure route detachment through verified fallback in under two minutes.
3. Attach the reviewed canonical Worker Route with its scriptless ACME exclusion. Source sync alone never
   attaches routes or activates schedulers.
4. Immediately verify signed-in EN/VI, auth handoff, provider connection, one read
   and one write. The operator's production browser owns signed-in checks.
5. Watch errors, exceptions, 5xx and auth loops for 30–60 minutes. Any auth or data
   error triggers immediate routing rollback, followed by a fix and a fresh flip.

Mail additionally needs provider/webhook/attachment checks; Calendar needs
provider/offline/Tasks checks; Meet needs hosted media/reconnect/SFU/TURN; Apps
needs redirects and canonical-host fence checks. Meet rollback captures **both**
frontend and realtime versions. Calendar/Mail/Apps use the
[private production preparation workflow](/build/devops/wave1-native-publishers#route-free-production-preparation).

### Calendar route and certificate continuity

Calendar admits exactly two root hosts: canonical `calendar.tuturuuu.com` and
staging `calendar.staging.tutur3u.com`. Unknown hosts remain rejected and one-origin
mounts stay disabled. The temporary production-smoke host
`calendar-cutover.staging.tutur3u.com` is retired now that the canonical flip is
accepted. `rootHosts` is shared source compiled into **both** the staging and the
production artifact, so a temporary host can never be proved to bind only the
production Worker; it must not outlive its smoke window. The former
`calendar-staging.tuturuuu.com` and `calendar-cutover.tuturuuu.com` names stay
reserved from managed projects and are rejected by the Calendar host boundary.
A future app's production smoke host follows the same rule: admit it in its
cutover PR, attach it only after the private publisher succeeds, detach its domain
before the canonical switch, and remove it from `rootHosts` in an immediate
follow-up after acceptance. Detach any `calendar-cutover.staging.tutur3u.com`
Custom Domain or DNS record that remains on the `tutur3u.com` zone.

Export the full zone and Vercel fallback before writes. Proxy only Calendar's
existing CNAME, retaining its Vercel target. Verify HTTPS, legacy smoke, redirects,
headers, uncached identity and the ACME challenge path through Cloudflare. A
Vercel bot challenge on Cloudflare egress fails this fallback gate. Retain any
operator-approved Cloudflare-IP firewall bypass while Vercel is the rollback
origin, then remove that bypass rule once Calendar leaves Vercel. If this
baseline fails, restore DNS-only immediately. Do not change zone-wide TLS, cache
or firewall settings. Measure attach/detach/fallback on a disposable noncanonical
route, then prepare two explicit routes:

- `calendar.tuturuuu.com/.well-known/acme-challenge/*` with **no script assigned**.
- `calendar.tuturuuu.com/*` → `tuturuuu-calendar`.

Create the scriptless exclusion first and capture its returned ID immediately
before the main route flip. Record the main route ID after attachment. The capture
tool retains every zone route and reports both named Calendar handles, including
scriptless exclusions. Rehearse rollback using both exact IDs. Delete the main
route first, confirm the Vercel fallback, then delete the owned ACME exclusion.
Preserve any exclusion that predates this cutover instead of deleting another
operator's route. `calendarRollbackRoutes` validates both handles and deletion
order; its `createdAcmeRouteId` must match the ID returned by this cutover's
route-creation operation. Record that creation receipt with the capture. Without
that proof, rollback preserves the existing ACME exclusion. If its captured handle
is missing during an emergency, rollback may still remove the verified main route
and preserve all ACME exclusions. API observations must
confirm the captured pattern and owner before each delete. The accepted proxied
baseline avoids a DNS propagation wait.
The rollback target is Vercel serving the same legacy behavior as before cutover.
The accepted CF baseline has robots 200, login redirects 307, protected requests
401, uncached Vercel identity and GET/HEAD ACME origin reachability. The legacy
Next app omits `X-Frame-Options: DENY` and redirects crawler requests instead of
rendering native SSR. These are pre-existing legacy behavior: Cloudflare passes
response headers through and the status paths retain the legacy Next responses.
Record those differences instead of claiming the legacy target passes native
acceptance. Native smoke and post-flip security expectations remain unchanged.

[Vercel uses HTTP-01 for non-wildcard certificate renewal](https://vercel.com/docs/domains/working-with-ssl).
The more-specific [scriptless route bypasses Workers](https://developers.cloudflare.com/workers/configuration/routing/routes/#matching-behavior)
and sends ACME traffic to the retained proxied Vercel origin. There is no Worker
forwarding path. Keep `global_fetch_strictly_public`: fetching the canonical URL
inside this Worker would re-enter the public route and could recurse. Route
exclusions apply to the complete matching path prefix; origin handling still owns
the HTTP method and challenge response. After the flip, verify GET and HEAD ACME
requests end to end with uncached Vercel identity and no native Worker execution.
The production publisher filters attachments by `script === name`, so this
scriptless exclusion does not attach the Worker or prevent its private upload.
Regression coverage includes `calendar-routes.test.mjs`, `capture.test.mjs`, the
canonical-host ACME negative case and retired-host rejections in
`root-cutover.test.ts`, and the publisher's
scriptless-topology control. A currently valid certificate alone does not prove
future renewal safety.

For Meet restore the captured frontend version, then realtime if changed; preserve
Custom Domains. For Calendar/Mail/Apps retain their immutable Vercel deployments.
Reverting Worker code does not restore routing. Restore exact captured Route/Custom
Domain and DNS/proxy topology before disabling a candidate. Never replay uncertain
Mail sends or change ingestion/R2 ownership as a frontend rollback. Rehearse recovery;
DNS TTLs and provider convergence prevent assuming instantaneous rollback.

## Subdomain cutover tools

Native apps go live on their own subdomain first (root mode). Two read-only
scripts support rollback capture and post-deploy checks:

- `node scripts/native-cutover/capture.mjs --host <app>.tuturuuu.com --vercel-project <project> [--cf-zone-id <zone>] --out tmp/native-cutover-<app>.json`
  records DNS, the live edge (`server`, `x-vercel-id`, `cf-ray`, runtime
  header), Vercel's current production deployment (URL and `dpl_` id) and, with
  a dedicated `CLOUDFLARE_READONLY_API_TOKEN`, the host's DNS record (proxied
  flag, TTL) and **every route in the zone**, including wildcard routes and
  scriptless exclusions. Run it again immediately before the flip; production
  deployments keep moving.
- `node scripts/native-cutover/smoke.mjs --origin https://<app>.tuturuuu.com --app <id> --expect native|legacy`
  checks robots, the anonymous login handoff (return URL on the app host,
  `nextUrl` kept), a protected API (401), build-info, the server-function guard,
  crawler SSR with a working asset, a wildcard `Accept-Language`, the runtime
  header and the anti-framing headers on every response. Run `--expect legacy`
  before the flip as the baseline and `--expect native` after it.

The dedicated capture token needs only **Zone DNS:Read** and **Workers Routes:Read**,
restricted to the **tuturuuu.com** zone. Do not supply a generic deployment token.
The zone ID must contain exactly 32 lowercase hexadecimal characters; the host
must be a DNS hostname without a scheme, port, path or query.

Captures contain production `*.vercel.app` URLs, which can reveal origin-bypass
hints. Store them only under gitignored `tmp/` or the private operations ledger,
and never commit them. CLI stderr retained in a failed capture is limited to
2,000 characters. Cloudflare credentials are redacted from results and upstream
error details are omitted.

`matchesRoute(pattern, requestUrl)` in `scripts/native-cutover/route-pattern.mjs`
implements the [Cloudflare route pattern rules](https://developers.cloudflare.com/workers/configuration/routing/routes/#matching-behavior):
optional HTTP/HTTPS scheme, leading host `*` (including `*.` and `*host`),
case-sensitive paths and trailing path `*`. It matches individual URLs, including
query strings; it does not select the winning route or establish DNS/zone eligibility.
Host matching uses the current case-insensitive rule; pre-15 October 2023 routes
can have case-sensitive host semantics. Keep the full inventory regardless of
which routes match a probe URL, since narrower paths and scriptless routes matter
for rollback.

Smoke checks resolve relative `Location` headers against the tested origin.
Transport, redirect parsing, body-read and asset-fetch errors produce a failed
row and leave the remaining checks running. Run the synthetic regression suite
with `node --test scripts/native-cutover/*.test.mjs`; it uses no provider tokens.

Prefer a rollback that does not wait on DNS: once the host's record is proxied
and serves the Vercel origin correctly, cut over by attaching the Worker route
and roll back by detaching it. A DNS-only CNAME switch rolls back only as fast as
its TTL.

Observe Apps for at least 14 days and Meet/Mail/provider-critical Calendar flows for
30 days or the relevant business cycle before separately authorized decommissioning.
No hold removal, resource provisioning, deployment or DNS change is authorized by
this runbook alone.

## Shared-origin mount flags

Meet and Mail move from their subdomains to `tuturuuu.com/meet` and
`tuturuuu.com/mail`. Meet's Worker entry and Mail's request handler run
`decideOneOriginRequest` (`@tuturuuu/utils/one-origin-routing`) before anything
else. It reads two per-app
Worker variables:

| Variable | Values | Effect |
| --- | --- | --- |
| `TTR_ONE_ORIGIN_MEET` / `TTR_ONE_ORIGIN_MAIL` | `off` (default and any unknown value), `shadow`, `on` | `off`: the shared origin returns 404. `shadow`: both hosts serve; shared-origin responses carry `X-Robots-Tag: noindex`. `on`: subdomain navigations redirect to the shared origin. |
| `TTR_ONE_ORIGIN_<APP>_REDIRECT_STATUS` | `307` (default), `301` | Use `307` (`Cache-Control: no-store`) through observation: 3 days for Meet, 7 days for Mail. Promote to `301` only after that window, because a cached 301 cannot be revoked by a route rollback. |

Redirects apply only to subdomain GET/HEAD navigations: `Sec-Fetch-Mode: navigate`,
or an HTML `Accept` header without Fetch Metadata. They keep the raw path and query
bytes, and the subdomain root maps to the canonical `/<app>/` (the bare `/<app>`
is canonicalized by a zone redirect, because Worker routes cannot match it once a
query string is present). Machine traffic is always served on the subdomain and never redirected.
That covers `/api/*` (webhooks, OAuth callbacks), `/assets/*`, `/.well-known/*`,
WebSocket upgrades, server functions (`/_serverFn` and the legacy app bases) and
Meet's `/live-connect`. The decision never rewrites URLs. The Start bridge
resolves the base per request, serving the subdomain at its root and the shared
origin under `/<app>` from one artifact.

Each app's `basePathReady` constant (`apps/meet/cloudflare/one-origin.ts`,
`apps/mail/src/runtime/one-origin.ts`)
stays `false` until its Start bridge build routes under `/<app>`. While false, the
shared origin is refused in every mode and the subdomain behaves exactly as before.
Setting the variables, attaching zone routes and changing the redirect status are
release actions that need user approval.

### Document security headers

Same-origin apps form one trust domain, so each app carries its own document
policy (`@tuturuuu/utils/security-headers`). Meet's Worker entry and Mail's
request handler apply it to `text/html` responses only. They never replace a
header the route already set.

- **Enforced now:**
  - `X-Content-Type-Options: nosniff`.
  - `Referrer-Policy: strict-origin-when-cross-origin`.
  - An explicit `Permissions-Policy`. Meet allows `camera`, `microphone` and
    `display-capture` for itself. Mail denies all three, so a camera grant made to
    Meet on the shared origin cannot be used from a Mail document.
- **Report-only:** `Content-Security-Policy-Report-Only` sets no `'unsafe-inline'` or
  `'unsafe-eval'` for scripts, plus `require-trusted-types-for 'script'`,
  `object-src 'none'`, `base-uri 'none'` and `frame-ancestors 'none'`. On the
  shared origin, "self" is path-scoped to `https://tuturuuu.com/<app>/` plus
  `https://tuturuuu.com/api/`, so Meet's policy reports a fetch to `/mail/...`.
  Violations stay in the browser console unless the Worker variable
  `TTR_CSP_REPORT_URI` names a report endpoint.

Report-only is burn-in on the subdomain, not admission. Every app shares one
session on `tuturuuu.com`, so the CSP and Trusted Types must be **enforced** before
an app is routed onto the shared origin in any mode, `shadow` included.
Enforcement needs a per-request script nonce passed to the Start router
(`ssr.nonce`) through the Start bridge request context, and zero remaining
violations for each app. Inline scripts are expected to report until then.

### App-switch metrics

App-switch time-to-interactive (ASI) is measured from the click on a link to
another app until the destination's `ttr:app-ready` mark. It runs on both
topologies, so the subdomain baseline and the shared-origin result are
comparable.

- **Source:** `AppSwitchTracker` (`@tuturuuu/satellite/app-switch-tracker`) is
  rendered by the satellite `ClientProviders` and by Web's client providers. On a
  click to another app it writes a 30-second `ttr_switch=<epoch-ms>.<from>` cookie
  on `.tuturuuu.com`.
- **Destination:** Meet and Mail read the cookie two frames after hydration on a
  non-auth page, clear it and set `ttr:app-ready`. A sign-in handoff on the way is
  recorded as `handoff`. 10% of switches send a beacon to `<mount>/_rum`.
- **Payload:** app slugs, topology, duration, prerender/handoff flags, protocol,
  connect time and effective connection type. No user, URL or workspace
  identifiers.
- **Ingest:** `handleAppSwitchBeacon` (`@tuturuuu/utils/app-switch-rum-ingest`)
  turns one anonymous POST into at most one Workers Analytics Engine data point.
  Every gate must pass, and any failure drops the beacon with a `204`:
  - The `APP_SWITCH_RUM_INGEST` Worker variable is exactly `on`. Any other value,
    including unset, answers without reading the body.
  - An `APP_SWITCH_RUM` dataset binding exists.
  - The body is at most 1 KiB in **bytes**, read as a stream that is cancelled on
    overflow (`413`) or after a one-second deadline (`408`).
  - The isolate's pre-filter has room: 30 points per 60 seconds per isolate.
  - The durable admission shared by every instance has room in its window and is
    not stopped. Admission that is missing, never started or failing admits
    nothing. An operator stop survives restarts and redeploys, and resuming never
    replays dropped beacons.

  Failed writes are never retried. Client sampling and ingress rate limits are not
  spend caps. `app-switch-rum-ingest.test.ts` covers concurrent instances against
  one budget, stop after restart, storage failure and the byte bound. Meet and Mail
  bind no admission today, so ingest cannot write. The durable admission (a Durable
  Object store), its operator controls and the `APP_SWITCH_RUM` dataset binding
  (`ttr_app_switch`) ship together as one reviewed Worker configuration change.
  That change also needs exact-commit evidence that it meets the
  Cloudflare billable-operation rules.

`scripts/perf/app-switch-lab.mjs` is the lab counterpart. Run it on a Studio host
through `ttr resources run`.

- `switch` mode clicks a link from `--from` and waits for `ttr:app-ready`. It falls
  back to `--ready-selector` or the load event on builds without the tracker. It
  reports p50/p75/p95 over `--runs` with optional `--throttle slow4g` and `--warm`.
- `ttfb` mode compares `--urls` for gate W1 (Web through Cloudflare compared with
  direct Vercel).
- Signed-in runs take a Playwright `--storage-state` file for a synthetic account,
  created out of band. The report never includes its path.
