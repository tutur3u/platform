## Scope and admission

Land the production hold before these publisher changes. Meet, Calendar, Mail and
Apps production publication remains **held for wave-1 cutover**. The production
planner holds in `tuturuuu.ci.ts` remain authoritative. Native Calendar/Mail/Apps
jobs retain the fallback hold diagnostic in `scripts/ci/wave1-native-profiles.json`.
The validated per-app `productionPublicationPolicy` controls the new private production
uploader. A later explicit cutover PR must admit only that app and its exact
production promotion range; deleting a diagnostic string never admits publication.

These workflows add no automatic schedule and perform no provider or DNS setup.
PR profile qualification has read-only deployment permission. Each caller grants
`deployments: write` only to its separate staging publication job, after successful
profile qualification and staging policy admission on a main push or dispatch.
The reusable qualification workflow never calls a publisher, so read-only callers
do not need to grant nested write permissions. `wave1-native-permissions.test.js`
covers this boundary, including same-repository PR events.

Main pushes and trusted main dispatch can publish **staging only**, after provisioning
the repository enable flag and an exact source/artifact admission. PRs and other branches qualify artifacts without
publication. Existing Vercel deployments, project framework settings and disabled
Git deployment remain unchanged. Existing central APIs and scheduler/provider owners
stay authoritative; a native frontend is not a completed Vercel exit.

## Identities and resource continuity

Owner decision: staging stays in the production Cloudflare account. The
`stagingAdmission` record in `scripts/ci/wave1-native-profiles.json` records this
exception as `same-account-staging-only`, with `shared-account` residual risk and
a required scoped token. The account identity is supplied by the repository variable
`CLOUDFLARE_STAGING_ACCOUNT_ID`; publication compares its value with the reviewed
profile account and fails closed if absent or different. No new account is created.
This is resource and credential isolation within one account, with shared account
administration, account-wide limits and billing risk. A secret name cannot prove
its actual permission scope: the owner must provision and review a token limited
to the staging operations/resources supported by Cloudflare, and acknowledge any
remaining account-level Worker permission exposure before admission.
`CLOUDFLARE_WORKERS_SUBDOMAIN` is the owner's actual account subdomain, not a guessed
hostname. Configure it as a repository variable. Staging hosts are the corresponding
Worker name followed by `.<CLOUDFLARE_WORKERS_SUBDOMAIN>.workers.dev` as an identity
only; those URLs are disabled for serving.

| App | Staging Worker | Held production Worker / canonical host |
| --- | --- | --- |
| Calendar | `tuturuuu-calendar-wave1-staging` | `tuturuuu-calendar` / `calendar.tuturuuu.com` |
| Mail | `tuturuuu-mail-wave1-staging` | `tuturuuu-mail` / `mail.tuturuuu.com` |
| Apps | `tuturuuu-apps-wave1-staging` | `tuturuuu-apps` / `apps.tuturuuu.com` |

Publication profiles are derived explicitly from the original Void-emitted config;
the source configs are retained. The derived config, original modules/assets and
manifest are sealed together, then restored without rebuilding. Nonempty source
resource bindings, routes and unreviewed vars fail qualification rather than being
dropped. Frontends have only ASSETS; Calendar and Mail preserve central API ownership.
There is no D1, KV, DO, queue or scheduler binding for these three frontends.
The publisher uses a separate owner-provisioned D1 control database; it is never
bound to application Workers.

Staging uses `https://web.staging.tutur3u.com` and staging Supabase/public configuration.
It does not activate production callbacks or processors. Mail's production R2 S3
access continues to the existing `tuturuuu-mail` bucket; its staging descriptor names
`tuturuuu-mail-wave1-staging` with separate credentials. Never repoint the existing
`tuturuuu-mail-email-routing` ingestion Worker, signing identity, bucket, MX records
or canonical webhook as part of frontend staging. Preserve optional SES credentials
for legacy attachment reads before production admission.

Apps staging has no canonical routes, `APPS_CANONICAL_HOST_ENABLED=0` and noindex.
Its separately built production profile sets the fence to `1` and declares its
canonical Custom Domain. That configuration is qualified by original/restored
workerd checks while publication remains held. Merely attaching the staging profile
to the canonical host would return 503 and is forbidden.

## One-time owner provisioning

1. Retain the production hold. Create protected GitHub environments
   `wave1-<app>-staging` and `wave1-<app>-production` for Calendar, Mail and Apps.
   Production needs explicit release-owner approval. Use a least-privilege
   `CLOUDFLARE_STAGING_API_TOKEN` for staging only; this is the only deploy-token
   secret referenced by staging publication. Never store a production token under
   that name. The workflow never reads `secrets.CLOUDFLARE_API_TOKEN` or production
   token secrets. Only the staging token is mapped to Wrangler's standard
   `CLOUDFLARE_API_TOKEN` process variable, after admission. Never copy credential
   values into source or evidence. Set `CLOUDFLARE_STAGING_ACCOUNT_ID` to the reviewed
   shared account identity. Missing or mismatched identity denies publication.
   Provision `WAVE1_CONTROL_READ_TOKEN` with repository Variables read permission
   for the fresh stop-fence observation. Do not assume `actions: read` supplies
   that permission; see [GitHub's variable API permissions](https://docs.github.com/en/rest/actions/variables#get-a-repository-variable).
   Both reusable workflows declare and explicitly forward only these two staging
   credentials plus the two public Supabase inputs; neither uses secret inheritance.
   Only the protected publisher step receives deploy/control process variables.
   Keep deploy/control values exclusively in the protected staging environment,
   restricted to main and owner approval; never give PR jobs a repository-level copy.
   The staging deploy token also needs D1 write access to the staging control database.
   GitHub job tokens and the Variables-read token must have no D1 authority.
2. Set the actual `CLOUDFLARE_WORKERS_SUBDOMAIN` repository variable. Provision the
   three staging Workers with `workers_dev=false`, `preview_urls=false`, no routes,
   and an accepted initial version. The publisher intentionally refuses a missing
   Worker or missing rollback deployment instead of bootstrapping resources.
   Bootstrap through the owner's reviewed infrastructure procedure with the identities
   and resource descriptors in `wave1-native-profiles.json`; do not use canonical configs.
3. Provision Mail's isolated staging R2 bucket and scoped S3 credentials according to
   that descriptor. Never reuse production storage/resource IDs or encryption/signing
   keys in staging. Grant only staging access to staging secrets. Confirm the existing staging central
   issuer/API and Supabase instance are admitted for disposable acceptance.
4. Provision Worker secret **names** from each app's `secrets` list in the profile
   file. Values stay in the provider. The workflow checks names through the API and
   never uploads secrets. Calendar additionally requires the registered Google and
   Microsoft callback URLs declared in the profile vars. Mail's ingestion secret,
   connected-account encryption key and storage credentials preserve the owning
   environment's identity. Optional names are listed separately; provider acceptance
   must identify which are required for the configured transports and old attachments.
   Calendar alone treats `TUTURUUU_APP_COORDINATION_SECRET` as optional because its
   shared token service accepts `SUPABASE_SECRET_KEY`. Preserve Mail and Apps
   requirements. Hosted auth continuity must prove agreement with the staging issuer;
   declaring the fallback does not prove matching signing keys.
5. Supply the public GitHub repository variables `STAGING_SUPABASE_URL` and
   `STAGING_SUPABASE_PUBLISHABLE_KEY` for trusted-main staging qualification.
   Qualification has no environment membership or forwarded credentials, so it
   neither waits for a protected-environment reviewer nor receives publisher
   secrets. Existing native source workflows also use these public variables.
   The protected `wave1-<app>-staging` environment remains publication-only; retain
   its existing deploy/control secrets and matching public-input secret names for
   the publisher. Do not duplicate credentials into repository secrets.
   Held production builds retain fixtures and
   read no production inputs. Only public Supabase inputs reach staging builds.
   Missing values allow source-only fixture artifacts, which cannot publish: the
   publisher rejects fixture URLs, different public-input fingerprints or a different
   account subdomain. Environment overrides must agree with the qualified artifact.
6. After owner review, set the exact `WAVE1_STAGING_PUBLICATION_ADMISSION` record
   described below and repository variable `WAVE1_STAGING_PUBLISH_ENABLED=true`.
   Only that admitted main source and artifact can publish once; later sources
   default to denied. Retain the same qualified archive when resuming a failed
   publication job after updating admission.
   Turning it off is the durable stop fence for subsequent writes; the publisher reads
   it freshly immediately before its sole deployment. This cannot cancel a write
   already accepted by Cloudflare. No resources, settings, secrets or DNS were created
   by authoring these workflows.
   Both control values remain repository variables. Their fresh API observations
   use the existing Variables-read token; no environment-variable read permission
   or token rotation is required.

## Exact artifact and publication gates

`wave1-native-app.yaml` builds staging and held production profiles in exact-source
CI. Each runs original workerd acceptance, the credential-free
`wave1-native-publish.mjs dry-run` size guard, seal, bounded archive, separate-job
restore, repeated workerd acceptance and the same size guard, then final seal
verification.
Mail has its own original/restored native Worker checks. Calendar and Apps keep their
existing deeper SSR/offline/RPC/browser gates; the new checks do not replace them.

The native public `/api/build-info` endpoint reports bundled full SHA, app and
environment before session middleware, accepts only GET/HEAD/OPTIONS, and is no-store.
It exposes release metadata only; the shared [product contract](/platform/applications/native-release-identity) records scope and exceptions. Original/restored checks compare this identity,
actual static asset bytes, anonymous private-page login handoff for Mail/Calendar,
and Apps' staging canonical refusal versus admitted production fence behavior.
Runtime credentials are disposable and network egress is denied. This finite fixture
is not hosted provider, signed-in browser, or complete SDK descendant-cleanup proof.
CI step/job timeouts fail a stuck runtime rather than relaxing assertions.

The publisher restores the same-run archive and rechecks runtime before credentials
are introduced. It observes [Cloudflare's deployment/version APIs](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/deployments/methods/list/) and captures the existing deployment's weighted rollback versions,
checks expected secret names, rechecks the fresh stop fence and seal, then invokes
Wrangler once against the sealed config. The version tag is the complete artifact
receipt digest and its message is the source SHA. The hosted active version/tag
and disabled workers.dev/preview state must match before recording a GitHub
deployment marker. Original/restored CI proves the HTTP build identity locally.
Staging and production marker environments remain distinct.

## Finite publication admission and uncertain outcomes

`WAVE1_STAGING_PUBLISH_ENABLED=true` alone authorizes zero uploads. The owner must
also set the repository variable `WAVE1_STAGING_PUBLICATION_ADMISSION` to one exact
app/source/artifact record after reviewing the qualified artifact receipt. All
fields are required, unknown fields are refused, and the account is named by
variable reference, never copied into the admission JSON:

```json
{
  "schema": 1,
  "app": "mail",
  "sourceSha": "<full admitted source SHA>",
  "artifactSha256": "<SHA256 from artifactDigest of wave1-artifact.json>",
  "isolation": "same-account-staging-only",
  "accountIdEnv": "CLOUDFLARE_STAGING_ACCOUNT_ID",
  "tokenSecret": "CLOUDFLARE_STAGING_API_TOKEN",
  "scopedTokenRequired": true,
  "residualRisk": "shared-account",
  "publicationVariable": "WAVE1_STAGING_PUBLICATION_ADMISSION",
  "maxUploadsPerArtifact": 1
}
```

This admits at most one upload for that artifact, with zero application retries.
Later main pushes and other apps are denied until the owner explicitly replaces
this record. Deleting the record or disabling the enable variable stops future
uploads. Both are freshly read from GitHub before preflight and again immediately
before upload; deletion, malformed data, denial or timeout fails closed. The earlier
policy job checks source admission; the publisher additionally checks the exact
restored digest. These controls stop publication, not invocations of an already
serving Worker; the owner must separately disable serving to stop its runtime spend.

Before enabling publication, the owner must provision a dedicated staging D1
control database and set `WAVE1_STAGING_ATTEMPT_D1_ID`. This is option (a): D1 SQL
supports atomic comparison against the previous record, whereas KV visibility can
lag, and repository Deployments remain writable/deletable by PR job tokens.
No new GitHub App/bot credential or public control Worker is needed. The table is:

```sql
CREATE TABLE wave1_attempts (
  app TEXT PRIMARY KEY,
  record TEXT NOT NULL
);
```

Seed one row per app (`wave1-mail-staging`, `wave1-calendar-staging`,
`wave1-apps-staging`) through the owner's separately reviewed infrastructure
procedure. The `record` value is the output of exported `signAttemptState(data,
stagingToken)` from `scripts/ci/wave1-native-attempt.mjs`, with data shaped as:

```json
{
  "schema": 1,
  "scope": {
    "databaseId": "<WAVE1_STAGING_ATTEMPT_D1_ID>",
    "repository": "tutur3u/platform",
    "app": "mail",
    "worker": "tuturuuu-mail-wave1-staging",
    "accountId": "<CLOUDFLARE_STAGING_ACCOUNT_ID>"
  },
  "entries": []
}
```

The token must come from private environment injection, never command arguments,
source or logs. The signed envelope contains serialized data plus a domain-separated
HMAC-SHA256, using only the staging deploy token as signing authority. Each entry
binds the original GitHub run ID/attempt, full admission, SHA, digest, account,
Worker and rollback versions to progress. Only a genuinely unused app may be seeded
with empty history. Never reseed an existing app to retry: migrate/reconcile prior
GitHub attempt records and provider versions first, preserving all consumed and
uncertain identities. Token rotation requires owner verification and re-signing
of the existing complete ledger, never resetting its history.

The publisher only SELECTs and conditionally UPDATEs the existing app row; it never
creates a missing row/table or inserts a replacement. Before any upload it persists
signed pending state with a compare-and-swap and authenticates the readback. A
lost write response remains consumed/uncertain on restart. Missing/deleted records,
invalid signatures, wrong scopes, failed queries and concurrent changes block upload.
An ordinary GitHub deployment/status, including a forged terminal or newer record,
has no authority over this ledger. The ordinary success marker remains diagnostic.
The exact owner admission remains a separate fresh GitHub Variables observation;
a valid D1 ledger alone grants no upload.

A definitive final fence/seal refusal records failed and consumes admission. Upload
exceptions remain pending, and failures after a returned upload stay uploaded.
Any preceding unresolved entry blocks a different artifact; terminal entries remain
in the signed history, so consumption cannot be erased by renewing the admission.

Reruns load this ledger and inspect the [Worker versions API](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/versions/methods/list/),
including inactive versions. Each listed version is read by ID because the list
response does not include artifact annotations. Exactly matching SHA plus digest is
reconciled against active 100% deployment, version annotations and disabled
workers.dev/preview URLs without uploading or activating anything. Public HTTP
identity probing is deliberately absent while ingress is disabled; real workerd
identity and behavior acceptance remains required on original/restored bytes in CI.
An inactive match remains uploaded until the owner resolves
activation under separate authority. A previous attempt with no matching version is
blocked, even after failed status; absence is not proof that the original write did
not happen. Preserve the original operation identity, inspect provider/audit evidence,
and obtain a new explicitly reviewed artifact admission only after resolving an
uncertain outcome. A lost Wrangler receipt does not permit a second upload.

Reads have 15-second deadlines, 1 MiB response bounds and no application retry.
The signed ledger is at most 512 KiB and fewer than 100 retained entries. A full
ledger blocks publication and requires reviewed archival/reconciliation; it is never
automatically truncated. Each SQL query uses the app primary key and at most one
row; a normal success uses seven D1 queries (one read, three conditional updates
and three readbacks), six other provider reads with empty version history, and four
GitHub variable reads. Version history has one page of fewer than 100 entries;
a full/additional page blocks, and each version needs one detail read. There is no
application retry. The publication step has a five-minute watchdog; each single
Wrangler invocation has a 180-second limit. Wrangler's internal asset requests/retries
are additional, bounded by that watchdog and the 50,000-member / 1 GiB artifact
ceiling. Non-cancelling app/environment concurrency and SQL conditional updates
protect consumption across runners. A new owner admission is required for another
artifact. No recurring producer, automatic renewal or public control endpoint exists.

## Serving cost and emergency stop

All staging profiles, including the prepared Meet frontend/realtime profiles, set
`workers_dev=false`, `preview_urls=false` and `routes=[]`. These
[Wrangler controls](https://developers.cloudflare.com/workers/wrangler/configuration/)
remove public ingress rather than charging for a secret-header check on each request.
No public identity exception, shared-secret gate, paid Access product or rate-limit
product is required. The publisher also observes disabled subdomain and preview
serving before marking an upload accepted. Do not attach a Custom Domain, zone Route,
external service caller, cron or queue to these identities. The only exception is
the [ingress-admitted class](#ingress-admitted-staging-identities) below, which
allows exactly one Access-protected Custom Domain. The owner must verify
that existing hosted identities have no such attachment before enabling publication;
source configuration alone is not hosted-topology evidence. The disabled workers.dev
URLs retained in app vars are identity placeholders, not usable callback/media URLs.

With no public ingress or scheduled/queue producers, arbitrary Internet traffic
cannot invoke these Workers; finite publishing and owner-controlled private probes
are the remaining work. This does not cap shared-account spend or an independently
added service binding/producer. Browser/provider callback/media acceptance needs a
separately approved private access plan; do not re-enable workers.dev to make it pass.

For emergency stop, first set `WAVE1_STAGING_PUBLISH_ENABLED=false` and remove the
exact admission to fence future uploads. In Cloudflare, disable workers.dev/preview
serving and remove any unexpected Routes/Custom Domains. If execution continues or
its ingress cannot be established, delete **only the named staging Worker** in the
Workers dashboard (Settings / Delete) under release-owner custody; include both Meet
staging Workers if used, never a production identity. Verify its disabled/deleted
state and absence of further executions. Preserve the D1 ledger and provider/audit
receipts: deleting a Worker does not restore consumed admission or permit replay.
No deletion or other provider mutation is performed by these source tests.

## Calendar per-environment hosts and Access

Each Calendar artifact serves exactly one root host. `CALENDAR_DEPLOYMENT_PROFILE`
is a required build input with no default. `production` serves
`calendar.tuturuuu.com`, and `staging` serves `calendar.staging.tutur3u.com`.
`vite.config.mts` validates the value and inlines it, so the other branch folds
away at build time. A missing or unknown value fails the build. `development`
is accepted only by the dev server, which `dev:app` sets explicitly; builds
refuse it. Every artifact answers the other environment's host with 404 before
middleware, assets or SSR.

Who sets it:

- `wave1-native-app.yaml` passes the matrix profile.
- `wave1-native-production.yaml`, the `calendar-native` job in
  `mail-calendar-tasks-builds.yaml`, and both Vercel Calendar workflows set
  `production`.
- `turbo.json` hashes the value, so the two profiles never share a cache entry.
- Vitest pins `production` in `vitest.config.mts`; the profile tests re-import
  the config under each profile and the unset and unknown cases.

`scripts/ci/calendar-host-scan.mjs` scans the original and restored sealed
bytes in both directions:

- The production bytes must not contain `calendar.staging.tutur3u.com`.
- The staging bytes must not contain the production Supabase project ref.
- Neither may contain the retired smoke host.
- Every folded `rootHosts` literal must equal the profile's single host. An
  unfolded list fails.
- For `staging`, the request-forwarding sources (`handler.ts`,
  `api-owner-routing.ts`, `request-init.ts`, `staging-access.ts`,
  `tasks-origin.ts`) must not name `tuturuuu.com` or any app subdomain. Shared
  registries may still carry production hosts in staging bytes, so the scan
  covers the forwarding source rather than the whole artifact. A guard line opts
  out with `host-scan-allow`.

Staging Calendar has no Tasks fallback. `resolveCalendarTasksOrigin()` needs an
explicit `TASKS_APP_URL` (or `NEXT_PUBLIC_TASKS_APP_URL`) that is HTTPS and not a
production host; otherwise Tasks API paths return 503 and no cookie is
forwarded. No staging Tasks host is registered yet, so staging Calendar's Tasks
paths stay disabled until one is. Production derives the Tasks origin from the
build-time `production` profile, not `NODE_ENV`.

`wave1-native-runtime.mjs` also starts each artifact on the other
environment's host and requires 404 (N8/N9).

The staging artifact is reachable only through Cloudflare Access, and it
verifies the `Cf-Access-Jwt-Assertion` header itself:

- **JWT check:** RS256, the team issuer and the application AUD, through
  `@tuturuuu/utils/cloudflare-access`. A missing or invalid token gets 403
  before any middleware or asset work.
- **Service token:** server-side forwards to the issuer carry the Calendar
  service token only when the target origin is exactly
  `https://web.staging.tutur3u.com` and the fetch uses `redirect: 'manual'`.
  If the token is missing, the forward fails with 503 without contacting the
  issuer.
- **Credential stripping:** every forward removes client Access headers
  (`cf-access-jwt-assertion`, `cf-access-authenticated-user-email`,
  `cf-access-client-id`, `cf-access-client-secret`) and the `CF_Authorization`,
  `CF_AppSession` and `CF_Binding` cookies, matched by exact parsed name.
- **Secret names:** the staging profile adds the Worker secret names
  `CF_ACCESS_TEAM_DOMAIN`, `CF_ACCESS_AUD`, `CF_ACCESS_CLIENT_ID` and
  `CF_ACCESS_CLIENT_SECRET`. Production never requires them.

The workerd gate serves fixture team keys and checks that missing,
foreign-key, wrong-AUD, expired and malformed tokens get 403 (N19). The
service-token origin, redirect and stripping cases are unit-tested in
`staging-access.test.ts` (N18).

## Ingress-admitted staging identities

Two staging identities serve staff over an Access-protected Workers Custom
Domain. Their profile entries set `"ingress": "access-custom-domain"`:

- Calendar: `tuturuuu-calendar-wave1-staging` on `calendar.staging.tutur3u.com`.
- The Web issuer: `webStaging`, `tuturuuu-web-wave1-staging` on
  `web.staging.tutur3u.com`.

Their configs keep `workers_dev=false`, `preview_urls=false` and
`routes=[]`. The release owner attaches the one Custom Domain. The publisher
never attaches or detaches domains, and its token has no Access or DNS write
permission. Mail, Apps and Meet keep the no-ingress model above.

The Web issuer entry sits outside `profiles.apps`, so the wave-1 publisher can
never publish it. Its own publisher arrives with the staging Web workflow.

### Preflight

Before any D1 ledger read, CAS or upload, `wave1-native-publish.mjs` runs
`ingressPreflight` from `scripts/ci/wave1-ingress-preflight.mjs`. It makes
seven bounded, single-page, read-only Cloudflare reads and one fresh GitHub
variable read. `wave1-ingress-topology.mjs` evaluates the observations:

- **Serving intent (S0):** the `WEB_STAGING_SERVING` variable must read
  exactly `on`. Anything else refuses publication, so a publish can never
  revive a host the owner switched off.
- **R1:** the host has exactly one Custom Domain, bound to the staging Worker
  in zone `tutur3u.com`. That Worker holds no other hostname, and no
  production Worker holds any `tutur3u.com` domain.
- **R2:** no zone Worker route captures the host, and the zone has no
  wildcard routes.
- **DNS and N10:**
  - every record named exactly the host is the proxied, read-only A/AAAA
    record Cloudflare manages for the Custom Domain. A grey-cloud record, a
    CNAME, any other type or a missing record refuses, because each could
    route around Access;
  - no wildcard DNS record that could mint an unknown
    `<x>.staging.tutur3u.com` name: `*`, `*.tutur3u.com`,
    `*.staging.tutur3u.com` or anything deeper.

  The issuer's CORS trust in single-label staging origins holds only while
  this check passes.
- **Access phase (R-a):** the `STAGING_ACCESS_PHASE` repository variable is
  read fresh and must be exactly `bootstrap` or `staff`. Anything else
  refuses. No workflow or script ever writes it.
- **Access:**
  - an enabled self-hosted application covers the whole host and nothing
    else;
  - in `bootstrap`, the policies are **only** service-auth policies whose
    named tokens are **exactly** `STAGING_ACCESS_HEALTH_TOKEN_IDS`. Zero
    allow, deny or bypass policies are permitted, and there are no other
    tokens;
  - in `staff`, the staff selector rules below apply;
  - its OPTIONS preflight bypass is on for the issuer and off for Calendar;
  - at least one allow policy exists, and its includes name only staff. The
    permitted selectors are:
    - the configured `STAGING_ACCESS_STAFF_GROUP_ID` group;
    - the configured `STAGING_ACCESS_STAFF_EMAIL_LIST_ID` list;
    - an explicit `email`;
    - `email_domain` `tuturuuu.com` only.

    Any other domain, `login_method`, `any_valid_service_token`, IP, geo,
    certificate, `external_evaluation`, `auth_method` and any unknown
    selector refuse;
  - no policy includes `everyone`;
  - service-auth policies name at least one specific service token;
  - the host-wide application never carries a bypass policy. A future
    exact-path exception must be a separate Access application whose
    destinations are exactly those paths.
- **workers.dev:** workers.dev and preview URLs are disabled.

Any failure refuses before the ledger, so it consumes nothing. Incomplete or
failed list reads also refuse.

The publish step needs two inputs:

- `STAGING_TUTUR3U_ZONE_ID`: the `tutur3u.com` zone ID.
- `STAGING_ACCESS_APP_IDS`: a JSON object mapping each host to its Access
  application ID.
- `STAGING_ACCESS_STAFF_GROUP_ID`: the staff Access group ID. Without it, a
  group selector refuses.
- `STAGING_ACCESS_STAFF_EMAIL_LIST_ID`: the staff email list ID, if the allow
  policy uses one. Without it, an `email_list` selector refuses.

The staging token additionally needs these read permissions: Access Apps and
Policies, Zone DNS, Workers Routes and Workers Custom Domains.

### Readback

`node scripts/wave1-staging/readback.mjs [--app web|calendar] [--expect-sha <sha>]`
is the read-only post-publication readback. It repeats the topology checks,
then adds:

- **R3:** the active deployment is one version at 100% carrying the SHA.
- **R4:** with the CI Access service token (`CF_ACCESS_HEALTH_CLIENT_ID` and
  `CF_ACCESS_HEALTH_CLIENT_SECRET`), `/api/build-info` returns the staging
  build.
- **N1–N4:** anonymous and forged-credential requests (GET, POST, HEAD,
  OPTIONS, a forged `CF_Authorization` cookie and a forged
  `Cf-Access-Jwt-Assertion` header) are denied. The issuer may answer only
  the empty local preflight.
- **N5:** the workers.dev and preview hostnames don't serve.
- **N10:** live DNS doesn't resolve a random staging sibling.

It prints a JSON report and exits 1 on any failure. Its regression coverage
uses fixture transports only: `wave1-ingress-topology.test.mjs`,
`readback.test.mjs`, and the publisher refusals in
`wave1-native-publication.test.js`.

### First readback: record the DNS record shape

The C3 check assumes that Cloudflare manages a Custom Domain's DNS record as a
proxied A or AAAA record with `meta.read_only: true`. On the first readback,
the release owner records the shape actually observed for each host in the
private operations ledger, by field name only: type, `proxied`, `meta`
fields. If Cloudflare marks the record differently, the preflight refuses.
Update `workerManagedRecord` from that evidence; never relax it to pass.

## Staging Web publisher

`.github/workflows/wave1-web-staging.yaml` publishes the staging issuer
(`tuturuuu-web-wave1-staging`) and its protected Next fallback. The fallback is
one immutable deployment in the dedicated `tuturuuu-web-staging` Vercel
project. The workflow runs only on `workflow_dispatch` from `main`, for one
`source_sha`, with `cancel-in-progress: false`.

### Jobs and order

1. **`admit`** (no credentials):
   - `source_sha` is an ancestor of the dispatched `main` commit;
   - `WAVE1_STAGING_PUBLISH_ENABLED=true`;
   - `WEB_STAGING_NEXT_ADMISSION` names exactly this SHA (one deployment, the
     staging target, the `VERCEL_WEB_STAGING_PROJECT_ID` project);
   - the `web-start-candidate.yaml` `candidate` check passed at this SHA.
2. **`next-deploy`** (environment `wave1-web-next-staging`):
   - bundles the build identity (`staging`, the exact SHA);
   - runs `vercel pull --environment=staging` and
     `vercel build --target=staging --local-config vercel.staging.json`;
   - runs `wave1-web-next.mjs deploy`. That command re-reads the stop fence
     and admission, CASes the signed `wave1-web-next-staging` row to
     `pending`, and runs `vercel deploy --prebuilt --target=staging` once,
     never with `--prod`. The Vercel CLI receives no Cloudflare or GitHub
     credential.

   A lost receipt stays `pending`. A rerun reconciles it from Vercel by SHA
   and never deploys again.
3. **`next-verify`** (same environment). `wave1-web-next.mjs verify` must
   pass every check below; only then is the entry CASed to `verified`, bound
   to the SHA, deployment ID, project ID (the row scope), origin and verify
   run ID. No other job writes `verified`.
   - **V1b, project protection:** Vercel Authentication on **all**
     deployments; no password protection, trusted IPs, OPTIONS allowlist or
     shareable links; exactly one automation bypass, equal to the Worker
     secret.
   - **Deployment:** READY, non-production target, the exact SHA, a
     `tuturuuu-web-staging-*` URL.
   - **Hosts:** every alias and project domain is enumerated. Before any probe,
     every parsed hostname must match `^tuturuuu-web-staging-[a-z0-9-]+\.vercel\.app$`.
     Ports and userinfo refuse. The proof request uses the first sorted allowed
     hostname; an empty allowed set refuses.
   - **N16:** on every host, anonymous `/`, `/login`, `/api/v1/workspaces`,
     `/_next/image?url=…` and `/monitoring` are denied.
   - **N15:** the bypass without an origin proof gets 403.
   - **N17:** no `_vercel*` cookie is ever set.
   - **Attestation:** a relayed request with bypass and proof carries the
     staging Supabase attestation.

   The `vercel build` step runs repository build code, so it gets **no**
   Vercel token, Cloudflare credential or control-read token (M1). Only
   `vercel pull` and the ledger-guarded deploy hold the Vercel token. The
   workflow-shape test enforces this for every build, install and seal
   step. Installs disable lifecycle scripts, and pull/deploy pass `VERCEL_TOKEN`
   through the environment only. These are step-level controls: build and deploy
   still share a runner. A credential-free build job requires a reviewed transfer
   of the authenticated pull output, including staging environment settings;
   those settings must not be copied into a general build artifact.
   Staff email selectors require exactly `@tuturuuu.com`, case-insensitively;
   subdomains, trailing dots and other domains refuse. Focused coverage lives in
   `scripts/ci/wave1-web-{next,vercel}.test.mjs`,
   `wave1-web-staging-workflow.test.js` and `wave1-ingress-policy.test.mjs`.
4. **`seal-worker`** (no credentials): builds the candidate, runs the
   emitted workerd suite and seals it with `NEXT_FALLBACK_ORIGIN` set to the
   verified origin. The artifact digest therefore binds the pair. The job
   summary prints the SHA, digest and `nextDeploymentId` for admission.
5. **`restored`**: restores the archive, recreates the Void pointer from the
   seal, re-runs the emitted suite and the dry-run size guard, and
   re-verifies the bytes.
6. **`publish-worker`** (environment `wave1-web-staging`):
   `wave1-native-publish.mjs publish web staging`. Before upload it requires:
   - the exact Worker admission (`WAVE1_STAGING_PUBLICATION_ADMISSION`, app
     `web`, with `nextDeploymentId`);
   - the ingress preflight, which needs the Custom Domain and
     `WEB_STAGING_SERVING=on`;
   - (a) the signed `verified` entry matching this SHA, deployment, project
     and sealed origin. It refuses on any mismatch, before the Worker
     ledger.

   Immediately before its single upload, it re-reads the Vercel protection,
   aliases and probes (b), because `verified` is point-in-time. A change
   consumes the admission as `failed`, and nothing is uploaded.
7. **`verify-ingress`**: runs the read-only `readback.mjs --app web`
   (R1–R4, N1–N5, N10, and N17 through the Worker with injected bypass
   controls). It then re-runs the full Vercel recheck after publishing (c):
   N15–N17, every alias, `_next/image` and monitoring. If any step fails, the
   job's last step (R-d) rolls **only** the staging Worker back to the
   deployment the publisher captured, using the signed attempt ledger. That
   is one Cloudflare deployment write. It refuses unless this SHA's version
   is the one serving, and it touches no Access, DNS, domain, Vercel, ledger
   or variable state. The release owner then decides on S1/S1b. If the
   rollback itself cannot be confirmed, apply S1/S1b immediately.

The first publication runs with a **service-token-only bootstrap**: no

   no staff allow, no bypass.

### Rollback

Run `wrangler rollback` to the version the publisher captured. That version's
sealed origin points to the prior immutable deployment, so the pair rolls
back together. There is no Next-only rollback: a Next fix is a new SHA and a
new admission.

### Serving off-switch for ingress-admitted hosts

Each layer below is durable on its own. Apply them in order, under
release-owner custody. None of them is automated except the Worker
rollback, which the workflow performs on a red `verify-ingress`.

| Layer | Action | Effect |
| --- | --- | --- |
| S0 intent | `WEB_STAGING_SERVING=off` | The publisher refuses every upload for both ingress hosts |
| S1 Access | On **both** Access apps, put a **Block: Everyone** policy first, and remove the Service Auth policies in the same change | The edge denies every request before the Worker runs, including service-token holders. OPTIONS still reaches the issuer Worker through the preflight bypass, which answers it locally with zero Vercel calls |
| S1b tokens | Revoke the `staging-ci-health` and `staging-calendar-to-web` service tokens | No remaining credential can pass Access |
| S2 ingress | Detach the Custom Domain; its DNS record goes with it | There is no hostname. The publisher never re-attaches it |

After any S-layer, the preflight refuses to publish until the release owner

phase.

### Cost and stop model

- **No public traffic.** Access denies unauthenticated requests before the
  Worker runs. workers.dev, previews and routes are off, and the Vercel URL
  needs both the bypass secret and an origin proof.
- **No scheduled work.** No cron, queue, Durable Object or alarm is added.
  `vercel.staging.json` has no crons.
- **Bounded runs.** Each run makes at most one Vercel deployment and one
  Worker upload, plus the single R-d rollback write on failure. Every write
  sits behind a fresh stop fence and a signed CAS.
- **What spend remains.** Staff and CI requests only. Access is free for up
  to 50 seats, and service tokens use no seat. Set Workers usage
  notifications on both staging scripts; they are alerts, not caps, and S1
  is the seconds-level stop.

four-minute step. Pre-upload
observations share a 90-second deadline; post-upload acceptance has 60 seconds.
Reconciliation reads at most 99 versions and 99 workflow runs, with 15-second/1 MiB

refuses before entering upload. A matching active artifact is accepted without upload. Once that SHA's version has
been rolled back and is inactive, the same SHA is refused during preflight.

the rolled-back SHA to reactivate it or bypass the inactive-version fence. Inspect

failed. Retain the original run and operation identity for operator reconciliation.

proceed. A matching version uses the newest earlier deployment excluding that
version as its rollback, and requires the original receipt if no such deployment
remains. An upload exception leaves the private receipt `pending`; post-upload
acceptance failure leaves it `uploaded`. No automatic retry, new admission or traffic switch
follows either state.

the seal and measure its actual modules. Qualification and restored qualification
check the same limits. The publication receipt retains exact uncompressed bytes,
deterministic gzip bytes, module count/per-module sizes, uploaded sourcemap sizes,
eligible asset count/max size and binding counts/max plain-variable size. A limit
refusal stays `refused-before-upload`; it never starts a provider upload.

The account uses Workers Paid, confirmed by the release owner. Limits were read
on **2026-10-27** from [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

100,000 static assets of at most 25 MiB each, and 128 variables of at most 5 KB.
The current page has no compressed Worker-size limit. Gzip above 10 MiB is an
informational warning only. Module count and individual sizes are measurements;
do not invent additional module ceilings.

Omission is unsafe with the pinned CLI's automatic map discovery. Retain map

and artifact digest normally, without deleting or editing qualified module bytes.

The current Calendar staging Worker was only an inert bootstrap; its earlier
upload did not prove acceptance of the native payload. After the reviewed fix is
merged and synced, publish the real native staging artifact once through the
existing staging publisher, then smoke its staging host. Only after that acceptance
may the release owner dispatch the production replay. The staging publisher keeps
its own D1 attempt fence, exact source/digest admission and fresh stop checks.
Startup CPU at global scope must fit within one second; byte checks do not prove
that runtime condition. Report any hosted startup rejection explicitly from the
sanitized diagnostic, keep the pending fence and stop without retrying.

Upload failures retain only allowlisted exit/signal/Cloudflare-code metadata and
sanitized provider `code: message` pairs (at most eight). If those pairs cannot be
parsed, retain only one Wrangler `[ERROR]` headline, capped at 300 characters.
Known credentials, token/key-shaped strings and URL credentials are redacted.
Raw child stdout/stderr and error causes never enter the receipt or logs. Each
message is one line and capped at 300 characters. Diagnostics do not establish
whether a write succeeded; the receipt stays `pending` and replay stays fenced.
Within the 1 MiB stderr capture, known credentials are scrubbed from raw text
and its ANSI-stripped form before line selection. Decoded messages are scrubbed
again after ANSI removal and control-to-space normalization, before clipping.
Known-value matching covers whitespace, Unicode control/combining characters and
the supported box-prefixed/code-suffix wraps. Whitespace/control/combining runs
have no length limit within the input budget; at most 64 code-suffix units are
allowed between token characters. Arbitrary display encodings are unsupported.
Each diagnostic line is clipped to 4,096 characters before diagnostic matching.
When a line clip cuts through a token-shaped run, a backward scan drops that
partial run, preventing the line clip from exposing a shortened credential.
The same rule applies at the 1 MiB capture boundary for string and Buffer input;
when the next character is unavailable, discard the trailing run conservatively.
This is a boundary rule, not a guarantee for arbitrary encodings. Decoded JSON messages have
their own line budget. Only the final `[code: ...]` suffix is parsed for a provider
pair; the preceding text is trimmed without a prefix-matching regex. Retained
messages still have the 300-character, one-line limit. Clipped trailing runs and
detail outside these budgets are discarded, including potentially useful text.
Query values within analyzed lines are redacted. Credential keywords include
auth, credentials, pwd, sig, signature and numbered names, including supported
closing bracket/quote/backtick key wrappers and escaped JSON quotes. Quoted values are scanned through
escaped quotes and semicolon continuations. Maximal runs of workflow-command

### Staging cookie isolation

All app staging hosts use `<app>.staging.tutur3u.com`. Web staging uses
`web.staging.tutur3u.com`. Preview and canary hosts must also stay outside the
production cookie zone. Production hosts are unchanged.

Staging sets `NEXT_PUBLIC_TUTURUUU_SHARED_COOKIE_DOMAIN=.staging.tutur3u.com`
using the shared cookie helper from #7085. Without that variable the staging
override is inactive. #6951 must use this same helper and environment contract
rather than introduce another cookie-domain mechanism.

Production must never receive the override. Vercel production ignores it via
`VERCEL_ENV`, but Cloudflare Workers have no `VERCEL_ENV`, so production Worker
configs must omit the variable entirely. If it ever leaks onto a production
Worker, production hosts fall back to host-only cookies; they never take the
`.staging.tutur3u.com` scope. `packages/utils/src/shared-cookie.test.ts` and
`scripts/ci/wave1-native-calendar-profile.test.mjs` cover both cases.

Managed projects can never serve a platform cookie-zone hostname. One shared
rule, `@tuturuuu/utils/managed-project-hostnames` (plain-Node core
`packages/utils/src/managed-project-hostnames-core.cjs`), rejects
`tuturuuu.com`, every `*.tuturuuu.com` name, and `staging.tutur3u.com` and its
subdomains. It also keeps the exact non-zone reservations (`localhost`,
`nova.ai.vn`, `rewise.me`). It compares after lowercasing and stripping the
scheme, path and trailing dots. It fails closed: anything that is not an ASCII
DNS name (253 characters, 63 per label) counts as reserved. Input longer than
512 characters is rejected before any regex runs, so oversized request bodies
cannot stall the event loop. The web API, the infrastructure app and the
blue/green watcher all import this rule, so the three surfaces cannot drift
apart, and no file needs a guard exemption.

The guard (`scripts/check-staging-hosts.js`) scans every tracked source and
configuration file, including root files such as `.env.*`, `wrangler.toml`
and Dockerfiles. Tests, Markdown and lockfiles are skipped. Before matching, it
applies NFKC (folding fullwidth letters), lowercases text, and decodes hex,
unicode, octal and numeric-entity escapes of hostname characters. It also
decodes escaped dots (including `&period;` and percent-encoding) and
fullwidth and ideographic dots. It also joins string
concatenations and inlines simple same-file string constants used in
templates. It then extracts whole dotted hostnames, bounded on both sides so
`tuturuuu.com.attacker.net` stays one foreign host. After stripping the
scheme, port and trailing dot, each hostname is compared exactly against the
production zone. Any variable or property whose
name contains `staging` followed by host, domain, origin, zone, pattern or
allow fails if it names the production zone. Non-production labels in a regex
alternation in front of the zone or any production subdomain also fail, for
example `(staging|preview)\.calendar\.tuturuuu\.com`. Values that only exist at runtime,
such as `${env}.tuturuuu.com` with `env` read from configuration, are outside
what a static guard can see.

Run `node scripts/check-staging-hosts.js` and
`node --test scripts/check-staging-hosts.test.js`. The guard runs in
`bun check:changed`, as the **Staging cookie-domain isolation** job in Cheap PR
Checks, and its repository test runs in the root CI suite.
