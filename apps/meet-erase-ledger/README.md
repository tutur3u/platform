# Meet erase independent ledger (V9)

Implementation of design r5.1 `5af2611365e00025b0c22843c115f48c440d64ea328f75e79d1a7b7d1f0fa5df`, §8.20.2. No deployment or provisioning is authorized.

The dedicated Worker exports `EraseLedgerService` for an authenticated private RPC service binding. It has no HTTP API, routes, WebSockets or public preview. V12's dedicated erase runtime binds `MEET_ERASE_LEDGER` to service `tuturuuu-meet-erase-ledger`, entrypoint `EraseLedgerService`. Pass that binding to `eraseLedger(binding)` in meet-core. Do not bind to realtime or channel rooms. A service binding grants the capability; no client credential is accepted.

`append(Append)` returns `{seq, prev_mac, kind, operation_key, ws_id, meeting_id, at, key_version, body, mac}` only after SQLite and locked R2 acknowledge the exact same bytes. `read(after, limit)` (1–500) returns entries and the acknowledged head, checking both copies. A pending append reserves its bytes before R2 I/O and is completed idempotently by the next append, including after eviction. A conflicting append fails with `LEDGER_CONFLICT`; callers must raise a counts/code-only ops alert. No payload logging is allowed.

For restore, call the private `verify()` RPC to verify both copies and the complete MAC chain and rebuild the hold registry. It returns `{head, holds}`. Key access stays inside the isolated Worker. Compare its head to the separately recorded recovery head. The shared `verifyChain` and `rebuildHoldRegistry` helpers implement that verification internally. V22 must recheck the head before releasing quarantine or replay batches. Never project an incomplete page as the authoritative registry. Hold transitions use `operation_key = hold_id` and UUID `transition_id`. Approval references are opaque generated UUIDs, never free text. Outcome retries distinguish `aborted/refused`, `aborted/cancelled` and `committed`. The replay owner enforces terminal cancellation and hold-barrier ordering.

Only this Worker receives dedicated `MEET_ERASE_LEDGER_KEY_V1` (32 bytes encoded as 64 lowercase hex characters); no key is checked in or provisioned. Bea owns key custody; Selene approves the identity. V6 owns the separate subject key and canonical helper integration; this module's canonical encoding follows §8.20.1 without depending on unpublished V6 work.

Rex and Bea must configure Bucket Lock before publishing. Its retention must cover the longest PostgreSQL/PITR, history, DO SQLite, Storage recovery and configured ledger retention windows. **Bucket Lock cannot be shortened.** Cora must confirm the period first. E7 configuration affects future locks only. Active hold events must survive the hold lifetime plus recovery window; finite expiring locks alone are insufficient. No lifecycle rule, delete API or automatic purge is provided: all entries and active hold events remain retained. Independent backup/custody must never restore the ledger alongside product stores.

The `meet_transcript_erase` flag remains default OFF and is the kill switch for new erases. Turning it off must never stop completion of committed operations. `MEET_AI_DISABLED` does not stop erasure. A missing ledger binding fails closed with `MEET_ERASE_LEDGER_UNAVAILABLE`. This PR changes no flags or deployed environment. Security HOLD, GA HOLD and EC restrictions remain. Test fixtures contain generated IDs and injected test-only keys.

Verification on skr-macbook-i9 uses a shallow clone under `/var/tmp`. Run Bun tests from `/var/tmp` with absolute file paths to avoid the repository-root Turbo preload. `node --test apps/meet-erase-ledger/src/runtime.test.mjs` requires the repository's Wrangler tooling dependencies (`miniflare`, `esbuild`); the isolated qualification used Miniflare 4.20260730.0, esbuild 0.28.2 and Bun 1.4.4. That workerd supports compatibility dates only through 2026-08-06, which the runtime fixture uses; the checked-in deployment date is 2026-11-03. Exact-date release qualification remains Rex's gate. No Bucket Lock is created by the fixture.
