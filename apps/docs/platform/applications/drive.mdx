## Overview

`apps/drive` is the canonical Tuturuuu Drive application. Production Drive
traffic should use `https://drive.tuturuuu.com/{wsId}` instead of rendering the
Drive explorer inside `apps/web`.

- `apps/drive` owns the workspace shell, Drive explorer UI, local
  `/verify-token` handoff, and local app-session logout.
- `apps/web /{wsId}/drive` remains a compatibility route. It checks
  `manage_drive`, preserves the query string, and redirects to the Drive app.
- Drive uses local port `7817` and Portless host `drive.tuturuuu.localhost`.

## Native mobile directory behavior

The mobile Drive screen uses the shared floating dock for search, view, sort,
and permission-gated actions. Search temporarily occupies the shared search
surface rather than adding a second search field to the directory body. Closing
search clears its query and reloads the current directory.

Directories retain their visible entries during refresh. Additional pages load
when the viewport is within 400 logical pixels of the end, including directories
that initially do not fill the viewport; the explicit load-more action remains
available. Appended entries are deduplicated by name within the current directory.
Workspace or account changes clear search, selection, and the previous directory.
Late responses and signed-file actions cannot restore or open content from the
previous account, workspace, or request generation. Definitive authorization
failures clear displayed files; verification challenges and temporary failures
retain the current view. This includes `MFA_REQUIRED` responses identified by
the API error code even when the typed verification flag is absent; the challenge
message remains visible, and a subsequent definitive denial still clears entries.

Regression coverage: `apps/mobile/test/features/drive/drive_page_test.dart`.

## API Ownership

Protected storage APIs remain centralized in `apps/web`:

- `apps/drive` forwards `/api/*` traffic to `apps/web`.
- Client Drive data flows must use `@tuturuuu/internal-api` helpers with
  TanStack Query.
- Do not create direct Supabase browser reads or storage mutations in
  `apps/drive`.
- `apps/web` storage routes authenticate normal web sessions and Drive
  app-session cookies through the shared storage route auth helper, then enforce
  `manage_drive` or the route-specific permission fallback.

When adding new Drive behavior, add the protected route in `apps/web`, expose it
from `packages/internal-api`, and consume it from `apps/drive`.

## Private attachment boundaries

Drive permissions apply to ordinary Drive files. They do not grant access to
application-owned chat attachments. In every workspace, Drive share, download,
list, export, upload, rename, and delete boundaries reserve the root names `chat`,
`chats`, `external-apps`, `AI Agent Imports`, and `recordings` for their owning
applications. Only the two-segment prefix `mira/images` is reserved for Mira image
results; `mira` itself and ordinary files such as `mira/notes.txt` remain available.
Root/directory listings and Drive analytics omit private objects; quota accounting
continues to count their bytes. Exports omit private descendants. Recursive Drive
renames/deletes validate every enumerated object before any mutation, so a parent
operation cannot expose or remove `mira/images`. A `mira` folder containing only
ordinary files can be renamed or deleted normally.

This applies to Web, the Drive satellite, mobile Drive, and API-key storage APIs.
Even an attachment's owner must use the owning application API for these paths.
Chat and Mind APIs retain their own ownership and content checks, including
quarantine; Drive cannot mint an alternate URL for a rejected attachment.
Normal Drive files and the existing finance/task-specific permission rules stay
available. Meet files intentionally saved into the owner's personal Drive retain
that behavior.

Regression coverage: the Web workspace storage share/list route tests,
`legacy-api-routes/v1/storage/reserved-paths.test.ts`, and storage-core
`drive-path-policy.test.ts` / `storage-analytics.test.ts`.

### Reserved-name collision check

A user-created `recordings` root folder could plausibly collide with the reserved
meeting prefix: older generic folder/upload APIs allowed arbitrary root names,
and objects beneath a user-selected `recordings` folder use the same namespace.
This is source reasoning only; no production inventory was read and no collision
is confirmed. Keep `recordings` reserved. A later approved operator check should
inventory that prefix, distinguish meeting/session objects from user-created
files, and plan reference-preserving relocation for any collisions. Do not infer
ownership from the folder name or automatically move/delete matching objects.

### Previously issued signed URLs

The workspace share route defaults to 31,536,000 seconds (one year); this change
preserves that TTL. Denying new requests does not revoke bearer URLs already
issued for private objects, and this PR does not close direct Supabase Storage
access governed by existing RLS. The separate Storage RLS lane owns that fix.

Remediation is an approval-required operator action: inventory exposed object
keys and references, copy/re-key or move each object to a new unpredictable key,
verify the replacement and update owning-application references, then retire the
old key only after the replacement is durably confirmed. Account for provider/CDN
caches and verify that each previously issued URL no longer serves bytes before
claiming revocation. Preserve ownership, consent, retention, and deletion rules.
No object move, removal, key rotation, or production write is authorized or run
by this implementation PR. Obtain explicit per-case approval before execution.

## CI/CD

Preview and production deployments use dedicated Vercel workflows:

- `.github/workflows/vercel-preview-drive.yaml`
- `.github/workflows/vercel-production-drive.yaml`

Both workflows are registered in `tuturuuu.ts` and use the shared
`ci-check.yml` switchboard with affected-path gating. They require
environment-scoped Vercel credentials:

- preview environment: `vercel-preview-drive`
- production environment: `vercel-production-drive`
- project secret: `VERCEL_DRIVE_PROJECT_ID`
- shared secrets: `VERCEL_TOKEN` and `VERCEL_ORG_ID`

The app-specific project secret should live in those GitHub Environments, not in
workflow-level `env`.

## Validation

Use these focused checks when changing Drive deployment wiring:

```bash
node --test scripts/ci/check-workflow-config.test.js scripts/ci/release-workflows.test.js
```

Run focused checks locally without app builds. Require the applicable lint,
type-check, test, and real app-build workflows to pass in CI for the exact
commit; do not run `bun validate` or app builds on the shared machine.
