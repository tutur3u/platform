Meet (`apps/meet`) combines meeting planning and live collaboration.
The canonical destination is `tuturuuu.com/meet` after cutover. Public product explanations live on the main site; operational
rooms, plans, and workspace meeting records are excluded from search indexing.

## Web product and public-plan pages

Web's public Meet landing and plan pages use `/products/meet` and
`/products/meet/plans/<id>`, with Vietnamese canonicals below `/vi/products/meet`.
Their share controls use that product-plan URL. A successful deletion returns to
the localized product landing page. Meet's operational app retains its separate
root or `/meet` paths and its existing indexing policy.

The old Web `/meet` landing, `/meet/plans/<id>` and localized equivalents return
307 redirects only. Exact Calendar and AI landing aliases, including Vietnamese
equivalents, also use 307 redirects to their existing product pages. `/meet` and
`/calendar` are reserved for apex mounts. The temporary Web aliases take effect
when the gateway forwards a request to Web. Nested app routes and
APIs are excluded. Existing `/meet-together` routes are outside this relocation.

Web and satellite workspace settings reserve the `meet`, `calendar`, and `ai`
handles so these root aliases cannot be assigned to workspaces. Reservation
rejections are covered in both workspace route test suites.

Follow-up: the shared `packages/ui` legacy Meet defaults still use
`planBasePath="/meet/plans"` and copy-link URLs that pass through these redirects.
They remain unchanged here; migrate those defaults before removing the rules.

`apps/web/src/lib/product-marketing-redirects.test.ts` exercises Next's actual
redirect matcher for locales, plan ids, repeated/empty query values and excluded
siblings. The Web build gate runs `node scripts/ci/web-product-marketing.runtime.mjs`
against the built Next server. It verifies all eight temporary redirects, including
repeated query parameters; the focused route tests cover the excluded application
and Meet Together paths. Build and browser acceptance remain separate from that
matcher test.

## Before, during, and after a session

Before joining, verify the correct workspace/plan, participant access, and the
configured meeting provider. During the call, recording, transcription, and
assistant behavior follow the documented session controls and provider state.
Afterward, review notes and proposed follow-ups before writing to Tasks or
Calendar. A proposal is not an executed action, and a room URL is not broad
workspace authority.

## Transcription credit admission

Live transcription bills Gemini usage to the host's personal workspace. Each
upload window is admitted against AI credits before its transcript row is
reserved, so a refusal never leaves a "[Missing audio segment]" gap. A failed
credit check (RPC error or unreadable result) is retried at most three times
with backoff, then returns a retryable 503 that stays within the client's
five-minute recovery window. A real refusal (credits used up, daily limit, model
not on the plan, or another plan restriction) is a non-retryable 402 with a
client-safe reason code. Meet then stops capture, finalizes the session, and
shows the specific reason in English and Vietnamese instead of the generic
partial-transcript alert. Notes generation keeps its own admission check.
Regression controls: `server/credit-admission.test.ts`,
`server/chunks-credit-admission.test.ts` and `use-meeting-ai.test.ts` under
`packages/meet-core/src/features/meeting-ai`.

## Public authentication callback

Meet's native app renders the tokenless `/verify-token` and `/vi/verify-token`
callback shell for exact GET and HEAD requests, including locale context, without
consuming a verification token or requiring an account session. The explicit
English locale prefix retains normal locale canonicalization. This lets a direct
callback visit render the bilingual loading/logo UI and its hydration assets.
An explicit `token` query parameter, including an empty value, and other methods
continue through the shared verifier; token validation, safe next destinations,
session cookies, login routing and protected routes retain their existing rules.
The exception applies only to these exact callback routes, not API or workspace
routes. Real-proxy controls live in `apps/meet/src/proxy.public-callback.test.ts`;
SSR, hydration assets and both locales still require the emitted Worker CI gate.

## Browser language selection

When a Meet page has no supported locale in its URL or locale cookie, browser
language negotiation uses valid locale tags from `Accept-Language` in their
quality order. Wildcard ranges and invalid locale tags are ignored before locale
matching. If no valid preference remains, Meet uses its existing English default.
Valid regional English and Vietnamese preferences continue to select their
supported language. Zero-quality ranges remain excluded by negotiation.

A supported URL locale takes precedence over the locale cookie, which takes
precedence over the browser header. Public callbacks retain their existing locale
handling; authentication, SSO destinations and safe next-path rules are unchanged.
Real-proxy and Request-bridge regression controls live in
`apps/meet/src/proxy.public-callback.test.ts`. Hosted original and restored Worker
acceptance remains a separate gate.

## Public login locale routing

For the exact locale-prefixed public login paths `/vi/login` and `/en/login`,
Meet uses the configured English default for `as-needed` prefix handling.
Explicit `/vi/login` continues to the login renderer with the Vietnamese locale
header, even when the locale cookie or browser language prefers English.
Explicit `/en/login` intentionally retains its redirect to unprefixed `/login`.
Unprefixed `/login` retains the existing cookie and browser language selection;
all other paths retain their existing locale handling.

This path-scoped rule leaves the default authentication policy, public callback
handling, token verification, session checks and branch ordering unchanged.
Central SSO continues to return through Meet's `/verify-token` callback, and the
shared safe next-path guard continues to reject external destinations.
The real-proxy/bridge regressions in
`apps/meet/src/proxy.public-callback.test.ts` cover both login paths with absent,
English and Vietnamese headers and conflicting locale cookies, preserving the
encoded query, forwarded locale, exact callback continuation and zero fetches.
Their fixed Start SSO response establishes only proxy/bridge continuation; shared
login-page rendering and emitted original/restored Worker acceptance require
separate runtime evidence. These controls do not establish the cause of a past
hosted redirect.

## Plan guest passwords and sessions

Scope: guests who join a Meet plan by name, with or without a password, on
both the Meet satellite and the web-hosted plan page. Signed-in platform users
are unaffected.

- **Storage.** Guest passwords are stored with the shared server-only KDF in
  `@tuturuuu/utils/crypto` (scrypt, encoded as `scrypt$N$r$p$salt$key` with
  N=2^15, r=8, p=1, a 16-byte random salt and a 32-byte key). The salt lives
  inside the encoding, so `password_salt` is written as an empty string for new
  rows. Verification uses a constant-time comparison.
- **Credential flow.** The guest submits the plaintext password over HTTPS to
  the guest login server action. The server verifies it and returns a signed
  guest session (`@tuturuuu/utils/meet-guest-session`) bound to that guest and
  plan, valid for 12 hours. Availability updates and guest poll actions present
  that session (`guestSession`); the server re-verifies the signature, plan,
  guest and expiry, and checks that the guest still belongs to the plan. Stored
  password hashes are never returned to the browser and are not accepted as a
  credential.
- **Default.** Passwordless guests keep working: the empty password is hashed
  like any other value. The saved-name auto login on reload still applies only
  to passwordless guests; the password and the session are not persisted.
- **Plan access.** Guest login, guest poll actions and guest availability writes
  (create and delete) follow the anonymous plan-access rule: they run
  `getPlan(planId, { actorUserId: null })` before any session or database work,
  so a guest, including one holding a session issued earlier, only reaches public,
  non-workspace plans. Regression coverage:
  `packages/apis/src/meet/actions/timeblocks.test.ts` and
  `apps/web/src/app/api/v1/meet/plans/[planId]/availability/route.test.ts`.
- **Expiry.** When a session expires the guest action is rejected and the guest
  signs in again from the plan page.
- **Attempt limits.** Guest password attempts are limited per plan and guest
  name and per client IP (see
  [shared-secret password budgets](/build/devops/adaptive-abuse-rate-limits#shared-secret-password-budgets)).
  While a budget is spent the form shows a localized retry message, even for
  the correct password. Verified logins refund one target attempt; source counters
  retain the charge. The source budget is 300 attempts per 15 minutes to tolerate
  shared office addresses. Creation reserves 10 attempts per plan and source
  network per 15 minutes, independent of the chosen name. Different networks do
  not share a plan-wide creation cap. IPv6 addresses share their /64; unknown IPs
  share a bucket. Missing plans do no hashing. Creation denials use distinct
  English/Vietnamese copy about attempts to join.
  The optional Durable Object password store is default-off. When assigned, each
  IPv4 /32, IPv6 /64 or shared unknown-source bucket, under the same pepper, may
  spend at most 5% of the password family's daily command share across
  creation/login scopes, including rejected probes and successful refunds.
  This bounds one bucket, not a network allocation or one actor: rotating 20 /64s
  within one /48 can still drain the family. HIGH activation hold
  `FAIR-R1-SYBIL-DRAIN` remains open. Shared NATs and unknown-source callers can
  also exhaust their common bucket; P2 `FAIR-R1-SHARED-SOURCE-LOCKOUT` remains open.
  A repeated denied reservation is cached for at most one second. See the
  [fairness activation holds](/platform/architecture/system-design/security-architecture).
  Regression coverage: `apps/abuse-guard/src/fairness.test.ts` and
  `packages/utils/src/abuse-protection/__tests__/password-attempt-store.test.ts`.
  The participant view and guest table are available only to server/admin clients;
  client roles cannot query either directly. Regression coverage lives in
  `packages/apis/src/meet/actions/auth.test.ts`,
  `packages/utils/src/abuse-protection/__tests__/password-attempt-limits.test.ts`,
  and `apps/database/supabase/tests/security-meet-guest-grants.sql`.
- **Table access.** `meet_together_guests` keeps row level security with no
  client-role policies, and client-role table grants are revoked; only server
  code using the service role reads it.
- **Signing secret.** Sessions are signed with the shared server token secret
  (`TUTURUUU_APP_COORDINATION_SECRET`, falling back to `SUPABASE_SECRET_KEY`)
  through a purpose-derived key, so they cannot be replayed as any other token
  type. Rotating that secret ends all active guest sessions.

### Password hash migration

1. **Reset markers.** `verifyPassword` accepts only the `scrypt$` encoding.
   Any other non-empty stored hash, including the legacy unprefixed salted
   SHA-256 hex digest, returns `resetRequired: true` and never verifies or
   upgrades from a submitted password. Guest sign-in returns
   `PASSWORD_RESET_REQUIRED`, and the plan creator recovers the guest with
   **Reset a guest password**. The full policy is in
   [shared-secret password reset](/platform/features/shared-secret-password-reset).
2. **No backfill.** Legacy rows cannot be converted without the plaintext, so
   the existing hash format is the durable reset marker; there is no schema
   change, migration step or bulk update.
3. **Parameter rehash.** When a scrypt hash with older parameters verifies,
   the login request replaces it with a fresh scrypt hash using an update
   filtered on the previous `password_hash` value, so a concurrent upgrade is
   never overwritten. A failed upgrade is logged and the login still succeeds.
4. **In-flight clients.** Browsers holding a page from before this change send
   the retired hash field, which the server now rejects. Those guests see a
   failed save or vote and sign in again after reloading.

The native renderer uses TanStack Start SSR, Vite+ and the official Void SDK.
Shared meeting behavior and the separate realtime Worker retain their existing
ownership. Framework source or a successful build does not establish production
cutover or hosted media acceptance.

Preserve supplier-generated `src/routeTree.gen.ts` bytes, including generated casts.
Meet and Calendar need owning-config `formatter.includes` set to
the root Oxc `ignorePatterns` entries for `**/routeTree.gen.ts` and `**/*.bridge.gen.ts`. Preserve generated bytes and test authored files separately.

Use `bun run build:cloudflare` in CI. Discover the emitted Worker configuration
through exactly one of `.wrangler/deploy/config.json` or Void's saved
`.void/preview-deploy-config.json`; reject missing or simultaneous pointers.
Void preserves the pointer bytes when moving it, so resolve `configPath` from
the original `.wrangler/deploy` directory in either case. Do not assume an
output directory or recreate a missing pointer.
Preserve the existing Worker identity, targeted placement, bindings, secret names
and Durable Object migration history. Qualify, seal and restore the complete
output before publishing those exact bytes with the app-local Wrangler adapter.
Void CLI deployment is not interchangeable: the released CLI rebuilds, prepares

Meet's fixed resource policy and pinned supplier/parser profiles. It measures
materializer and loader-selection facts twice, rejects typed-source, input or

history and placement remain exact. Inspect the bounded field-rejection reason
when qualification fails; diagnostic absence does not approve a value.

The schema-2 artifact seal retains the original input path/hash, platform and
qualification profile alongside exact output hashes. Restored discovery requires
the seal, external expected SHA and complete file hashes before policy checks.
It compares historical metadata without opening or rebasing the original input
path and never falls back after a malformed seal. Raw emitted config bytes stay
unchanged. This relationship does not prove historical retained-state provenance.

Both the original prepack dry-run and production restored dry-run use
`scripts/ci/meet-dry-run-scratch.mjs` from `apps/meet`, passing `"$SOURCE_SHA"`.
The wrapper derives the emitted config through the existing artifact verifier,

seal and absence of the config parent's `.wrangler` and `.wrangler/tmp` before
running the same app-owned `bun x --no-install wrangler deploy --dry-run -c`
command with the discovered config and inherited environment.

child. After successful child close, the wrapper accepts no residue or exactly

rechecks the manifest and strict directory seal afterward. Preexisting, partial,

### Consent evidence and retention schema (M1-B)

The consent log is private server data. Neither authenticated nor anonymous
clients can insert, update, or delete evidence; the server appends decisions and
orders them by `created_at DESC, id DESC`. Only the service role can erase rows.
A withdrawal cannot be removed by a client to revive an earlier allow (F7).
A BEFORE UPDATE trigger also refuses privileged evidence edits; only nested server/Auth account-deletion actions
can clear `user_id`, retaining all other fields.
A random UUID `participant_ref` is minted on first consent per session/participant,
reused for later decisions in that pair, and stored only on consent rows. It is
neither a user-ID digest nor an email/name hash. Deleting an account sets the
consent `user_id` to NULL while retaining that random pseudonym and the evidence.
Clients cannot delete Auth accounts or trigger this anonymization. Auth account
deletion clears consent identity immediately, even though the legacy Auth trigger
retains the public profile. Later service profile erasure removes its personal
workspace after Auth deletion; consent evidence survives both steps.

These decisions apply by default to Meet and Parley session consent, including
live and recording sources, with no client-role exception. Meeting deletion and
account deletion are distinct from an explicitly authorized evidence erasure.
They do not expand transcript purge into evidence deletion. Guardian/legal
retention policy remains an independent product/legal decision.
Meeting/session deletion is refused while consent rows exist (`ON DELETE
RESTRICT`). Only a trusted service erasure flow explicitly deletes consent rows
before deleting the session or meeting. Transcript retention purges text in place
and retains the session and consent evidence; it needs no consent erasure.
This schema does not enable audio storage.

Meet and Parley retain host-only visibility for existing sessions and callers
that omit visibility. Workspace settings default new application-created sessions
to participants, explicit per-person opt-in, an ask prompt, zero audio retention,
and 365 days of text retention. Retention is bounded to 1–365 days or NULL
(forever); audio retention is enforced at zero until audio storage is implemented.
Notice versions are capped at 80 characters. Workspace settings enforce required
account MFA in addition to membership/admin RLS. Applying workspace overrides
belongs to the server integration; adding settings does not bypass participant consent.

The M1-B migration explicitly replaces `private.purge_meet_transcripts_batch`:
`purge_after <= now()` selects expired sessions in both dry-run and delete;
NULL retains a session forever. Existing deadlines are backfilled from
`coalesce(ended_at, created_at) + 365 days`. New sessions default to 365 days
from creation. Purging clears both original and edited notes, and transcript
chunks; legacy recording transcripts retain their separate 365-day policy.
The migration and rollback close the purge fence and withdraw delete approval.
A database owner must approve fresh dry-run counts before enabling deletion.
The existing batch, daily, terminal-state and stop-fence limits remain in force.

## Shared documents and Mira presence

A call has one primary shared document plus up to 11 more tabs (12 in total)
of kind document, notes, rubric or summary. The primary tab keeps the
`meeting-document-<meetingId>` channel and its workspace checkpoint, so
existing rooms and the native collaboration view keep their content. Each
additional tab uses `meeting-document-<meetingId>-<tabId>`; its content lives in
that channel's Durable Object storage and makes no workspace checkpoint
request. Tab metadata, Mira's presence and Mira edit records live in the room
state and follow room admission: any admitted participant can open, create and
rename a tab; only the host or the tab's creator can close one; the primary
tab cannot close. The tab list refreshes on a short poll because room messages
do not carry tab state.

Mira appears in a document only through server-authorized paths. The channel
rewrites every browser awareness frame to the socket's account, strips the
reserved `isMira` and `mira` keys and refuses the reserved Mira awareness
client, so a participant cannot show a Mira caret. The server publishes Mira's
named caret (`Mira • Chat` or `Mira • Live`) and selection, sets her active tab
and short status for 90 seconds, and records each edit with its source, action,
requester and bounded before/after excerpts (eight per room). Ask Mira in the
document toolbar uses Private Mira: it requires the requester's current
Continue choice, deployment and account authority, and their credits, then
returns text that the requester's editor inserts. After generation, including
a recovered receipt, the server rechecks that choice before any room-visible
write, and the room accepts Mira's edit and presence only while the choice is
still Continue at the exact revision checked for the request. A refused write
clears only that request's presence. The document API reads at most 64 KiB of
request body, cancelling the stream at that bound. The requester can accept an
edit or undo it while the inserted text is unchanged.

## Whiteboard and breakout groups

Both classroom tools are off by default. Enable the Meet Worker binding
`MEET_EDUCATION_ENABLED` with the exact value `true`, then opt the meeting's
workspace in with `ENABLE_EDUCATION`. Reload the call to discover the tools in
the call activities menu. The API checks both flags on each read and write.
Workspace opt-in governs the meeting, so admitted guests can participate.

The whiteboard shares completed freehand strokes, rectangles, text and sticky
notes. Each participant has their own drawing tools and can undo their own
edits. The host can undo the most recent edit or clear the board. Open panels
refresh every three seconds and reuse drawing data while the revision is
unchanged. The room stores up to 200 items or 256 KiB. Each author can store
up to 32 items or 32 KiB.

The host can create timed breakout groups with automatic placement, manual
assignment or participant choice. The host can move participants, send a
message to all groups, extend the deadline or close the session. Group members
can request help. Audio and video continue in the main call during grouping.

Deploy the compatible Meet and Meet realtime Workers before enabling the
binding. Use one opted-in workspace to verify both panels with two admitted
participants, then verify that another workspace stays off. Both tools use the
existing meeting room snapshot and follow its lifecycle. Removing either flag
disables access.

Regression coverage lives in
`packages/realtime/src/meet/room-classroom-tools.test.ts` and
`apps/meet/src/app/api/meet-call/[meetingId]/classroom-tools/route.test.ts`.

control applies to Meet and Parley callers of the shared gate. Private Mira

## Managed-WAF request contracts

Meet's native Start functions use `POST /_meet/functions/*`. Their validators,
request identity and authorization run on the server. TanStack Query and router
cache keys stay at the call sites; POST does not make reads into mutations.
There is no shared HTTP response cache contract for these authenticated reads.

| Function | Input and transport |
| --- | --- |
| `loadMeetPage` | Validated `{ path }`, POST |
| `fetchWorkspaces` | No application input; POST avoids Start query serialization, including framework context |
| `resetGuestPasswordTransport`, `guestLoginTransport` | Credential tuples, POST |
| `togglePlanLockTransport`, `removeUserFromPlanTransport` | Plan/user tuples, POST |
| `createPollTransport`, `deletePollTransport` | Poll tuples, POST |
| `addPollOptionTransport`, `deletePollOptionTransport` | Option tuples, POST |
| `submitVoteTransport`, `toggleWherePollTransport` | Vote/plan tuples, POST |

`packages/meet-core` defines no Start server functions. Its Parley admin
`'use server'` exports are Next server actions with POST form bodies, not GET
query transports. Only `fetchWorkspaces` requires a transport change in this
inventory. Reads remain idempotent; no validator, handler, actor resolution,
retry, or cache-key change accompanies the transport choice.

### Cookie ownership and limits

| Cookie | Scope / representation | Treatment |
| --- | --- | --- |
| `meet_pending_invite` | Host-only, Path `/`, HttpOnly, SameSite=Lax, 30 minutes | Compact locale/notes flags and room code, alphanumeric/hyphen only; accepts validated legacy paths during handoff |
| `NEXT_LOCALE` | Shared `.tuturuuu.com`, Path `/`; `en` or `vi` | Small preference; retain cross-app language behavior |
| `sidebar_state`, `sidebar-collapsed`, `sidebar-behavior`, `sidebar-behavior-updated-at`, `tuturuuu-apps-launcher-open-mode` | Host/shared Path `/`; booleans, enum or timestamp | Small layout preferences; no serialized app state needed |
| `tuturuuu_app_session`, `tuturuuu_web_app_session`, `tuturuuu_app_session_refresh`, `tuturuuu_web_app_session_refresh` | Auth-owned, Path `/`; signed tokens | Preserve signing, refresh, propagation and deletion semantics; token punctuation may also contribute, so inspect redacted events |
| `sb-<project-ref>-auth-token`, `.0`, `.1`, ... | Shared Supabase session, Path `/`; encoded JSON/JWT chunks | Potential restricted-character contributors; not proven offenders without redacted event evidence |
| `ttr_mfa_mobile_approval` | Auth-owned recovery cookie | Preserve MFA recovery handling |

The invite must reach the root, localized login/callback and room routes, so a
narrower Path would break continuation. It has no Domain attribute and cannot
be scoped away from other paths on the same host while retaining that flow.
Shared cookies arrive at Cloudflare before application code can filter headers.
Stripping a Cookie header in the Worker cannot fix an ingress WAF rejection.
Do not rename, truncate, re-encode or delete shared auth cookies as a WAF remedy.

### Contributor-rule exception proposal (approval required)

No blocked sample identifies a cookie name yet. Before approving an exception,
obtain the contributor rule, cookie **name only**, route and request method;
never publish cookie values. If Supabase auth is confirmed, resolve the literal
storage key from `getSupabaseAuthStorageKey(NEXT_PUBLIC_SUPABASE_URL)` and list
only its actual chunk names. Do not match arbitrary `sb-*` cookies.

Proposed predicate: host exactly `meet.tuturuuu.com`, method GET or POST,
validated affected path(s) only, and presence of that literal cookie key (or
its observed chunks) in `http.request.cookies` (Pro, Business or Enterprise). A literal-name
condition is `any(http.request.cookies["sb-<project-ref>-auth-token"][*] ne "")`,
OR-ed with the exact observed chunk keys; replace the placeholder before approval.
The [cookie field reference](https://developers.cloudflare.com/ruleset-engine/rules-language/fields/reference/http.request.cookies/)
documents the map lookup. Start with
`starts_with(http.request.uri.path, "/_meet/functions/")`; add individual
page/API paths only when an event proves they are affected. Scope skips to
OWASP contributors **942420 and 942421 only**; retain 949110 and other SQLi/XSS
rules. Cloudflare rule resource UUIDs must be resolved by the WAF owner from
those contributor IDs; CRS IDs are not Cloudflare resource UUIDs.

A cookie-presence condition skips those two rules for the matching **request**,
not just that cookie's value. It is not a per-cookie inspection exclusion.
Prefer a supported per-cookie exclusion if the plan exposes one; otherwise
approve this residual exposure explicitly. If cookie-name conditions are
unavailable, approval must specify the exact host/path/method fallback and
expiry rather than silently widening to a host-wide skip. This is a proposal,
not an instruction to install or extend an exception. See Cloudflare's
[managed-rule exceptions](https://developers.cloudflare.com/waf/managed-rules/waf-exceptions/)
and [API exception semantics](https://developers.cloudflare.com/waf/managed-rules/waf-exceptions/define-api/).

### Audio uploads and acceptance evidence

`useMeetingAi` attaches WAV Blobs as `audio_0`, `audio_1`, ... multipart binary
file parts; only source metadata is JSON. `uploadMeetAiChunk` forwards FormData
without JSON/base64 conversion. The dormant decoder retains its 480,044-byte
per-file cap, aggregate byte/clip caps and PCM validation. The public chunks POST
handler unconditionally returns 403 before reading audio. Removing an audio
exception therefore needs no encoding or consent change while transcription is
off; WAF rejection can still mask that application 403.

If transcription is explicitly restored and binary multipart still produces a
confirmed false positive, propose only 949110 with host `meet.tuturuuu.com`,
method POST, an anchored path matching
`^/api/meet-ai/[^/]+/[^/]+/chunks$`, and Content-Type beginning
`multipart/form-data;` with a boundary. Approve only after contributor analysis;
a threshold skip suppresses every contributor's aggregate block on that route.
Do not install a speculative exception or expand it to all Meet APIs.

Regression evidence: `apps/meet/src/runtime/server-function-transport.test.ts`,
`packages/meet-core/src/features/call/lib/invite-continuation.test.ts`,
`packages/meet-core/src/features/meeting-ai/use-meeting-ai.test.ts`,
`packages/internal-api/src/meet-ai-upload.test.ts`,
`packages/meet-core/src/features/meeting-ai/server/audio-input.test.ts`, and
`packages/meet-core/src/features/live-assistant/phase-a-denial.test.ts`.
These tests do not execute Cloudflare managed rules. Require the exact-commit
Meet build in hosted CI and replay representative authenticated navigation,
workspace reads, plan actions, and the denied upload through managed rules
without the relevant skips. Record contributor IDs and redacted outcomes.
POST bodies are still inspected; POST alone does not prove a score below 949110.

## Explicit Mail draft handoff

The active Meet call overflow offers Mail to a host who can read the workspace.
Parley, guests without workspace access, and nonmanagers do not receive this
people-directory surface. Copy invite and room admission retain their own rules.
The dialog uses the permitted people email projection and requires explicit
selection of up to 20 recipients; hidden or absent emails cannot be selected.

Open Mail carries only a versioned draft in a URL fragment to the registered
first-party Mail origin. Its join URL uses the existing room code, and the subject
and body contain only bounded meeting title text and that URL. Notes, transcripts,
recordings, account selection, reply metadata, HTML and attachments are excluded.
The payload grants no membership, room admission, Mail permission or sender proof.
Neither opening the handoff nor previewing it sends mail or provider invitations.

Mail shows a pending preview. Open draft is separate consent to initialize a
composer: the managed composer can then autosave using normal Mail permissions;
the connected composer persists only through its normal explicit actions.
Existing or retained composers block import. Open in new Mail tab leaves that
work untouched and requires preview confirmation again in the new tab.

Version 1 accepts a UUIDv4 handoff ID, current actor/workspace UUIDs, a five-minute
age with 30-second future skew, a 160-character subject, a 1024-character body,
a 512-character canonical Meet room URL and a 16,384-character encoded fragment.
The body is exactly the subject followed by the join URL on a new line. Header
control characters, malformed input and unknown fields are rejected. Recipient
addresses are trimmed, lowercased and deduplicated. Literal HTML in meeting text
stays plain text and is escaped by the managed composer.

Browser replay receipts store only random IDs and expiry, never recipients or
body. A Web Lock serializes import claims; missing locking/storage support,
corrupt receipts or 128 unexpired receipts fail closed. Receipts expire at issue
time plus five minutes and 30 seconds. This is browser-local draft replay
protection, not a delivery guarantee or a server authorization mechanism.

Sign in to Mail before sharing. Signed-out redirect hops can discard the
fragment; resumable login handoff is not established. Generate a fresh handoff
from Meet if it is lost or expired. Handoff data must never be placed in login
returnTo queries or the room pending-invite cookie. Native acceptance requires
stripping the fragment before loader server-function serialization and binding
Mail's personal alias to the server-verified workspace UUID.

Coverage includes the real producer picker, both Mail clients/composers, replay
and scope/lifecycle tests in `meet-mail-share`, `meet-mail-handoff`, and the
portable protocol tests. Cross-app signed-in runtime acceptance remains a
separate release gate.

## Canonical path cutover

The operational app moves to `https://tuturuuu.com/meet`. The product landing
stays at `/products/meet`. The gateway gives the exact `/meet` path and its
subtree to the Meet Worker ahead of the Web marketing aliases. The Web aliases
remain the fallback when the mount is withdrawn. English and Vietnamese
operational URLs are under `/meet` and `/meet/vi`, respectively.

Follow the [cutover procedure](/build/devops/meet-standalone-release#canonical-path-cutover)
for route admission, 302 and 301 promotion, and rollback.
