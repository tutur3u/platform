Contacts (`contacts.tuturuuu.com`, `apps/contacts`) owns the workspace-user CRM
surface. A CRM workspace user and a signed-in platform account are different
entities; links between them are explicit. Central login, the Contacts app
session, workspace membership, and feature/role checks govern access.

## Find the right area

| Area | Workspace route | Purpose |
| --- | --- | --- |
| Users | `/{wsId}/users` | CRM overview and user operations |
| Database | `/{wsId}/users/database` | User records and details |
| Groups | `/{wsId}/users/groups` | Group membership, calendars, schedules, and content |
| Attendance | `/{wsId}/users/attendance` | Attendance workflows |
| Reports | `/{wsId}/users/reports` | User/group reporting |
| Guest leads | `/{wsId}/users/guest-leads` | Lead workflows |
| Topic announcements | `/{wsId}/users/topic-announcements` | Contacts, templates, announcements, delivery, and import |
| Workforce | `/{wsId}/workforce` | Workforce surface where available |

Some areas depend on workspace modules. An unavailable module must distinguish
access denial, disabled configuration, and loading/failure states; it should not
pretend that all of these mean a missing record. See
[Contacts module availability](/platform/applications/contacts-modules).

## Related workflows

### Cross-app people integration

The shared people-search integration is under development. Its first slice adds
`GET /api/v1/workspaces/{wsId}/people` and the
`@tuturuuu/internal-api/people` client; this does not establish that every app
already uses the endpoint. Mail recipient selection, Calendar attendees, Tasks
contacts search, and Meet invitations adopt it in separate slices.

In the shared Tasks assignee popover and task-card assignee menu, a search of
2–100 characters can show a separate Contacts group. Each contact opens its
workspace record in Contacts. Contacts never enter the assignee list or its
numeric shortcuts, including when a contact ID, explicit linked account or email
matches a member. Board-viewable members and direct guests remain the assignment
source, and existing assigned users can still be removed. Contact-read denial
does not disable board assignment. Existing task mention notifications keep
their authenticated-member semantics; opening a contact sends no notification.
This applies to active apps using the shared Tasks UI; standalone contact views
and member assignment permission checks retain their own rules. Regression
coverage lives in `task-contact-results.test.tsx`, `assignee-select.test.tsx` and
`task-assignees-contacts.test.tsx` in `packages/tasks-ui`.

Search is workspace scoped and requires membership and contact-read permission.
Results contain only a contact or member identity and permitted name, email and
avatar fields. CRM notes, addresses, guardians, birthdays, balances and identity
documents are excluded. Hidden member names and emails cannot be used to find
records through this endpoint, including linked Contacts records. Contact email
requires private-information permission; public names and avatars require
public-information permission. Query text is bounded to 2–100 characters and
results to at most 20. Wildcard queries are unsupported.

A contact ID remains distinct from an authenticated member ID. Searching does
not create membership, send an invitation, change a profile, or make a contact
eligible for task assignment. Assignment and notification keep their existing
member and board access checks. Explicitly adding a mail sender uses the existing
contact-create permission and requires a separate user action.

The shared account/profile panel proposal builds on the existing satellite and
Web panels and current-user profile API. Global account names remain separate
from workspace CRM profiles; shared name fallback and private-detail policy stay
with their existing owners. Email changes retain verification and sensitive
action checks. No database migration is part of the initial search slice.

Focused coverage lives in the Web `workspace-people` tests, the people route tests,
and `packages/internal-api/src/people.test.ts`. Execution and deployment evidence
are required separately before this proposal can be described as shipped.

[User management](/platform/features/user-management) describes user and account
boundaries. [Reports](/platform/applications/reports) and
[Tutoring](/platform/applications/tutoring) explain the education/CRM flows.
Group access does not grant a linked parent unrestricted editing rights.
Outreach and topic announcements require their own delivery configuration and
recipient rules.

## Ownership and privacy

### Explicit Mail sender creation

Mail's sender card offers **Add to Contacts** only after the API confirms the
current member has `create_users`. The action creates a workspace contact through
the existing audited RPC; it never creates an authenticated member, guest group,
identity link, invitation or notification. The message's displayed sender name
is bounded to the contact name limit. The server accepts only an operation UUID,
email and display name, and derives the contact ID from the verified actor,
workspace and operation. It does not accept actor or contact IDs from the client.
The handler opens its contact-operation write client only after the membership
and create-permission checks. Shared authentication and permission helpers may
already open read-only admin clients under the verified user.

The browser retains the operation UUID in tab storage scoped by actor, workspace
and a hashed sender identity before the explicit submit. Reopening the action or
checking an UNKNOWN result performs a read-only status request, never another
create. An unobserved result remains UNKNOWN; it does not mean no contact exists.
A later confirmed commit opens the contact without replaying the write. Storage
failure prevents submission. Server reconciliation returns only state and a
contact ID, with no CRM fields. Repeated or concurrent calls with the same
operation converge through the existing contact primary key and audit RPC.

This rule applies to Mail's workspace sender card. Existing Contacts forms keep
their own creation behavior. No database policy or migration is changed.
Regression coverage includes `contact-create-operation.test.ts`, the active Web
`people/contacts/route.test.ts`, and Mail's sender-operation and create-control
tests. Signed-in runtime acceptance remains a separate release check.

Contacts owns the users routes removed from Web. Shared domain/UI code lives in
`packages/users-core` and `packages/users-ui`. Non-owned workspace destinations
redirect to their canonical app rather than being implemented as catch-all API
proxies. Workspace CRM records, reports, attendance, and outreach are private
and receive noindex directives. The public product description belongs on the
main site's CRM page.

[Source routes](/reference/repository/routes/contacts) list all Contacts pages
and handlers. [Permissions](/platform/architecture/workspaces-permissions)
and [Satellite apps](/platform/architecture/satellite-apps) explain the shared
access contract.

The additive Contacts Worker is restricted to the separately admitted staging

retain Next ownership; only an inert candidate probe is native. EN/VI paths,

## Calendar invitation creates

The shared Calendar create dialog supports explicit contact guest selection for
writable Google and Outlook sources when legacy color generation is disabled.
A dedicated authenticated, read-only capability query binds availability to the
selected workspace, provider, connection and calendar. Missing, stale or refreshing
capability disables guest selection and submission. Retry refreshes availability
inside the open dialog without changing draft fields, guests or request identity;
failed or denied refresh keeps submission blocked. Discovery never sends invites
or refreshes provider colors. The server retains final authority over generation
and retained-request refusals.

Creation preserves the draft request identity for explicit recovery of an uncertain
response. Guest addresses use the existing normalized people-picker projection,
100-guest limit and time zone. Saved-event attendee editing, native sources and
provider-color invitations remain unavailable. Google color discovery remains
separate for recoverable color creates.

Regression coverage: Calendar invitation-capabilities route tests, shared UI
`calendar-event-create-payload`, `use-calendar-invitation-capabilities` and
`use-calendar-draft-save` tests, plus existing provider meeting and generation tests.
