Infrastructure (`infrastructure.tuturuuu.com`, `apps/infrastructure`) is the
privileged operational console. It exposes workspace/account controls,
monitoring, configuration, and selected provider gateways. The existence of a
console route never bypasses its operator eligibility and permission checks.

## Operational areas

- Workspace/user administration, internal accounts, external-app registration,
  account benefits, and app coordination.
- AI policy, agents, credits, rate limits, abuse intelligence/events, blocked
  IPs, recovery/appeals, and entity-creation limits.
- Email queues/templates/audit, push notifications, and Calendar sync.
- Mobile/desktop deployment records, versions, translations, holidays,
  timezones, Devboxes, and migration diagnostics.
- Monitoring for requests, logs, analytics, projects, deployments, rollouts,
  resources, and retained cron/control surfaces.

The [route reference](/reference/repository/catalog) lists every current
Infrastructure entry point in its numbered source pages. Feature-specific
operating rules remain in [DevOps](/build/devops/overview) and
[Commercial controls](/platform/features/commercial-controls).

## Current schedulers

Hosted Calendar provider sync and smart scheduling run through Infrastructure's
Vercel schedule and authenticated Calendar gateway. The
[Cloudflare Cron Control Worker](/build/devops/cloudflare-cron-control) owns
immediate notification recovery. The Docker cron runner is retired. Retained
Docker controls and stale local heartbeat records do not establish the health
of either hosted scheduler.

Use the [active runtime map](/build/devops/active-runtime) to trace a job from
scheduler to gateway to processor. Verify recent domain results as well as a
successful scheduler invocation.

## Privacy and change control

Console pages and APIs are noindex, including errors, auth redirects, and
non-HTML responses covered by the app policy. Search controls supplement actor,
workspace, permission, token, and storage checks. Runtime logs use native
`console.*` with the original severity; operational log-drain services are
separate boundaries.

A configuration edit, deploy action, external registration, or production write
requires its own authorized workflow. Reading a runbook or recalling a private
record is not authority to execute it.

## Account passwords and access

Administrators with root-workspace `manage_internal_accounts` permission use
**Reset any password** to select an account by email, or **Reset password** in
an internal account's menu. Both dialogs accept a chosen password or generate a
20-character temporary password locally using Web Crypto. Passwords must contain
12–72 characters. The global reset dialog freezes its target and password and
prevents dismissal while the request is pending; a failed request keeps the form
editable, and a successful request exposes the credential handoff. Passwords are
not written to application logs.

The internal-account menu shows **Disable access** for active accounts and
**Enable access** for disabled accounts. Both require matching target-email
confirmation. Enable removes the provider ban; it does not change the password
or perform managed-employee restoration. These existing password/access actions
have no optional activation gate. Current administrator identity, permission,
target eligibility and self-target protections still apply. Administrators cannot
use these actions on their own account; managed-employee lifecycle recovery
continues through its separate inspection and restoration flow.

Regression coverage: `account-password-reset-dialog.test.tsx` exercises password
bounds, pending-request protection, generation and refusal;
`internal-account-row.test.tsx` exercises the existing active/disabled menus and
self-target controls; `service.test.ts` verifies exact confirmation and provider
ban changes. Route authorization and password-boundary suites cover the existing
Infrastructure API contracts. These synthetic tests do not establish provider or
production acceptance.

## Employee API routing

Web owns `/api/v1/infrastructure/internal-accounts/employees` and its descendants,
including CREATE readiness, employee inspection, restore, and reconcile.
Infrastructure forwards that exact subtree in `beforeFiles`, including the base
path with zero wildcard segments. A fallback-only rewrite lets the local
`internal-accounts/[userId]` PATCH route capture `employees` and answer GET with
an empty 405 before Web can handle it.

The local internal-account list and legacy UUID PATCH remain in Infrastructure;
address-migration endpoints retain their existing Web fallback. The installed
Next matchers in `apps/infrastructure/next.config.test.ts` cover these boundaries.
Routing checks do not establish downstream readiness: require the exact-commit
Infrastructure CI build and an authorized production recheck after deployment.

## Employee SQL transport qualification

### HTTP RPC runtime candidate

The Web employee CREATE route can compose the durable operation journal with
fixed service-only Supabase RPCs. CREATE is available by default to all authorized
root administrators with `manage_internal_accounts`; no administrator activation
exception or `EMPLOYEE_CREATION_RUNTIME_ENABLED` opt-in applies. Server
configuration and SQL/provider readiness still determine availability.
Infrastructure consumes the same availability endpoint; its create control
remains disabled while the runtime is unavailable. Isolated SQL, generated-type,
HTTP/Auth, target-project migrations and exact-build checks remain release evidence.

The adapter uses the configured server Supabase project for both Auth and SQL.
The request still requires an eligible root administrator, current membership and
permission, and the account-action origin/header checks. SQL repeats the actor
assertion and denies expanded function ACLs. An original actor/operation key owns
one target UUID. Durable attempted phases and single-use invocation capabilities
precede provider effects; unknown responses retain that identity for inspection.

Every RPC write acknowledgement is followed by a separate persisted-state
observation. A function response from a transaction configured to roll back cannot
authorize provider creation or publish account success. Lost responses, malformed
state and readback disagreement fail closed without an automatic retry. Passwords
remain transient Auth inputs and never enter the operation tables or RPC body.

This adapter does not activate the fixed child-worker prototype below. That
prototype retains its separate operator, connection and asset qualification
requirements. RESTORE and legacy-domain migration remain separate runtime flows;
successful CREATE qualification does not establish either behavior.

In the Infrastructure CREATE form and Web boundary, the shared password schema
requires 12–72 characters with lowercase and uppercase ASCII letters, a digit
and ASCII punctuation before journal admission. The password remains transient.
Normal success confirms that the account is ready to sign in without an extra
observation request. After an uncertain response, the browser retains the original
operation reference scoped to actor and workspace, without retaining the password,
and admits up to six observation checks within 30 seconds of the first check.
These reads never replay CREATE. Completion requires independent active onboarding
identity and fresh SQL account/profile/mailbox/grant proof; incomplete outcomes
retain the original operation and stay blocked against another CREATE. This
behavior does not promise a creation latency. Regression coverage and remaining
runtime evidence are recorded in the
[CREATE qualification contract](../../build/development-tools/employee-schema-qualification#original-create-response-recovery).

### Managed employee inspection

Web serves `GET /api/v1/infrastructure/internal-accounts/employees/:userId`
for the native Infrastructure management client. It returns the retained
restoration inspection contract, provider observation time and next action.
It requires a current confirmed, active canonical-domain root `MEMBER` with
`manage_internal_accounts`; it rechecks the same request actor before SQL and
before disclosing private recovery details. Responses are private and uncached.

The adapter reads the exact provider UUID and calls only
`private.inspect_employee_management` in the same configured Supabase project.
Missing schema, conflicting tuples, unavailable reads and changed authority fail
closed. An unresolved restore operation remains `inspect`; it never relaunches
provider work. Unmanaged legacy addresses remain an adoption/migration concern.
The portable restoration boundary lives under
`packages/utils/src/internal-accounts`, with Infrastructure compatibility exports.

This GET path does not enable CREATE, RESTORE writes or legacy-address migration. No runtime flag is changed. Route and transport
regressions live beside the Web implementation, while the existing Infrastructure
restoration suites cover compatibility. Exact-source CI builds, deployed request
authentication and target-project SQL qualification remain separate release gates.

### RESTORE and reconciliation POST candidate

Web owns `POST /api/v1/infrastructure/internal-accounts/employees/:userId/restore`
and the sibling `/reconcile` route. Both are available by default to all authorized
root administrators with `manage_internal_accounts`; no administrator activation
exception or `EMPLOYEE_RESTORATION_RUNTIME_ENABLED` opt-in applies. Configuration,
request authorization and lifecycle/SQL/provider guards remain mandatory. The
Infrastructure console consumes this contract through the managed-access dialog
below; legacy-domain address migration remains a separate flow.

The routes reuse the portable restoration HTTP/orchestration helpers, with
Infrastructure compatibility exports. The server supplies the actor and provider;
strict request input supplies only confirmation email, expected revision and,
for reconciliation, the original operation UUID. Current request authentication,
root membership/permission and active canonical-domain actor checks repeat before
every RPC and provider call and before a successful or pending response is disclosed.

The fixed five-function transport uses the same configured Supabase project for
Auth and SQL. Separate `inspect_employee_management` requests must observe the
matching reserved and attempted operation before the sole provider unban. SQL
confirmation/reconciliation receipts must match independently observed completed
state, revision and managed name. Rollback responses, missing or malformed
readbacks and lost responses retain an unknown outcome without automatic retry.
Reconciliation uses the original actor/target/revision/operation tuple and never
begins an operation or dispatches another provider mutation.

`employee-restoration-rpc.test.ts` and `employee-restoration-runtime.test.ts` in
Web exercise actual loopback HTTP against a disposable synthetic SQL endpoint,
including unpersisted replies, revocation and provider acknowledgement loss.
The shipped route test proves RESTORE and reconciliation work with unset or false
activation flags independently of CREATE, while nonadmins and unavailable server
configuration remain denied. `employee-creation-runtime.test.ts` covers the same
production-composition policy for CREATE and retains SQL-readiness failures.
The retained Infrastructure suites cover helper compatibility. These fixtures
qualify source and HTTP serialization only: before release, independently
verify the five deployed function definitions and service-only ACLs, commit and
rollback/readback behavior through real PostgREST/PostgreSQL, request-session
and actor revocation behavior with real Auth, and the exact-source Web and
Infrastructure CI builds. Production migration completion and authorized
delivery remain release-owner gates; neither GET inspection nor CREATE
qualification establishes RESTORE delivery.

### Managed-access console

The Infrastructure account directory exposes **Inspect managed access** for
other accounts. The administrator explicitly reads current state; only an active,
managed, mailbox-ready canonical account with a confirmed provider ban and a
RESTORE next action offers restoration. Creation recovery, adoption, conflicting
or unconfirmed provider state and legacy migration have explanatory states
without a restore button. This dialog never renames an account or implements
stable-UUID legacy-domain migration.

Confirmation requires the exact inspected account email. Every submit performs
another uncached inspection and compares revision and operation before dispatch.
The portable consumer retains the original expected revision and server operation
UUID across pending results and dialog close/reopen. A lost POST response blocks
another RESTORE in that dialog lifetime, even if a subsequent read has no operation.
Only the matching persisted operation can be reconciled; reconciliation never
replays the provider mutation. No client-generated replacement UUID or automatic
POST retry is used. State is private and ephemeral; a new page lifetime recovers
operations from the authorized persisted inspection rather than browser storage.

RESTORE is enabled by default for authorized root administrators at the Web endpoint. Inspection does not
advertise write availability. A capability-unavailable response therefore locks
writes for the current dialog lifetime while preserving read-only inspection and
any retained uncertain operation; it does not establish account absence. Session
and permission denial retires actions until the page is reauthorized. Client
actor lifetime checks surround each awaited stage, while the endpoint remains
authoritative for current actor, root membership and permission.

A successful POST alone is not displayed as restored. The console requires a
separate GET showing the matching completed operation, original revision plus
one, managed active registry, ready mailbox and confirmed active provider. Missing,
malformed, mismatched or failed readbacks preserve uncertainty. Directory status
and private management state remain separate observations.

`employee-restoration-consumer.test.ts` covers revision/UUID fences, explicit
reconciliation, unavailable capability, duplicate admission and revoked actors.
`employee-restoration-dialog.test.tsx` covers rendered English/Vietnamese controls,
exact confirmation, pending close/reopen, independent readback and actor replacement.
These are synthetic source regressions. Exact-commit Infrastructure/internal-API
CI and authenticated deployed session/provider/SQL acceptance remain separate;
no runtime flags, account activation or migration are performed by the UI change.

### Fixed child-worker prototype

The fixed child-worker transport remains unavailable until its protected SQL supplier and
project readiness are independently qualified. The fixed transport prototype
accepts only preflight, finalize and activation-confirm operations. Each request
owns one terminable child and TLS connection; no shared pool, caller SQL,
account password or inherited database configuration enters that boundary.

The executor is shared through the server-only
`@tuturuuu/inventory-core/infrastructure/employee-sql/process` leaf; only this
leaf's dependency closure is framework-free. Original Infrastructure entry
points remain compatibility entries, while the canonical raw worker and protocol
are colocated under `packages/inventory-core/src/lib/infrastructure/employee-sql/`.
Before binding the Web supplier, verify that the compiled route's `.nft.json`
trace and resolved `fork()` target load the canonical worker, protocol, and
runtime dependencies. Relocation requires qualification of the exact source and
build with refreshed signed attestations, even when raw worker/protocol hashes
are unchanged.

The parent requires external Ed25519-signed project and execution attestations,
including the exact worker and protocol hashes. Missing bindings deny before
spawning. Ordered, same-connection catalog checkpoints validate the role, cluster,
ledger, function bodies and effective privileges before effects and COMMIT.
The parent records an uncertain commit before authorizing COMMIT; lost commit
acknowledgement never authorizes a blind retry or replacement account ID.

The process requests cancellation at 13 seconds and kills only its owned child
at 14.5 seconds, reserving cleanup time within the qualification profile's
15-second budget. It waits for actual child closure. Client process/TCP drain
controls do not establish server transaction rollback or row-lock release.
Before wiring the supplier, qualify delayed connection/query/lock/COMMIT cases
against disposable PostgreSQL, verify backend and lock drain, and verify the
static worker/protocol assets in the exact hosted Next build and file trace.
Source tests, schema assertions and signed synthetic fixtures cannot replace
those gates or activate account creation.


### Legacy employee address migration

The internal-accounts page has a separate legacy address migration dialog.
Migration changes the original UUID's `@xwf.tuturuuu.com` address to the same
localpart at `@tuturuuu.com`, preserving its identity and linked data; RESTORE
instead re-enables a previously suspended managed employee at its existing
address. Neither flow creates a replacement account. Migration does not repair
verification or claim/provision somebody else's mailbox. It requires existing
approved active source and destination mailboxes owned by the original UUID,
email-provider readiness, revision zero and no CREATE/RESTORE registry ambiguity.
A separate bounded exception supports a confirmed legacy account whose sole
Google identity already verifies the exact canonical destination with matching
provider ID/subject. The explicit Web `address-migrations/prepare` endpoint may
first adopt an empty, unowned, disabled canonical personal mailbox, then requires
committed ownership readback before a fresh migration binding. Quarantined,
archived, populated, shared or owned mailboxes remain unavailable. This path
needs no source mailbox and permits only GoTrue's one verified email identity
addition while preserving the original Google identity/data exactly. Completion
stores distinct actual before/after fingerprints. See the [supplier contract and
qualification](../../build/development-tools/employee-address-migration). The
Google provider and Web state-flow regressions plus the separate 30-assertion SQL
packet cover this exception with the stated fixture boundaries.

Web migration availability follows current root administrator permission,
configuration and fresh SQL/provider readiness. Neither composition nor
reauthorization consults an optional activation environment flag; unset or false
legacy migration flag values do not block an otherwise authorized operation.
The operator can supply the existing operation UUID before the first action;
leaving it blank creates a new operation only for a new intent. The first inspect
or explicit preparation freezes and retains the exact operation UUID, target UUID,
source, destination and revision, including after denial, dialog reopening and
same-session remount. The locked fields cannot mint a replacement operation.

Mailbox preparation is an explicit, separate administrator action. It requires
retyping the exact target UUID and both addresses and calls only the existing
`address-migrations/prepare` endpoint. Neither inspect nor migrate silently
prepares a mailbox. Preparation acknowledgement is shown separately and requires
inspection before migration. Migration requires both exact address confirmations
again and a fresh authorization/readiness inspection before its single request.

Recovery distinguishes unattempted, prepared, uncertain inspection/preparation
and dispatched migration receipts. Unknown preparation stays inspect-only until
inspection positively observes exact readiness, which may unlock migration only.
Denied, forbidden or invalid inspections never clear the preparation fence or
allow another preparation. A dispatched migration, including an old
bare recovery tuple, never regains dispatch permission, even after a ready or
denied inspection. Unknown reads cannot remove either write fence. Independently
observed completion is required. Recovery storage is scoped to actor/workspace
and this browser session; changing actor/workspace retires the old workflow.
No password or token is requested.

This decision applies only to the Infrastructure operator surface and Web
migration endpoints; CREATE/RESTORE keep their existing contracts. The
`address-migration-session.test.ts`, `address-migration-dialog.test.tsx`, Web
migration runtime tests and typed consumer tests cover these boundaries with
fixtures. Hosted mail ownership/delivery, full-schema qualification,
exact-commit CI and the named real account's preservation remain separate gates.
See the [migration runbook](/build/development-tools/employee-address-migration).

### Employee POST origin boundary

Web owns CREATE, RESTORE/reconcile and address-migration POST handlers behind
Infrastructure's external rewrite. Next preserves the browser `Origin` while
changing the destination Host, so the request URL alone cannot identify the
browser's origin. A configured production Infrastructure origin is accepted only
with a cryptographically verified app-session bearer targeted to `infra`.
Forwarded host/protocol headers never grant this exception. Actor, root membership,
permission and operation checks remain required independently.

Foreign origins and cross-site fetch metadata remain denied. Direct Web requests
retain their existing same-origin and non-browser bearer behavior. Migration
continues to reject missing-origin cookie requests. No runtime flag is enabled by
this boundary. `employee-request-origin.test.ts` covers signed tokens, wrong app
and forged credentials, spoofed forwarding headers and all three active adapters;
it does not certify production Auth, SQL or provider actions.

A domain match alone grants no access. Reports remain private; ordinary actors
receive only their own content-free receipt, and staff reads grant no management

### Rejected first employee creation

The default for an unknown employee CREATE is to retain the original operation
and prohibit replay. In the root Infrastructure account dialog, the original
administrator may explicitly adjudicate a terminal rejection of the first Auth
attempt at unknown/version 2. This exception requires retained evidence, an
explicit no-request-in-flight attestation and independent SQL absence checks;
nearby logs or absence alone do not prove rejection.

A committed one-time repair preserves the UUID, intent and history and returns
reserved/version 3. Matching audit readback unlocks a fresh password field
for one explicit normal CREATE submission with the original UUID, email and
name. Neither closing the form nor losing the repair response clears that
reference. Uncertain repairs stay fenced for explicit readback. Later phases,
revoked operations and other actors/workspaces are excluded. Route, recovery
helper and dialog regressions enforce this rule; the optional disposable Web
session fixture exercises authenticated adjudication and CREATE end to end.
