The dashboard assistant's Live mode connects directly to Gemini using the Google
Gen AI SDK. The server supplies a single-use, constrained ephemeral token;
`GOOGLE_GENERATIVE_AI_API_KEY` must remain server-side. The model is selected by
`/api/v1/live/token` and passed to the client. Google documents the protocol in the
[Live API guide](https://ai.google.dev/gemini-api/docs/live-api).

## Experience

Start or stop Live with the waveform icon in the chat composer. Live keeps the
same message timeline visible, with a compact gradient visualization and media
controls above it. Spoken turns, typed prompts, tool calls, and search sources
appear in that timeline and share the workspace artifacts. Close Live or press
Escape to stop media capture and continue typing.

Finalized Live turns are saved to the same chat through the owner-checked
`/api/ai/chat/live-messages` endpoint. Stable message IDs make retries idempotent;
ordered parts keep text and tools interleaved after refresh. Complete transcript
text lives in canonical parts metadata; the separate search/fallback content field
is capped at 10,000 Unicode characters to satisfy its database limits of
10,000 characters and 40,000 bytes. Pending saves finish
before a subsequent typed request. Failed saves show a retry action; keep the page
open until they succeed. In-progress speech remains provisional until the turn
finishes or the session closes. Audio and video are not stored as chat attachments.
Live starts with up to 64,000 characters of conversation context: bounded earlier
excerpts preserve original roles alongside recent turns and compact tool results.
This is deterministic compaction, not a generated summary. This bound does not remove older saved messages. Temporary session notes
remain separate from workspace documents.

Chat and Live share a persistent composer panel in the page layout. Switching
modes swaps the toolset and preserves the text draft. Chat shows its model and
credit controls without a redundant mode label. Screen/camera sharing uses a
compact thumbnail that expands on demand; the composer does not cover messages.
Transitions respect reduced-motion preferences.

The assistant opens tasks, calendar, finance, and meetings next to the conversation
through tool calls. The chat toolbar has no product, sidebar, or layout controls. One artifact splits the available space in half; multiple
artifacts automatically use a four-cell grid with chat in one cell. Side-by-side,
stacked, and grid controls override the arrangement. Narrow containers stack
panels so sidebar width is included in the responsive decision. Up to three
artifacts remain open; opening a fourth replaces the oldest. Artifacts are scoped
to the workspace selected when opened and can be refreshed or closed individually.
Task previews use the Tasks app’s personal feed, showing 12 rows at a time with
Show more. Calendar previews cover the next seven days, and wallet balances retain
their own currencies. APIs remain the
permission boundary and panels expose loading, empty, and retry states.

The assistant can call `show_workspace_artifact`, `set_sidebar` (expanded,
collapsed, hover, hidden), and `set_theme` (light, dark, system) in chat and Live.
Chat applies UI commands when the streamed tool output arrives, independently of
whether the result card is visible. Restoring history does not replay old UI
commands. Sidebar changes use the existing preference provider and respect its
local/account synchronization settings. Ask the assistant to restore navigation
when it is hidden.

Meeting panels provide a creation form to eligible `@tuturuuu.com` accounts using
`createWorkspaceMeeting`. The existing meeting API authenticates the account,
checks workspace membership, and enforces the domain policy. Opening the panel is
not meeting creation; success is shown only after the creation request succeeds.
No meeting API or database policy changes are part of this interface update.

Live mode displays both speakers' streamed transcripts, task visualizations,
Google Search sources, tool activity, and temporary session notes. Typed prompts
and voice share one session. Camera and screen sharing require an explicit media
control action; a preview indicates what is shared. Microphone mute sends
`audioStreamEnd`, and interruption stops queued assistant playback.

Workspace artifacts remain beside the shared conversation. Tool results and Google
Search sources stay in the message timeline. Temporary notes are not workspace
documents. The existing five-minute credit authorization limit remains in force;
expiration ends media capture and keeps the saved conversation available.

## Mobile audio capture

On mobile, Chat and Live use the same top header mode switch and page background.
Live keeps the floating bottom navigation visible. Its idle start action is the
icon-only microphone button beside that navigation; the top header opens Live
settings in a sheet with the Keep Live while browsing switch. The idle screen
does not show an availability badge or a second start button. During a session,
the controls above the navigation provide camera, microphone, typing, and end
actions. Connection problems show a retry message without changing the page
background.

Starting mobile Live with the microphone enabled requests permission and captures
speech while the connection initializes. A memory-only FIFO holds at most 30
seconds of 16 kHz mono PCM. Once ready, chunks drain in order; cancelling capture
or leaving the session discards unsent audio. Connection errors do not persist
this buffer to disk.

The normal mobile chat microphone replaces the text field with a real microphone
waveform inside the same persistent floating dock. It opens no recording sheet.
Pause reveals restart, attach, send, and resume; the two-minute limit pauses
capture rather than discarding it. Restart erases only the current unsent local
recording. Attach keeps the text draft and uploads through the existing attachment
flow; send explicitly attaches and submits it. Backgrounding pauses capture.
Leaving the Assistant, switching actors or workspaces, and disposal cancel the
unsent recording. Async completion cannot attach or send into a different scope.

Mobile assistant Markdown renders directly against the app background. Text,
reasoning, and separate tool activity follow canonical persisted part order after
history restoration. User messages keep their own bubble. Chat and Live both
expose the shared quick-settings action. Regression coverage lives in the voice
capture, composer dock, and transcript bubble tests under
`apps/mobile/test/features/assistant/`.

## Flash and Pro

Flash uses `gemini-3.8-live`; Pro uses `gemini-3.8-live-extended-thinking`
with high background reasoning. The chat response labels are now Flash/Pro;
existing saved Fast/Thinking preferences remain compatible. Live starts with that
preference and offers its own Flash/Pro control. Switching restarts authorization
and media capture, preserves the shared conversation, and uses a separate
resumption scope for each model.

Both models declare tools as `NON_BLOCKING`. Each incoming tool batch runs up to
four calls concurrently, so pending approval does not hold up independent reads.
Speech interruptions stop audio without falsely cancelling background tools;
provider cancellation IDs or disconnects end those calls. Flash omits `thinkingConfig`;
Pro never uses `MINIMAL` or function-response scheduling. Pro's `turnComplete`
ends an utterance, while `interactionStatus: IDLE` finalizes the interaction.
The UI shows background work until that signal, allowing further speech and tools.
Both modes compress context at 100,000 tokens toward a 64,000-token window,
using more of the new models’ 131,072-token input capacity.
Proactive audio stays enabled by the provider. Camera and screen frames remain
opt-in, and mutation approval/cancellation checks still apply.

Before deploying this upgrade, apply
`20260916100000_mira_live_38_models.sql` through the database release process.
It registers model pricing and extends existing Live model allowlists. Without
these rows new sessions fail closed; they do not silently bill another model.
Production migration application is user-operated. Existing sessions keep their
original pricing snapshot. The installed `@google/genai` 2.22 SDK already supports
interaction status and asynchronous tool declarations.

Google's [migration guide](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)
and [Thinking guide](https://ai.google.dev/gemini-api/docs/live-api/thinking)
define the session contract. Rates come from the
[pricing table](https://ai.google.dev/gemini-api/docs/pricing).

| Capability | Execution boundary |
| --- | --- |
| Tasks, members, task visualizations | Existing `/api/v1/live/tools/execute` |
| Current local time and timezone | Browser clock |
| Calendar events | `listWorkspaceCalendarEvents` through `@tuturuuu/internal-api` |

| Session notes | Memory in the current live interface |

Calendar reads require an explicit ISO date range of at most 31 days and return
at most 50 events to Gemini. Event creation validates timestamps and text lengths.
Model arguments cannot select a different workspace or calendar provider. Existing
calendar APIs enforce authentication and workspace permissions. Calendar tools
themselves require no additional schema changes.

The dashboard token has its own expanded tool declarations and instructions.
Legacy assistant voice clients retain their original tool catalog.

Task mutations and calendar creation wait for approval of an on-screen argument
preview. This is a user-interaction gate; server-side authorization remains the
security boundary. Calls are deduplicated by provider ID, cancellation includes
queued calls, and late cancelled results are not sent back or displayed. Stopping
a request cannot roll back a mutation already accepted by the server. Failed
mutations are not retried automatically; verify their result before retrying.

## Recovery and billing

The client forwards `sessionResumption.handle` even with ephemeral authorization,
without supplying replacements for server-constrained tools or instructions.
`GoAway` schedules reconnection, and unexpected closure attempts recovery at most
three times. Explicit disconnect and unmount invalidate pending connections and
retries. Manual restart obtains fresh authorization. Paid dashboard sessions retain recovery handles in memory for the current billing
reservation only, so a fresh authorization cannot replay cumulative usage from a
previous reservation. Legacy unmetered consumers retain workspace/conversation
scoping through the existing session API.

Credit reservation and cumulative usage settlement remain on the live Next.js
backend. Rust is a future migration target, not the deployed API. The token route
is tracked in `apps/tanstack-web/migration/route-overrides.json`.

### Compact product panels

The Tasks artifact uses the same personal task feed as the Tasks app. A Personal context includes tasks across workspaces and applies personal overrides; a team context stays scoped to that workspace. Compact cards reuse Tasks label colors, priority icons, estimation mappings, and assignee avatars. Due-date filters and board links keep the task feed actionable. Search filters the loaded panel, and Show more reveals additional tasks without discarding the rest of the feed.

### Assistant-managed workspace

Use `show_workspace_artifact` to open or update a panel. Its optional `presentation` carries a concise title plus search, taskStatus, currency, date, or itemIds filters. Scope captions and assistant explanation blocks are omitted so product cards have the space. Legacy descriptions and highlights remain accepted for compatibility but are not rendered. Calendar dates start a seven-day local range. Keep explanations in chat, grounded in tool data, and only use IDs already returned by data tools. Artifacts fetch their own authorized data; presentation text never grants access or changes source records.

Use `manage_workspace` with `close_artifact`, `focus_artifact`, `close_all`, or `set_layout` to manage screen space as the task changes. Opening a new panel automatically collapses expanded navigation; collapsed, hover, and hidden modes are preserved. Updating an existing panel leaves navigation alone. Opening or updating a panel without a layout preserves the current arrangement. Focusing retains that panel's presentation and closes the others; closing all restores full-width chat. The user can still search, filter, refresh, open the full product, and close each artifact directly. Distinct theme-aware product accents distinguish task urgency, calendar days, wallet balances, and meetings.

For artifact orchestration, a successful UI command is complete: issue only the remaining requested actions and then answer. Replacing one panel uses `close_artifact` and `show_workspace_artifact`; `focus_artifact` deliberately closes the others. Opening a panel does not return its data to the model. Use a title-only presentation until a relevant data-read tool supplies facts; the panel itself displays authoritative counts and balances.


### Chat capability discovery and reliable actions

Chat starts with a small discovery set. `search_tools` returns at most eight authorized matches plus focused domain guidance and activates them for the next step. `select_tools` supports a working set of at most twelve known operations. Add tool definitions, directory metadata, permission mapping, and an executor together; discovery indexes the directory automatically. This is progressive tool loading, not arbitrary code execution or automatic access to external MCP servers.

Workspace verification fails closed before context reads. Mutation permissions are resolved for the selected workspace, and operations retain that authorized workspace if another concurrent call changes context. The per-turn runtime ends repeated identical read/discovery/UI cycles and repeated failures. Gemini native search reports `server:GOOGLE_SEARCH_WEB`; recognize it alongside `google_search` before forcing another search, and do not retry a wrapper that already returned grounded sources. Identical task creations share their first result within a turn, including concurrent calls. This is not cross-request idempotency. Task creation saves creator, start/due dates, and estimates, then reads the saved task location. Assignment or readback failures return an incomplete result with the created ID; recover that task rather than inserting another. `get_task` and paginated `search_tasks` locate saved tasks in the current workspace. Existing label, project, assignee, and task mutation tools remain available.

Chat Calendar automation and event writes forward the authenticated request through the existing Calendar API, including selected Google/Microsoft destinations. It can inspect connection health, provide Google OAuth authorization, sync connected calendars, lock/unlock events, read schedulable tasks, and preview/apply scheduling. Apply requires a successful same-workspace/window preview in the current turn and uses safe apply; the Calendar service recomputes availability and rejects unresolved warnings. Provider authorization and locked commitments remain enforced by Calendar. These new automation tools are not exposed in legacy Live/Meet sessions without the corresponding authenticated execution path.

When debugging a reported false completion, inspect the stored tool result and returned task ID first, then read that ID in its recorded workspace. A chat confirmation or artifact opening alone is not evidence of a product write. Runtime verification of provider sync or scheduling requires an authorized test account; mocked tests only verify dispatch and failure handling.

### Native search completion

Mira keeps `google_search` as an executable function tool. Do not override it
with a provider-native tool in the main mixed tool set: Gemini maps required
tool choice to `ANY`, which can issue many server-side searches inside one
provider step without answering. The outer step guard cannot interrupt that
provider-step loop.

Explicit search requests require the search executor before proceeding. The
executor uses native Google search through the direct Google provider used by chat, with
automatic tool choice, a 30-second deadline, one provider step, and at most one
grounding retry. It requires grounding evidence and a nonempty final answer.
Other required workspace and task tools keep their required-tool policy.
Verify a real grounded answer and visible sources after orchestration changes;
mocked tool events alone are insufficient.

The search executor must use the configured direct Google connection, like the
chat route. Routing only search through AI Gateway adds a separate credit and
authentication dependency; a gateway 403 does not mean Google search is down.

### Conversation chronology and native presentation

Assistant history stores the ordered provider content for every generation step in
`metadata.ai.parts`. Tool results update their original call slot, including failed
and unfinished calls; they do not move to completion order. The message content
column contains all text segments in order. History loading prefers these canonical
parts over legacy text/tool arrays, and only adjacent tool activity is grouped.
When metadata must be compacted, text spans reference the content column and tool
payload previews shrink while later timeline entries remain present. The fallback
omits the detailed context breakdown to prioritize conversation history. The
current schema allows 10 MiB of AI message metadata and exempts message content
from generic short-text limits. Old records
that already lost interleaving cannot have their original chronology reconstructed.

Explicit requests to show tasks, calendar, finance, or meetings activate the native
artifact opener directly. Follow-ups such as "show it in an artifact" use recent
conversation context. Product panels fetch their own data; a task-data read or
Markdown table must never be described as an opened artifact. Workspace resolution
still precedes presentation when a named workspace needs to be selected.

### Reading retried tool chains

The collapsed action summary counts unresolved failed attempts, rather than all
calls in a chain. A later successful call with the same tool name and normalized
input changes the summary to "Completed after retry". The original failed attempt
remains expandable, labeled as recovered. Different inputs and missing inputs do not establish recovery. A logical failure
output is not a successful retry; a later verified success can recover either
a transport error or a logical failure. This outcome is derived from
ordered message parts, so restoring a conversation produces the same summary;
assistant prose is never used as proof of success.

Presentation destinations such as "in the task panel" are not workspace names.
An explicitly requested artifact can still open after repeated discovery calls,
subject to the existing three-attempt artifact limit.

## Mira chat tool discovery

Mira chat uses AI SDK `toolSearch()` with deferred tool definitions (AI SDK
7.0.107 or later). The first step exposes only the selected control tools.
Search results make matching capabilities available on the next model step;
searching does not perform the operation or approve a mutation. Explicit tool
selection remains supported for clients that already know the tool names.

The per-generation discovery adapter rechecks workspace permissions before each
step, while the existing executors authorize writes independently. A workspace
change during permission resolution fails closed. Forced artifact/workspace
steps and terminal loop guards retain their restricted tool sets. Definitions
are never mutated in the shared registry. This change applies to streamed Mira
chat; live voice retains its separate tool protocol.

Run the SDK-backed tests in `packages/ai/src/tools/mira-sdk-tool-search.test.ts`
when changing discovery. They exercise real SDK model steps with a mock provider,
including deferred loading, denied permissions, workspace changes, explicit
selection, and approval-gated writes. These tests do not replace authenticated
provider or meeting-invitation round trips.

## Mobile tool ordering and session ownership

Mobile Live runs the currently declared workspace tools on the authenticated
server API; only screen context is resolved locally. Tool batches execute in
provider receipt order. Finalizing a turn waits for its pending tool results,
including errors, before saving ordered text/tool parts. Both canonical Chat
history and legacy Assistant history restore those parts without replaying tools.
Provider text and output transcription are alternate streams: text takes priority
when both are present, preventing duplicated replies.

Each batch belongs to the actor, workspace, and connection generation captured
when received. Disconnecting, replacing the session, or changing actor discards
late output and prevents remaining calls from executing or reaching a new socket.
An already dispatched server mutation cannot be undone by client cancellation.
Starting a new typed turn keeps the completed previous turn's original text and
attachment metadata; its pending output cannot overwrite the new draft.

Regression evidence lives in `assistant_live_persistence_test.dart` and
`assistant_live_turn_parts_test.dart`. These are lifecycle and metadata checks;
provider latency and live device connectivity require separate runtime evidence.

## Mobile startup measurements

After the authenticated token arrives, mobile binds the owned conversation and
initializes its native audio player concurrently. Both must finish before the
provider socket is opened. A failure settles both operations; cancellation or an
actor/workspace epoch change prevents later connection and timing publication.
Native playback initialization and disposal retain their existing serial queue.

Live state records monotonic millisecond durations for token minting, history
binding, audio initialization, socket connection, provider readiness, and the
whole attempt. These measurements contain no tokens, account identifiers, message
content, or error payloads and are not uploaded automatically. Concurrent stage
durations must not be added to estimate total latency. Failed attempts retain
only completed phase timings; obsolete attempts publish none.

`assistant_live_startup_phases_test.dart` verifies independent overlap, the
settle-all failure barrier, cancelled scope fencing, and immutable measurements.
This removes serial client-side waiting; actual device/provider speed remains a
runtime measurement rather than a promised fixed latency reduction.

## Canonical mobile Live capabilities

New mobile clients request the `canonical-v1` tool protocol. The token response
selects the protocol; an absent or unsupported response value keeps the legacy
execution route. Existing clients keep legacy declarations and execution. A
canonical session discovers authorized operations through `search_workspace_tools`
and executes their validated input through `execute_workspace_tool`. Schemas come
from the same Mira registry used by Chat, so registered capabilities do not need
a second manually maintained mobile tool declaration list.

Every canonical request authenticates the actor, verifies workspace membership
and the voice tier, and executes through the canonical permission-aware factory.
This transport stays in the session workspace; workspace switching, interactive
rendered UI, and approval-gated tools are unavailable. Screen metadata remains a
local, opt-in capability. Discovery does not authorize a later request: execution
rechecks access. A tool error is retained as an error rather than represented as
a completed action. Provider call identifiers are preserved; this does not claim
network-wide mutation deduplication or cancellation of dispatched writes.

Resumption handles use protocol-specific, UUID-validated chat scopes so a
canonical connection cannot restore legacy tool declarations, or vice versa.
Both scopes still require ownership of the same conversation. The Rust GET
session port follows the same validation; web remains the production runtime.

`canonical-tool-bridge.test.ts`, the canonical execution route tests,
`session-scope.test.ts`, and `assistant_live_repository_test.dart` cover schema
validation, permissions, unavailable tools, scope separation, and compatibility.
Provider calls and latency still require authenticated runtime verification.
