---
title: Mobile analytics and crash report privacy
description: Device consent for Firebase telemetry in the Flutter app.
---

Settings > Preferences > Privacy exposes **Share analytics and crash reports**
on the Flutter iOS and Android apps, in English and Vietnamese. This single
device-wide choice controls Firebase Analytics events and Crashlytics reports,
including operational and fatal error reporting. It persists across restarts,
sign-in, sign-out and workspace changes; it is not synchronized to an account.

Sharing is **off until the user taps Allow, in every region**. There is no
locale or region default and no region list: Firebase Analytics and Crashlytics
collect nothing before an explicit Allow, from the first-run prompt or from
Settings. The app works fully either way. The answer is stored on the device
together with the notice version it was given under (`telemetry-consent-v1`) and
the time. Changing the prompt or Settings wording bumps the version, which voids
stored answers and asks again; nothing is collected in between. An answer stored
by an older build (including the earlier regional-default key) is never trusted:
those users see the prompt once on the first launch after the update, with no
collection until they answer. The wording is DRAFT LEGAL COPY: not
lawyer-reviewed; for testing, not release.

## First-run prompt

Production builds show a one-time, full-screen prompt (route
`/telemetry-consent`, above the shell) once a signed-in user has a workspace and
the device has no stored answer for the current notice version. **Allow** and
**Don't allow** share one size and style, in that order, nothing is preselected,
and **Privacy details** opens the public privacy notice. Closing the prompt with
the back gesture counts as **Don't allow**, never as consent. An answer persists
exactly like the Settings switch (declining revokes before persisting) and the
prompt is not shown again until the notice version changes. Settings stays the
place to change the choice, and choosing there first also ends the prompt.
Settings routes are never interrupted, and a deep link is restored after the
answer. Development and staging builds default to no prompt and no collection; the QA override below is the only exception.

## Advertising identifiers

No advertising identifier (Android AD_ID, iOS IDFA) is collected. Android removes
the merged `com.google.android.gms.permission.AD_ID` and
`android.permission.ACCESS_ADSERVICES_AD_ID` permissions and sets
`google_analytics_adid_collection_enabled` to false. iOS sets
`GOOGLE_ANALYTICS_ADID_COLLECTION_ENABLED` to NO and links Firebase Analytics
without ad-ID support (`$FirebaseAnalyticsWithoutAdIdSupport` in the Podfile, so
the `GoogleAppMeasurement/IdentitySupport` subspec and AdSupport are not
linked). The native-config test guards these settings.

Native collection defaults are disabled. Startup reads the preference before
Firebase initialization and explicitly configures both collection SDKs. Turning
the toggle off revokes collection before waiting for preference persistence.
Turning it on requires successful persistence first. Settings shows a
description under the switch. A failed update shows an
inline retry message. Non-production flavors do not collect unless the non-release QA override is active and the saved choice is Allow. This setting does not control push notifications, backend request
logs or other app surfaces; it cannot retract reports already transmitted.

Whenever collection is disabled, at startup or on opt-out, the app deletes
unsent Crashlytics reports, so crashes recorded without consent never upload
later. Builds before this setting persisted Firebase collection on, and the
SDKs prefer that stored override over the platform default and act on it before
Dart runs. Two native gates close this, both reading the stored consent
(shared_preferences: `FlutterSharedPreferences` with the `flutter.` key prefix on
Android, NSUserDefaults on iOS) and treating anything other than an explicit
Allow under the current notice version as "off":

- Android's `TelemetryConsentGateProvider` (initOrder 200) clears the Crashlytics
  override before `FirebaseInitProvider` (100), and `TelemetryCollectionLockProvider`
  (initOrder 50) calls `setAnalyticsCollectionEnabled(false)` and
  `setCrashlyticsCollectionEnabled(false)` right after it unless the choice is
  Allow. Providers install before `Application.onCreate`, so this also covers
  process starts that never open `MainActivity`.
- iOS clears the Crashlytics override in `willFinishLaunching` and calls the same
  two setters right after `FirebaseApp.configure()` unless the choice is Allow.

Dart enables collection only after reading an explicit Allow. The gates mirror
SDK-internal storage and the consent keys, so recheck them when upgrading
Firebase or bumping the notice version (a unit test ties the native constants to
`TelemetryPreference`).

Signing out, switching accounts and removing the active account run the auth
cubit's `onBeforeSignOut`, which calls `TelemetryPreference.reloadConsent()`:
collection is revoked, then enabled again only if the stored choice, read
afresh, is an explicit Allow. A storage or SDK failure leaves it off and never
blocks the sign-out. The choice itself stays device-wide.

Android also removes the merged `ACCESS_ADSERVICES_ATTRIBUTION` permission: the
app does no ad measurement, so Privacy Sandbox attribution reporting stays
unused.

## iOS privacy manifest

`ios/Runner/PrivacyInfo.xcprivacy` declares, as unlinked and not used for
tracking, the data Firebase Analytics, Crashlytics and installation IDs may
collect (device ID, product interaction, coarse location and diagnostics) and
the UserDefaults required-reason API (`CA92.1`, the consent and Crashlytics
gates read the app's own defaults). Purchase history and user ID are not
declared: the app has no StoreKit purchases and never calls `setUserId`. The
manifest states what the app may collect; the consent gate decides whether it
does. The text is a draft that is not lawyer-reviewed; reconcile it with an Xcode
Privacy Report from the CI archive and the App Store Connect labels before
release.

Regression coverage: `telemetry_consent_page_test.dart` covers prompt
eligibility, no collection before Allow, redirect and both answers;
`telemetry_preference_test.dart` covers no collection in any locale, stored
version and time, version changes, legacy values, startup ordering, consent
reloads and the native gates; `auth_cubit_consent_hook_test.dart` covers the
reload on every session transition; `TelemetryConsentDecisionTest` (Android
unit test) covers the native decision; `telemetry_settings_tile_test.dart` covers
label and switch activation; `mobile_observability_test.dart` covers deletion of
unsent reports at startup and on opt-out. The preference suite checks native
defaults, duplicate keys and native gate ordering.
Validation uses `flutter gen-l10n`, `flutter analyze`, focused `flutter test` and
`bun check:changed` on an admitted Flutter host. No release build is required.

## QA with development Firebase

Use a development-flavor debug build to exercise the production consent flow
without sending QA telemetry to production Firebase:

```sh
# Before the iOS run in a fresh clone:
python3 ../../scripts/mobile-deployment/firebase-service-config.py --platform ios
flutter run --flavor development --target lib/main_development.dart --dart-define=CONSENT_GATE_QA=true -d <sim>
flutter run --flavor development --target lib/main_development.dart --dart-define=CONSENT_GATE_QA=true -d <emulator>
```

The const flag is ignored in release mode. It enables the same prompt, Settings
Allow control and collection gate on non-production flavors; it never changes
the flavor or Firebase options. Development still uses development Firebase.
No user-facing wording changes. Native AppDelegate and Android providers already
read stored consent irrespective of flavor.

For iOS Analytics debug output, add launch argument
`-FIRAnalyticsDebugEnabled` in the development Xcode scheme. For Android use
`adb shell setprop debug.firebase.analytics.app <development-application-id>`;
reset with `adb shell setprop debug.firebase.analytics.app .none.`.
Enable Crashlytics debug logs with `-FIRDebugEnabled` on iOS or
`adb shell setprop log.tag.FirebaseCrashlytics DEBUG` on Android.

Use disposable simulator/emulator data. Capture network traffic from process
start, through fresh Deny and relaunch, then Allow as a positive control.
Repeat an upgrade preserving earlier persisted Firebase-enable overrides with
missing, denied and stale-version consent. Before Allow, expect zero Analytics
and Crashlytics requests; use a proxy alongside debug logs, since logs alone
cannot prove zero requests. Run the focused observability suite both normally
and with `flutter test --dart-define=CONSENT_GATE_QA=true`; the
`consent_gate_qa_test.dart` regression covers release exclusion and development
Firebase identity on both mobile platforms.

Development iOS/macOS flavor plists and Android's
`android/app/src/development/google-services.json` are committed public Firebase
client configuration. PR builds receive no Firebase CI secret. Dart development
options and native resources use `tuturuuu-mobile-dev`. Earlier development
builds targeted `tuturuuu-mobile` for analytics and crash data; this corrects
development only. Staging still targets production and is tracked separately.
No development web/Windows registrations exist, so those targets fail explicitly.
The supplied dev Firebase registration has no Google OAuth client; Google sign-in
requires separate OAuth provisioning before it can be accepted on this flavor.
For Android Analytics logs, use `adb shell setprop log.tag.FA VERBOSE` and
`adb shell setprop log.tag.FA-SVC VERBOSE`. Vera re-runs iOS and Android device
checks; unit tests do not establish device network acceptance.
