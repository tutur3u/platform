title: "Meet Whiteboard and Timer"
description: "One Whiteboard and one Timer in the Meet Activities menu, and how older whiteboard and timer activities still open."
audience: users
---

With `MEET_UX_V2` on in Meet, the Activities menu offers one **Whiteboard**
("Bảng trắng") and one **Timer** ("Hẹn giờ") instead of several older entries.
With the flag off, and in Parley, the menu is unchanged.

## Whiteboard

**Scope.** The Activities menu, the stage pane title, the minimized-activity
chip in the dock and the phone activity switcher.

**Default.** The Whiteboard entry opens the Tuturuuu Whiteboard (Excalidraw)
linked to the meeting. It is always kept in the workspace whiteboard as people
draw, so nothing in Meet asks anyone to save it and there is no Save button. The
board's host controls (link, create, guest access, remove) are unchanged; see
[Saved whiteboard](/platform/features/meet-calls#saved-whiteboard).

**Who gets which board.** The entry opens the first of these the person may use:

| Order | Older entry | Stage id | Who has it |
| --- | --- | --- | --- |
| 1 | Saved whiteboard | `board` | People who may use the room's tools; anonymous guests only while `MEET_GUEST_WHITEBOARD` is on, view-only until `MEET_GUEST_WHITEBOARD_DRAW` is approved |
| 2 | Pen whiteboard | `tool:pen-whiteboard` | People who browse the tools, including activity runners in host-only rooms and guests where tools are open to everyone |
| 3 | Classroom whiteboard | `whiteboard` | Rooms with classroom tools |

While `MEET_GUEST_WHITEBOARD` is off, a room with an anonymous guest in it puts
the pen board first for everyone, so the whole room draws on a board the guest
can open. The Tuturuuu Whiteboard stays last in that order, so it still opens
where no pen board is offered.

**Older ids.** Every older id still routes to its own pane, so a saved layout,
a host's default activity, a Follow or a Summon from a client without the flag
still opens the pane, and nothing stored is moved or deleted. Each of those
panes is titled **Whiteboard** with the pen icon.

**Exceptions.**

- Summon has no room view for the Tuturuuu Whiteboard, so it is shared through
  Follow (layout mirroring) only. This is a known limit; the pen board keeps
  Summon.
- Opening the Whiteboard shows the boards linked to the meeting. The host links
  an existing workspace whiteboard or creates one from that picker; nothing is
  created automatically.
- Pen board strokes and classroom whiteboard drawings still end with the room;
  only the Tuturuuu Whiteboard stays after the call.

## Guests on the Tuturuuu Whiteboard

**Switch.** `MEET_GUEST_WHITEBOARD` on the Meet Worker, read by the server like
`MEET_UX_V2`. It is on only for the exact string `true`; the default is off.
It stays off until the security review approves the guest path. If that review
has not approved it by 30 November 2026 18:00 ICT, EduFest runs with it off,
on the pen board.

**Who it covers.** Everyone outside the meeting's workspace: anonymous guests
and signed-in people who are not workspace members. Workspace members and the
host are not affected by the switch.

**On.** A person outside the workspace opens the Tuturuuu Whiteboard from the
Whiteboard entry, or follows a leader onto it, and views it as the link's
guest access allows (**No access**, **Can view**, **Can draw**, set by the
host). They draw only on a **Can draw** board while guest drawing (below) is
also on. Co-Programming and the live document still ask a guest to sign in.

**Guest drawing.** A second switch, `MEET_GUEST_WHITEBOARD_DRAW`, read the
same way: on only for the exact string `true`; missing, empty or any other
value is off, and off is the default. It stays off until guest drawing
hardening is separately approved, so with `MEET_GUEST_WHITEBOARD` on, people
outside the workspace are view-only on the Tuturuuu Whiteboard and draw on
the pen board in class instead. While it is off:

- The whiteboard API mints view tickets for everyone outside the workspace,
  whatever the board's guest access says, and lists their boards as view-only.
  Their editor opens in Excalidraw's view mode with the **View only** badge,
  so it shows no drawing tools.
- The board room, on the Meet Realtime Worker, reads its own copy of the
  switch and honours a guest ticket only as view, even one signed with edit.
  A guest's drawing message is refused and the connection closed (code 1008),
  like any viewer who draws. The cap is rechecked on every write, so a
  connection opened before the switch went off cannot write either, and a
  ticket refresh cannot raise a guest to edit. Cursors and selections, which
  change nothing on the board, still relay.
- Hosts see **Can draw** as **Can draw (view only for now)** ("Được vẽ (tạm
  thời chỉ xem)"). The stored guest access is unchanged, so turning the switch
  on later lets those boards' guests draw without relinking.

Guests draw only when the switch is `true` on both the Meet Worker and the
Meet Realtime Worker; either one off keeps them view-only. Workspace members
and the host are not affected.

**Off.** The whiteboard API refuses everyone outside the workspace (HTTP 403)
before it reads any board, anonymous guests keep the sign-in state on a board
pane, and with `MEET_UX_V2` the Whiteboard falls back to the pen board for
them and for everyone in a room with one of them. Without `MEET_UX_V2` the
board stays listed for signed-in non-members, and opening it reports that the
whiteboard could not be opened.

**What a guest can reach.** Only boards linked to the current meeting whose
guest access is view or draw, in the meeting's workspace, never archived. A
guest never sees the workspace board list, link settings or management
actions, and the board accepts no images or files. Everyone on a board is
named by a per-board id derived from their user id, so nobody sees another
person's platform user id. From people outside the workspace the board keeps
only the drawing fields Excalidraw uses for the element's type, and every
field that type draws from must be present (position, size, angle, stroke,
fill, roughness, opacity, seed and groups for every shape; points for lines,
arrows (two or more, or one once deleted) and freehand strokes (one or
more); text, font size, font family and line height for text). Each field is
checked for type, size and range: positions within 1,000,000 px, sizes up to
10,000 px, point coordinates within 100,000 px, stroke widths 0.5 to 64 (16
for freehand), roughness 0 to 5, opacity 0 to 100, font sizes 1 to 256, line
heights 0.5 to 10, pressures 0 to 1, binding focus within -1 to 1, bounded
text, known styles, at most 32 groups, 256 bound elements and 500 lines of
text. A freehand stroke needs a pressure for every point or simulated
pressure, since Excalidraw draws one with neither invisibly. A line, arrow or freehand stroke from someone outside
the workspace holds at most 10,000 points, and its render cost (below) limits
a rough line or arrow to about 5,000; a longer stroke is refused, so very long
strokes need to be drawn in parts. The editor holds back a new line or arrow
until it has its second point, so starting one never reports a refused edit;
deletions, and lines the board already has, always go out. An arrow from
someone outside the workspace never carries a text label: every label entry is
dropped before the arrow is stored or relayed. Members' arrow labels are kept.

Drawing from people outside the workspace is budgeted to limit the work and
memory each viewer spends on the board. The budgets assume 100% zoom at a
device pixel ratio of two. The board's editor never caches an element above
its 100%-zoom size, so zooming in draws the cache upscaled instead of growing
it, and it fits an arrow's label canvas within the per-element cap, for
everyone on the board (see Excalidraw canvas cap in the development guide;
regression test `packages/whiteboard/src/excalidraw-canvas-cap.test.ts`). Every
element has one render cost, roughly the lines and
points a viewer draws for it: one, plus its fill, its stroke points, its
dashes and its text lines.

- A hachure, zigzag or cross-hatch fill on a rectangle, diamond or ellipse
  costs its diagonal over four times the stroke width, plus its diagonal over
  16 for the scan across it. A filled line or freehand stroke may be concave,
  so each edge costs half the scan lines it crosses, which bounds the lines for
  any shape, and the scan costs its whole outline over 16, since it touches
  every edge on each step. Zigzag and cross-hatch count twice and cross-hatch
  scans twice; a missing fill style counts as hachure, and a transparent
  background, an arrow or text draws no fill. A solid fill on a line or
  freehand stroke costs 1.25 per point.
- A line, arrow or freehand stroke costs one per point, two for a solid line
  or arrow with roughness, which roughjs strokes twice.
- Dashed and dotted outlines cost their length over 16 or 7.5 units; along a
  line or arrow the length counts 1.7 times, for its curves.
- Text costs one per line.

Every viewer also caches each element on its own canvas of up to 16.7 million
pixels (64 MiB). The board measures that canvas at a device pixel ratio of
two: twice the element's box (the bounds of its points for a line, arrow or
freehand stroke, grown by a quarter on each axis plus four units per
roughness for a rounded line or arrow, which draws a curve past its points)
plus Excalidraw's padding on each side, which is half the font size for text,
twelve stroke widths for a freehand stroke and 20 px otherwise, up to that
cap. An arrow that lists a text label also gets a square
label canvas, twice its longest side plus ten paddings, which Excalidraw never
caps; it counts whether or not the label exists.

One element from someone outside the workspace may cost at most 10,000. Their
growing edits are refused once the whole board, members' shapes included,
would cost more than 200,000 or cache more than four full-size canvases
(67 million pixels, 256 MiB). Each of their connections spends a churn
bucket of 40,000 that refills 4,000 a second, and every change from anyone
outside the workspace also spends the board's shared bucket of 120,000 that
refills 12,000 a second, so the 30 guest connections a board allows cannot add
up their buckets. Every applied change is charged its render cost plus one per
4,096 canvas pixels, since each viewer redraws a changed element's canvas, so
re-sending the same large or costly shape is bounded too; a full-size canvas
costs 4,096. Deleting costs nothing. A connection's bucket survives the room
being evicted; the board's bucket restarts full. The runtime currently
evicts an idle room only after about ten seconds without an event, and the
bucket refills from empty in ten seconds, so that grants nothing extra; an
earlier eviction or a restart grants at most one extra bucket.
Members' own edits are never refused for cost, and anyone may still shrink or
delete a shape on a full board. A refused edit reports that the board is
full.

An element with a malformed or out-of-range field is refused and the sender is
told. Links must be http(s) or same-site, with no backslash or
control character; other links are cleared.

**Revocation.** Board tickets for people outside the workspace last one minute
and the call renews them every 30 seconds through the Meet API. Each renewal
asks the room's `board.access` check whether the person has an open connection
to the room right now, and checks again that the switch is on and the board is
still linked with guest access. Waiting, removed and only remembered guests
are refused, and so is someone whose call connection dropped, even while the
room still shows them during its 30-second reconnect grace period. The last
ticket a person received stays valid for at most a minute, so after they
leave, are removed, drop off, or their board is unlinked, archived or set to
no access, they receive board data and can send edits for at most one more
minute. The board room closes the expired connection at its next sweep, at
most a minute after that, without sending it anything in between. Members
keep two-minute tickets.

**Limits.**

- The Meet whiteboard API allows each person outside the workspace 30 list or
  join calls a minute per meeting (HTTP 429 with `Retry-After` beyond that),
  counted in the shared abuse-guard store or, when it is unavailable, per
  isolate.
- People outside the workspace get 20 board messages a second (members 40),
  messages up to 256 KiB (members 1 MB), at most three open board connections
  each and six connection opens a minute each. Guests hold at most 30 of a
  board's 50 connections, so members always find room. A connection over a
  limit is refused or closed; the client reconnects with a fresh ticket. The
  open counts are stored with the board room, so an eviction does not reset
  them (except while `MEET_WHITEBOARD_FLUSH_DISABLED` keeps storage off).
- Each board broadcasts its participant list at most once a second, with at
  most 50 entries sent to at most 50 sockets. Joins, leaves and ticket
  refreshes that change an honoured role are batched into one snapshot of
  the current participants. New connections receive the scene immediately
  and the participant list with the next broadcast.
- Cursors and selections from people outside the workspace are relayed at
  most ten times a second per connection; updates in between are replaced by
  the latest, never queued. Every such relay spends the board's shared relay
  budget by its size times the people it reaches: a 512 KiB burst that
  refills 256 KiB a second. A relay over the budget is held, still only the
  latest, until the budget refills. The first update waiting for bytes gets
  the next refill before later updates can spend it. The relay timer uses
  the time needed to refill the missing bytes and stops when no updates
  remain. Their selections name at most 100 elements; a larger one is not
  relayed. Members' cursors and selections are relayed at once and never spend
  the budget. The budget and held updates
  live in memory, so an eviction restarts the budget full, which grants at
  most one extra burst: the room sits idle about ten seconds before eviction,
  and the budget refills from empty in two.
- A board that nobody is connected to reloads from the database for its next
  joiner only if its last load is at least 30 seconds old, so rapid reconnects
  cost no database read. The load time is stored with the board's state and
  survives an eviction.

**Exceptions.** Rules for under-18 and unconfirmed participants and every host
control are unchanged.

## Timer

**Scope.** The Activities menu and the Timer pane or page.

**Default.** One Timer with a **Just me** / **Everyone** switch ("Chỉ mình tôi"
/ "Mọi người"). Hosts and co-hosts who may set the room timer start on
**Everyone**; everyone else starts on **Just me**.

- **Everyone** is the room's class timer with its server rules unchanged: it
  needs `MEET_CLASS_TIMER_ENABLED`, hosts and co-hosts start it, and only the
  host pauses, resumes and stops it. Everyone admitted sees the read-only chip.
- **Just me** is the private countdown on this device. It never writes room
  state and keeps running while hidden.
- People who may not set the room timer see **Everyone** disabled with the
  reason: "Only hosts and co-hosts can set a timer for everyone." or, when the
  room has no shared timer, "This room does not offer a timer for everyone."

**Where it opens.** For people who browse the tools it is the Timer pane
(`tool:timers`). A host or co-host who does not browse the tools (for example in
a host-only room) still gets the Timer as a page in the Activities dialog
(`class-timer`), with the same switch. The older ids keep routing; a `tool:timers`
pane is titled **Timer**.

**Default activity setting.** With `MEET_UX_V2` on, the host's **Open for
everyone who joins** setting names the pen board **Whiteboard** and the
private timer **Timer**. The stored values (`tool:pen-whiteboard`,
`tool:timers`) are unchanged, so a room that already has one keeps it.

## EduFest classes

The EduFest run (guest join, Upskii presenter, Follow, classroom quizzes, Q&A,
transcripts) does not use either activity. With `MEET_UX_V2` on and
`MEET_GUEST_WHITEBOARD` off, a class with guests in it gets the pen board as
its Whiteboard. With both on, guests view the Tuturuuu Whiteboard and draw on
the pen board in class, which the host summons when guests should draw. Guest
drawing on the Tuturuuu Whiteboard waits for `MEET_GUEST_WHITEBOARD_DRAW` to
be approved; once it is on, guests draw there when the host sets the board's
guest access to **Can draw**.
