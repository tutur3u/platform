## What it is for

The Fleet view answers one question first: what is going on, and what needs me?
It is a read-only board view over a board's existing tasks, through the same
permission-gated task source as the other views. Slice 1 adds no database
migration and no endpoint.

## Scope and default

- **Where:** a board offers the Fleet view when any of its tasks carries a fleet
  signal: a fleet label (`needs-user`, `state:`, `owner:` or `product:`), a
  needs-user flag, an external key, an agent assignee, external links, or a legacy
  fleet header.
  Such boards list Fleet first in the View menu, and it becomes the default view
  until the viewer picks another. The last choice is remembered per viewer, as for
  the other views. Boards without fleet tasks are unchanged.
- **Default triage:** the view opens on three buckets, in this order: **Needs me**,
  **Live** and **Blocked**. A card that needs you is listed under Needs me even if
  it is also blocked. Live means running, in review or CI running, whatever the
  day; it is not limited to today.
- **Up next and Recently done:** below the triage, two collapsed sections list
  the cards the buckets leave out. Up next holds open queued work in triage order.
  Recently done holds done cards, newest update first. Each lists at most 20
  cards with a count of the rest, and both start collapsed so the triage stays
  the first thing on screen. Archived (closed list) and documents-list cards never
  appear in these sections.
- **Grouping:** Triage (default), Product, Priority or Owner. Groups with a
  needs-you card come first, then groups with a blocked card, then the rest by
  size. Priority groups run P0 to P3. Empty groups are hidden.
- **Density:** comfortable by default; compact keeps one title line and one row
  of fields, for dense boards only.

## The card face

Every fleet card shows the same parts in the same places:

1. A scan row: product, priority as P0 to P3, and the task number.
2. A bounded title: a subject of at most 72 characters, clamped to two lines
   (one in compact). A leading copy of the card code (`N-165: `, `[N-165] `) is
   dropped because the code already sits in the scan row; only the card's own
   code is removed. The full stored title stays in the hover text and the card's
   accessible name. Longer titles are announced to screen readers as too long,
   not cut silently. Status prose, commit hashes and notes belong in fields or
   the description.
3. A **Needs you** callout with the one-line ask when `needs_user` is true. It is
   the only ink-filled element on a card.
4. A **Blocked by** line whenever the card is blocked: the blocked reason, else
   the number of blocked-by task relationships, else **Reason not set**. Done
   cards never show it. Under a Needs you callout, and in compact density, it is
   a quiet one-line row, so a card that waits on you still says what it waits
   behind. The relationship count includes blockers that are already finished,
   so such a card stays in Blocked until the relationship is removed.
5. Four fixed fields: status, owner, ETA and last update. The owner carries an
   agent or person icon when the owner came from an agent identity or an
   assignee; an `owner:` label stays unmarked. A missing value is a word
   (**Unowned**, **No ETA**, **No update**), so data gaps stay visible. Last
   update never falls back to the created time.
6. Up to two links (PR, commit, thread, run, doc), then +N.

Status words always travel with an icon and a colour: needs you, running, in
review, CI running, blocked, done. Queued and unknown stay quiet. Inside the
fleet, blocked uses the red tone rather than the usual gray, because it is a stop
someone must clear.

Freshness comes from `last_update`: fresh under 2 hours, aging 2 to 24 hours,
stale at 24 hours or more. An ETA is due soon within 2 hours and overdue once
past, unless the card is done. Stale and overdue add their word, so colour is
never the only signal.

## Where card data comes from

Fleet state lives in first-class task fields. The view reads, for each value, the
first source that has one:

| Value | Sources, in order |
| --- | --- |
| Status | task fleet status, then a `state:` label, then the list's status (not started = queued, active = running, review = in review, done or closed = done) |
| Owner | an `owner:` label, then the first agent assignee, then the first human assignee |
| Product | the first linked project, then a `product:` label |
| Priority | the task priority |
| ETA | the task end date |
| Last update | the task `updated_at` |
| Needs you | the task needs-user flag and reason, then the `needs-user` label |
| Blocked | blocked-by task relationships, the task blocked reason, or a blocked status |
| Links | the task's external links (http(s) only become links) |
| Code | the task's external key, then the task number |

The Tasks API stores agent assignees, the needs-user flag and reason, and
links on each task. Incoming blockers use task relationships. The database
sets `updated_at` on creation and edits to task content, status, placement,
or Fleet metadata. Older tasks gain it on the first such edit.
Fleet cards can read the legacy `<!-- fleet:v1 -->` description block for
values the fields leave empty. Once a task's fields are verified, the board
sync can remove the legacy header and leave the editable notes in place.
The CLI field flags and output are documented in the [SDK reference](/reference/packages/sdk#fleet-task-fields).

## Surfaces

- **Web (Tasks app and every app that embeds the Tasks board):** the Fleet board
  view, with the summary strip (Needs me, Live, Blocked, Stale 24h+). Clicking
  a card title opens the existing task side panel.
- **Mobile:** board tiles and list cards for fleet tasks use the same bounded
  title and structured fields. The task sheet shows the field grid, the needs-you
  callout and every link.
- **Design source:** the Tuturuuu design system's Fleet cockpit section and its
  FleetCard, FleetStatusChip, NeedsUserBadge, EtaIndicator, StalenessIndicator,
  DecisionCard, Timeline and CapacityPanel components. The web components live in
  `@tuturuuu/ui/custom/fleet`.

## Intentional exceptions and later slices

- Approve and steer decision cards, the activity timeline merged with fleet
  events, and the machines and capacity panel are designed but not in Slice 1.
  They arrive with the fleet event ingestion slice. Only `manage_mastermind`
  holders will be able to approve or steer.
- Done-card archiving after 24 hours is done by the board sync, not the view;
  the view only hides closed lists and caps Recently done.
- Fleet is a board view (`?view=fleet`), not a new route, so the navigation menu
  is unchanged.
