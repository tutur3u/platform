Meet Live uses `gemini-3.1-flash-live-preview` through a Durable Object in the
existing `tuturuuu-meet` Worker. It does not require a self-hosted process.
The Worker holds the Gemini API key; browsers receive short-lived,
purpose-bound session tokens and connect through `/live-connect`.

## Availability and eligibility

Product decision (20 November 2026). Scope: Private Mira (Live voice, private
chat, document assist, programming, polls and quiz boards) and room Mira (room
chat **@mira**) in Meet and Parley. Default: off. Every check runs on the
server against current Auth and stored data; client values and environment
defaults never satisfy it.

| Requirement | Rule |
| --- | --- |
| Deployment | The raw Worker binding `MEET_AI_DISABLED` must be exactly `false` or `0`. Source configuration keeps `true`, so enabling is an explicit release-time override. The API key stays server-side in `GOOGLE_GENERATIVE_AI_API_KEY`. |
| Workspace gate | The meeting workspace must pass the Meet AI gate described in [Meet calls](/platform/features/meet-calls): hard denies (the workspace excluded in code and `MEET_AI_PROTECTED_WORKSPACE_IDS`), the kill switch and `MEET_AI_DISABLED_WORKSPACE_IDS` always apply, then either the allowlist or the reviewed opt-in `MEET_AI_ALL_WORKSPACES=reviewed-allow-all-2026-11-20`. |
| Account | The same rule as Meet hosting (`canVerifiedAccountHostMeeting`): a verified @tuturuuu.com staff session (`isVerifiedTuturuuuStaffSession`), or a confirmed account whose own Personal subscription is Plus, Pro or Enterprise while `MEET_PAID_TIER_HOSTING_ENABLED` is exactly `true`. Free accounts are denied even in an attested workspace. |
| Membership and presence | Workspace membership and current admitted meeting participation are required independently. |
| Audience (18+) | The meeting workspace needs a stored 18+ audience attestation, set by a workspace settings manager. Exception: verified staff using Private Mira in their own Personal workspace (`personal = true`, `creator_id` = account). Room Mira has no exception, because other participants are present. |
| Billing | Staff requests drain the Tuturuuu root workspace. Paid accounts pay with their own credits: Private Mira charges the requester's Personal workspace and room Mira charges the meeting workspace. Reservation is atomic, as before. A selected tool workspace never changes the payer. |

An active Private Live session rechecks the kill switch and the full workspace
gate (protected ids, denylist, reviewed opt-in or allowlist) on every client
turn (including a client stop), on an abnormal socket close and on its
20-second tick, before any end-of-input signal, recovery or reconnect.
A closed gate ends the session with `workspace_not_enabled`. Every stop path,
including the internal `/control` stop, alarms and failure stops, passes the
current gate to the provider drain, so a revoked session's provider is closed
without further input (no end-of-stream signal); usage already
received settles, pending usage is marked incomplete, and cleanup runs. The Live Durable Object rechecks the account, audience and payer before
code tools run, reading the paid tier and attestation over its server-only REST
client. A saved session whose billing workspace no longer matches the payer
(for example, a staff session after the account loses staff status) is denied.

### Workspace 18+ setting

Workspace settings in `workspace.tuturuuu.com` and `tuturuuu.com` show **Meet
Mira → Meeting audience is 18+** to holders of `manage_workspace_settings`
(Personal workspace owners hold it). Turning it on opens a confirmation; turning
it off withdraws immediately. The setting is stored in the service-only
`private.workspace_mira_audience_attestations` table (one row per workspace).
The settings route checks the permission, records the authenticated manager and
server time and withdraws by deleting the row; browsers and the anon or
authenticated roles have no table access. Erasing the attesting account clears `attested_by`, which invalidates
the attestation until a current manager confirms again.

### 18+ notice and the in-call switch

Meet and Parley show the 18+ notice at Mira entry points, including room chat
**@mira**, Private Mira, document assistance, polls, Quiz Arena, and Forms. Every **Continue** prompt
says to proceed only if you are 18 or older and requires an explicit choice.

In **Meeting settings → Mira**, the workspace owner can confirm or withdraw
**Everyone in this workspace is 18 or older** with one switch. The owner is
responsible for members' access and use. The Meet dialog checks workspace
ownership before offering the switch. The legacy Web settings path above
continues to use the workspace settings permission until the Web owner check
is deployed. The setting starts off by default.
When a workspace policy blocks Mira, the owner can open the setting directly
if the workspace lacks a declaration. Other participants can ask the owner to
check the setting. Each Mira feature still applies its own access policy.

Room chat shows room Mira as one chip, for example **Mira · waiting for 2 ·
Details**, with an icon for its state: choose Continue, waiting, ready, pausing
or paused. **Details** opens a popover (Escape closes it and returns focus to the
chip) that holds the full status, the 18+ note, **Continue** and **Pause** for
the viewer, the Continue progress, and the capabilities the host sets. The
consent rules are the same as before the chip: 18+, a per-person Continue, host
set capabilities and Pause. Without room Mira the chip opens only the
capabilities.

Regression coverage (`*.test.tsx`): `mira-audience-settings`,
`mira-workspace-off`, `call-settings-mira`, `private-notice`, `personal-chat`,
`chat-assistant-notice` and `room-mira-notice`.

## Participant choice and microphone privacy

The notice offers **Continue with Mira**, **Mute Mira for me**, and **Leave**.
Continue is focused but does not imply acceptance. A click records the notice
version, choice, meeting, account, server time and revision in the room Durable
Object before a token can be issued. The notice text, retention line and privacy
link sit behind an info button. Choices are offered only while this device's room
socket is open and admitted, because the room service requires live presence.
Every outcome is visible: the clicked button shows progress, and a missing
presence, pending stop, timeout, unconfirmed or unavailable result shows its own
reason with Retry where retrying can help. Only a server-confirmed Continue on an
available policy enables the personal assistant. Choice records remain in that room's stored
state until that state is erased; there is no automatic expiry promise.

Private Mira receives only the requester's microphone and private typed input.
It receives no room chat history, room roster or selected-workspace context.
The microphone uses echo cancellation and noise suppression. Use headphones to
avoid physical speaker audio being picked up by the microphone. Starting private
capture mutes the meeting microphone; unmuting the meeting pauses private capture
and playback. Replies play only on the requester's device and are never published
as a room track. Other participants see a private-use indicator.

Mute and Leave first stop every registered private session before recording the
new choice. Leave never waits on that record: it stops Mira, records the choice
when it can within a few seconds, then ends the call on this device and shows the
left screen with Rejoin and Back. Token issuance and reconnect recheck the durable choice. Tokens last
120 seconds and bind the account, meeting, app and private mode. Audio frames
must identify that same account and the microphone source.

## Unavailable invitations

Meet and Parley show localized unavailable feedback when a Live start is denied
by the AI availability gate or missing Live service configuration. No assistant
joins on those denials. The shared Live error mapper retains specific device
feedback and the existing fallback for other failures. This feedback does not
enable Live or bypass its authorization, audio consent, or limits. Synthetic
regression coverage: `invite-unavailable.test.tsx`, `live-errors.test.ts` and
`live-workspace-identity.test.tsx`.

## Room Mira and the all-participant fence

Room chat generation through **@mira**, **@ttr** or **@tuturuuu** requires room
Mira authority for the requester (deployment, workspace gate, account rule and
the meeting workspace's stored 18+ attestation) and an all-participant fence.

While room Mira is available in a meeting, chat shows a **Room Mira** notice to
every admitted participant, anonymous guests included. Each participant chooses
**Continue** or **Pause** for their own account; nobody can choose for someone
else. The notice shows only aggregate counts, never who has not chosen. The
meeting room Durable Object stores each choice with the notice version
(`2026-11-20-room-v1`), meeting, account, server time and revision.

The room releases chat context for a mention (`ai.reserve`) or resumes an
approved tool step (`ai.review.claim`) only while every admitted account has a
current Continue, checked atomically with the state it reads. One Pause, a new
participant who has not chosen, or a new notice version pauses room Mira for
everyone; a mention then shows that Mira answers after everyone chooses
Continue. The context sent to the provider contains only messages written by
accounts with a current Continue. Mira's own earlier replies are omitted, since
they can quote people who have since withdrawn; messages from people who left
without choosing never leave the room. Choices are cleared when an
ended room is restored.

Each reserved request records its source accounts (the requester and every
author whose messages it carries) with their exact consent revision. Sending
that saved context to the provider again (`ai.review.claim`), every provider
request (below), saving a private review
and every publication (a reply posted by `ai.finish`, `ai.review.share`) require
the all-participant fence and every source unchanged.

Every outbound provider request, including each model step and the
model-backed web search, holds a dispatch lease in the meeting room. The room
admits it (`mira.room.dispatch`) only while the fence and every source revision
are current, serialized with consent changes, and the release
(`mira.room.release`) reports whether consent stayed unchanged until the
answer arrived. The provider key and destination stay in the Meet Worker; the
room records only admission. Admission returns the lease lifetime, and the
Meet Worker measures its deadline from before the admission call so it never
outlasts the room's: nothing is sent once the caller's signal (or the
`Request` input's own signal) is aborted or the lease has expired, transport aborts at the deadline, and usage observation
stops there too. An expired request is refused (`MIRA_ROOM_LEASE_EXPIRED`) along
with every later request, and a send interrupted after it started counts as
unpriced.

A Pause is deferred while already-admitted requests carry the participant's
words. From the click, the participant no longer counts as Continue, so no new
provider request, reservation, resume or publication can start; the admitted
requests finish under their bounded leases, and their answers are discarded
(their usage still settles). The Pause becomes the effective choice, with a new
revision, when the last lease covering the participant releases or expires (at
most two minutes); overlapping requests from several requesters all have to
settle. Meanwhile the notice shows **Pausing…** without choice buttons and
refreshes every two seconds. Choosing Continue before then cancels the Pause
with a new revision, so requests reserved earlier stay stale. A Pause with no
admitted request covering the participant takes effect immediately.

Settlement carries what was received: usage measured from every provider
answer (including a discarded one) bills both the AI Studio run and the room
cost. When a received answer lacks usage, a completed generation reports no
measurable usage, or a request failed without an answer, the run settles once:
the room cost is unpriced and AI Studio captures the reserved hold. With no
request sent, nothing is billed. A source who pauses and
leaves, or returns with a new Continue (a new revision), makes the request and
its saved review stale; the requester can still discard it, and incurred cost
settles without posting a reply. Requests reserved without recorded sources are
stale. The server checks the fence again before any credit
work. Generation uses the Meet Worker's own provider key; the room
transcription provider binding stays closed.

Room Live input and output (mixed room audio) remain denied on the server,
independent of environment settings. The fence above is the gate a future room
Live transport must use; it does not enable room voice by itself. Private text
inside an accepted Live session remains available. The Private Mira tab in room
chat uses the same current account choice and eligibility as Private Mira Live.
It sends the requester's question and bounded private history, charges the
Private Mira payer, and shows the reply only to that requester unless they
share it. An eligible requester can choose **Enable Mira** in private chat,
confirm the current consent notice, and retry the same message.
See the [private chat regression tests](https://github.com/tutur3u/platform/blob/main/packages/meet-core/src/features/call/components/personal-chat.test.tsx).

Meeting WAV transcription and notes are off. Mixed audio stays outside provider
requests. A room chat mention denied by room Mira authority shows an inline
notice that Room Mira is unavailable and points to Private Mira. Private Mira startup reports blocked, missing or busy
microphones and unavailable audio output with specific messages.

Meet and Parley offer `/poll`, `/summary`, `/actions`, and `/review` in the room
composer. Selecting a command fills an editable **@Tuturuuu** draft. Sending
uses the same room request and availability checks as a typed mention. In
**Private Mira Tutor**, **Share snippet to room** opens an editable confirmation
before posting the selected text to the room. Room tool controls require an
authorized operation from the owning surface. Access to private notes and
tutor chats is blocked in the room permissions card.

the room Live denials before `tuturuuu-meet`. Enabling requires an explicit
runtime override because the source configuration retains

## Memory and context

Memory is disabled by default. Owners can enable it and inspect, edit, or delete
saved entries in meeting settings. Database policies restrict reads to the owner.
Memory changes first stop the owner's active personal sessions so cached private
context cannot continue speaking after a deletion. A durable pending command
blocks new personal sessions until an interrupted mutation has recovered.

Context compression and session resumption support long conversations within
available quota. They do not create a literally infinite model context window.
The active journal keeps bounded recent turns and rolling checkpoints; a private
Durable Object archive supports searching earlier turns in that session. Model
summaries can omit details. Ending the session clears its journal, private review
text, resumption handle, and archive in bounded batches; approved user memories
and billing receipts remain separate. The client retries interrupted connections, including temporary token-refresh failures.
Provider GoAway events use resumable sessions; bounded checkpoints are the fallback
when a handle is no longer valid. Choose a voice before starting. Microphone and
speaker changes in meeting settings also apply to the active personal assistant.
Pausing or interrupting speech clears queued playback on the receiving devices.

Audio is not archived, and audio never received by
the service cannot be reconstructed after an outage.

## Usage and costs

Live reservations and settlement use the platform's existing AI credit ledger
as follows. The room assistant (meeting transcription and notes) charges the
meeting workspace (`workspace_meetings.ws_id`), and the initiating user remains
attributed for per-user limits. Room Mira chat charges the meeting workspace for
paid requesters. A personal assistant session ("Talk to Mira", voice or text)
charges the participant's own personal workspace. Requests by verified staff
charge the Tuturuuu root workspace instead, on every Mira surface, with the
staff member still attributed. A selected tool workspace does not change
billing. Usage is accumulated from
provider events by modality. Reservations use nine-minute holds and renew after eight minutes or before exhaustion; failed
settlements remain durable and retry after the session ends. Final provider usage
is collected during shutdown. Interrupted turns without a final usage receipt
remain marked incomplete even if subsequent turns succeed.

Room admins can see aggregated Live provider costs in meeting settings.
The count represents billing periods, including renewed reservations and
separate approved speech requests, rather than unique people. Updates are
sequence-checked so retries do not count the same period twice. Personal
transcripts and memories are not included in the cost response.

Prices come from the existing model catalog and
[Google's Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.1-flash-live-preview).
The published paid rates verified on 2026-09-10 are $0.75 per million text input
tokens, $3 audio input, $1 image/video input, $4.50 text output, and $12 audio
output. Google Search is $14 per thousand queries after shared allowances.
Project-wide free allowances and Cloudflare Live Worker duration, storage, and
requests are not fully allocated to individual meetings. Missing usage stays
marked incomplete; these estimates do not replace provider invoices.

## Active-session alarm scope

A successful active Live tick schedules the next alarm for twenty seconds later.
The tick first settles pending public billing and expires reviews, then maintains
registry discoverability, sends the room heartbeat or personal context command,
and performs primary quota settlement and usage reporting when billing exists.
Renewal can add settlement, usage and reservation work; reconnect and queued tool
responses add separate provider operations. Count those calls and persisted keys
separately from the alarm itself.

Pause suppresses provider input; it does not skip this alarm's registry, room or
billing work. The registry lease renews after successful registration. Its
23-hour failure boundary limits tolerated registry outages, not the lifetime of
an otherwise healthy session. A future recurring-work bound must preserve active
consent, quota coverage and privacy discoverability, with explicit expiry and
an authenticated durable stop checked before dispatch and rescheduling.
These are source-path findings, not measured billed-operation or hosted shutdown
evidence; duplicate/restart, slow downstream, no-progress and Stop-race probes
remain required before certifying a cost envelope.

## Ended-session compensation and retry safety

Ending Live stops capture and provider output, but unresolved server obligations
can still require work. The session retains registry removal, room release,
quota settlement, usage reporting and private-context erasure independently.
`cleanupEndedLiveSession` handles registry/room compensation while
`finalizeSessionBilling` handles billing and context. The session alarm can invoke
both after `ended` is persisted. A completed flag for one obligation does not
prove completion of the others.

The current registry/room helper arms a future alarm before I/O and persists
completion flags afterward. It does not reserve a finite attempt count or job
expiry before the registry call. Repeated registry failure can therefore keep
scheduling work; a successful external operation followed by a failed progress
write can replay after reconstruction. Persisted session termination alone is
not an independent stop fence for this background work. The nominal one-minute
retry interval is not a hard operation or spending cap: billing retries, duplicate
invocations and restarts must be counted separately.

Active-session registry renewal has a separate privacy lease. It starts at the
12-hour boundary, and retryable failure is tolerated until 23 hours since the last
recorded renewal; at that boundary the helper throws after attempting registration.
These age checks do not reserve attempts: repeated reconstructed calls before the
boundary still each perform a registry RPC. Successful renewal suppresses later
calls only when its timestamp survives persistence. Invalid or future recorded timestamps
now fail closed before registration, as described in the clock-integrity contract
below. This clock fence does not reserve finite retry attempts.
If Stop arrives during registration, the helper attempts compensating removal;
removal failure must remain recoverable without authorizing an unlimited retry job.

Context erasure separately lists at most 128 archived turns per wake and deletes
those keys in a batch; each deleted key remains part of the storage envelope.
A full batch schedules a confirmation wake to discover any remaining turns.
Deletion failure retains the archive and schedules another attempt. Session
finalization persists state from both public-billing settlement and its final
step when the persisted completion receipt is absent, incomplete or inconsistent
with current obligations. Context erasure alone does not establish completion.
The completed-receipt guard described in the runbook performs one session-key
read and skips finalization writes only when durable and current completion agree
for the same session and owner, with no pending usage or public billing. It
rechecks obligations after the read. An in-memory flag alone cannot establish that
a prior progress write succeeded; registry and room compensation remain separate.

Public-billing settlement currently iterates the entire saved billing map in one
invocation. A record needing quota settlement, share completion and usage reporting
can perform three downstream requests and two session-state writes, followed by
one write for the map. Successful quota settlement is persisted before usage
reporting, so a usage failure can retry reporting without re-settling quota.
However, each failed record requests retry scheduling separately, and a failed
final map write can replay reporting after reconstruction. Count those scheduler
calls separately from delivered wakes: repeated scheduling can overwrite one alarm.
A bounded replacement needs a durable cursor and per-record progress; truncating
the map or dropping acknowledged-but-unpersisted obligations loses recovery state.

This is an operating limitation, not permission to discard unresolved work.
Approved memories, private-context deletion obligations, quota reservations and
billing receipts must remain distinguishable and durable. Do not mark cleanup
complete, delete recovery state or settle unknown usage as zero to stop retries.

Before changing this path, require a joint compensation contract:

- Reserve attempts and a finite job deadline durably before downstream work.
  Persist each obligation's idempotent progress and stop automatic scheduling on
  terminal completion or exhaustion while retaining unresolved obligations.
- Bound downstream calls, response consumption and storage keys/rows per wake.
  Include registry/room cleanup and independently scheduled billing/context work
  in the operation envelope; an outer alarm cap alone is insufficient.
- Provide authenticated recovery for pending obligations and a durable stop fence
  checked before dispatch and rescheduling. Concurrent Stop, privacy revocation,
  queued callbacks and billing retries must not replenish or bypass the budget.
- Test duplicate alarms, reconstruction, clock boundaries, no progress, repeated
  downstream failure, reservation-write failure and successful downstream work
  followed by failed persistence. Count actual downstream calls and written keys,
  and exercise the corresponding real Worker/SQLite storage boundaries.

`packages/meet-core/src/features/live-assistant/session-cleanup.test.ts` verifies
that registry failure does not prevent independent room cleanup and that confirmed
completion stops later helper work. It does not establish finite retries,
reschedule-race safety, billing bounds or hosted alarm behavior. Keep those gates
explicit until their implementation and evidence exist. Billing alerts and
per-invocation CPU limits do not establish a total-spend cap.

## Registry lease clock integrity

Active Live sessions require nonnegative safe-integer start and renewal timestamps.
A renewal must lie between session start and the current server clock. Corrupt,
nonfinite or future timestamps fail before a registry request; the session tick
uses its existing `session_unavailable` stop path to end capture and retain billing,
room-release and privacy cleanup obligations. A server clock rollback can therefore
end an active session instead of silently extending privacy discoverability.

This applies to personal and room Live sessions. Valid leases retain the twelve-hour
renewal and twenty-three-hour retryable-failure boundaries. Ended sessions still
attempt registry removal even when their lease timestamps are invalid. These checks
do not introduce finite compensation attempts, authenticated background Stop or a
spending cap. Count those independent obligations separately.

Regression coverage: `registry-heartbeat.test.ts` exercises invalid timestamps,
reconstruction without registration I/O, exact lease boundaries, duplicate renewal
and ended-session removal. `session-cleanup.test.ts` checks independent compensation.
These helper tests use controlled namespaces; real SQLite persistence, hosted
privacy revocation and the complete stop/reschedule path remain release gates.

Apply the additive `meet_private_ai_memory` and
`20261120223430_workspace_mira_audience_attestations` migrations through the

### Voice recovery and review outcomes

Microphone capture uses the browser's 16 kHz resampler and flushes its final
partial frame when stopped. A disconnected personal microphone pauses Live input;
select a working microphone in settings before resuming. Starting personal voice
mutes the meeting microphone; a failed startup restores its previous enabled state.
Room playback requires the listener to enable audio, with at most three seconds of
recent audio buffered while the browser awaits that gesture.

Approved tool outcomes are saved before provider delivery. After a reconnect they
are supplied as completed results, never automatically executed again. A workspace
operation with no completion acknowledgement after two minutes becomes an unknown
outcome for the requester to inspect and discard; discarding never retries the action. Permission checks and approval are required
for every private workspace operation. Task metadata tools without a matching
permission gate are not exposed.

Deployment checks require `GOOGLE_GENERATIVE_AI_API_KEY` on the Meet Worker.
Missing provider token allocation or search grounding usage remains marked as
incomplete cost coverage instead of being counted as free.

Server requests carrying room tokens or database credentials use `redirect: 'manual'`
and reject non-success statuses. Cloudflare's workerd runtime does not implement
`redirect: 'error'`; using it throws before the request reaches the upstream and
can fail the Live WebSocket upgrade. Do not replace this with `follow`, which
could forward credentials to a redirect target. Verify the deployed upgrade in
addition to the Next.js start-session route and provider-only tests.

### Continuous speech playback

Live output is scheduled consecutively on the browser audio clock with an 80 ms
startup/underrun buffer. Provider bursts longer than three seconds do not interrupt
speech. Interruption, playback mute, privacy suppression, and session teardown
still clear the queue; pausing input lets the current answer finish. Room transport
preserves generation and sequence fences, stamps freshness
at dispatch, and bounds queued PCM to 120 seconds. Test slow delivery and a burst
of at least twelve seconds before releasing playback changes.

## Local playback volume and finishing a turn

Use **Playback volume** in the meeting header to adjust master volume, Mira voice,
and each participant. Master volume scales the individual settings, including
screen-share audio and notification sounds. These settings affect only your local
playback for the current call; they do not change anyone else's microphone,
recording, or audio sent to Mira. Deafen and per-feed mute remain independent.

**Ask @mira in chat** opens Everyone, adds a mention without replacing your draft,
and focuses the composer. Private drafts stay private.

When the last microphone included in Mira's room input is muted or excluded,
the final buffered audio is flushed and Mira receives an end-of-input signal.
Other included microphones can continue the shared turn. Pausing personal input
also ends the input turn while allowing Mira's answer to play; privacy suppression
still prevents private playback while your meeting microphone is on.
