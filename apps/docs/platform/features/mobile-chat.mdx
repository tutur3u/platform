## Conversation browsing

Mobile Chat retains the shared app shell and navigation while compact screens
switch between the conversation list and a selected thread. Wide screens keep
both panes visible. The list remains scrollable with tall filter content.

Conversation pages load automatically when the remaining scroll distance falls
below three quarters of the viewport, including when the first page cannot fill
the screen. Only one automatic request is made for an unchanged scoped list;
failed or empty pages retain a manual Load more action rather than retrying in a
loop. The manual action also remains available when filters show no rows.

Pagination results and failures from an older workspace or refresh generation
cannot publish into the current list. Pending local rows continue to use the
existing scoped Chat collection overlay.

## Composer

Attachments use the adaptive sheet shared by compact and expanded mobile
surfaces. Send remains disabled while a message or attachment upload is in
flight, and the icon exposes a localized tooltip. This changes neither message
transport nor attachment permissions; live device and production verification
are still required for delivery.

(`ws_id IS NULL`); writes derive the actor from the session. This authentication
repair does not establish cross-platform notification delivery or enforcement.

## Stream completion

Native Chat and Mira replies stop reading their NDJSON response after a verified
`done` event. Chat requires a saved message receipt; Mira requires a saved
assistant message receipt. Text or tool deltas alone do not prove persistence.
An explicit server error remains a failed reply even when followed by `done`.
Malformed data before completion and EOF without completion remain errors.
Completed replies ignore post-terminal rows and bytes, and UTF-8 decoding retains
partial characters across transport chunks. Response cancellation starts at
completion; cleanup failures or stalls do not replace the saved receipt or an
earlier transport failure. This applies to native Chat streaming;
legacy Assistant SSE and explicit Live sessions keep their separate protocols.

### Durable assistant receipt and cleanup

After the native Chat/Mira batch RPC returns saved assistant messages, shadow
resource cleanup is supplementary. A thrown cleanup failure cannot remove the
saved JSON/NDJSON receipt or turn an accepted reply into a retry prompt. Failures
before authoritative persistence, including permission or database errors,
remain failures; no text-only success or remote fallback is introduced.

## Assistant reply error and save receipts

Native Chat and mobile Mira use the canonical messages POST adapter. By default,
an upstream SSE error produces the fixed public message `AI response unavailable`
when request-scoped server history contains no saved assistant reply. Upstream
error text, provider bodies, credentials, URLs, and model diagnostics are never
used as public error messages. Unknown error payloads use the same fixed fallback.
This applies to streaming and ordinary JSON requests.

A saved partial assistant reply remains authoritative even when the upstream
stream fails. Failed history readback retains the separate send failure response.
Without an upstream error, missing saved history retains `AI response was not saved`.
Replaying a saved client request returns its existing messages without generating
or charging again. This error mapping does not establish the cause of any
customer save incident or repair database persistence.

## Explicit mobile Assistant model and credit settings

Native Chat-backed Assistant model and credit-source choices use the authenticated
conversation settings PATCH, with its `manage_chat` permission check. The client
admits one request after credential preparation, bound to the current actor,
workspace, conversation, selection revision and page lifetime. It validates the
returned conversation ID and complete model, credit source, credit workspace and
thinking-mode tuple before publishing the choice or its local preferences.
Concurrent choices are denied while one is pending. Native history restoration
hydrates the complete validated model, credit source, nullable credit workspace
and thinking mode before admitting Send. It is a read-side operation under the
current actor/workspace/chat generation; opening history never PATCHes settings
and needs no manage permission. Old native snapshots without a complete tuple
must revalidate it. Server-default nullable credit scope and fast mode remain
exact values, rather than being replaced by workspace preferences.

Permission denial, malformed receipts, uncertain transport and stale completion
retain the prior local settings and draft. A stale or missing response can still
follow a physical server write; the client does not compensate or retry it.
Localized notices direct the user to inspect settings before another explicit
choice. This is a client lifecycle fence, not cross-client compare-and-swap.

With no selected conversation, a choice is a local intent. First native creation
captures a one-use model/credit/thinking tuple and includes it in the existing
creation request. The route retains `view_chat`; the canonical creation transaction
retains `create_chat` for AI conversations and writes the complete initial settings
with the conversation and owner membership. It returns the stored tuple bound to
the actor, workspace and new chat. There is no automatic post-creation settings
PATCH and no new `manage_chat` requirement for otherwise authorized first use.
Explicit later settings edits still require `manage_chat`.

Workspace credits may target only the active workspace; personal credits resolve
to the actor's personal workspace. An explicit null scope is retained while billing
resolves the corresponding authorized workspace. An unavailable selected model is
rejected rather than silently replaced by a plan default. No-tuple creation clients
retain existing defaults; DM/group/channel creation cannot provide the new AI tuple.
Malformed, mismatched, unknown or retired creation receipts retain the draft and
creation hold, without a replacement creation or blind retry. Creation POST checks
the captured actor/generation after awaited credential preparation and before its
single HTTP dispatch;401 or challenge responses are not replayed. Ordinary
follow-up sends only read and validate stored settings; they never PATCH them.
The optional creation tuple requires the atomic database migration before activation;
a route-only rollout cannot acknowledge an old RPC response missing that tuple.

creation route's `initial-settings.test.ts`, and `chat-initial-ai-settings.sql`.
Route/page fixtures do not certify migration execution; isolated SQL qualification

## Handled Assistant operational failures

Mobile Mira reports active handled failures through an injectable typed boundary.
The phases distinguish server conversation creation (`assistantCreate`), local
conversation-pointer persistence (`assistantPreferencePersist`), and reply
transport or protocol failure (`assistantReply`). A protocol error contains no
trusted persistence classification, so its text never determines a save-failure
code or a customer root-cause claim. Successful durable completion is not an
incident. Superseded operations, stopped streams, workspace ABA and session
invalidation are excluded.

By default, the production flavor sends a nonfatal Crashlytics event containing
fixed phase/failure codes, valid HTTP status when available, a Retry-After bucket,
and bounded numeric app version/build. It sends no original exception, captured
stack, chat content, personality, memory, email, token, URL or request body.
The SDK receives a fixed synthetic frame and event-local information, rather than
persistent custom keys. No correlation ID is included because these call sites
have no independently trusted opaque request ID. Global fatal hooks remain a
separate path and retain their existing stack behavior.

Repeated signatures are suppressed for five minutes with a 128-entry cache that
prunes expired entries and evicts the oldest at capacity. This is best-effort
bounded reporting, not a per-occurrence alert, event queue or autonomous repair
bridge. Sink failures never delay chat state or retries. Development collection
stays disabled. Provider retention/consent and authenticated device ingestion
must be verified separately before release; this client path adds no private
feedback storage or staff access.

Regression coverage includes `assistant_chat_operational_reporting_test.dart`,
`assistant_chat_transport_terminal_test.dart` and
`operational_error_reporter_test.dart`. These exercise actual native NDJSON and
legacy SSE adapters, separate creation/local persistence/transport failures,
privacy, cancellation and sink isolation. They do not prove a customer incident's
cause or native Crashlytics delivery.


## Assistant conversation persistence

Mobile Assistant uses an explicitly acknowledged native Chat creation response.
Offline placeholders remain available to ordinary Chat consumers, but cannot
become an Assistant conversation identity. Attachment preparation and a queued
send share one creation acknowledgment for the same actor, workspace and fallback
generation. The repository retains one instance-local result for that current
generation. An uncertain failed result retains the existing creation hold. Upload and send use
the same validated durable conversation ID. Cancellation settles the send without
dropping a still-current attachment creation.

Workspace loading, actor lifecycle through workspace loading or closure, and a
confirmed explicit reset invalidate this generation monotonically. A raw actor
getter changing away and back without any lifecycle signal is not observable;
callers must use these lifecycle boundaries. A stale acknowledged result cannot
qualify a later generation. Opening a different conversation also invalidates
pending creation before changing selection. Creation publication and ordinary
selection writes share one actor/workspace preference lock. An already-admitted
old write drains before the current selection is durably written; stale callbacks
cannot change the newly selected history or start an old attachment upload. The native creation API validates
its committed receipt before returning it. A later realtime publication failure
does not change that known receipt into a failed creation response.

Bare conversation UUIDs select native Chat storage. `ai-chat-` and `legacy-ai-`
prefixes select existing AI storage. Native permission or availability failures
never switch stores. Restore failures preserve the selected conversation and
its history. Only an authoritative missing response for an explicitly selected
legacy conversation may remove that selection. Ambiguous historical bare UUIDs
remain selected with an error rather than being silently rewritten.

Native sends read authorized stored AI settings. They do not PATCH persistent
settings merely to send a message. The native message endpoint has no per-turn
model, credit, or thinking override; an unsupported selection produces an error.
`manage_chat` permissions remain required for editing stored settings.

Saved user receipts retain the original client request ID alongside the server
message ID. Restore and retry preserve that original identity. Changed payloads
remain subject to the server's idempotency conflict checks. Attachment ownership
and saved assistant receipts retain the existing stream completion behavior.
The native composer helper waits for `submitAcknowledged`, which distinguishes
acknowledged, denied, unknown, and stale outcomes. Only a matching validated saved
user receipt for the original request can consume the current draft. Starting a
stream or receiving an assistant reply is insufficient. Composer attachments
remain until that acknowledgment and are cleared only if their snapshot is still
current. A later model failure preserves the known saved user and its retry ID.
Identical follow-up text uses a new request identity; explicit retries retain the
original one. Queue discard and stale transport completion settle waiting callers
without a new request or retry timer. A validated saved user acknowledgment
returns independently of observer cleanup. Cleanup remains owned and drained;
a delayed or failing cancellation cannot replace that receipt or settle a newer
request. Selecting another chat retires only the stale request’s still-owned queued
entry before its debounce can send; drafts and attachments remain available, and
a later send requires its own matching USER receipt. Default stop and explicit supersession settle only the queued or active
request they cancel. A canceled attempt retains its draft and attachments; idle
status is never an acknowledgment. Pre-stream failures, including decoder errors,
settle the owning request without bypassing uncertainty holds.

For an unresolved native request, ordinary repeated Send reads the original saved
USER receipt through the authorized messages endpoint; it does not issue another
POST or allocate a new request identity. The pending turn retains immutable text,
attachments and actor/workspace/chat identity for the current Assistant session,
including selection retirement during settings preparation. Known pre-dispatch
preparation failures release that tentative hold.
Changed draft or attachments remain held until that original turn is resolved.
Missing, denied or malformed readback remains unknown; no timer retries generation.
A stale actor/selection generation cannot consume the current draft. A validated
original USER receipt resolves persistence even if the model failed afterward;
it does not claim an assistant response succeeded. Once acknowledged, an equal-text
follow-up is a new turn. Explicit model Retry keeps its existing request identity.

The active creation and native message API boundaries validate PostgreSQL receipt
timestamps and return UTC ISO text before strict mobile decoding. SQL space
separators, microseconds and numeric offsets normalize without dropping fractional
precision; invalid calendars, offsets or fractions fail closed after persistence.
This response adaptation does not change global SQL serializers or prove migration
execution. Regression fixtures cover SQL-shaped creation with and without an initial
tuple, native JSON/NDJSON/history receipts, invalid dates and retained-draft identity
in `assistant_native_identity_v108_test.dart` and the active route tests.

Native stream and JSON receipts validate raw UUIDs, canonical message kinds,
string content, explicit ISO timestamps and metadata before generic model
coercion. User receipts also require the original request UUID. Malformed batch
rows reject the batch instead of disappearing during filtering. Ordinary Chat
parsing retains its existing compatibility behavior.

Assistant snapshots capture the injected actor, workspace, conversation, locale,
lifecycle epoch and cache revision before awaiting storage. Reads check that origin
before and after storage/network work; writes pass its revision and scope fence to
the existing cache store. A changed scope or revision cancels an obsolete snapshot
without moving it to another actor or retrying it. Completion snapshots are immutable,
tracked and serialized per key; identical protocol/transport completion requests
share one publication. A completed failed or cancelled result is evicted so a later
explicit request can publish the same snapshot after recovery; this schedules no
automatic retry. Pending requests and published results still coalesce.
Same-scope supersession skips work before admission;
an admitted authorized write and its rollback finish before the successor. Local
queue order cannot revoke rollback authority. If the successor fails, the last
authorized snapshot survives. Close invalidates their leases and drains owned work.

Cache cancellation does not undo a validated USER receipt. Genuine storage failures
retain the prior authorized snapshot and produce safe diagnostics; valid network
history remains usable. Explicit restore observes all thrown failures and retains
selected history on failure. Real disposable encrypted-store controls cover held
publication, latest reopen, storage faults, scope departure, clear, held reads and
close drain. Synthetic transport in those tests does not prove live authentication,
provider behavior or a device session.

Provider-free contract fixtures exercise creation, two sends, reopening after
each send, and retry after reopening. They also cover malformed IDs, workspace
mismatches, pending creation rows, denied or unavailable restore, and interrupted
creation. These checks prove source contracts with synthetic dependencies; they
do not prove provider calls or an authenticated device session.

Mobile Assistant stores the selected chat, workspace context, and creation hold
in one private versioned actor/workspace envelope. Every owning reader and writer
uses the same scope lock and reloads the host value. Legacy selected/context keys
are read-only fallback only when the envelope is absent; a legacy clear marker
never grants creation. Malformed or unsupported records require inspection and
cannot be overwritten or replaced by legacy fallback. The envelope contains IDs,
status, revisions, and reset evidence, with no prompts, attachments, or credentials.

Native reset prepares a pure, current shell capability before making any effect.
An acknowledged pending intent first retains the selected/context beforeimage and
holds creation. Only its known current receipt permits a second whole-tuple write
that selects no chat, selects personal context, advances the generation, and binds
informed consent to that operation and prior hold. Pending intent on restart stays
held and retains the beforeimage; it is never finalized automatically. A known
current final receipt publishes the prepared shell/chat reset synchronously.
Loading a workspace reads its stored context without writing it back, preserving
pending reset beforeimages and known process consent. Other model and credit
normalization remains separate from this context read.
Postcommit notifications are observed and cannot veto a known commit.

`resetConversationAcknowledged` reports `deniedBeforeEffect`, `committedCurrent`,
`committedStale`, or `uncertain`. The compatibility `Future<bool>` is true only for
`committedCurrent`. False, thrown, or stale host writes can have physical effects;
callers must retain drafts/history and show honest uncertainty rather than promise
that persistence stayed unchanged. An absent prepared adapter denies before effect.
The former effectful guarded callback cannot qualify this protocol. The owning
page now prepares the pure shell capability and consumes the typed outcome.
An uncertain or absent creation envelope offers localized Cancel, Check history,
and Start a new chat choices. Consent is an opaque, one-use process capability
bound to the observed actor, workspace, selection, context, and hold beforeimage;
a changed hold or an observed departure cannot reuse it. Cancel, denial, stale
completion, and uncertainty retain the current draft and attachments. Only a
current committed reset clears its still-owned draft. History stays open until
that reset completes; Live cleanup failures remain explicit after a known reset.
These defaults apply to remote Assistant Chat; local conversations retain their
separate reset flow. Regression coverage is in `assistant_new_chat_reset_test.dart`,
`assistant_new_chat_confirmation_test.dart`, and
`assistant_reset_consent_target_test.dart`; device/provider behavior remains a
separate delivery gate.

A known selected chat denies new creation before any hold write or POST; its clear
status remains truthful and its history remains usable. Empty selection is required
independently of clear status or informed consent.
Only a current-process final receipt authorizes one next creation. Restart,
lifecycle departure, or another selected/context write revokes that grant. Close
entry fences reset immediately, before waiting for stream cancellation. Creation
rechecks its captured origin after host acknowledgement and immediately before
transport admission. Beginning
creation consumes it and writes the next unknown attempt before HTTP. A validated
server acknowledgment writes the durable selected ID and clear status together;
only the exact verified pre-effect coded validation denial may release a failed
attempt. Timeouts, transport errors, server failures, and uncoded rate limits hold
creation with no automatic retry or replacement UUID. Known-history follow-up
remains available. This is one-key logical tuple atomicity with a process scope lock,
not multiprocess CAS or a physical disk guarantee. If intent storage is unavailable,
no durable hold can be promised and no other reset/create effect proceeds.

### First remote Assistant message

For an empty remote Assistant chat with captured initial settings and no
attachments, mobile sends its fallback conversation UUID and the original user
request key directly to the native message stream. The server validates the
actor, workspace membership and selected model/credit source, then creates the
conversation and deduplicated user message in one database transaction. Creation
replays must match the original actor, workspace, AI type and initial settings.
Later settings edits do not change that immutable creation snapshot. Deletion
retains a minimal identity tombstone until account/workspace erasure so an old
request cannot recreate a deleted conversation.

The `x-mira-chat-creation` response header contains a bounded, encoded creation
receipt. Mobile validates its identity/settings and durably selects the chat
