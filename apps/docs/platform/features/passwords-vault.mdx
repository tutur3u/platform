title: "Managed Passwords Vault"
description: "Password vault security boundaries, access policy and delivery gates."

Passwords is a workspace-scoped managed secrets store at
`passwords.tuturuuu.com`. It reuses the mobile deployment vault envelope format.
The service can decrypt secrets. It is not an end-to-end or zero-knowledge store.
This page describes the implementation contract; activation requires the migration
approval, independent security review and operator acceptance below.

## Encryption and trust

Each vault version has a random 256-bit data key. AES-256-GCM encrypts secret
bytes with a fresh 96-bit nonce and a 128-bit authentication tag. The existing
workspace-key wrapper encrypts that key under `ENCRYPTION_MASTER_KEY`. New
Passwords ciphertext authenticates the workspace, vault, key version and item
identity as associated data. Mobile ciphertext retains its existing format.

Only wrapped keys and ciphertext enter the private database and private object
storage. Non-secret labels, actor identifiers, timestamps, versions, byte counts,
roles and operation identifiers are metadata. Never put a secret value in a label.
Passwords does not retain plaintext suffixes or secret-content hashes. It does
not use or extend the old `workspace_secrets` table.

The Worker, its master-key configuration, Supabase service-role credentials and
operators with those credentials are trusted. Compromise of the master key and
ciphertext compromises the vault. Reusing the mobile master-key mechanism also
shares that key's trust boundary; deployment approval must account for both apps.
Compromised browsers, authorized recipient devices, screenshots, OS clipboard
history and secrets already copied by a former member are outside encryption's
protection. TLS protects transport; authorized reads contain plaintext in the
trusted server and receiving process memory. Do not capture read/write bodies.

## Access and step-up

A human actor comes from a cryptographically verified Passwords satellite app
session. Workspace membership and active account state are rechecked at the
service boundary. A vault membership grants one of three roles:

| Role | Operations |
| --- | --- |
| Owner | Read and write items, change sharing, rotate keys and grant machine access. |
| Editor | Read and write items. |
| Viewer | Read items. |

A recent provider-verified MFA proof is required before revealing or downloading
a secret and before issuing machine grants or changing sharing. A token issue
or refresh timestamp is not step-up evidence. Missing or stale proof fails
closed. Browser mutations require same-origin/CSRF protection. Responses that
contain secrets use `Cache-Control: no-store` and never enter loader caches,
analytics, error telemetry, request logs, URLs or persistent browser storage.

Revealed values expire from the UI. Copy attempts to clear the clipboard after
its timeout only when the clipboard still holds the copied value. Clipboard
clearing is best effort: browser permissions, tab closure, system clipboard
history and another clipboard writer can prevent it. Users must still treat
copied secrets as exposed to the recipient device.

## Machine identities

CI exchanges a GitHub-signed OIDC assertion pinned to issuer, the
`tuturuuu-passwords` audience, repository, environment, workflow, ref and supported
event. The existing `tuturuuu-mobile-deployment` audience and mobile release
workflow remain unchanged. A human owner explicitly grants a machine access to
one vault, an allowed item set and read/write scopes. A grant cannot exceed its
issuer's current authority. Tokens expire quickly, are stored only as unkeyed
SHA-256 digests of random 256-bit bearer credentials and are invalidated when the grant or membership is revoked.

CLI inputs and outputs are files. `put --from-file` never accepts a secret value
on argv or through an environment variable. `get --to-file` creates a regular
owner-only file, refuses overwrite unless `--force`, and never prints the value.
Credential storage uses mode 0600 and secure file handling. The CLI does not need
a vault decryption key under this server-managed design. Status and error output
contain operation metadata only. An uncertain mutation retains its operation
identifier and is reconciled before retry; automatic retries must not invent a
new operation identity.

## Audit and lifecycle

Secret reads, reveals and writes must persist an append-only, metadata-only event
before returning success or bytes. The database commits an operation receipt,
state change and audit event atomically. Audit failure fails the operation. Events
contain fixed event types, actor and resource IDs, time and bounded counters;
client-provided error messages, filenames and arbitrary metadata are excluded.

Every new database table enables RLS. Anonymous and authenticated database roles
have no direct access. The service uses tightly granted atomic operations;
definer functions have a fixed search path and are granted only where required.
The encrypted-file bucket has no client download, upload or listing policy.
Object names are derived from server-validated identifiers, never filenames.

Removing a member invalidates outstanding machine authority. Rotation creates a
new data key and replaces ciphertext for the remaining items with a concurrency
guard; partial work must not activate a mixed version. Rotation and member
removal cannot revoke plaintext a recipient previously saved. Master-key rotation
requires an explicit rewrap procedure and retention of the old key until every
retained data-key envelope is accounted for; replacing the environment variable
alone makes older versions unreadable.

## Account and workspace erasure

Account deletion remains available to vault members, creators and machine-grant
issuers. Lifecycle triggers only append a durable metadata job; they do not lock vault
rows or append vault audit events. Vault operations fail closed while relevant work
is pending, including after the five-attempt retry limit. A separate bounded
service-only retry revokes membership and issued machine authority, advances the
authorization epoch, requires rotation and clears live identity references. Live identity references become null; audit rows keep their original
opaque actor IDs and are never rewritten. Surviving owners must rotate before
revealing another item. If the deleted account was the last owner, the vault
stays frozen; there is no automatic transfer or privileged reveal/recovery path.
Ordinary sharing still cannot remove the last owner.

Soft-deleting a workspace denies vault access while preserving its normal restore
path. Hard deletion, including orphan-workspace cleanup after account deletion,
revokes all vault members and machine authority, retires the vault and sets its
live workspace link to null. An immutable original workspace ID remains as the
internal FK/encryption context. It does not authorize access or reattach a vault
to a newly created workspace. Encrypted payloads and key versions are retained
behind this retirement fence; deletion of a workspace or account cannot erase
append-only audit history.

The real-secret activation gate remains closed until the separate history
retention follow-up is merged and accepted. That change replaces retained request
inputs with SHA-256 intent digests and implements bounded tombstone/superseded-key
purging. Until then, no real-secret escrow, including PKTM, is activated.

## Operational bounds

No scheduler or autonomous retry loop is added. The private lifecycle outbox is
drained through the explicitly invoked service-only retry RPC described below. Each operation has bounded
input sizes, page sizes and database/storage calls. Remote object failures cannot
trigger unbounded retries. A durable administrative stop must prevent new reads,
writes and token exchanges before further billable work. Activation acceptance
covers the stop, restart, retry and operation-count behavior; rate limits and
billing alerts alone are not spend caps.

## Verification and approval

The shared crypto tests cross-decrypt the legacy mobile scalar representation,
retain the mobile file envelope and reject wrong keys, changed authenticated
context and malformed ciphertext. Mobile store, OIDC, storage reservation and
hydrate regressions exercise their existing import paths. The existing mobile
audit is best effort and some mobile metadata includes plaintext suffixes/hashes;
those behaviors are retained for compatibility and are not Passwords guarantees.

Passwords migration tests must exercise the full isolated migration chain, role
permission denials, owner/editor/viewer isolation, replay/CAS handling, append-only
audit, revocation and file-storage boundaries. API tests must reject forged or
stale step-up, wrong workspace, unscoped tokens and altered OIDC claims. The final
CLI round-trip uses synthetic file bytes and verifies the destination mode and
ciphertext persistence without logging the value. The operator, not this lane,
handles the first real PKTM backup GPG escrow.

Run `tests/password-vault-operations.sql` through `bun sb:validate:isolated` in
`apps/database` on the admitted remote host. Before that disposable database is
stopped, run `node apps/database/scripts/test-password-vault-concurrency.mjs
<owned-database-container>`. The contention check observes an actual PostgreSQL
lock wait before releasing the holder, then requires a stale-write or revoked-read
denial. It also requires an unrelated FK-referencing insert to finish while the
vault transaction remains open. It creates synthetic fixtures only in an owned disposable `tt` project;
it is not a command for a shared or production database.

Before merge, the user must approve the migration summary and the parent must
obtain an independent security review from a different model family. Before
activation, the operator verifies the exact built commit, bindings, domain,
stop switch, rollback and a bounded read/write canary. No existing release or
migration guard is bypassed by a green unit suite.

Machine metadata listing is limited to the grant's item IDs. It returns labels,
revisions and key-version metadata, without ciphertext, keys, file paths or other
vaults. Receipt lookup derives the item scope from the authenticated original
request and repeats current token, grant, role and epoch checks. An explicitly
supplied mismatching item ID is refused. The grant issuer must remain an owner,
and only that issuer can issue another short-lived token from the grant.

## Lifecycle recovery and cleanup SLA

The operational cleanup SLA is five minutes after a committed account/workspace
or membership erasure when the admitted service/operator pump invokes
`private.password_vault_retry_lifecycle(25)` at least once per minute and drains
its bounded backlog. One invocation locks at most 25 jobs with `SKIP LOCKED` and
handles at most 25 vaults per job. Vault row contention fails immediately with
`NOWAIT`; a failed batch rolls back its vault changes and audit together, records
only SQLSTATE, and becomes eligible again after 30 seconds. Five failures stop
that job. Pending and terminal jobs continue to deny operations; there is no
permission transfer, stale-token revival or automatic terminal retry.

No scheduler/pump is shipped by this SQL-only PR. If the retry RPC never runs,
cleanup has no finite completion guarantee and operations stay denied indefinitely.
The deployment owner must provide the once-per-minute caller and alert on any
terminal job or `oldestPendingAt` older than five minutes before activation.
The existing real-secret retention/purge hold remains closed independently.
This SLA covers authority revocation, retirement and clearing live identity links;
retained ciphertext, versions, opaque job/audit IDs and receipts are not purged.

Invoke the following in a separate service-role transaction, outside a user request:

```sql
select private.password_vault_retry_lifecycle(25);
```

It returns processed, failed, remaining and terminal counts plus oldest pending
time. Successful jobs have `completed_at`; replay performs no additional writes.
Concurrent callers skip each other's locked jobs. If a batch fails, every vault
mutation and its audit event roll back together, so retry cannot duplicate an
already committed epoch transition. Inspect only `last_error_code` and the job's
opaque IDs. After fixing the cause, an authorized database operator can reset an
exact reviewed terminal job and invoke the bounded RPC again:

```sql
update private.password_vault_lifecycle_jobs
set attempts = 0, next_attempt_at = clock_timestamp()
where id = '<reviewed-job-uuid>'::uuid and completed_at is null and attempts = 5;
```

Auth/workspace foreign keys are intentionally absent from the vault's live UUID
references: automatic FK actions could block erasure even if trigger errors were
caught. Every supported vault operation still validates live workspace membership,
account state and archive state. Capture handles ordinary SQL exceptions without
raising an error into the parent write and logs SQLSTATE only. If capture storage
itself fails, retained UUIDs and live-source mismatches deny access; each retry
also reconstructs at most 25 missing jobs from those retained references. Repair
capture infrastructure promptly: a missing membership event followed by a restore
before reconciliation cannot be reconstructed from current state alone. Such an
infrastructure incident requires the vault stop fence and an operator authority
reconciliation before restoring vault traffic.

Regression evidence: `password-vault-lifecycle.sql` injects both outbox and vault
audit failures and covers signup/update/deletion, no-vault identities, terminal
failure, failed-closed access, recovery and idempotency. The original operations,
machine and 30-assertion erasure fixtures retain their assertions and explicitly
drain asynchronous work at the lifecycle boundary. The concurrency script retains
its four original scenarios and adds simultaneous retry, idempotent replay and
account deletion while a vault row remains locked.

## Pre-activation rollback

`private` is a shared platform schema. **Never run `DROP SCHEMA private CASCADE`
on a shared database.** The exact scoped rollback is
`apps/database/supabase/fixtures/password-vault-rollback.sql`: stop vault traffic,
verify the real-secret hold is still closed, then obtain the normal migration/data
approval before executing it. It refuses any existing vault, audit or bucket object
instead of destroying history. With data present, retain the schema and use a
forward fix; dropping it is not a safe production recovery.

The script drops the five triggers on `auth.users`, `public.workspaces`,
`public.workspace_members`, `public.workspace_users` and
`public.workspace_user_linked_users` first. Then it removes the ten vault tables and only `private.password_vault_*`
functions, preserving the shared schema. It intentionally keeps the empty private
bucket and both restrictive Storage policies. With an approved, project-bound
service-role Storage client, perform the second step:

```ts
const { error } = await supabase.storage.deleteBucket('password-vault-files');
if (error) throw error;
```

Use the Storage API, because provider protection rejects direct SQL deletion from
`storage.buckets`. Finally execute
`apps/database/supabase/fixtures/password-vault-storage-rollback.sql`; it refuses
to remove either fence while the bucket still exists. If the API step fails,
retain the private bucket and both fences, resolve the error, then resume that
same bounded cleanup. The third script removes the two specifically named
policies with 5-second lock and 30-second statement timeouts. The vault tables' own triggers/indexes
and the three service-role function grants disappear with those objects. There
are no vault functions in another schema and no added public/auth columns. Keep
existing schema-wide `USAGE ON SCHEMA private TO service_role`: it is shared with
other products and cannot safely be revoked as a vault rollback. A whole-schema
drop is appropriate only when discarding an entirely owned disposable database,
never as this feature's rollback on the shared platform.
