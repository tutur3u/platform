An Upskii account link lets Tuturuuu read a signed-in user's own Upskii
classes, lessons and assessments, so Meet can present them. It reuses the
[external-app flow](/platform/architecture/app-coordination#external-app-flow)
(registered app, app secret, PKCE-bound handoff and token exchange). Neither
side stores the other side's user tokens.

## Decision

| Item | Rule |
| --- | --- |
| Scope | One Tuturuuu account links to at most one Upskii account, and the reverse. A link is per person, not per workspace. |
| Default | Unlinked. Nothing is shared until the user connects from Upskii and confirms the Tuturuuu account. |
| Who can link | Verified `@tuturuuu.com` staff (confirmed exact-domain email, no QA identity, the configured Azure directory) unless the catalog lists Upskii as explicitly `available`. Any other status, or a missing catalog entry, keeps linking staff-only. Any lookup failure denies. |
| Data shared | Read-only: the user's Upskii classes, lessons and assessments, as scopes `upskii:classes:read`, `upskii:lessons:read` and `upskii:assessments:read`. Upskii receives only the Tuturuuu account id and email for its link row. |
| Surfaces | Upskii settings (connect, status, disconnect). The Tuturuuu sign-in confirmation. Tuturuuu settings → Account → Integrations on apps/web and every satellite (status, disconnect, connect hands off to Upskii). The catalog card. Meet reads content server-side. |
| Revocation | Either side can disconnect at any time. Data flows only while both sides hold an active link. |
| Exceptions | Workspace-level sharing and write access are out of scope. Platform admins cannot create or read another user's link. |

## Link ceremony

Upskii starts every link, because Upskii owns the data being shared and shows
the consent. The Tuturuuu **Connect** button opens Upskii settings.

1. In Upskii settings, the signed-in Upskii user `U` chooses **Connect
   Tuturuuu account**, which submits a CSRF-protected `POST`. Upskii shows the
   three read scopes. Its server then sets a `__Host-` cookie (`HttpOnly`,
   `Secure`, `SameSite=Lax`, `Path=/`, 10 minutes) holding
   `{ state, U, sessionId, code_verifier }`, sealed with an Upskii server key
   (AEAD). It redirects to the Tuturuuu login with its registered callback as
   `returnUrl` (carrying `state`), plus `code_challenge` and
   `code_challenge_method=S256`.
2. Tuturuuu shows a confirmation before it issues any handoff for an app whose
   grant is a link-only scope: the signed-in account, the app, what the link
   shares, **Continue as**, and **Use another account**. Such an app never
   auto-continues, even with strict PKCE. A user who is not signed in signs in
   first, which is the same explicit choice.
3. The Upskii callback answers with `Referrer-Policy: no-referrer`, keeps the
   token URL out of logs and analytics, and redirects as soon as it finishes.
   It opens the sealed cookie and refuses the link when the cookie is missing,
   expired or tampered, when `state` does not match (constant-time compare), or
   when the current Upskii session is not `U` and `sessionId`
   (`LINK_SESSION_MISMATCH`). It then calls `POST /api/v1/auth/app-token/exchange`
   with the `upskii` app id and secret, the token, `codeVerifier`, and
   `requestedScopes: ["upskii-link:write"]`.
4. An exchange that issues a link-only scope returns a bearer that carries only
   link scopes, lives at most 120 seconds, and comes with no refresh token.
   With it, Upskii calls `POST /api/v1/integrations/upskii/link` with
   `{ upskiiUserId, upskiiEmail, scopes }`. Tuturuuu checks that the bearer
   belongs to the enabled `upskii` app, carries `upskii-link:write` and
   postdates the app's current secret. It applies the staff gate and stores
   the link for the bearer's user, never a user named in the body. Each bearer
   links once: its `jti` is recorded on the row (`link_jti`, unique), and a
   later request with the same bearer gets `401 LINK_BEARER_USED`.
5. Upskii stores its own row `{ U, tuturuuuUserId, linkId, scopes, linkedAt }`
   and discards the bearer.

No other route accepts the link bearer: it lacks every first-party session
scope, every profile scope and every external-project scope, and only the
link route names `upskii-link:write`.

Registry settings for the `upskii` app: `requirePkce=true` (only after
migration `20261101090000` is confirmed applied in production),
`callbackPaths: ["/api/upskii/integrations/tuturuuu/callback"]` and
`allowedScopes: ["upskii-link:write"]`.

The handoff confirmation is enforced by the login page, not by a
server-side nonce. A server nonce would add a second store and round trip,
while PKCE and Upskii's sealed state already bind the handoff to the browser
that started it.

## Mismatch and conflict handling

| Case | Result |
| --- | --- |
| The callback arrives in a browser whose Upskii session differs from the one that started the link | Upskii refuses with `LINK_SESSION_MISMATCH` before calling the exchange. Nothing is stored. |
| A link started by someone else is opened in the victim's browser | The victim's browser has no sealed cookie for that `state`, so Upskii refuses. Tuturuuu never auto-continues, so the victim sees which account would be linked. |
| The Tuturuuu account already has an active link to a different Upskii account | `409 LINK_CONFLICT` with `side: "tuturuuu"`. |
| The Upskii account already has an active link to a different Tuturuuu account | `409 LINK_CONFLICT` with `side: "upskii"`. |
| The same pair links again | Idempotent: returns the existing `linkId` and refreshes its scopes. |
| The Tuturuuu and Upskii emails differ | Allowed. Both settings rows show the other side's email. |
| A user who fails the staff gate | `403 EARLY_ACCESS_ONLY`. |

## Storage

Tuturuuu stores `private.external_account_links`
(migration `20261124020000_external_account_links.sql`), one row per link:
`id`, `user_id` (references `auth.users` with `on delete cascade`), `provider`
(`upskii` only), `external_subject` (the Upskii user id), `external_email`,
`scopes` (read scopes only), `linked_at`, `revoked_at`, `revoked_by` (`user`,
`provider` or `admin`). Partial unique indexes on `(user_id, provider)` and
`(provider, external_subject)` apply only while `revoked_at` is null. RLS is
on with no policies; `anon` and `authenticated` have no access, and
`service_role` has `select`, `insert` and `update` only, so history cannot be
deleted through the API. Revoking a link clears `external_email`; the revoked
row keeps ids and times as the history.

Upskii stores the matching row in its own database. Neither row holds a token.

## Routes

| Route | Caller and auth | Purpose |
| --- | --- | --- |
| `POST /api/v1/integrations/upskii/link` | Upskii server, link-only bearer | Create or refresh the link. |
| `GET /api/v1/integrations/upskii/link` | The user: web session or a first-party satellite app session | `{ canLink, link }`. `link` includes the linked Upskii email. |
| `DELETE /api/v1/integrations/upskii/link` | The user: web session or a first-party satellite app session | Disconnect. |
| `POST /api/v1/integrations/upskii/unlink` | Upskii server, `Authorization: Basic base64(upskii:<app secret>)` | Disconnect from Upskii. |
| `POST /api/v1/integrations/upskii/introspect` | Upskii server, same Basic credentials | Check a read token. |
| `POST /api/v1/integrations/upskii/link-status` | Upskii server, same Basic credentials | `{ active }` for `{ linkId, upskiiUserId }`, so Upskii's settings stop showing a link disconnected on Tuturuuu. |

The app secret is read only from the `Authorization` header, never from a
body. Each route admits requests per client IP and per app and secret digest
before the credential check. It paces failed secrets per app and IP, logs
every refused credential with `console.warn`, and counts verified calls per
app (and per user for link writes). Over a limit it answers `429` with
`Retry-After`.

## Disconnect

- **From Tuturuuu:** `DELETE /api/v1/integrations/upskii/link` sets
  `revoked_by = 'user'`. Reads stop at once, because Tuturuuu mints read
  tokens only for an active link and introspection answers `active: false`.
- **From Upskii:** Upskii deletes its row, then calls the unlink route with
  `{ linkId, upskiiUserId }`. Tuturuuu sets `revoked_by = 'provider'`. If that
  call fails, reads still stop, because Upskii refuses a link it no longer
  holds; Upskii retries the call.
- **Upskii learns of a Tuturuuu disconnect** when introspection of a validly
  signed token answers `active: false` with `revoked: { linkId, upskiiUserId }`,
  or the unlink route answers `LINK_NOT_FOUND`. It then deletes exactly that
  row. An invalid token never names a link, so it cannot delete anyone's row.
- **Account deletion:** deleting the Tuturuuu account deletes its links.
  Deleting an Upskii account calls the unlink route first.
- **Secret rotation or disabling the app** stops every read at once. Links
  stay stored and resume when the app works again.

## Secret rotation runbook

The Upskii app secret lives only in Upskii's server environment, never in a
`NEXT_PUBLIC_` or other client-exposed variable.

1. Rotate the secret in **Infrastructure → External apps** (root admin). This
   also signs out every Upskii session that used Tuturuuu sign-in.
2. Put the new secret in Upskii's server secret store and deploy. Until then,
   unlink and introspect answer `401`, so Meet cannot read Upskii content.
   Links themselves are unaffected.
3. Confirm with one introspect call from Upskii's server, then a Meet read.

## Read API contract (for Meet)

Meet calls one server-only route with the user's session:

`GET /api/v1/integrations/upskii/content?kind=classes|lessons|assessments&classId=<id>`

- The link comes from the session user alone. The route takes no `userId` or
  `linkId`, and clients never receive a read token or an Upskii credential.
- `classId` is required for `lessons` and `assessments`. Upskii authorises it
  against the introspected `upskiiUserId` and refuses a class the user cannot
  see.
- Tuturuuu mints the read token server-side through
  `mintUpskiiReadTokenForUser`, which re-checks the staff gate. It answers
  `404 NOT_LINKED`, `403 EARLY_ACCESS_ONLY` or `403 SCOPE_NOT_GRANTED`.
- The Upskii base URL is pinned in server configuration, never taken from the
  request, so the route cannot be pointed at another host. Production always
  uses `https://app.upskii.com`; other runtimes may set `UPSKII_API_ORIGIN`.
- Listings cover what the linked user teaches: the classes they own or teach,
  and every lesson (including drafts) and assessment of one of those classes.
  Classes the user only attends as a learner are out of scope.
- Response: `{ items: Array<{ id, title, updatedAt, url, kind, classId? }> }`,
  at most 100 items with titles cut to 300 characters; there is no paging yet.
  Each `url` must be on Upskii's exact origin with no credentials; anything
  else (including `javascript:` and other hosts) is dropped. Bodies and
  answers are never included. Upskii failures answer `404 NOT_LINKED`
  (Upskii confirmed the link is inactive), `403 SCOPE_NOT_GRANTED` (including an
  educator who is no longer eligible), `404 CLASS_NOT_FOUND` or
  `502 UPSKII_UNAVAILABLE`. Anything Upskii could not answer or confirm (a
  timeout, `429`, `5xx` or a check Upskii could not make of this token) is
  `UPSKII_UNAVAILABLE`, never `NOT_LINKED`, so an outage is not shown as an
  unlinked account.
- In a Meet room only the presenter's session fetches. Other participants see
  only what the presenter shares.

The read token is a purpose-bound `external_link_read` token, not an
app-coordination bearer: `target_app: "upskii"`, `sub` set to the Tuturuuu
user, one read scope, `external-link:<linkId>`, and for `lessons` and
`assessments` one `upskii-class:<classId>` scope naming the class it was minted
for. It expires 60 seconds after issue, with no clock-skew allowance. Introspection
returns that `classId`, and Upskii opens only that class with the token. The
token's `jti` is not consumed: with the 60-second life and the class binding, a
captured token can only re-read one class's metadata inside that minute. Consuming
it needs a shared store on the Upskii side and is a follow-up. Tuturuuu sends it to Upskii's
`GET /api/integrations/tuturuuu/v1/<kind>`. Upskii checks it with the
introspect route, which answers
`{ active, tuturuuuUserId, upskiiUserId, linkId, scopes, classId? }`. The answer is
active only when the token is valid and unexpired, carries exactly one link
id, at most one class and only read scopes, and names an active link owned by its user that
still grants those scopes. Upskii serves the request only when its own row for
that `linkId` and user is still active.

## Audit

Link, relink, disconnect and refused attempts are logged with `console.info`
or `console.warn` and the fields `{ event, provider, userId, linkId, side,
reason }`, with no emails or tokens. Revoked rows keep the history.
