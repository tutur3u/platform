Every app opens account and app settings in one fullscreen settings dialog. Its
open state and active tab live in the URL, so links can be shared, the page can
be refreshed, and browser Back works.

## URL contract

Scope: apps/web and every satellite that renders a settings dialog (the shared
satellite user menu, plus the dedicated Calendar and Tasks hosts).

| URL | Result |
| --- | --- |
| `?settingsTab=<tab>` | Opens the dialog on `<tab>`. |
| `?settingsDialog=open` | Opens the dialog on the app's default tab. |
| `?settingsDialog=open&settingsTab=<tab>` | Opens the dialog on `<tab>`. This is the canonical form every writer emits. |
| Neither param | Closed. |

- A bare `settingsTab` is enough to open the dialog. Before 2026-10-23, the
  dialog opened only when `settingsDialog=open` was also present, so links such
  as `/personal?settingsTab=security` silently stayed closed.
- Tab ids are lowercase `[a-z0-9_-]`, at most 64 characters. Malformed values
  are ignored.
- An unknown or unavailable tab falls back to the app's first enabled tab. The
  URL is not rewritten, so a tab that registers later (for example after a
  permission check resolves) still opens.
- Host-specific params travel with the dialog and are cleared with it:
  `settingsBoardId` (Tasks/web board settings) and `settingsLinkedProvider`
  (web identity-link callback).
- When the signed-in web root (`/` or `/<locale>`) redirects to the default
  workspace, settings params are carried over. Other root query params are still
  dropped, as before.

## History

- Opening a closed dialog pushes a history entry, so Back closes it and Forward
  reopens it.
- Switching tabs and closing replace the current entry, so tab browsing does not
  fill the history stack.
- All updates are shallow (no server round-trip) and keep the scroll position.
- apps/web shows the dialog optimistically on an open intent, before the URL
  updates. That optimistic state is dropped as soon as the URL acknowledges the
  open, even if the lazy dialog bundle is still loading. Back always closes the
  dialog.

## Identity-link callback

`settingsLinkedProvider` is set on the return URL whether the provider flow
succeeded, failed or was cancelled. apps/web shows the "linked" success message
only after a fresh identities read contains that provider. Otherwise it shows a
neutral "couldn't confirm" message.

## Tabs every app has

Scope: every satellite that renders the shared satellite user menu. Default:
every such app shows one **Account** group with the same tab ids as apps/web,
so `?settingsTab=<tab>` means the same thing in every app.

| Tab id | apps/web | Satellites |
| --- | --- | --- |
| `profile` | Full profile panel | Shared `SatelliteProfileSettingsPanel`: avatar upload, display name, full name, user id. Email is read-only, with a link to the web profile tab. |
| `accounts` | Account switcher management | Explains the tab and opens the same tab in apps/web. |
| `security` | Password, 2FA, passkeys, linked identities | Explains the tab and opens the same tab in apps/web. |
| `sessions` | Devices and session revocation | Explains the tab and opens the same tab in apps/web. |
| `appearance` | Theme, language, timezone, time format | Theme and language. |

Apps with their own dialog (ai, calendar, cms, contacts, drive, finance, forms,
git, infrastructure, inventory, rewise, tasks, track) add the Account group with
`createAccountSettingsNavGroup` and render `SatelliteAccountSettingsPanel`, next
to their app tabs. Apps without one (chat, learn, lettin, mail, meet, mind,
parley, storefront, teach) get `SatelliteDefaultSettingsDialog`: the Account
group, appearance and the onboarding guide. The satellite user menu has a
**Settings** item (Cmd/Ctrl+,) that opens the same dialog.

App-specific tabs stay pluggable. An app adds its own nav groups and panels, and
`SatelliteAccountSettingsPanel` renders nothing for tabs it does not own.

### Security-sensitive tabs stay in apps/web

Satellites do not reimplement password change, 2FA, passkeys, identity linking
or session revocation, and they do not proxy those mutations. apps/web owns
re-authentication, the WebAuthn relying party and session revocation. The
satellite `accounts`, `security` and `sessions` tabs link to
`<web origin>/personal?settingsDialog=open&settingsTab=<tab>` in a new tab
(`rel="noopener noreferrer"`), which opens the web dialog on the same tab.

Satellites edit only display name, full name and avatar upload, through the
existing web profile endpoints (`/api/v1/users/me/*`) in
`@tuturuuu/internal-api`, using the satellite session and the `/api` proxy
contract.

- **Email is a link-out.** A satellite session's admin client has no provider
  session and cannot change the auth email. Satellites show the email read-only
  and link to `?settingsTab=profile` in apps/web, which owns verification. They
  never call `PATCH /api/v1/users/me/email`.
- **Avatar removal is off in satellites**
  (`SATELLITE_AVATAR_REMOVE_ENABLED`) until the web avatar route fix is merged.
  Users remove avatars in apps/web.

### Exceptions

- apps/web keeps its own dialog with the full tab set.
- nova keeps its own single-page profile dialog. It does not use the satellite
  user menu.
- hive, pay, apps, tools, external, playground and shortener have no user
  settings dialog.
- Personal timezone and notification preferences are only in apps/web.
- Calendar keeps workspace timezone under its own calendar tabs.

## Implementation

`packages/ui/src/hooks/settings-dialog-url.ts` is the single source of truth: the
param names, tab-id sanitizing, parse/serialize, fallback resolution, href
building and history mode. `useSettingsDialogUrlState`
(`packages/ui/src/hooks/use-settings-dialog-url-state.ts`) is the only way a host
reads or writes the dialog URL state. Build links with `buildSettingsDialogHref`
instead of hand-writing query strings.
