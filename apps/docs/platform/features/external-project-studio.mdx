## TL;DR

Tuturuuu CMS now lives in the dedicated `apps/cms` satellite app.

New CMS-backed sites should use the [global CMS site v1 contract](/platform/features/cms-site-contract-v1). Add
site-specific structure through template and collection metadata instead of a
new adapter unless the integration has genuinely different authentication or
runtime behavior.

- `apps/cms` owns the CMS authoring UI, workspace picker, overview/content/preview/members routes, and the root `/{wsId}/projects` linking console (reached as `/internal/projects` for the root workspace).
- `apps/web` remains the only backend/API owner for CMS and external-project traffic.
- `apps/cms` rewrites `/api/*` to `apps/web`, so proxy behavior and bot protection stay centralized.

## Product Vocabulary

The visible CMS experience is a site/content product, not an implementation
console. Bound-workspace UI should say site, site template, connection, content,
section, URL path, custom details, media, publishing, preview, people,
invitations, and team access.

Avoid implementation terms in normal UI copy, including external project,
canonical, adapter, binding, slug, schema, metadata, profile data, payload, and
JSON. If operators need exact implementation values, show them only in collapsed
Developer details panels or internal root-console advanced controls. Keep code,
API routes, database objects, migration names, and integration docs on the
existing `external-project*` contracts.

## Route Model

The route tree below mirrors `apps/cms/src/app/[locale]/(dashboard)/[wsId]`.
Workspace navigation is defined in
`apps/cms/src/app/[locale]/(dashboard)/[wsId]/navigation.tsx`. Every route is
workspace-scoped under `/{wsId}`; the root workspace uses the `internal` slug
(it resolves to `ROOT_WORKSPACE_ID` via `normalizeWorkspaceId`).

### Root workspace

- `/{wsId}/projects` (reached as `/internal/projects`): internal site-template
  registry, workspace-indexed connection list, and connection audit history.
  The internal workspace is not a bindable content workspace, so its overview,
  content, and `/settings` routes redirect into `/{wsId}/projects`.

### Bound workspaces

- `/{wsId}`: overview / continue-editing home.
- `/{wsId}/content`: primary content operations surface (search, status
  filtering, publishing, reusable content).
- `/{wsId}/content/collections/{collectionId}`: collection (section) detail.
- `/{wsId}/content/entries/{entryId}`: entry (content) detail.
- `/{wsId}/pages`: page-builder surface for landing-style sections.
- `/{wsId}/media`: media library.
- `/{wsId}/products`: product catalog content.
- `/{wsId}/storefront`: storefront configuration.
- `/{wsId}/taxonomy`: taxonomy (terms, categories, tags).
- `/{wsId}/games`: game content surface, shown only when CMS Games is enabled
  for the workspace (`getCmsGamesEnabled`).
- `/{wsId}/preview`: site preview.
- `/{wsId}/members`: workspace member search, invite, removal, role assignment,
  and role/default-permission management.
- `/{wsId}/settings`: redirect-only route. It sends the internal workspace to
  `/{wsId}/projects` and every other workspace to `/{wsId}/members`; CMS has no
  standalone settings screen.

## Root Linking Console

- Treat `/{wsId}/projects` (the root workspace's `/internal/projects`) as a workspace-first control room.
- The main left panel is the searchable workspace list.
- Each row shows the current connection state, site type, site template, and most recent change signal.
- The selected workspace panel owns connect and disconnect actions.
- The site-template registry is secondary and stays on the same page for create/edit flows.
- Binding audits stay anchored to the selected workspace instead of living as a detached global feed.

## Workspace CMS

- Use `/{wsId}` as the concise starting point for continue-editing tasks, launch readiness, attention queues, recent activity, and connected-site context.
- Use `/{wsId}/content` for broader content operations: search, status filtering, publishing queues, collection health, and reusable content.
- Use `/{wsId}/pages` for focused landing-style page edits, page readiness, and preview-first section work.
- Use `/{wsId}/media`, `/{wsId}/products`, `/{wsId}/storefront`, and `/{wsId}/taxonomy` for the corresponding media, catalog, storefront, and taxonomy surfaces.
- Use `/{wsId}/games` for game content when CMS Games is enabled for the workspace.
- Use `/{wsId}/members` for routine collaborator management without leaving CMS.
- Keep collection configuration on `/{wsId}/content/collections/{collectionId}` and entry authoring on `/{wsId}/content/entries/{entryId}`.
- Use `/{wsId}/preview` as the delivered-content surface backed by the existing preview delivery route.
- CMS has no standalone settings screen; `/{wsId}/settings` is a redirect-only route to `/{wsId}/members` (or `/{wsId}/projects` on the internal workspace).

## Member Management In CMS

- Workspace member search, invite, remove, and role-assignment controls now have a dedicated `/{wsId}/members` sidebar route.
- The members surface also absorbs the essentials of the workspace roles page so CMS operators can manage named roles and default permissions without leaving CMS.
- This keeps standalone CMS usable without forcing operators back into the main platform app for routine collaborator changes.
- CMS members data must load through external-project-aware `apps/web` API routes and `@tuturuuu/internal-api` helpers. Reads should authorize by CMS workspace access so app-session users do not hit workspace settings-route 403s; writes still respect member and role management permissions.
- Use CMS copy in this area: team access, people, invites, access levels, member defaults, guest defaults, and Advanced access.

## Onboard editors for the first site

Use this runbook after the site-builder permission and publish changes have
passed security review. Keep editor invitations on hold until
the acceptance checks below pass on the deployed revision.

### Verify the permission contract

Verify the reviewed data/API contract before onboarding:

- Confirm `edit_external_projects` exists in the permission enum and generated types.
- Map **editor** to edit and preview; map **publisher** to edit, preview, and
  `publish_external_projects`. Role names are labels; authorize by effective
  permissions, workspace membership, and the enabled site connection.
- Keep `manage_external_projects` for existing administrators. It currently
  implies publish access; do not grant it to editors or add edit access to the
  existing manage helper, which the publish helper also calls.
- Add an edit authorization helper and policies for draft writes and private
  preview. Deny non-members and permission lookup errors. Restrict page versions
  and entries to the connected workspace and site.
- Require publish permission for every public transition, including direct
  status updates, bulk actions, imports, scheduling, and pointer changes.
- Keep preview read-only. The legacy entry publish endpoint accepts
  `eventKind: 'preview'` but writes `status: 'published'`; it cannot serve as
  editor preview.
- Commit the published version and its `workspace_external_project_publish_events`
  record atomically. Include the authenticated actor, workspace, entry, site,
  event kind, and version identity. A failed audit write must leave the public
  version unchanged. The legacy store updates the entry before inserting the
  event and does not provide that guarantee.

The editor route and publish controls must consume the same permission contract
as the API. Hiding a button does not authorize a request. Do not substitute an
unrecognized permission string or a role-name comparison for the generated
permission type and existing external-project access helpers.

### Connect the workspace and configure access levels

1. Have an authorized operator select the workspace for **first site** in the
   internal CMS **Projects** console and enable its site connection.
2. Open that workspace's **Members** page. Create the **editor** and
   **publisher** access levels with the reviewed permissions above.
3. Check member defaults, guest defaults, and every additional role. Remove
   publishing grants from the editor's effective permissions before inviting.
   Keep administrative, member-management, role-management, and billing grants
   out of both content roles unless separately authorized.
4. Record the selected workspace, site, role IDs, reviewed source revision, and
   operator in the private operations record. Keep real IDs and addresses out
   of source control.

### Invite an editor with an access level

1. In **Members**, select **Invite**, enter the approved address, and select
   **editor**. Use an operator authorized to manage members and roles.
2. Submit through the existing CMS invitation flow. It uses
   `inviteWorkspaceExternalProjectMembers(workspaceId, emails, { roleIds })`
   from `@tuturuuu/internal-api` and sends `POST` to
   `/api/v1/workspaces/{wsId}/external-projects/members/invite`.
3. Inspect each result in `results` and confirm `successCount`. A successful
   HTTP response alone does not mean every invitation succeeded. Seat limits,
   invalid roles, and existing invitations can reject individual addresses.
4. For an existing pending invitation, use the access-level editor. It calls
   `updateWorkspaceExternalProjectInvitationRoles` through `PATCH` on the same
   endpoint. Do not create a second invitation to change its role.
5. Have the invitee sign in with Tuturuuu Auth and accept the workspace
   invitation. Confirm membership and the assigned access level after acceptance.
   An invitation alone must not grant editor access.

The existing invitation code validates that selected role IDs belong to the
workspace, checks assignment authority and seat limits, and stores roles through
`create_workspace_email_invitation_with_roles`. Use the external-project member
routes; ordinary workspace settings routes can reject valid CMS app sessions.

### Configure renderer invalidation

Set `CMS_RENDERER_SITES` on the publishing API to a hostname-keyed map with one
verified renderer hostname per site: each value has `id` (the connected site
ID), `workspaceId`, and `defaultLocale`. This trusted configuration matches the
renderer-side `CMS_SITES` mapping. Inject the same `CMS_PURGE_TOKEN` on the API
and renderer at deployment time. Never pass it through PR workflows or clients.

Publication captures the previous version before the atomic publish, then sends
one authenticated `POST /__cms/purge` for its public path, locale, and version.
An absent old version needs no purge. The publish response includes
`cacheInvalidation`: `purged`, `not-needed`, or `failed`. If invalidation fails,
the publication remains committed; investigate the renderer rather than
repeating the publish. Missing configuration for an existing page prevents
publication before any write.

### Verify gates before enabling the first site

Run these checks with disposable identities in an isolated test environment.
Exercise direct API requests as well as the CMS controls:

- **Editor:** open the page editor, save a draft, and preview it. Confirm the
  public version stays unchanged. Publish controls are unavailable, and publish,
  unpublish, public status updates, and scheduled publication are denied.
- **Publisher:** edit and publish. Confirm one successful publish event records
  the actor and the correct workspace, entry, site, and version.
- **Non-member or pending invite:** deny editor, draft, preview, and publish
  access, including requests with another workspace's entry or role ID.
- **Lookup failure:** fail membership, connection, or permission resolution and
  confirm no content is returned or changed. A loading or error state must not
  enable the publish control.
- **Audit failure:** reject the publish-event insert and confirm neither the
  published pointer nor public entry status changes.

Record the exact source revision, executed checks, security approval, and any
remaining failures privately. If a gate fails, keep onboarding held and return
custody to the permission or publish API owner. Do not broaden an editor's role
as a workaround.

## Linked-Site Email Security

Outbound email requested through
`POST /api/v1/workspaces/{wsId}/external-projects/emails` is denied unless the
workspace binding has an explicit `settings.outboundEmail` grant. A valid app
secret and matching workspace binding are necessary but no longer sufficient.

Workspace security managers configure the grant on the main platform workspace
settings page:

- `enabled` must be `true`.
- `allowedRecipientDomains` must contain every exact recipient domain. A grant
  for `example.com` does not include `sub.example.com`, and wildcards are
  rejected.
- `useRootWorkspaceCredentials` allows the workspace to borrow the managed
  platform sender while retaining workspace rate limits, blacklist checks, and
  audit attribution. Only a root user with `manage_external_projects` may
  change this flag.

Missing, malformed, or disabled policy data always fails closed with HTTP 403.
An allowed request still passes the existing small-recipient cap and monthly
budget checks before entering the mail service.

Richfield public submissions use `TURNSTILE_SECRET_KEY_RICHFIELD` when present,
falling back to the platform-wide `TURNSTILE_SECRET_KEY` only for backwards
compatibility. This lets operators add or rotate Richfield's widget without
changing the Turnstile secret used by other platform surfaces.

Validate focused behavior from the repository root:

```bash
cd apps/web
bun run test -- src/lib/external-projects/email-policy.test.ts \
  'src/app/api/v1/workspaces/[wsId]/external-projects/email-policy/route.test.ts' \
  'src/app/api/v1/workspaces/[wsId]/external-projects/emails/route.test.ts' \
  'src/app/api/v1/workspaces/[wsId]/external-projects/submissions/route.test.ts'
```

## Implementation Notes

- Keep CMS as a pure satellite frontend. Do not move API ownership into `apps/cms`.
- Continue adding or extending client helpers in `packages/internal-api` for CMS-facing API calls.
- Keep preview sourced from the existing delivery route instead of introducing a second preview payload contract.
- Backend/database naming remains `external-project*`; the product surface is what changed.
- Protect CMS-owned product copy with the CMS copy hygiene test, and add
  explicit admin/developer-detail exceptions only when a staff workflow truly
  needs an implementation value.
- Translation validation now treats `null` leaves as invalid so missing shared keys fail checks instead of silently passing parity.
- `POST /api/v1/workspaces/{wsId}/external-projects/setup` enables the studio and is restricted to root external-project admins (see [CMS studio enablement](/platform/applications/cms#studio-enablement-and-canonical-projects)). For a root admin, setup preserves an existing same-adapter binding while refreshing the project schema and field definitions; otherwise it creates the canonical `{adapter}-main` project if needed, binds the workspace, and writes a binding audit row. A linked app using its app credentials may call setup only for its already-enabled workspace, which refreshes field definitions and template without touching the canonical project. Workspace managers use diff/apply on an enabled studio instead.
- External apps can mark manifest assets with `metadata.publicPath`, `metadata.localAssetPath`, or a relative `sourceUrl` such as `/media/hero.png`.
- For a registered branded app using the `custom` adapter, make its app ID equal to the linked canonical template key (for example, `rennu`). Token exchange and subsequent content requests match that exact key, not the shared `custom` adapter name. Built-in integrations still match their adapter. The registered app workspace allowlist, enabled binding, user membership, and scoped permissions are all still required. A mismatch produces `App is not linked to this workspace`; do not fix it by sharing another site's app credentials.
- Before diff/apply, run the public-folder linker so the manifest stores deterministic Drive paths under `external-projects/{adapter}/{collectionSlug}/{entrySlug}/{filename}`.
- Diff/apply routes are workspace-scoped. They may persist manifest schema into the bound workspace's collections and field definitions, but they must not update `canonical_external_projects` or other root/canonical registry state.
- Before apply, upload those files through the external-project asset app-server upload route. Abort the apply if a local public asset is missing so CMS never receives storage paths for objects that were not uploaded.
- Asset `storagePath`/`storage_path` values must stay under `external-projects/`. Do not point CMS assets at Drive, finance, or other workspace storage namespaces; delivery and admin cleanup only operate on assets that satisfy the CMS namespace invariant.

## Storage analytics cache

The authenticated external-project storage analytics endpoint reads Supabase project
statistics from a private Postgres snapshot keyed by workspace and adapter. It
calculates file totals and highlights from `storage.objects` metadata, with a
1,000-object cap and an explicit `truncated` flag. Archived versions and folder
placeholders do not contribute to file totals.

Snapshots expire after five minutes. Storage inserts, updates, deletes, and moves
invalidate workspace snapshots in the same transaction, including direct uploads.
A shared workspace lock serializes refresh and invalidation so a concurrent file
change cannot leave a newly stored stale snapshot. Workspace quota is read live.
The cache is available only through a service-role RPC, after endpoint access and
rate-limit checks.

R2 uses the bounded provider scan. A missing RPC during an additive migration
rollout also uses that scan; other database failures remain visible. Production
activation requires the normal gated Supabase migration workflow. No cache
backfill is required.

The first-class Next handler preserves bodyless `HEAD` responses and request-time
authorization. Its future Rust port mirrors the Supabase cache response with live
quota and falls through to Next for fully configured R2 providers and unported
methods. Rust is not deployed; satellite-session and rate-limit parity remain
tracked prerequisites for a future cutover.

### Database contract gate

`external-project-storage-analytics-contract.yaml` checks the exact PR head with
all tracked Supabase schema inputs. Its verifier requires the reviewed migration
body under the root-reserved forward filename, runs all 15 strict SQL assertions,
generates actual public/private/storage types, and closes its owned disposable
stack. A skipped wrapper or local source test does not establish this DB gate.
After the 15-assertion sequential fixture, the gate uses distinct bounded psql
sessions for first-cache-row refresh versus insert/update. It observes the
contender waiting on the actual workspace advisory lock (namespace 73007), then
requires invalidation and exact recalculation after both sessions complete.
Authored Node wiring tests do not establish that race; its actual hosted receipt
is required before merge. Linux's shared rootful Docker daemon is not a
qualified contained executor; do not run this verifier there to bypass that gate.

## Team Guidance

- Link into the CMS-native route map directly.
- Prefer the root `/internal/projects` console (the root workspace's `/{wsId}/projects`) for site-template and workspace-link operations.
- Keep bound-workspace collaborator management on the dedicated `/{wsId}/members` route, and do not surface the root projects console inside non-root workspace sidebars.
- Update both `apps/cms/messages/en.json` and `apps/cms/messages/vi.json`, then run `bun i18n:sort` whenever CMS copy changes.

## Content reference scope

CMS root administration requires `manage_external_projects` in the root
workspace. Role administration alone does not grant this capability. Content
blocks reference entries in their own workspace, and collection-specific fields
reference collections in that workspace. Global fields may omit a collection.
These rules apply to the CMS satellite and Web's shared content store; regression
coverage lives in the CMS access tests and Web's
`store-reference-scope.test.ts`.
