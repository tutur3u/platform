## Overview

The mobile app now ships first-party workspace surfaces for:

- Drive at `Routes.drive`
- CRM at `Routes.crm`
- Education at `Routes.education`

These modules are registered in the Apps hub and available through the mini-app navigation system.

The mobile Apps hub uses the v0.9.2 colored cards with consistent icons and clear descriptions. Keep module ordering explicit in the hub view rather than relying on registry insertion order. For workspace modules that need dense controls, prefer the same shell-owned chrome used by Calendar:

- `ShellMiniNav` for mode or section switching
- `ShellChromeActions` for quick actions such as filters, create, sort, and view toggles
- A compact overview with a small number of relevant metrics
- The v0.9.2 AppCardPalette gradient cards, consistent icon blocks, readable labels, and shared theme colors

Background warmups for optional products should also respect access state before fetching. Do not let Apps hub or boot-time cache warmups call product endpoints blindly; skip the warmup when the corresponding access cubit is not loaded and enabled, and fail soft on opportunistic `404` responses.

Meet is a standard launcher module, with meeting search, scheduling, editing, and deletion. Workspace visibility flags still apply. Every launcher module includes an English and Vietnamese description.

## Responsive Loading And Cache Verification

Root tabs initialize on their first visit and retain their state afterward. Hidden
tabs stop ticking animations. Page content and navigation no longer wait for
staggered entrance animations. Opening Apps does not prefetch every product.

`CacheStore` shares initialization and concurrent fetches for the same scoped key.
Expired entries wait for replacement; eligible stale entries can refresh in the
background. Invalidation and logout prevent older in-flight requests from writing
back into the cache. Keys must include user, workspace, and all query filters.
Keys longer than Hive's 255-byte UTF-8 limit use a SHA-256 digest of the complete
scoped identity. Keep short keys stable, and test persistence/reopening with real
UUIDs and long search filters; short mock IDs can hide storage failures.

Mail list snapshots use the existing encrypted Hive store, with a one-minute
freshness window and a twenty-minute expiry. Cached rows appear while refresh is
in progress. Pull-to-refresh bypasses freshness, and successful mutations
invalidate the workspace's Mail variants. Thread details use the same scoped
cache; permissions and individual messages (including editable drafts) are
fetched from the server. Attachment bytes, credentials, and active compose buffers are
not cached. Authorization failures discard the displayed list. Search waits 300ms
after typing, and list rows are built lazily. Folder metadata loads independently
so it cannot hold up the inbox.

### Tablet layouts and shared controls

Use the available window width, including split-screen windows, when choosing
columns. Home uses a full-width workspace selector and independently flowing card columns;
the Apps hub uses content-sized rows so larger text can grow.
Drive and CMS allow their grids to use the wider workspace. Kanban and timeline
are work surfaces: do not wrap them in the reading-column width constraint.
Tablet Kanban fills the available height and puts dock clearance inside each
scrolling task list. It shows multiple independently scrolling lists; compact windows keep
the swipe-between-lists interaction. Leave room for the shell dock and task actions.

The shell's Apps button opens a searchable picker using the same module visibility
rules and descriptions as the hub. Primary top-bar actions remain visible; extra
actions use the overflow menu. Tablets can display more actions. Register Mail
workspace actions only while its nested workspace route is current, so a reader
or composer cannot leave stale workspace actions active.

Mail controls scroll with the message list, and formatted messages render inline
in an isolated native WebView. JavaScript, file access, forms, and browser-session
sharing remain disabled. Remote images require an explicit action. Its shared
document builder sanitizes the original body HTML off the UI thread, preserves
newsletter styles and email tables, and uses the web reader's typography and
overflow rules. Do not force every table into fixed equal-width columns. CID
images load through the authenticated attachment API, limited to raster images,
12 requests and 8 MiB retained bytes per message. The WebView receives only
prepared image data, never API credentials. Large attachments remain available
through the attachment actions.

Meet uses cached, account/workspace/query-scoped pages, explicit refresh, and
mutation invalidation. Workspace changes must invalidate pending UI requests even
when the new workspace is absent. A 401/403 clears the cached and displayed data.

Verify at least 768×1024, 1024×768, and 1366×1024, plus a compact split window,
larger text, and an open keyboard. Check dock height and taps, multiple Kanban
columns, horizontal and vertical scrolling, task-detail return position, picker
filtering, and the last visible row above the dock. Widget checks supplement
authenticated simulator checks; native email rendering requires device verification.

When changing this behavior, verify cold launch, returning to a visited tab,
pull-to-refresh, slow/failed requests, rapid search changes, and switching accounts
or workspaces. Run the focused cache, Mail workspace, lazy tab, and shell back
navigation tests, followed by `bun check:mobile`. Use an iOS simulator to inspect
light/dark appearance, larger text, keyboard interaction, and narrow layouts.

Time Tracking and CRM user mobile calls stay on the live platform origin: Track and Contacts require
app-session credentials, while mobile currently uses Supabase Bearer sessions.
Do not move those paths to their satellites until mobile supports that authentication contract.

### Native API requests and hosting challenges

An HTTP 429 HTML response with `x-vercel-mitigated: challenge` is a Vercel browser
challenge, not the application's JSON rate-limit response. Native HTTP clients
cannot complete that challenge.

Production mobile Calendar requests use the infrastructure app's
`/api/v1/mobile-calendar/api/v1/…` gateway. Development uses the local Calendar
app directly. The gateway validates the Bearer session with Supabase before
reading any forwarding credential. It forwards only event CRUD, connected-account
list/disconnect, calendar connection list/toggle, and OAuth URL discovery to the
fixed `https://calendar.tuturuuu.com` origin. Calendar validates the original
session again and enforces workspace permissions. Incoming cookies, forwarding
headers, and client-supplied gateway credentials are never relayed. Redirects and
non-JSON upstream responses are rejected; mutations are never automatically retried.

The server credential is stored as a versioned encrypted envelope in the root
workspace's `workspace_secrets` row named `mobile_calendar_gateway:v1`. Its data
key is encrypted with the infrastructure app's existing `ENCRYPTION_MASTER_KEY`.
The envelope contains `version: 1`, `encryptedDataKey`, and `encryptedSecret`.
Only the server decrypts it; it must never enter mobile build configuration,
logs, source control, or the signing bundle.

Configure Calendar's custom WAF exception to require both its API path and an
exact `x-tuturuuu-calendar-gateway` header value matching that private credential.
Do not accept the mere presence of an Authorization header as a WAF bypass.
The private credential allows verified gateway traffic through hosting challenges;
it does not replace Calendar's application authentication or authorization.

For cutover, deploy and verify the gateway, then publish clients using it. Replace
the old path-plus-Bearer exception with the server-credential rule once both store
builds are available. Verify invalid sessions return JSON 401 from the gateway
without an upstream request, a signed-in Calendar loads real events, and direct
Calendar requests with a forged Bearer or gateway header still receive the hosting
challenge. Older clients that call Calendar directly need the mobile update.
Keep publication on hold if gateway verification fails. Inspect the exact project's
active rules and unpublished draft before changing or publishing its WAF config.

For credential rotation, create a new encrypted envelope, temporarily allow both
old and new **server credentials** at the WAF, update the secret row, verify a live
Calendar read, then remove the old credential. Never restore the public Bearer
exception as a fallback. Missing or invalid secret configuration fails closed with
JSON 503. Responses use `private, no-store`; request bodies are limited to 512 KiB,
response bodies to 8 MiB, and forwarding to 20 seconds.

## Mobile App Lock And Web QR Approval

The mobile app supports a device-level app lock from Settings > Session. The
setting is stored in secure storage and uses the OS local authentication prompt
with device PIN/passcode fallback allowed. When enabled, the app locks on an
authenticated cold launch and after at least 30 seconds in the background.

QR session handoff approval is gated by this setting:

- The scanner lives at `Routes.settingsQrLoginScan`.
- The scanner only accepts `tuturuuu://auth/qr-login` payloads from trusted
  Tuturuuu or local development origins.
- The QR challenge must have been created by the same account that is active in
  the mobile app. Public unauthenticated QR sign-in is not supported because it
  would let an attacker poll a victim-approved challenge.
- Before approval, mobile runs local authentication and then calls
  `/api/v1/auth/qr-login/challenges/:id/approve` with the current Bearer
  session.

If a user wants to approve QR session handoff for a different account, both the
creator session and the mobile app must be using that account before scanning.

The mobile app can approve web MFA challenges when the active mobile Supabase
session is already at `aal2`:

- The web MFA screen creates an `/api/v1/auth/mfa/mobile/challenges` request and
  shows a pair code.
- `MobileMfaApprovalListener` is mounted at the app shell and polls
  `/api/v1/auth/mfa/mobile/approvals` while the user is authenticated, the app is
  in the foreground, and app lock is not covering the UI.
- Pending pair codes open an app-level approval dialog. The Settings > Session
  tile remains a manual fallback surface for the same pending approvals.
- Mobile approves through
  `/api/v1/auth/mfa/mobile/challenges/:id/approve`.
- The web poller consumes the approved challenge and sets an HTTP-only
  `ttr_mfa_mobile_approval` cookie. The central auth proxy accepts that cookie
  only for the same user, the hidden web challenge secret, and an unexpired
  consumed `mfa_mobile_approval` challenge.
- After a mobile TOTP challenge succeeds, `AuthCubit.verifyMfa` must sync the
  refreshed `aal2` Supabase session into the active multi-account store. Without
  that sync, later mobile API calls can restore/send an older `aal1` token and
  the approvals endpoint will respond with `requiresMobileMfa`.
- Multi-account removal and all-account logout must treat Supabase
  `auth.signOut()` as required before clearing the local account store or
  emitting an unauthenticated Cubit state. Google/provider logout and stored
  refresh-token revocation can be best-effort, but a failed Supabase logout must
  leave the account visible with an error so the persisted session cannot
  silently reappear later.
- Auth account models may serialize refresh tokens and session JSON only for the
  encrypted secure-storage store. Do not include those raw secrets in
  `Equatable.props`, `toString`, or other Cubit/Bloc state debug output because
  the global Bloc observer logs state changes during development.

For mobile-facing collection APIs, keep list routes request-aware and list-shaped. A cookie-only helper or `.single()` response on a collection endpoint can work in the web dashboard but break mobile Bearer-token callers or pagination assumptions.

The mobile endpoint registry is guarded by `bun check:mobile-api-mappings`.
The check extracts Flutter `/api/*` templates from `api_config.dart` and the
production endpoint catalog used by the `ttr` CLI SDK. It verifies that both
legacy clients still resolve to a canonical owner in a checked-in Next
satellite, the legacy route wrappers, or the Rust/TanStack migration manifest.
The `Mobile API Mappings` workflow runs whenever either client catalog, an app
API route, or the migration manifest changes. If a route is migrated or
removed, update Flutter and the CLI SDK in the same change instead of leaving a
legacy client to discover the break in production.

Also select real join columns such as `module_id`; do not assume those bridge tables expose a synthetic `id`.

## Import And Export Format Notes

- The web CRM page still has richer spreadsheet tooling, including XLSX-oriented flows.
- Mobile import and export currently use CSV plus native share sheets.
- Keep the server contract for bulk import as a raw JSON array of `{ email, fullName }` rows.

This format choice is intentional for now: the current Flutter dependency graph in `apps/mobile` does not accept a stable XLSX package cleanly without conflicts, so mobile should prefer CSV/share flows unless spreadsheet generation is moved server-side later.

## Verification

For Drive, CRM, or Education mobile changes:

1. Update `apps/mobile/lib/l10n/arb/*.arb` for every new user-facing string.
2. Run `flutter gen-l10n`.
3. Run `bun check:mobile`.
