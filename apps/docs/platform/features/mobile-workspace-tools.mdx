## Overview

The mobile app now ships first-party workspace surfaces for:

- Drive at `Routes.drive`
- CRM at `Routes.crm`
- Education at `Routes.education`

These modules are registered in the Apps hub and available through the mini-app navigation system.

The mobile Apps hub uses the v0.9.2 colored cards with consistent icons and clear descriptions. Keep module ordering explicit in the hub view rather than relying on registry insertion order. For workspace modules that need dense controls, prefer the same shell-owned chrome used by Calendar:

- `ShellMiniNav` for mode or section switching
- `ShellChromeActions` for quick actions such as filters, create, sort, and view toggles
- A compact overview with a small number of relevant metrics
- The v0.9.2 AppCardPalette gradient cards, consistent icon blocks, readable labels, and shared theme colors

The Apps screen defaults to the compact grid. A List/Grid switch in the top
shell header sits beside Customize and changes the same visible, ordered modules
between icon-and-name tiles and descriptive cards. Grid tiles have more space below
the shell header and can be held and dragged to reorder without entering Customize.
The
choice stays in the mounted Apps screen while navigating within the mobile shell;
search, pins, and workspace access rules apply to both layouts. Descriptions remain
searchable in grid mode even though they are hidden from the tiles.
Holding a tile produces a pickup haptic, moving onto a new navigation target
produces a selection tick, and completing a drop produces a light confirmation.
The floating dock uses the same semantic feedback. Haptics are enabled by default
on iOS and Android, can be disabled in Preferences, follow system haptic policy,
and throttle repeated feedback during a continuous gesture.
Shell actions and standalone primary actions give a selection tick, and a
speed dial distinguishes opening from choosing an action. Finance transaction
actions give a light completion tap after the local edit is accepted; this tap
does not claim that a queued offline edit has synchronized.

Background warmups for optional products should also respect access state before fetching. Do not let Apps hub or boot-time cache warmups call product endpoints blindly; skip the warmup when the corresponding access cubit is not loaded and enabled, and fail soft on opportunistic `404` responses.

Meet is a standard launcher module, with meeting search, scheduling, editing, and deletion. Workspace visibility flags still apply. Every launcher module includes an English and Vietnamese description.

## Navigation preferences and recovery

Phones and tablets share a compact floating icon dock. Leaving a mini-app returns
to its Home or Apps launch screen. Root screens remain mounted with hidden
animations paused, preserving search and scroll state. The brand control opens
the Apps screen within the normal shell, with compact search and arrange actions.
Apps is always available in the root dock. In the picker, Customize exposes pin and
drag controls; pinned apps sort first. Order and pins persist on the device and
never bypass each module's visibility rules.

The shell reserves physical bottom clearance, including for lists with explicit
padding. Screens inside the shell must not add another dock inset. The dock hides
on downward scrolling and returns on upward scrolling or after a short idle period;
its clearance stays stable to avoid moving content. Primary actions register with
`ShellActionSpec.inDock`; `ExtendedFab` automatically uses that registration inside
the router shell and keeps its standalone presentation elsewhere. Action buttons
show icons on phones and labels on tablet widths. Do not duplicate these actions
in page-level floating buttons or top-bar actions.

Nova spins once when entering Assistant and remains static afterward. Loading
indicators continue animating, while pull-to-refresh uses an opaque circular
surface. Reduced-motion preferences disable spinning.

Calendar forms and event details use readable, blurred root-navigator sheets.
High-contrast mode uses an opaque surface. Failed event
edits or deletions restore the previous in-memory and cached list and expose the
server error. Verify the next reload as well as the immediate rollback.

Dock action handoffs retain presentation only, never callbacks or permission
state. Destination actions remain disabled until their mounted page registers
current handlers; missing destinations discard previews after a short handoff.
Long-press navigation supports dragging between enabled destinations and commits
only on release. Releasing outside the dock cancels the change.

Notification Inbox and Archive actions share a bordered segmented control with
primary selected colors and accessibility selection state. Use `segmentGroup`
on related `ShellActionSpec` entries instead of unrelated highlighted icons.

Mail owns folder, mailbox, and filter selectors through `ShellMiniNav`. Opening
a message replaces the shell title with its subject and reuses the dock back
action. Child composers and attachment previews suspend reader chrome. Background
read-state changes and revalidation do not display a refresh indicator; explicit
pull-to-refresh does. Reply-all and forwarding remain in the message actions sheet.

Chat bubbles expose copy through long press or secondary click. Markdown in these
bubbles must not install a competing native text-selection long-press recognizer.
Other standalone markdown views remain selectable.

## Responsive Loading And Cache Verification

### Device task and calendar reminders

Settings → Preferences → Reminders controls task and calendar alerts separately.
Both default on, with selectable 3-day, 1-day, 12-hour, 3-hour, and 1-hour
lead times. The app refreshes the existing user/workspace-scoped task and
calendar caches after sign-in and when it resumes after 15 minutes. It then
schedules the nearest 60 future device alerts, replacing outdated entries and
cancelling them on sign-out. An all-day event uses 9 a.m. local time as its
reminder anchor. Android boot/package-replacement receivers restore pending
alarms after a restart or update.

Calendar alerts use a localized timing title (for example, “Calendar: In 3
days”) and the event name as the description, including for all-day events.
Tapping one opens that event in the mobile Calendar detail sheet. If the event
was removed or cannot be loaded, the app returns to Calendar and shows a brief
message. This behavior applies to device-scheduled reminders on iOS and Android;
task reminders keep their existing title and description.

The Reminders page shows the last successful fetch, the number of alerts still
pending in the operating system, the next scheduled alert, notification
permission, and a manual refresh action. A scheduled count is local state,
not proof that the device displayed an alert. If the app remains suspended,
new items created on another device cannot enter the local schedule until the
next app refresh. The deployed web cron checks watched task deadlines every five
minutes across workspaces, queries only the active reminder windows, and creates
notifications through each user's channel preferences, including mobile push.
Workspace task reminder settings can change or disable the lead times; without
an override, the server uses the five device
defaults. Its receipt includes the due date, so a rescheduled task is eligible
again. Calendar event reminders still depend on the device schedule until the
server calendar reminder flow is shipped.
Verify this flow on physical iOS and Android devices with the app closed,
notifications enabled and disabled, account switching, changed due dates, and
completed tasks.

Root tabs initialize on their first visit and retain their state afterward. Hidden
tabs stop ticking animations. Page content and navigation no longer wait for
staggered entrance animations. Opening Apps does not prefetch every product.
Screen routes use subtle fade and horizontal motion on Android and desktop;
iOS retains the native swipe-back transition. Reduced-motion settings skip the
custom transition. The floating shell tabs animate their content in place.
Home shows Finance wallets and recent Notes alongside its existing summary cards
when those modules are available to the current account and workspace. Both cards
use scoped snapshots while refreshing, and clear their displayed rows when the
account or workspace changes. They link into their corresponding mobile screens.

`CacheStore` shares initialization and concurrent fetches for the same scoped key.
Prefetch returns stored snapshots immediately and starts background
revalidation, even past their expiry window. Explicit refresh waits for the network.
On startup, the encrypted
store consolidates legacy aliases into canonical scoped keys and retains the newest
snapshot for each identity. Pending offline mutations remain separate and intact.
An encrypted entity index now materializes rows with stable IDs from scoped
snapshots. It is rebuilt automatically from existing snapshots when its schema
version is absent, updates alongside new snapshots, and removes rows when their
source is cleared or evicted. Local queries require a user ID, workspace scope,
and namespace; they can overlay the matching queued edits without a network
call. Storage limits include the indexed entity payloads. This is the database
foundation for module read adapters, rather than evidence that every module is
already locally readable or writable.
Mail keeps an explicit request path for authorization cleanup on 401/403.
Meet now returns the scoped meeting snapshot immediately, refreshes in the
background, and purges denied data if the refresh returns 401/403.
Pending Notes, Mail, Finance, Calendar, and Inventory product edits are stored in the account-scoped encrypted
mutation queue and replayed in order per module and workspace on reconnect. A
conflict holds dependent edits in that scope while other modules continue. A queued item uses a dashed
border and lower opacity until the server confirms it; conflicts and failed
writes remain visible in Settings > Offline changes for retry or removal.
Removing a queued change requires confirmation and does not undo a write that
may already have reached the server. A user-initiated retry gives a completion
haptic only when that specific outbox entry is removed after replay. Finance
creates and transfers, Mail sends and attachments, and Notes creates use stable
client IDs so replay can recognize a prior successful write. Other modules still
need individual offline mutation adapters before this is an app-wide write replica.
Calendar event lists use scoped snapshots and overlay pending edits. An uncertain
Calendar create stays in manual review because it may have already reached an
external calendar provider.
Inventory product lists overlay queued creates and updates on their cached
catalog; an uncertain product create also requires manual review.
Education course, quiz, and flashcard edits and basic CRM user and feedback
edits use the same encrypted queue. Education course, quiz-set, quiz, flashcard,
and attempt reads and CRM user, group, feedback, and audit reads use scoped
snapshots while revalidating. Education authored cards and CRM user and feedback
cards show queued edits with the pending treatment. Other Education and CRM
actions still need individual mutation adapters before those modules meet the
full replica contract.
Documents lists and details use scoped snapshots. Document create, update, and
delete enter the encrypted outbox when offline, and list rows expose their
pending state. A newly created offline document uses a local ID for navigation;
its create must finish syncing before edits to that document can be replayed
against a server ID. The outbox persists a scoped local-to-server ID mapping
when the create response supplies an ID and rewrites dependent queued paths and
structured payload fields before replay.
Drive directory and analytics, CMS collections and entries, and Habit tracker
lists and details also read scoped snapshots while revalidating. CMS collection
and entry CRUD uses the outbox and marks pending tiles. CMS entries targeting a
locally created collection use the persisted ID mapping during replay. Drive
folder create, rename, folder and file delete use path-scoped
queued edits with pending rows. Drive uploads also queue encrypted file bytes;
replay requests a fresh signed URL, uploads the bytes, and finalizes the file.
An uncertain upload remains in manual review to avoid overwriting a file twice.
Habit trackers, entries, and streak actions also queue edits, with pending
cards and activity rows. Create responses that omit a server ID still need
dedicated replay support.
Meet meeting create, edit, and delete also queue offline with a pending list
treatment. Live room access, realtime tokens, and assistant actions remain
network-dependent and must not be represented as queued calls.
Task summaries, board lists, and board task pages read scoped snapshots while
revalidating. Core task create, edit, description, delete and restore, plus
board create and lifecycle edits, enter the outbox offline. Task and board
cards expose pending status. Label, project, and initiative lists revalidate
from scoped snapshots. Their
create, edit, and delete actions queue offline with pending cards. Task
relationships and task/project/initiative links queue as scoped edits. Bulk
task actions queue as one ordered edit with every affected card marked pending;
the bulk action reports a queued result without claiming server success.
Partial bulk replay stays in manual conflict review so successful tasks are not
silently retried with failed ones.
Board task create, edit, and move and board list create, edit, and reorder
also queue offline. Their list reads overlay pending edits; task cards and
list headers distinguish unsynchronized rows. Project updates read scoped
snapshots and queue create, edit, and delete with pending cards.
Chat conversation and message lists also return scoped snapshots while
revalidating. Conversation create, edit, and delete and user message sends enter
the encrypted outbox offline. A queued message appears immediately with a
dimmed dashed frame. Each send carries a stable client request ID so replay can
use the server's idempotency check. Message edit, delete, read acknowledgment,
reactions, AI settings, and friend requests also queue offline. Attachments
stage encrypted bytes in the outbox, request a fresh signed URL on replay,
and rewrite dependent queued message paths after upload. An ambiguous upload
remains in manual review. Assistant generation remains network-dependent.
Timer sessions, history, categories, goals, requests, and summaries use scoped
snapshots while revalidating. Session start, stop, pause, resume, edit, missed
entry creation, and deletion queue offline, with dimmed dashed session cards.
Timer category creation, goal create, edit, and delete, request approval changes,
comments, and threshold updates queue too. Category, goal, request, and comment
cards show pending sync state. Local ID reconciliation supports edits made
before a create syncs; ambiguous sends remain in manual review. Request image
uploads still need encrypted offline staging. Running session state applies
queued lifecycle edits over the latest snapshot.
Finance category and tag lists also read scoped snapshots while revalidating;
their create, edit, and delete actions queue offline, and queued cards use the
dimmed dashed treatment. An uncertain transaction
update or delete enters manual review rather than automatic replay. Once a
transaction or transfer update is acknowledged, failure to refresh its detail
does not invite another money write.
Invalidation and logout prevent older
in-flight requests from writing back into the cache. Keys must include user,
workspace, and all query filters.
Failed disk writes do not hide successful network responses. Mail and Meet retain
the original authorization error and disable their cache if denied-data cleanup fails.
Keys longer than Hive's 255-byte UTF-8 limit use a SHA-256 digest of the complete
scoped identity. Keep short keys stable, and test persistence/reopening with real
UUIDs and long search filters; short mock IDs can hide storage failures.

Mail list snapshots use the existing encrypted Hive store, with a one-minute
freshness window and a seven-day retention window. Cached rows appear while a
background refresh runs, including after their freshness window. A background
authorization denial revokes the affected workspace snapshot, clears the inbox,
and closes an open reader. Pull-to-refresh forces a network read, and successful mutations
invalidate the workspace's Mail variants. Thread details use the same scoped
cache; permissions and individual messages (including editable drafts) are
fetched from the server. General attachment bytes, credentials, and active compose buffers are
not cached. Authorization failures discard the displayed list. Search waits 300ms
after typing, and list rows are built lazily. Folder metadata loads independently
so it cannot hold up the inbox.
Small inline images keep an encrypted thread-scoped copy. A cached image renders
immediately while one shared background request refreshes it; a denied image
request revokes the affected Mail workspace and clears its thread media.

Inventory can synchronously restore an unexpired user/workspace-scoped snapshot
before currency and permission requests finish. Editing remains disabled until
current permissions are confirmed. A denied request removes displayed content;
cached data must never grant mutation permissions.

### Tablet layouts and shared controls

Use the available window width, including split-screen windows, when choosing
columns. Home uses a full-width workspace selector and independently flowing card columns;
the Apps hub uses content-sized rows so larger text can grow.
Drive and CMS allow their grids to use the wider workspace. Kanban and timeline
are work surfaces: do not wrap them in the reading-column width constraint.
Tablet Kanban fills the available height and puts dock clearance inside each
scrolling task list. It shows multiple independently scrolling lists; compact windows keep
the swipe-between-lists interaction. Leave room for the shell dock and task actions.

The shell's Apps button opens a searchable picker using the same module visibility
rules and descriptions as the hub. Primary top-bar actions remain visible; extra
actions use the overflow menu. Tablets can display more actions. Register Mail
workspace actions only while its nested workspace route is current, so a reader
or composer cannot leave stale workspace actions active.

Mail controls scroll with the message list, and formatted messages render inline
in an isolated native WebView. JavaScript, file access, forms, and browser-session
sharing remain disabled. Remote images require an explicit action. Its shared
document builder sanitizes the original body HTML off the UI thread, preserves
newsletter styles and email tables, and uses the web reader's typography and
overflow rules. Do not force every table into fixed equal-width columns. CID
images load through the authenticated attachment API, limited to raster images,
12 requests and 8 MiB retained bytes per message. The WebView receives only
prepared image data, never API credentials. Large attachments remain available
through the attachment actions.

Meet uses cached, account/workspace/query-scoped pages, explicit refresh, and
mutation invalidation. Workspace changes must invalidate pending UI requests even
when the new workspace is absent. A 401/403 clears the cached and displayed data.
The native Meet room keeps the shell's top bar and places its leave/back control in
the room content, so the route title and dock follow the rest of the app.

Verify at least 768×1024, 1024×768, and 1366×1024, plus a compact split window,
larger text, and an open keyboard. Check dock height and taps, multiple Kanban
columns, horizontal and vertical scrolling, task-detail return position, picker
filtering, and the last visible row above the dock. Widget checks supplement
authenticated simulator checks; native email rendering requires device verification.

When changing this behavior, verify cold launch, returning to a visited tab,
pull-to-refresh, slow/failed requests, rapid search changes, and switching accounts
or workspaces. Run the focused cache, Mail workspace, lazy tab, and shell back
navigation tests, followed by `bun check:mobile`. Use an iOS simulator to inspect
light/dark appearance, larger text, keyboard interaction, and narrow layouts.

Time Tracking and CRM user mobile calls stay on the live platform origin: Track and Contacts require
app-session credentials, while mobile currently uses Supabase Bearer sessions.
Do not move those paths to their satellites until mobile supports that authentication contract.

### Native API requests and hosting challenges

An HTTP 429 HTML response with `x-vercel-mitigated: challenge` is a Vercel browser
challenge, not the application's JSON rate-limit response. Native HTTP clients
cannot complete that challenge.

Production mobile Calendar requests use the infrastructure app's
`/api/v1/mobile-calendar/api/v1/…` gateway. Development uses the local Calendar
app directly. The gateway validates the Bearer session with Supabase before
reading any forwarding credential. It forwards only event CRUD, connected-account
list/disconnect, calendar connection list/toggle, and OAuth URL discovery to the
fixed `https://calendar.tuturuuu.com` origin. Calendar validates the original
session again and enforces workspace permissions. Incoming cookies, forwarding
headers, and client-supplied gateway credentials are never relayed. Redirects and
non-JSON upstream responses are rejected; mutations are never automatically retried.

The server credential is stored as a versioned encrypted envelope in the root
workspace's `workspace_secrets` row named `mobile_calendar_gateway:v1`. Its data
key is encrypted with the infrastructure app's existing `ENCRYPTION_MASTER_KEY`.
The envelope contains `version: 1`, `encryptedDataKey`, and `encryptedSecret`.
Only the server decrypts it; it must never enter mobile build configuration,
logs, source control, or the signing bundle.

Configure Calendar's custom WAF exception to require both its API path and an
exact `x-tuturuuu-calendar-gateway` header value matching that private credential.
Do not accept the mere presence of an Authorization header as a WAF bypass.
The private credential allows verified gateway traffic through hosting challenges;
it does not replace Calendar's application authentication or authorization.

For cutover, deploy and verify the gateway, then publish clients using it. Replace
the old path-plus-Bearer exception with the server-credential rule once both store
builds are available. Verify invalid sessions return JSON 401 from the gateway
without an upstream request, a signed-in Calendar loads real events, and direct
Calendar requests with a forged Bearer or gateway header still receive the hosting
challenge. Older clients that call Calendar directly need the mobile update.
Keep publication on hold if gateway verification fails. Inspect the exact project's
active rules and unpublished draft before changing or publishing its WAF config.

For credential rotation, create a new encrypted envelope, temporarily allow both
old and new **server credentials** at the WAF, update the secret row, verify a live
Calendar read, then remove the old credential. Never restore the public Bearer
exception as a fallback. Missing or invalid secret configuration fails closed with
JSON 503. Responses use `private, no-store`; request bodies are limited to 512 KiB,
response bodies to 8 MiB, and forwarding to 20 seconds.

## Locked Notes

Mobile Notes defaults to a device-first encrypted lock. Where OS local
authentication is available, Face ID or Touch ID gates a random note key in
device-only secure storage; otherwise the lock sheet defaults to a six-digit
app PIN. The lock encrypts the note body; the title and list metadata retain
their existing visibility. The PIN gates that local key and is never used as
the encryption password. Five incorrect PIN attempts pause retries for 30
seconds. The server
also stores a wrapped copy of the random key in the note envelope using the
configured encryption master key. Creating a device lock fails if wrapping is
unavailable. Web releases that key only for the note creator after a verified
passkey sign-in within five minutes, on web or mobile. Account sign-in alone
does not release it. Native passkeys use `webcredentials:tuturuuu.com` on iOS
and the `get_login_creds` Digital Asset Links relation for the production
Android signing certificate. Keep the association files and mobile signing
identities aligned when changing app IDs or certificates.
The user can also show a two-minute QR code on web and scan it from the
original phone's note actions; the phone requires fresh local unlock and sends
the key encrypted with a one-time QR secret. The QR secret stays on the two
devices. The server relays only the sealed key. A custom passphrase remains
available and existing passphrase-locked notes keep their current behavior.
Server-wrapped recovery means this lock is not end-to-end encrypted against the
server. Preserve the configured encryption master key when rotating deployment
secrets; losing it disables passkey recovery for existing locked notes, though
the original phone or its QR transfer can still open them. On compact layouts,
Back closes any open Notes action sheet and returns
from note detail to the Notes list.

## Mobile App Lock And Web QR Approval

The mobile app supports a device-level app lock from Settings > Session. The
setting is stored in secure storage and uses the OS local authentication prompt
with device PIN/passcode fallback allowed. When enabled, the app locks on an
authenticated cold launch and after at least 30 seconds in the background.

### Device authenticators and trusted registrations

Home suggests registering the current device when local authentication is
available, the account has no verified authenticator on that device, and new
registrations are unlocked. “Not now” suppresses this invitation for seven days
per account. A failed policy lookup never produces a misleading invitation.
Settings > Session always provides the explicit management entry point.

Registration creates a Supabase TOTP factor and a separate random device proof.
The mobile app saves both in account-scoped secure storage before verifying the
factor. iOS uses a non-synchronizing, this-device-only Keychain item. Each code
reveal, approval and management change requires fresh OS authentication; PIN or
passcode fallback is allowed. Codes disappear when the app backgrounds.

`/api/v1/auth/mfa/devices` uses request-scoped authentication for web cookies and
mobile Bearer tokens. Server-owned `app_metadata.tuturuuu_device_authenticators`
contains the registration policy and proof hashes, never TOTP secrets. The
registry API serializes writes with a bounded Upstash lease and fails closed if
`UPSTASH_REDIS_REST_URL` or `UPSTASH_REDIS_REST_TOKEN` is unavailable. Do not log
registration response bodies, proofs, TOTP secrets, or session tokens.

The trusted-device list supports revocation and locking new registrations.
Enabling the lock requires two currently verified trusted factors. Unlocking
requires a current trusted-device proof and AAL2; the last trusted device cannot
remove itself while locked. Keep a backup trusted device: there is no automatic
lost-all-devices recovery bypass. The lock governs Tuturuuu device registrations;
it does not disable third-party enrollment through Supabase's own MFA APIs.
Only canonical, verified registry entries with valid proofs can approve Tuturuuu
sign-ins. A client-supplied device identifier or editable profile cannot grant
trust. Provider-level MFA enrollment can invalidate other sessions, so setup
explains that other devices may need to sign in again.

### QR and number-matching approvals

The scanner at `Routes.settingsQrLoginScan` accepts Tuturuuu QR payloads from
allowlisted origins; manual link entry supports devices without a camera.
Approval requires fresh local authentication, a trusted-device proof and a
verified mobile MFA session. The server checks the challenge secret, origin,
protocol kind, expiry and one-time consumption. QR handoff creates a new session;
Supabase MFA requirements still apply to that new session.

The web MFA screen creates a session-bound
`/api/v1/auth/mfa/mobile/challenges` request and shows a six-digit number.
The mobile user must enter that number. The pending-approval API never returns
it to the approving device. Approvals are rate-limited, expire after their short
challenge lifetime, and cannot be approved by the requesting session itself.
Users can explicitly deny an unexpected request.

`MobileMfaApprovalListener` polls while authenticated, foregrounded and unlocked.
Push receipt triggers an immediate refresh. A notification contains only account
and challenge identifiers plus expiry, never a code or credential. Tapping it
opens a page that re-fetches the authorized request. Notifications do not approve
from the lock screen. Polling remains the fallback when notification permission
or provider delivery is unavailable.

After consumption, the web poller sets the HTTP-only
`ttr_mfa_mobile_approval` cookie, bound to the same user, web session, hidden
challenge secret and unexpired canonical approval. This is an application-level
web approval; it does not mint a Supabase AAL2 token. Mobile AAL2 still comes from
Supabase MFA verification.

### Sessions and account connections

Settings > Session > Devices and connections lists active sessions and linked
sign-in identities. Users can revoke another session, revoke other sessions,
connect a supported OAuth provider, or disconnect an identity while retaining
another sign-in method. Destructive actions require confirmation and local
verification. Account changes during an asynchronous operation fail closed.

Multi-account persistence snapshots the current session after profile loading,
so a refresh during that request cannot save an older token. Authenticated API
retries are account-scoped and refuse to replay after an account switch.

- Multi-account removal and all-account logout must treat Supabase
  `auth.signOut()` as required before clearing the local account store or
  emitting an unauthenticated Cubit state. Google/provider logout and stored
  refresh-token revocation can be best-effort, but a failed Supabase logout must
  leave the account visible with an error so the persisted session cannot
  silently reappear later.
- Auth account models may serialize refresh tokens and session JSON only for the
  encrypted secure-storage store. Do not include those raw secrets in
  `Equatable.props`, `toString`, or other Cubit/Bloc state debug output because
  the global Bloc observer logs state changes during development.

## Profile activity privacy

The Profile timeline shows the signed-in user's task creations, transaction
creations, and notes from the current workspace for the most recent 30 days.
Calendar rows are explicitly labeled as **workspace events** because the calendar
table does not record a reliable creator. The timeline groups rows by the device's
local day, expands to individual items, and links to their native mobile views.
Its snapshot is encrypted and scoped by user and workspace; opening Profile returns
it first and then revalidates. Timeline data is private and never follows the
tracked-time sharing preference.

Profile shows your own tracked-time totals and activity. Nothing is shared by
default. In a team workspace, **Share activity** asks for confirmation before
saving that workspace's preference. Members can then view only tracked-time
totals and daily activity from that workspace, without raw session titles,
email addresses, personal aggregates, or activity from other workspaces.
Turning sharing off blocks future reads. Former workspace members lose access.

The API uses the existing owner-scoped `user_workspace_configs` preference
`PROFILE_ACTIVITY_VISIBILITY=workspace`; missing or other values mean private.
It checks viewer membership before privileged reads and subject membership and
consent before and after aggregation. Shared activity is never stored in the
mobile persistent cache. Test private defaults, confirmation cancellation,
revocation, former members, and account/workspace changes before release.

## Assistant and task verification recovery

A task write returning HTTP 403 with `X-Abuse-Challenge: turnstile` requires
verification, not broader workspace permissions. Mobile opens the existing
security dialog and retries the same request once using the returned token.
Cancellation sends no retry; an account change aborts the request. Other 403
responses remain permission failures. Never bypass the server authorization or
abuse check to repair this flow. Log status and error codes, not response bodies
or verification tokens.

Every satellite enforcing this challenge needs its own production
`TURNSTILE_SECRET_KEY` configuration matching the mobile `TURNSTILE_SITE_KEY`.
The mobile release vault also supplies `TURNSTILE_BASE_URL`. A successful client
challenge followed by another 403 requires checking the server challenge audit:
`not_configured` means the satellite secret is missing. Configure the existing
matching secret through the provider vault and redeploy the current production
source; never disable verification. Check names and readiness without logging
secret values.

Assistant credits must load independently of optional task, Calendar, soul, and
model-catalog insights. Calendar insights use the authenticated workspace
`/api/v1/workspaces/:wsId/calendar/events` gateway. A failed credit read offers a
retry in the credit-source sheet rather than displaying a fabricated Free tier.
Chat errors remain visible after stream completion, with the user's message
retained for retry. Older Assistant UUIDs are not native Chat conversation IDs:
the specific `Conversation is not an AI chat` settings rejection must use the
legacy Assistant stream through the shared authenticated API client, including
challenge and refresh handling. Other malformed-settings errors stay errors. Read-only `ai-agent-thread-` mirrors belong in Chat, not Mira's
editable history. Do not restore them as Assistant conversations or send their
synthetic identifiers to Live's UUID-backed chat endpoint; Live starts a new
owned session when no resumable UUID is available.

Live initializes PCM playback before starting microphone capture on iOS. Its
serialized audio queue preserves chunk order and discards queued chunks when
playback is interrupted or disposed. The vendored PCM plugin preserves existing
`AVAudioSession` category options when the category is already correct; resetting
those options can disturb an active microphone route. Native microphone failures
are recoverable UI states. A simulator without a valid input format cannot prove
physical-device audio quality; verify recording, playback, interruption, and
headset reconnection on hardware before claiming that a reported device crash or
stutter is resolved.
