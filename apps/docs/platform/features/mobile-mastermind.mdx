title: Mobile Mastermind
description: Who sees the Mastermind section in the mobile app, how it behaves before data arrives, and what it never shows.
---

Mastermind is an internal fleet overview. The mobile section reads one
sanitized snapshot from the Mastermind hub Worker. This page records the
product rules of the shell entry, the Home tab and the Inbox; later tabs extend it.

## Who sees it

- **Scope:** the Apps hub offers Mastermind only when the active workspace is
  the root workspace, the root permission set contains `view_infrastructure`
  (the root workspace creator and `admin` count, as for every permission), and
  the build has a hub source configured. Production, staging and any build with
  `MASTERMIND_HUB_URL` have one; see Data source.
- **Default:** hidden. It is not an experimental module and cannot be enabled
  from Settings. A user without root `view_infrastructure`, outside the root
  workspace, or while access is loading or failed never sees the entry.
- **Authority:** this check is cosmetic. The hub Worker's owner allowlist is the
  real gate, and a 403 from the hub hides the entry until the next access sync.
- **Production beta:** the production app reads the hub for the beta behind
  these gates: root workspace plus `view_infrastructure`, a configured source,
  and the hub's owner allowlist. Replies stay off until the hub's
  `GET /v1/capabilities` reports `replies: true`. Production reports
  `replies: false` today, so the Inbox is read-only there and the reply composer
  stays hidden; turning replies on needs no store release.
- **Deep links and push taps:** any `/mastermind/**` location is held on a
  neutral skeleton while the access check runs, then redirected to the Apps hub
  unless access is loaded and enabled. A 403 keeps the user on the screen so it
  can explain itself; the entry disappears from the Apps hub.
- **Account changes:** logout and account switch erase the cached snapshot,
  memory and disk, and re-check access for the selected workspace.
- **Access errors:** a failed access check hides the entry, so it is re-run when
  the app resumes and when the Apps hub is pulled to refresh; neither blinks a
  healthy entry while it checks.

## Data source

Fixture builds (development flavor with `MASTERMIND_FIXTURE`) read the bundled
synthetic sample. Staging reads `mastermind-hub-staging.tutur3u.com`, production
reads `mastermind-hub.tutur3u.com`, and any build reads `MASTERMIND_HUB_URL`
when it is set; an explicit value always wins over the flavor host, and a bad
one never falls back to it. A build with neither (development without a
fixture, an unknown flavor) stays disconnected, as does any value that is not
a bare HTTPS origin: no credentials, path, query or fragment, so the bearer
token never leaves over cleartext or to a lookalike host. The app-level runtime owns
the source, the cache and the refresh scheduler and closes them with the app.
Each Mastermind screen only attaches to and detaches from the scheduler, so
refresh runs only while a screen is open and the app is in the foreground. It
also runs at once when the app returns from the background (`hidden` or
`paused`); a brief `inactive` blip such as Control Centre or a biometric prompt
is not a resume and fetches nothing. The scheduler follows device connectivity,
and the freshness line (Offline versus Couldn't refresh) updates when
connectivity alone changes.

## Tabs

Home, Inbox, Work, Ship and Insights share one mini-app shell: the top navbar
shows the destination title and no Back button, and the floating dock owns Back.
Every tab sits behind the same access gate and freshness strip. Work is planned
to become Threads (Home · Inbox · Threads · Ship · Insights); until the hub
serves threads it shows today's lane list.

In-screen views (Needs you | Decisions, Lanes | Backlog | Staff) use the compact
`MastermindSegmentedControl`: a 32 pt track whose segments each own a 44 pt hit
area, instead of the tall pill. When the segments cannot fit across at the
current text size they stack into full-width 44 pt rows with a check on the
selected one; the control never becomes a hidden horizontal scroller and labels
are never truncated. List search uses `MastermindCollapsibleSearch`:
hidden until the navbar search icon is tapped, kept
open while a query is applied, folded away once cleared and unfocused. Every
sheet opens on the root navigator so the floating dock never covers it.

## Freshness strip

Each tab starts with one short line inside the scroll view. Data age is
informational because publishing is manual at first; only a failed refresh or a
degraded source is a warning. The visible line carries an age or a short GMT+7
time (with the day once the data is 20 hours old); screen readers hear the full
sentence with the absolute GMT+7 date and time.

| Condition | Visible line |
|---|---|
| Published within 5 minutes | Updated `<HH:mm>`, on Home only |
| Older | Published `<age>` |
| Refresh failed and the device has no connection | Offline · showing `<time>` |
| Refresh failed while the device is online | Couldn't refresh · showing `<time>` |
| Hub schema newer than the app | Update the app to read the latest Mastermind data · showing `<time>` |
| Hub answered something unreadable | Couldn't read the latest update · showing `<time>` |
| Any source not ok | appended: `<n>` sources degraded |

Healthy, fresh data hides the strip on every tab but Home. A warning tints only
the glyph and a 3 pt leading bar; the text stays foreground so it keeps 4.5:1
contrast in light mode. The line ellipsizes at normal text sizes and wraps past
130%. It is a live region only while it is a warning. With degraded sources it
is a 44 dp row with a chevron that opens the "Sources" sheet: every source the
snapshot reports, degraded first, each as a glyph, a name and a state word.
Home also has a "Data sources" navbar action that opens the same sheet.

## Before data arrives

| State | Shown |
|---|---|
| Loading, nothing held | Skeleton cards, never a spinner alone |
| Not configured | "Mastermind isn't connected on this build." No retry |
| 401 after a session refresh | "Mastermind couldn't verify your session." Try again, plus a secondary "Sign out and sign in again" that asks first |
| 403 | "This account isn't allowed to view Mastermind." and "Ask a Mastermind owner for access." No retry |
| 404 no snapshot | "Mastermind hasn't published yet." Retry |
| Network or 5xx | "Can't reach Mastermind." Retry |
| Rejected snapshot | A fixed category message, never the parser path. Retry |

A 401 can come from the Worker (audience or clock skew) rather than the
session, and signing out removes every saved account on the device, so it is
never the primary action and only runs after the user confirms.

## Home

Order: freshness strip, activity tiles, Needs you, replies waiting to send,
Ship, Quota, Activity and, last, recent decisions. Every list is capped and
ends in "Show all N" only when it holds more than the cap.

- **Activity tiles.** Running, Waiting, Idle and Failed, four across (two by
  two past 130% text), each at least 44 × 72 and opening Work filtered to that
  state. Waiting shows "`<n>` on you" when open decisions or actions wait on
  the owner. A muted footnote reads "`<n>` queued · `<n>` not reporting" and
  opens Work on queued lanes. Failed > 0 tints its glyph destructive; "0
  failed" keeps a neutral glyph.
- **Needs you.** Up to three normal items (decision, then action, then FYI,
  then publisher order) with the count in the caption. The kind is a leading
  glyph, the title is the display title, and the product is the second line
  unless the title names it. Rows push the item detail, so Back returns Home.
- **Ship.** Failing environments first, then the three most recent releases;
  a release with no age reads `—` and sorts last. A basis shared by every row
  moves into the caption ("Ship · GitHub deployment").
- **Quota.** The three most urgent pools (the Insights order) with a sparkline;
  a missing session budget or pacing reads `—`.
- **Activity** and **recent decisions** show three each; decision rows push
  their detail and "See all decisions" opens the Decisions segment.

**Security rows** render as a single non-tappable "`<Product>` · security fix"
line in a trailing "Security" group with no count. They have no severity, title
or detail anywhere, are never counted, and never reorder anything. Event
summaries apply the same collapse.

## Inbox

The Inbox tab opens on one compact segmented control: **Needs you · Resolved ·
Decisions**. Needs you lists the open asks grouped by kind ("Decisions for
you", "Actions", then "For your information"), each with its count, in publisher
order. Resolved lists the hub's `decisions_resolved` history ("Recently
resolved", newest first). Pull to refresh.

- **Rows** are two lines: the friendly title (`itemDisplayTitle`, so a redacted
  `Product · area · kind` title uses the first ask line), then the
  kind badge with the state and age: "Resolved · Yes · 2 h ago" for a resolved
  ask, "Sent · waiting for Mastermind" or "Waiting to send" for this device's
  reply. A separate two-line preview retains the ask. No age is shown where the hub
  publishes none (open asks). Options, "More" and the full ask live on the
  detail. A row is one screen-reader node ("Decision. Review plan. Review the
  plan", hint "Opens the ask").
- **Caps:** each group shows five rows, then "Show all N" expands it in place.
- **Search** is hidden until the navbar search icon
  of the list reveals it ("Search asks"); it covers every ask segment, including
  the resolved answer. Product chips (one row, 44 pt targets) appear only while
  two or more products are present.
- **Empty and no-match states say why:** "Nothing needs you" (Mastermind lists
  an ask here when a lane needs your answer), "Nothing resolved recently" (asks
  appear once Mastermind records an answer), and
  "No matching items" with a "Clear search and filters" row.
- **Security rows** keep the Home rule: one non-tappable line in a trailing
  "Security" group with no count, never counted, searched or filtered, with no
  severity, id or detail. Resolved does not show them.
- **Detail:** `/mastermind/inbox/item/:itemId` opens one ask in full, pushed
  from the Inbox and from Home, so Back returns to whichever opened it, with
  the same search text and product chips (the shell pops an item location
  instead of falling back to the Inbox). The navbar title is the kind
  ("Decision"), so the title is not repeated; the page leads with the display
  title as a heading and shows the full `ask_text` as plain text, never clamped.
  When the hub published only its "Open on Mac" stand-in, an info alert reads
  "Full details are on the Mac" instead. The id is looked up among the open
  asks, then the resolved history, and is only ever a route parameter; deep
  links carry tab roots only and never ids. A resolved ask shows an "Outcome"
  panel (Resolved, "Answer: Yes", GMT+7 time) and no composer. An id in neither
  list shows "This item is no longer in Mastermind" (or "This was answered or
  withdrawn" when it left while open) with a way back, never an error. A changed
  `version_hash` shows "This question was updated".
- **The "Reply on Mac" option** is a placeholder the publisher adds when an item
  has nothing to pick. It is never offered as a choice and the app never sends
  it.

### Decisions

The segment lives in the URL: Needs you is the bare `/mastermind/inbox`, and
Resolved and Decisions are `?segment=resolved|decisions`; old `all` maps to Needs you (an unknown
value is Needs you).
Switching is a `go`, never a push, so Back does not walk the segments. Home
links straight to the Decisions segment.

The Decisions segment lists the journal (`decisions[]`) newest first, grouped by
GMT+7 calendar day (a decision at 17:30 UTC belongs to the next GMT+7 day), each
day with a count. A row shows the title, the GMT+7 time, category, risk as the
words "Risk: low / medium / high" plus a signal glyph, and the product. Chips
filter by product and by reversible / not reversible; a chip only exists while it
can split the journal, and a filter whose chip left the data is dropped. The
filters survive opening a decision and coming back. When `decisions_skipped` is
above zero the list ends with "N older decisions aren't included in this
snapshot." An empty journal says "No decisions recorded yet."

`/mastermind/inbox/decision/:decisionId` opens one decision in full: why ("No
reason recorded" when absent), decided by (Mastermind, You, or "Role: `<slug>`"
with the slug verbatim), reversible ("Can be reversed" / "Not reversible"),
risk, category, area, product and the absolute GMT+7 time. It is pushed from the
Decisions list and from Home, and the shell pops it on Back like an item or
lane. The id is an opaque snapshot id and a route parameter only. An id the
snapshot no longer holds shows "This decision is no longer in Mastermind" with a
way back to the Decisions segment; a decision whose fields changed while open
shows "This decision was updated". The journal is history: there is no reply
control. Security decisions do not exist in schema 1.4 and are never rendered;
the Needs-you "Security" group never appears on this segment.

### Replies

Replies are gated at runtime by `GET /v1/capabilities` (`replies`, with schema
`1.4`), checked when an Inbox screen opens and at most every five minutes.
Where replies are off, or the hub cannot be asked, the detail shows the options
read-only and "Reply on your Mac"; there is no composer. The Worker owns the
switch, so it flips without a store release.

- **Gate in code:** submit, retry and flush all refuse to send unless the hub
  says replies are on, not only the composer's visibility. Entries queued while
  replies are off stay queued: neither sent nor dropped, until capabilities say
  `replies: true` again. Coming back online re-asks the hub before flushing.
- **Known answer kept offline:** a known "supported" answer survives a failed
  re-check. Going offline never flips it, so the outbox keeps working with no
  connection; only an answer from the hub turns replies off: `replies: false`
  from the capabilities check, or a 403 `replies_disabled` on a send (any other
  403 is a lost-access refusal, handled like a 403 on the snapshot).
- **One check at a time:** overlapping capability checks, forced or not, share a
  single request, and a reply sent during the first-ever check waits for its
  answer instead of being refused. Connectivity changes are de-duplicated, so
  several interfaces flipping together cause one re-check and flush.

- **Contract:** `POST /v1/replies` with exactly
  `{schema_version: "1.4", item_id, version_hash, option_index | text}`: one of
  an option index (into the item's own `options[]`) or free text of at most 500
  characters, counted in code points, and at most 10 lines (the hub's limit; the
  composer caps both as you type). An option button sends its index after a
  five-second undo window (see Undo window below).
  The text field has a placeholder and a counter; free-text sending requires
  confirmation.
- **Idempotency:** the `Idempotency-Key` is a random v4 UUID from a secure
  generator, made once per reply and stored in the outbox before the first send.
  Every retry reuses it, so an unknown outcome never becomes a second reply. A
  200 replay is treated exactly like 201. One reply per question version.
- **Offline outbox:** a reply that cannot be delivered (offline, timeout, 5xx)
  stays queued on the device, per user, in the snapshot cache directory, and is
  sent again when an Inbox screen opens, when the app resumes and when the device
  comes back online. It can be retried or discarded. Entries expire after seven
  days and are dropped when a live snapshot no longer has the item open. Queued
  replies live in the OS cache directory, not the documents directory: that
  keeps them out of device backups, at the cost that the OS may purge the cache
  under storage pressure and silently lose a queued reply. We accept that
  trade-off, because a reply is short-lived and a lost one is re-asked; a reply
  already accepted by the hub is unaffected. Logout,
  account switch and lost access erase the outbox with the snapshot cache, behind
  the same generation fences, so an in-flight send cannot revive it.
- **409 `stale_item`:** the item is refreshed, the typed words are kept, and the
  screen says "This question changed or was already answered. Review it again."
  Option buttons always use the current question version. `idempotency_conflict` drops the queued entry with "Something went
  wrong with this reply. Review it and send it again."
- **Other answers:** 400 (`unsafe_text` explains the text policy) and 413 keep
  the words to edit; 429 waits out `Retry-After` and disables the retry until
  then; 403 `replies_disabled` hides the composer and 403 `forbidden` is lost
  access.
- **401:** the reply stays queued. The first failure offers "Try again"; only
  after a repeat does "Sign out and sign in again" appear, and it asks first,
  because signing out removes every saved account on the device.
- **Waiting rows:** the Inbox shows "N replies waiting to send" while replies
  are queued; with exactly one, the row opens that item. A queued reply binds to
  its item id and `version_hash`, so a reply to an older version of a question is
  never shown as the answer to the current one. A 429 counts down on its own and
  re-enables "Try again" when `Retry-After` has passed.
- **Search:** it never matches the "Reply on Mac" placeholder option.
- **Accessibility:** the reply status line is a live region, and the character
  counter has a spoken label ("12 of 500 characters used").

Delivery status beyond "Sent · waiting for Mastermind" (the item leaving the
next snapshot) is not polled yet.

## Work

The Work tab has three segments, a segmented control under the freshness
strip: **Lanes** (the default), **Backlog** and **Staff**. Lanes lists lanes
grouped by state, the one that needs attention first:
failed, waiting, running, queued, idle, stale, completed, cancelled, then the
rare open, answered, withdrawn and unknown. Each group shows its count and is
ordered oldest first, a lane with no age last. A row shows the title, role and
provider/model (display text, shown verbatim), "Running for 2 h" (or
"Running · age unknown"), "About 20 min left" only when there is an estimate,
and product, area and kind chips. State is always a glyph and a word.

- **Filters:** a search field ("Search lanes"), one chip per state, and product
  and area chips while two or more of each are present. A state chip's count
  follows the product, area and search filters, so it always matches its group
  header. A product or area filter resets when its value leaves the snapshot,
  because its chip would be gone.
- **Segment and filters in the URL:** the segment lives in the location as
  `?segment=backlog` or `?segment=staff` (Lanes is the bare tab, and an unknown
  value reads as Lanes), beside the lane filters `?state=`, `?product=` and
  `?area=`. Every segment or chip change rewrites the location with `go`, so
  Back never walks through segments. The lane filters stay in the URL on the
  other segments, so switching back to Lanes finds them. The Home lane chips
  open `/mastermind/work?state=<state>`. An unknown value is ignored and "All"
  clears the state. A lane opens by push, so Back from it (the dock included)
  pops to the same filtered list, search text and all; the shell pops a lane
  location instead of falling back to the bare tab root. External deep links
  open the tab root and never carry a segment, filter or lane id.
- **A filter that leaves the snapshot leaves the URL too:** when a product or
  area filter resets because its value is gone, the location is rewritten
  without it once the frame is built, so a later visit to that location does
  not bring a stale filter back. Filters that are still valid stay.
- **No matches:** a filter combination with no lanes (including a state with
  none) shows "No matching lanes" with a "Clear filters" row that resets state,
  product, area and search.
- **Backlog:** `backlog[]` grouped by product (the item count in each group's
  header), open before answered before withdrawn, in the publisher's order
  within a state. An item with no product sits last under "No product". Each row
  is a title and a state glyph and word; it has no tap target, and its opaque id
  is never shown. The search field ("Search backlog") matches the title and
  product and is local to the segment. An empty backlog reads "Backlog is
  clear" and hides the search; no match reads "No matching backlog items".
- **Staff:** `observability.staff[]`, which is `{role, title, state, model}`
  and nothing else. Rows sort by the Lanes state priority and then by role,
  case-insensitively, never by activity. A row shows the title, the role and
  model (display text; the literal `unknown` reads "Unknown model") and a state
  glyph and word. A summary caption reads "11 roles · 4 running". Staff has no
  search, filters or sort control. **Privacy rule:** the screen never shows or
  derives a last-active time, a runs-today count, an "active today" label or
  any activity ordering; the hub does not publish them, and a change that adds
  one must be reviewed as a privacy change. An empty list reads "No staff roles
  reported."
- **Security rows** keep the Home rule on Lanes and Backlog: one non-tappable
  line in a trailing "Security" group with no count, never counted, searched or
  filtered. Staff has none, because the hub omits security roles.
- **Detail:** `/mastermind/work/lane/:laneId` shows the same fields in full and
  has no action. The id is an opaque snapshot id and only ever a route
  parameter. An id that is not in the snapshot shows "This lane is no longer in
  Mastermind" (or "This lane finished or was removed" when it left while open)
  with a way back, never an error. A lane whose state changed while open shows
  "This lane was updated".

## Ship

`/mastermind/ship` is read-only. It lists, under the freshness strip:

- **Environments by product.** A product with a failing environment (deploy or
  CI `failure` or `error`) comes first, then the rest by most recent release,
  then by name. Each product is one compact card. Its header row carries the
  name, "Live 2 h ago" with the age basis (left out when the age is null, never
  "Unknown" or 0) and, when failing, a destructive glyph and a "Failing" badge.
  Production comes before staging. An environment row shows deploy and CI as a
  glyph and a word, and its own `freshness` as a chip only when it is not fresh
  (it never follows the snapshot's age). Then come the version and the commit id
  (monospace, with a 44-pt copy button; it is a public commit id), and one muted
  line with the subject, "Released 2 h ago" and "Checked 30 min ago" measured
  from the snapshot time. The absolute GMT+7 release and check times and the
  evidence label are in the row's semantics label. A reading the hub did not
  publish is left out, while one it could not read keeps its reason, for
  example "Deploy Not connected · Last checked 19:22". The publisher's stand-in
  subject for a commit it will not send is shown as the localized label
  "Withheld, open on Mac", muted with an info glyph and the tooltip "Details
  stay on the Mac". A failing environment on Home opens Ship on its product, and
  its row carries a chevron like the release rows.
- **Not tracked yet.** A product with no release age whose every environment has
  deploy, CI, freshness and evidence `unknown` and no release time, version or
  commit id gets no card. All such products share one final "Not tracked yet"
  row that names them ("MasteryAI, PKTM"). Tapping it lists each with the hub's
  reason ("Not connected · Last checked 19:22") or "No deployments observed".
  The row is hidden while a product filter is on, and these products get no
  filter pill.
- **CI now.** `observability.ci[]`, queued and running per repository. A null
  count reads "Unavailable", never 0.
- **Release cadence.** Most recent production release first; a product with none
  reads "No production release observed" and sits last. The caption carries the
  row count, and the list shows five rows with "Show all N" for the rest.
- **Pull requests and merges.** From `observability.delivery`: the latest open
  pull request count and merge-to-live median per product, and "At least N
  production releases observed" (a lower bound). A null count reads
  "Unavailable"; a delivery source with no coverage says so once and shows no
  numbers. Nothing on this tab opens a pull request, merges or syncs anything.
  The schema carries no separate sync record, so production sync is only
  visible as the release age and cadence above.
- **Product filter in the URL.** One horizontally scrolling pill bar (All, then
  the tracked products in list order, failing ones marked with a warning glyph)
  appears while two or more tracked products are present. It never wraps and
  writes `?product=<product>` with `go`. A product the snapshot lacks
  is shown unfiltered at once and removed from the URL after the frame, but
  only while Ship is the top route: a rewrite is a `go`, so one that fired under
  an open route would drop it. External deep links open the tab root.

Ship shows no security rows, ids or digests.

## Insights

`/mastermind/insights` is the Usage view (the Fleet, Models, Coordination and
Delivery sections arrive later and reuse the table route below).

- **Pools** come from `observability.usage.instances[]`, most urgent first:
  SHORT, then unknown pacing, then OK, then SURPLUS, then the least session
  budget left, then label. A pool's pacing is the worse of its session and
  weekly windows, so a weekly SHORT outranks a session that is fine. Pool labels
  are opaque display strings, shown verbatim and never summed or stacked.
- **Pool card.** One pacing verdict per pool, as a shape and a word: "Running
  short", "On pace", "Surplus", or "No pacing data" (a static hollow square, not
  the dashed outline that read as a spinner). The verdict is the worse of the
  windows that report pacing, so a window without pacing does not hide the
  other's. Under it, one muted line gives the burn and the signed projection at
  reset for the window the verdict comes from. An info button opens the
  "Reserve pacing (chart rule)" note saying it is not the routing decision.
  Then "Session left" and "Weekly left" each show a meter toned by that
  window's pacing, the percent and the reset ("Resets 17:10", with the day when
  it differs from the reading's). A window the hub did not read shows a dash
  and its reason ("Not connected · Last checked 19:22"), never 0.
- **Contradiction guard.** Scope: the pool card's burn line. Default: when the
  verdict window is SHORT and its burn is 0 pp/h or less, the line reads "Burn
  not measured yet" instead of "0 pp/h", because a pool that burns nothing
  cannot run short and the hub reading is partial. Exceptions: a zero burn on an
  OK or SURPLUS window is shown as measured. Coverage:
  `presentation/ship_usage_model_test.dart` ("a zero burn next to SHORT") and
  `mastermind_insights_compact_test.dart`.
- **Charts** use the shared chart kit: one panel per pool (session solid,
  weekly dashed, a fixed 0 to 100 percent axis, a reset marker when it falls in
  range), and for each Codex pool in `usage.credits[]` a balance panel and a
  burn-against-target panel. "Credits" is a unit of its own, never money or
  tokens; a null daily target reads "Target unavailable". Each panel's header
  holds its title and the Table action (a ghost button with an icon and a 44-pt
  target), so the action is never at the bottom of the card under the floating
  dock. A muted caption says what the plot leaves out ("Partial data: Weekly
  window not reported.", the gaps and their reasons). The plot's semantics label
  is the full text summary. The legend names only series with at least one
  reading, and a live readout follows. X-axis ticks show the GMT+7 time alone
  ("20:30"), adding the day ("Oct 28 05:45") only where the day changes and
  never on a chart within one day. With `usage.coverage` of `missing` or
  `unavailable` the plot is left out and the summary and coverage note stand
  in. With `partial` or `stale`, the caption and summary lead with the coverage
  word. A pool with no series shows the summary only.
- **Quota table** (`products.quotas[]`, including `Unknown account`), least left
  first and unknown last, with "as of N min ago" (left out when the read age is
  null). **Forecasts** (`quota_forecasts[]`): "Projected empty `<time>` GMT+7"
  soonest first, or "Not projected to run out before reset". Both captions carry
  the row count and show five rows with "Show all N" for the rest.
- **Chart table route.** `/mastermind/insights/:section/table/:chartId` is
  pushed over Insights and shows the same series rows the panel draws (a null
  cell reads "Unavailable"). The section is `usage` and the chart id is
  `budget:<pool>`, `credits:<pool>` or `burn:<pool>`; both are route parameters
  only. A chart the snapshot no longer has shows "This chart is no longer in
  Mastermind" with a way back, never an error. The shell pops this location on
  Back instead of falling back to the tab root.

## Product decisions

- **True activity counts.** Scope: Home tiles now; the lane list header and a
  Threads badge read the same `MastermindActivity` model. Default: running,
  waiting and idle come from the hub's `work.counts` only when its status is
  `ok` and `checked_at` is within 15 minutes of the snapshot; stale/down
  readings fall back to the latest `observability.fleet.series` point when
  coverage is ok or partial and it is at most 15 minutes older than
  `generated_at`, else from lane states, captioned "From lane reports". Queued
  and failed always come from lanes; unknown or stale lanes are a "not
  reporting" footnote, never a headline. "On you" counts open decisions and
  actions, never FYI. Coverage: `presentation/activity_model_test.dart`,
  `view/mastermind_home_v1_test.dart`.
- **Friendly names.** Scope: every row and detail title. Default: the hub's
  `[Name] Role` title shows verbatim; a redacted `Product · area · kind` title
  is never shown: a lane uses its standing role, or "`<Product>` `<area>`" for
  a child lane; an item uses its real title or first ask line. Models shorten
  to "Sonnet 5.5" or "GPT-6.1 sol"; an unknown model reads "Model not
  reported". Coverage: `presentation/display_names_test.dart`.
- **No bare unknown.** Scope: Home now, Ship and Insights next. Default: a
  missing, blank or "unknown" reading renders a muted `—` (`ReportedText`)
  announced as "Not reported" plus the hub's reason; the word "unknown" never
  stands alone. Coverage: `view/mastermind_home_v1_test.dart`,
  `view/forge_v1_fixture_test.dart`.

- **Resolved is the hub's word.** Scope: Inbox rows, the item detail, the
  Resolved segment. Default: an ask reads "Resolved" only once the hub
  lists it in `decisions_resolved`; a reply this device sent reads "Sent ·
  waiting for Mastermind" (with its GMT+7 queued time on the detail) until then,
  never Resolved. Exceptions: an ask that leaves the snapshot without a history
  row reads "This was answered or withdrawn". Coverage:
  `view/mastermind_inbox_v1_test.dart` ("a sent reply reads Sent · waiting until
  the hub resolves", "a resolved ask shows the hub outcome").
- **Decisions journal.** Scope: the Inbox Decisions segment, the decision
  detail and Home's recent-decisions card. Default: the Inbox segmented control
  ends with Decisions, its segment in the URL; Home rows open the
  detail and "See all decisions" opens the segment. Exceptions: the journal is
  history and is not answerable; search and risk/area filters are not offered
  yet. Coverage: `mastermind_decisions_test.dart`,
  `mastermind_decision_page_test.dart`, the "Back from a decision" cases in
  `shell_peer_section_checks.dart`.
- **Offline reply queuing.** Scope: replies from the item detail, on every app
  surface that shows the "N replies waiting to send" row (Home and Inbox).
  Default: a reply that cannot be delivered stays queued on the device and is
  sent later instead of being refused. This is safe because each queued reply is
  bound to its item id and `version_hash`, and carries one `Idempotency-Key`
  reused on every retry: if the question changed meanwhile the hub answers 409
  `stale_item`, the item is refreshed, the typed words are kept and the user
  reviews it again, so a stale answer is never accepted as the answer to a newer
  question. Exceptions: replies off at the hub keep entries queued without
  sending, an entry expires after seven days or when the item leaves the open
  list, and logout, account switch and lost access erase the outbox. Coverage:
  `mastermind_replies_cubit_test.dart`, `mastermind_replies_gate_test.dart`,
  `reply_outbox_store_test.dart`.

## Push notifications

The web route `POST /api/v1/mastermind/push-events` (see the
[API reference](/reference/api-reference/mastermind-push-events)) receives
signed hub events and sends a mobile push to Mastermind owners.

- **Scope:** `needs_you.new`, `decision.awaiting` and `pin_batch.new` only.
  Recipients are the owners in `MASTERMIND_PUSH_OWNER_IDS` with a registered
  device and the account push preference on.
- **Copy:** always "Open Mastermind" (vi "Mở Mastermind") under the title
  "Mastermind". The event carries no title, product or text, so no item content,
  including security items, can reach a lock screen.
- **Tap:** `openTarget: mastermind` with the tab root (`/mastermind/inbox`, or
  `/mastermind` for pins), held by the same access gate as any deep link. The
  app navigates only when `route` exactly matches one of those two roots; any
  other or missing route opens the notifications screen, and a route from the
  payload is never followed otherwise. An item id is never in the push.
- **Rate:** at most one push per type per owner per minute; a burst inside the
  window is dropped, not queued, because the next snapshot shows it.
- **Retries:** successful owners are skipped for 24 hours per event, including
  partial retries after the coalescing window. Token-owned claims prevent stale
  requests from releasing newer claims. Fan-out stops after 60 seconds and
  returns 502 for unreached owners. Observed FCM success gets a bounded,
  best-effort receipt write before the deadline is honoured; receipt failure
  warns and still counts as sent. A retry inside a pending coalescing window
  remains failed and retryable until the outcome is confirmed or the window
  expires, rather than completing the event. Unstored receipts can allow
  duplicates after the window expires if another owner failed. These rules
  apply to the web push endpoint; mobile tap behavior is unchanged.
- **Default:** off until Release Desk provisions `MASTERMIND_PUSH_HMAC_SECRET`
  and `MASTERMIND_PUSH_OWNER_IDS`; without the secret the route sends nothing.
- **Regression coverage:**
  `apps/web/src/app/api/v1/mastermind/push-events/route.test.ts`,
  `apps/web/src/app/api/v1/mastermind/push-events/route.race.test.ts`,
  `route.delivery.test.ts` and, for the tap,
  `apps/mobile/test/features/notifications/push/mastermind_push_destination_test.dart`.

## Decision and usage metadata

Mobile accepts legacy scalar fields alongside Forge v1 field envelopes. Missing
values display “Not published yet”; connection and source failures retain their
explicit status. An accepted reply remains sent until a live snapshot closes its
stable item ID. Resolved items leave Needs you and can appear in Recently resolved.
Full asks use `ask_text` (up to 2000 characters); an absent full ask is stated on
the detail page. No mobile action can infer that the hub processed a reply.

Usage charts annotate timestamp gaps with published reasons (source failure,
account switch or quota reset). Without metadata they say “No samples published”.
A reset timestamp within an inferred gap supplies the reset reason. Pools remain
separate. Adapter and classification regressions live in
`apps/mobile/test/features/mastermind/presentation/hub_contract_test.dart`.

Optional resolved history is parsed row by row: invalid entries are skipped,
repeated IDs use their latest resolved entry, and the last 20 valid entries are
shown. Additive lane and staff metadata does not invalidate the snapshot; known
fields still receive strict validation. Native open items may supply `status`
without the legacy `state`. Checked field timestamps and spoken chart gap bounds
use the same GMT+7 wall time as the rest of Mastermind.

Pages consume the shell's published bottom clearance through `AppPageScrollView`.
The Sources sheet opens on the root navigator, above the floating dock, so the
system safe area pads its end and no dock estimate is needed.

Forge v1 publishes field health beside the legacy arrays: `ship[]` supplies
`deploy`, `ci`, and `released_at`; `work.lanes[]` supplies age/ETA observations;
`insights[].weekly` supplies weekly budget and pacing observations. Mobile adapts
these companion paths and can show their reasons even when legacy environment
and usage-instance lists are empty. `work.counts` supplies Home's top-level
running, waiting, and idle counts. Unknown root keys, `asks_source`, and
`decisions_unknown` are safe to ignore. The exact redacted publisher fixture is
covered by `test/features/mastermind/view/forge_v1_fixture_test.dart`; it verifies
all five tabs, open asks, resolved history, source reasons, gaps, and counts.

Optional companions are validated field by field. Ship observations apply only to
production; null companions retain a published legacy value. Unknown enums,
invalid numeric values and unparseable timestamps retain the legacy value with
`not_published` status and an “Unrecognised value” reason. ISO timestamps with
`Z` or an explicit offset normalize to UTC. These rules apply to Ship, weekly
Insights and Work age/ETA fields. A malformed lane or unknown decision status
is skipped without hiding the remaining snapshot. Decisions marked resolved in
`decisions[]` also populate Recently resolved. Home keeps a queued chip when
`work.counts` is published, deriving queued from lanes when absent.
Regression coverage: `test/features/mastermind/presentation/companion_hardening_test.dart`.

An unreported pacing value retains its dashed status glyph beside the explicit
reason. The label wraps within the row's content area so checked timestamps do
not overflow narrow screens. `mastermind_insights_page_test.dart` preserves the
one-glyph-per-window assertion for reported and unreported values.

Truncated asks carry a visible Mac continuation notice. Recorded answers remain
available regardless of length, with an expandable preview. Failed replies say
"Not sent · tap to retry" while the reply is still queued and a retry can go
out (offline); tapping retries the existing reply and opens its recovery
details. A 429, a 401/403 (behind the auth-failure guard) or a dropped reply
reads "Couldn't send · open to review" and a tap only opens the details. Grouped open rows omit the repeated kind badge. Coverage:
`mastermind_inbox_v1_test.dart` (truncation, long answers, failed sends).

Ask cards on Home and Inbox share the same row. The publisher title wins;
a redacted title falls back to the first ask line. Cards preview two lines,
project, status and created-at age; detail keeps the full published ask. Only
unique open ids appear in Needs you; a hub-answered id always wins. Home's
See-all link opens Needs you. A redacted title is the first ask line, so the
preview starts on the second line; screen readers hear at most 200 characters
of the ask on a row. The recorded answer shows "Show full answer" whenever it
overflows four lines at the current width and text size.

**Undo window (Theo, 2026-10-28).** Option replies stay one tap. The tap shows
"Sending “option” · Undo" for 5 seconds on the item detail; the reply enters the outbox only then, through the same
`submit` and Idempotency-Key. One window per item; the other options lock
meanwhile. Leaving the screen inside the window still sends; logout or an
account switch cancels it, and so does a live snapshot where the ask changed or
left. Coverage: `mastermind_replies_undo_test.dart`, `mastermind_option_undo_test.dart`.

## Read-only Threads preview

`MASTERMIND_THREADS` is a Dart define, default `false`. With it off, Work, Ship
and Insights retain their existing navigation. When enabled, Threads replaces
Work in the dock; Backlog and Staff remain segments, and Ship and Insights stay
separate. The flag is read through `mastermindThreadsEnabled`, which tests can
override with `debugOverrideMastermindThreads`, so the default `flutter test` run
covers both the flag-off and flag-on paths without a `--dart-define`.

P1a is Work's own page with a Threads segment control: it reads the same
accepted snapshot as Home and Work through the shared snapshot cubit and the
tolerant v1 parser, and never parses the hub payload on its own. The grouped
lane list, search, state, product and area filters, "Clear filters", Backlog and
Staff are Work's own components, so a Work or Home link keeps `?state=`,
`?product=` and `?area=` when it redirects to `/mastermind/threads`. The one
difference is the group and chip order: Waiting, Failed, Running (queued
follows), then Idle, each oldest first. The segment switch uses the compact
32 pt track with 44 pt hit areas. A row opens the existing lane detail under
`/mastermind/work/lane/:id`; the dock keeps Threads selected while it is open,
and a missing lane offers "Back to Threads". There is no send UI and no row
opens history. Loading, access loss, rate limits (the last snapshot stays) and a
404 with nothing published use the shared Mastermind section states.

Thread history is a separate P1b change, built to the design's mobile conditions
(app lock, screenshot protection, closed parsers, localized state words and
times). It is not part of P1a and has no flag here.

Regression coverage lives in `apps/mobile/test/features/mastermind/threads/`:
`threads_list_test.dart` covers the group order, filters, "Clear filters",
Backlog/Staff segments, 44 pt targets, dock clearance, rate-limit retention and
the 404 state with the flag on; `threads_flag_test.dart` keeps the flag-off
navigation unchanged and checks the flag-on dock selection, redirects with
filters kept, and the lane-gone copy. Enablement remains held for exact-commit
mobile CI and product acceptance.
