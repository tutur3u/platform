Mastermind is an internal fleet overview. Today, Inbox and Work read the live
fleet snapshot from Web (see Fleet sync); Ship and Insights still read the
sanitized snapshot from the Mastermind hub Worker. This page records the
product rules of the shell entry and every tab.

## Fleet sync

- **Scope:** the Today, Inbox and Work tabs, `PUT`/`GET
  /api/v1/mastermind/fleet/state`, `POST
  /api/v1/mastermind/fleet/decisions/{id}/answer` and `GET`/`POST
  /api/v1/mastermind/fleet/answers`.
- **Source:** `scripts/mastermind-fleet/publish.mjs` runs on the orchestrator
  Mac every 30 seconds. It reads the local T3 state database read-only
  (`PRAGMA query_only`) and selects run statuses, thread titles, project names,
  providers, models, lineage and the linked environments. It never selects
  message bodies, prompts or runtime requests. Thread ids leave only as
  one-way `lane-<hash>` ids.
- **Linked machines:** threads on linked T3 environments never reach the local
  database, so each run also asks every link in `peer_environment_links` for
  its threads with MCP `t3_thread_list` (running, then waiting, then queued,
  paged up to 300; then failed and idle threads that have a run and changed
  in the last 24 hours, paged until the cutoff within the peer budget) and its
  project names. Side chats are left out on every machine (T3's list omits
  them, so the local count does too). Past a peer's 300-lane cap, its active
  threads still count from T3's per-status totals. The list reports only a
  thread's update time, so a metadata
  edit on an older thread can count it as recent for a day. Replies
  must answer the request's JSON-RPC id with a well-formed thread list (every
  row and cursor checked), or the probe counts as failed and the last good
  listing stays. It uses the credential the local T3 server already holds for
  that link (`~/.t3/userdata/secrets/<secret_name>.bin`, opened without
  following symlinks and refused unless it is a regular file owned by the
  publisher's user with mode exactly 0600). Like T3 itself, it sends the
  credential only to a link address (HTTPS, or HTTP to loopback or the
  tailnet) whose unauthenticated `/.well-known/t3/environment` descriptor
  answers with the link's environment id (probes race; matching addresses
  are tried in link order), only for a fenced link (T3 treats an unfenced one
  as expired from its link time), and only while the link's lease holds,
  rechecked before every request: the database expiry,
  or a later `T3-Link-Expires-At` renewal the peer returned for the same link
  generation. It closes each MCP session and never writes the credential
  anywhere. A run has one 25-second budget inside the 30-second tick: each
  peer gets at most 10 seconds plus a 2-second close, the Web calls share the
  rest and are skipped once it is spent, and a watchdog ends a run still
  going at 29 seconds. Every file input (secret, config, decisions, cache,
  stamp) opens without following links or blocking and must be a regular
  file, so nothing planted at an input path can stall a run. No per-machine publisher or
  extra secret exists: a newly linked environment appears on the next run.
  Each lane carries the `machineId` of the machine it runs on, the same id
  as that machine's entry: the slugged link label, plus an environment hash
  when two machines' labels slug alike. A thread listed twice is counted once,
  preferring the local row, then a live listing over a cached one. Past 32
  machines, the extra machines are left out together with their lanes.
- **Heartbeat:** a linked machine is `online` when it answered this run's
  probe or within the last two minutes, `stale` while it has been silent for
  up to 30 minutes, and `offline` after that or once its link has expired.
  Silence is measured from the later of the last successful probe and T3's
  own `last_reached_at`. Lanes from the last successful listing stay while
  the machine is not offline and that listing is under 30 minutes old;
  reachability alone never brings older lanes back. Both live in
  `~/.local/share/fleet-sync/peer-cache.json` (mode 0600, keyed by link and
  credential, so a re-linked machine starts fresh); a failed cache write
  does not stop the publish. The orchestrator Mac is always `online`; the snapshot's
  receive time carries its age. A probe refresh alone does not force a
  publish; status changes and the two-minute heartbeat do.
- **Counts:** a lane is one non-archived thread with an active run (running,
  waiting or queued) or a run in the last 24 hours (failed or idle). Threads
  with no run in 24 hours are not counted, so idle reflects recent work rather
  than every thread ever created. `counts` cover every collected lane before
  the 300-lane cap; the cap keeps running, then waiting, queued, failed and
  idle lanes, newest first (ties by lane id). The phone counts each machine's
  active lanes from the list, so those counts stay exact unless more than 300
  lanes are active fleet-wide; the publisher log reports per-machine active
  totals from before the cap, and the snapshot carries no per-machine count
  field yet. The body is
  then fitted under 240 KiB (the route refuses over 256 KiB with 413) by
  dropping idle and failed lanes, then decision bodies, then optional lane
  detail (project, provider, model, parent, start time), then active lanes,
  then the newest decisions; `counts` are kept, and the log's per-machine
  counts come from the snapshot before trimming.
- **Decisions:** the orchestrator writes one JSON file per open decision to
  `~/.local/share/fleet-sync/decisions/open/<id>.json` with `id` (lowercase
  slug), `title`, optional `body`, `urgency` (`urgent`, `high`, `normal`,
  `fyi`), up to six `options` (`{id, label}`), optional `recommendedOptionId`,
  `laneId`, `deadlineAt`, and `createdAt` (any parseable timestamp; sent as
  UTC ISO). Files with a bad id, no title, or no usable `createdAt`, and
  unparseable files, are skipped and only counted (`skippedDecisions` in the
  log); an unknown urgency becomes `normal`, and an option whose label
  scrubs to nothing, an invalid recommendation, or a timestamp outside the
  contract format (such as an extended year) is dropped. Every text field
  leaves the publisher already run through the Web scrubber
  (`scripts/mastermind-fleet/scrub.mjs`, kept identical to `scrub.ts` by
  its test) at its contract cap until the server's own pass changes nothing,
  with at most ten emoji counted after any regrouping: the Web edge guard
  rejects the whole request with a 400 when any field has more than ten emoji
  or any `title` or `label` exceeds 280 graphemes, and a required field the
  route scrubs to nothing fails the whole snapshot with 422. Removing the
  file closes the decision on the next publish.
- **Decision notifications:** a newly published open decision can alert fleet
  owners with push enabled. The notification shows the scrubbed title and
  opens the Inbox. A shared one-minute cap limits bursts, and repeated
  snapshots, answers and withdrawals generate no new alert. The Inbox carries
  every open decision. See the [delivery contract](/reference/api-reference/mastermind-push-events#fleet-decision-pushes).
- **Decision context:** a decision may also carry `why` (why it is asked
  now), `defaultOutcome` (what happens at the deadline without an answer)
  and `requester` (the asking agent, lane or machine). All three are
  scrubbed free text. `kind` is `ask` (default) or `login`. Older clients
  ignore the extra fields and read a login request as an ask.
- **Access requests (`kind: "login"`):** a CLI or provider on a fleet machine
  needs the owner's sign-in. `login` holds `service` (`github`,
  `cloudflare`, `vercel`, `claude`, `openai`, `google`, `apple`, `supabase`,
  `microsoft`), `flow`, `state` (`waiting`, `approved`, `verified`,
  `expired`, `failed`), `url`, `userCode`, `expiresAt` and `machineId`.
  `device` flows show the URL and a short code for any device; `link` flows
  show only the URL; `local_callback` flows (the provider redirects to a
  loopback listener, as `wrangler login` does) complete only in a browser on
  that machine, so the card names the machine. The URL is the one fleet
  field that may hold a link: it must be https, without credentials, a port
  or a fragment, on the service's host allowlist (`FLEET_LOGIN_HOSTS` in
  `apps/web/src/lib/mastermind/fleet/login.ts`, mirrored by the publisher).
  A device page carries no query, and an OAuth authorize link must name a
  `redirect_uri` on loopback (the agent's own CLI) or on the same provider,
  so a code can never go to a third-party callback. A loopback callback
  reaches whichever device opens the link, so it is accepted only for the
  `local_callback` flow, which must name its `machineId`. The code must
  match a short device-code shape. An open request needs `expiresAt` within 24
  hours. Terminal states carry neither link nor code. The publisher turns a
  passed expiry into `expired`, and Web applies the same rule on every read,
  so a stopped publisher never leaves a live link behind. "I signed in"
  posts the `signed_in` answer, which only open login requests accept (409
  once expired or closed); the agent still verifies the sign-in itself
  before it marks the request `verified`. A malformed login file is skipped
  and counted, never published. Only open requests are published, at most
  10 (the newest), on top of the 50-ask budget, so a snapshot holds at most
  60 decisions and older clients still receive every ask. Clients declare
  support with the `x-mastermind-fleet-features: login` request header; reads without it
  omit login requests, because older apps would offer Approve and Hold,
  which Web refuses for them.
- **Resolved and release status:** the publisher adds decisions resolved in
  the last 24 hours from `decisions/resolved/<id>.json` (`id`, `title`,
  `kind`, `answeredVia` of `mastermind`, `mobile`, `whatsapp` or `cli`,
  `outcome`, `resolvedAt`; at most 20), so an answer given on WhatsApp shows
  where it went. `release.json` supplies the main freeze state, production,
  migrations and up to ten open incidents. Invalid entries are omitted. If
  Web still refuses the snapshot at the edge, as too large or as invalid (400, 413 or 422), the
  publisher republishes the v1 core without these additions so lanes and
  asks keep flowing. It reports runs as degraded until the full snapshot is
  accepted again at the next change or heartbeat. A small
  separate store key lists the open decisions plus those closed in the last
  48 hours (at most 200 closed; a decision counts as open until the publish
  that drops it). Only the publisher's PUT writes it, with a compare-and-set
  before writing the snapshot, so overlapping publishes keep each other's
  entries; only decisions some stored snapshot carried count as closed. Web
  refuses (409 `stale_snapshot`) a snapshot generated before the newest it
  accepted, ignoring a stored generation more than five minutes ahead of its
  own clock, and the publisher holds an exclusive `publish.lock` (taken over
  after 60 seconds) so a manual run cannot overlap the launchd tick, and the answers pull covers
  those as well as the open ones, so an answer given just before a decision
  closes elsewhere (or a fallback publish) is still picked up. More than
  200 decisions closing within 48 hours while an answer to the oldest is
  still unpicked is the documented bound where it could be missed. The
  publisher reads at most the 100 most recently written resolved files.
  Known bounds: when a killed run leaves a stale lock, a manual run racing
  the launchd tick can both take it over; and two publishers running
  together (bypassing the lock) can, in a narrow interleaving, store the
  older snapshot. Neither happens with launchd alone; avoid manual runs
  within a minute of a killed one. Each run
  publishes first and then pulls answers, acknowledging them in batches of
  100. When the snapshot exceeds the body budget, resolved history and
  release status are dropped first, and among decisions the newest login
  request goes before any ask. Login requests never trigger a decision
  push, because clients without the feature header would open an Inbox
  that hides them; they reach the owner through Iris's own channels.
- **Answers:** Approve, Hold and Reply post an owner answer with an
  `Idempotency-Key`. Web stores it as a durable record; a retry with the same
  key returns the same record, and a new answer to the same decision becomes
  the next revision. The publisher pulls unacknowledged answers to decisions
  that are still open, writes each to
  `~/.local/share/fleet-sync/decisions/answers/<id>.r<revision>.json` (mode
  0600) and acknowledges it. The phone shows "Waiting for Iris" until the
  acknowledgement, then "Received by Iris". Nothing messages a fleet thread;
  the orchestrator reads the answers folder.
- **Authentication:** reads and answers are owner-only: root Mastermind
  permission (the rule of `GET /api/v1/mastermind/access`) and membership of
  `MASTERMIND_FLEET_OWNER_IDS` (falling back to `MASTERMIND_PUSH_OWNER_IDS`);
  an empty allowlist admits nobody. Publisher calls carry an HMAC-SHA256 over
  `<unix seconds>.<METHOD> <path+query>\n<body>` with
  `MASTERMIND_FLEET_PUBLISHER_SECRET` (rotation slot
  `MASTERMIND_FLEET_PUBLISHER_SECRET_NEXT`), a five-minute skew window and a
  15-minute single-use signature fence. Without a secret every publisher call
  answers 503.
- **Payload rules:** every free-text field is scrubbed on Web before storage
  (URLs, emails, paths, IPs, UUIDs, token and key shapes, long opaque runs and
  invisible characters are removed) and length-capped; lane and machine labels
  fall back to a neutral label, and a decision whose title scrubs to nothing is
  refused. The phone never receives reply text back. Snapshot, answers and
  pickups live in the [Mastermind store Worker](/build/devops/mastermind-store)
  for 14 days; snapshot reads may lag a publish by up to five seconds.
- **Storage failure:** without a configured store (or with the store stopped,
  over budget or unreachable) every fleet route answers 503 and the phone
  keeps its last snapshot with the Couldn't refresh warning.
- **Freshness:** the publisher sends on change and at least every two minutes.
  The phone polls every 15 seconds while a fleet tab is in the foreground and
  on pull-to-refresh, shows `Updated <age>` from the receive time, and warns
  once the snapshot is more than five minutes old.
- **Runbook:** store the secret in Vercel production as
  `MASTERMIND_FLEET_PUBLISHER_SECRET` and on the orchestrator Mac in
  `~/.local/share/fleet-sync/publisher-secret` (mode 0600, at least 32
  characters). Optional `~/.local/share/fleet-sync/config.json` sets
  `machineLabel`, `machineId` and `orchestratorTitlePattern` (default
  `^\[Iris\]`). launchd job `com.skora.mastermind-fleet-publisher` runs the
  installed copy in `~/.local/share/fleet-sync/bin/` (`publish.mjs`,
  `fleet-state.mjs`, `peer-lanes.mjs`, `scrub.mjs`, `decision-extras.mjs`,
  with the source commit in
  `SOURCE_SHA`) as `node publish.mjs --origin https://tuturuuu.com` with
  `StartInterval` 30. Update it only after Web from the same commit is deployed (an older
  Web accepts but drops the additions, so login requests would show as
  plain asks), by copying those five files from `main` and
  running `launchctl kickstart -k gui/$(id -u)/com.skora.mastermind-fleet-publisher`.
  It logs counts only, plus per-machine status and lane counts; failures log
  the HTTP status in `logs/publisher.err.log`.
- **Mobile surfaces:** Today shows a health hero (open decisions, then
  failures, then running work), Running/Waiting/Queued/Failed/Idle tiles that
  open Work filtered (`?state=`), up to three open decisions and every machine.
  Inbox lists open decisions most urgent first with Approve (the selected or
  recommended option), Hold and Reply (a sheet on the root navigator), then
  answered ones with their pickup status; a failed send offers Retry with the
  same key. Work groups lanes by machine or provider (`?group=provider`) and
  filters by state. Work holds the dock slot alone; the hub Threads preview,
  the hub Needs-you asks and the decision journal are no longer routed from
  these tabs.
- **Regression coverage:** `apps/web/src/app/api/v1/mastermind/fleet/fleet-routes.test.ts`,
  `apps/web/src/lib/mastermind/fleet/contract.test.ts`, `apps/web/src/lib/mastermind/fleet/login.test.ts` (login URL allowlist, codes, terminal states and the publisher mirror), `scripts/mastermind-fleet/decision-extras.test.mjs`,
  `apps/web/src/lib/mastermind/fleet/store.test.ts` (revisions, retries,
  pickups and racing answers), `apps/web/src/lib/mastermind/store.test.ts`
  (store resolution and push-event claims),
  `apps/mastermind-store/src/*.test.ts`, `scripts/mastermind-fleet/*.test.mjs`
  (`fleet-state.test.mjs`: per-machine lanes and counts, the lane cap order;
  `peer-lanes.test.mjs`: heartbeat classes, priority paging, malformed
  replies, deadlines, credential and address checks; `publish.test.mjs`:
  decision clipping and rejects, linked machine lanes end to end;
  `scrub.test.mjs`: parity with the Web scrubber),
  `apps/web/src/lib/mastermind/fleet/publisher-output.test.ts` (worst-case
  publisher output through the real edge guard, contract and body cap) and

## Fleet command center on mobile

Today and Inbox are the phone's command center over the fleet snapshot. They
use the shared Sorbet-aware kit (`AppSummaryHero`, `AppStatTile`, `AppCard`,
`AppRichRow`) inside the Mastermind shell: one top title, the floating dock
owns Back, and every list reserves the dock clearance. Code lives in
`apps/mobile/lib/features/mastermind/fleet/`.

- **Feature header:** every snapshot read sends
  `x-mastermind-fleet-features: login`, so Web includes access requests.
  The parser stays tolerant per entry: a login request whose payload does
  not parse is dropped rather than shown as an ask, as is an open one
  without a safe https link, an expiry or (device flow) a code, and an
  unknown answer channel or release part is omitted.
- **Today:** the hero headline keeps the most pressing fact (decisions
  waiting, failed lanes, running lanes or a quiet fleet). Under "What's
  happening now" it composes a digest only from snapshot fields: running and
  failed lanes, the main freeze with its reason and queue, production down or
  degraded, open incidents, and each open login as "<service> on
  <machine>". Four figures follow: running lanes, need you, blocked on login
  and failed lanes, each opening Work or Inbox. The release strip (main,
  production, migrations, incidents) appears only when the snapshot carries
  `release`, and shows only the parts it reports. Spend is not shown: the
  snapshot carries no cost data. The machines list follows.
- **Settings:** there is no per-tier Mastermind notification setting to back
  a preferences screen, so none is shown; push follows the account push
  preference (see Push notifications).

### Fleet Inbox

- **Tiers:** Urgent (`urgent`), Access requests (every open login request,
  whatever its urgency, because it blocks work), Needs a decision (`high`
  and `normal`) and For your information (`fyi`), then Snoozed and Answered.
  "Nothing needs you" shows when no open card is left after snoozes. A login
  request that has ended stays in Access requests with its state but no
  longer counts toward Need you and cannot be snoozed; one answered with
  "I signed in" still counts as blocked on login until the agent verifies
  it.
- **Ask cards:** age and a deadline countdown ("Due in 19:00" under an hour,
  "Due in 2 h 5 min" beyond it, "Past deadline" after it), the title and
  body, then Why, If no answer and From rows when the publisher sent `why`,
  `defaultOutcome` and `requester`. With a recommended option the primary
  button answers it in one tap; More reveals the other options and Hold.
  Without one, the options, Approve and Hold show directly. Reply and Snooze
  are always offered.
- **Undo:** an answer waits five seconds ("About to send") before it is
  posted, and Undo in that window drops it unsent, even when a poll brings
  another device's answer meanwhile: the card keeps its place and this
  device's own submission (waiting, not sent or closed) shows over the
  other receipt until it settles. A queued answer to a decision another
  channel closed meanwhile, or to a login request that ended, is dropped
  unsent. A login request that has ended
  offers no Retry. After posting, Web keeps every answer
  as a revision, so there is no later undo.
- **Snooze:** 15 minutes, 1 hour, 08:00 the next day in Mastermind time
  (UTC+7) and, while it is more than five minutes away, until 5 minutes
  before the deadline. A snooze hides the card on this device only; the
  decision stays open for the fleet. Snoozes are stored on the device per
  signed-in user as decision ids and wake times (no titles), are bound to
  the account that read or made them (nothing is read or written while
  signed out, and a read or change finishing after an account switch is
  dropped; a failed storage read writes nothing until a read succeeds),
  survive app
  restarts, and are pruned once they pass or the decision closes. The toast
  confirms only an applied snooze; when the device's snoozes cannot be read
  it says "Couldn't snooze on this device" with Retry. The confirmation
  offers Undo, the Snoozed row offers Show now, and a card returns on its
  own when its time passes.
- **Answered:** answers given here show their pickup status. Decisions in
  `resolved` show where the answer came from ("Answered on WhatsApp",
  "Answered on Mastermind", "Answered on mobile", "Answered in the CLI",
  or "Closed" without a channel) with the chosen outcome. A 409 from Web
  marks the answer "This request has already closed" without Retry and
  refetches the snapshot.

### Access requests

- **Card:** "<service> on <machine>", the request title, its state badge,
  the expiry countdown, and Why and From rows.
- **Flows:** a `device` request shows its code in large mono type with Copy
  (a toast confirms; the code is never logged) and opens the link. A `link`
  request only opens the link. A `local_callback` request shows "Finish on
  <machine>" and offers no link, because the sign-in completes only in a
  browser on that machine. Links open through the app link launcher, which
  honors the device browser preference; the app keeps a link only when it is
  https with a host and no credentials.
- **States:** Waiting for you, Checking sign-in (`approved`), Verified by
  agent, Expired and Sign-in not detected (`failed`). I signed in posts the
  `signed_in` answer while the request waits; the agent still verifies it,
  so the code and the provider link stay on the card while it is open and
  only the answer controls give way to the answer line.
  When the countdown reaches the expiry the card reads Expired on the
  phone's own clock and drops the code, the link and I signed in, even
  before the next snapshot.
- **Regression coverage:**
  `apps/mobile/test/features/mastermind/fleet/fleet_login_card_test.dart`
  (code, Copy, the link launcher, local callback, `signed_in`, closed,
  countdown to expiry, every state, Sorbet light and dark),
  `fleet_inbox_snooze_test.dart` (snooze hide and return, toast Undo, Show
  now, answer Undo, tiers, context rows, resolved channel, Today digest and
  release strip) and `fleet_contract_test.dart` (parsing, the feature
  header, `signed_in`, 409 as closed, the undo window, per-user snooze
  storage).

## Native Worker live admission

The native Mastermind Worker also reads `GET /api/v1/mastermind/access` on every
request that passes its Access JWT, app session, and owner allowlist checks.
It forwards only the verified Mastermind app-session bearer token to the fixed
web endpoint, with caching disabled, redirects refused and a five-second timeout.
The endpoint accepts the `mastermind` audience with `internal-app:session` scope
and resolves the principal's root-workspace permissions afresh. Existing mobile
session access and the rollout rule below remain unchanged.

Revoking the active root permission denies the next Worker request without
changing its environment or waiting for its owner data memo to expire. An API
error, timeout, non-200 status or invalid response also denies access. The
endpoint must be deployed before adopting the Worker follow-up; an older endpoint
without the app-session opt-in denies the Worker. Regression coverage lives in
`apps/mastermind/src/native/auth.test.ts` and the emitted-Worker runtime smoke.

## Offline preparation

The default-off `offline_read_mastermind` flag registers the existing signed
snapshot flow with mobile offline preparation. Downloads verify that the
existing store can reopen the accepted snapshot; rejected exports, access loss,
and failed persistence do not count as ready. The section shows the stored
receipt time as Last synced while this flag is on. Flag-off reads retain their
existing behavior. Coverage: `mastermind_offline_preparation_test.dart`,
`file_snapshot_store_test.dart`, and the existing hub header/freshness suites.

## Who sees it

- **Scope:** the Apps hub offers Mastermind when the active workspace is the
  root workspace or the user's personal workspace, Web's
  `GET /api/v1/mastermind/access` answers `enabled: true` (root
  `manage_mastermind` once the rollout flag is on; see Access rule and
  Rollout), and the build has a hub source configured. Production, staging and any build with
  `MASTERMIND_HUB_URL` have one; see Data source. The personal workspace shows
  the same fleet data; nothing in Mastermind is workspace-scoped.
- **Default:** hidden. It is not an experimental module and cannot be enabled
  from Settings. A user the access answer denies, in any other workspace, or
  while access is loading or failed never sees the entry.
- **Authority:** this check is cosmetic. The server-side gates in Access rule
  decide, and a 403 from the hub hides the entry until the next access sync.
- **Production beta:** the production app reads the hub for the beta behind
  these gates: root or personal workspace plus the access answer, a
  configured source, and the hub's owner allowlist. Replies stay off until the
  hub's `GET /v1/capabilities` reports `replies: true`. Production reports
  `replies: false` today, so the Inbox is read-only there and the reply composer
  stays hidden; turning replies on needs no store release.
- **Deep links and push taps:** any `/mastermind/**` location is held on a
  neutral skeleton while the access check runs, then redirected to the Apps hub
  unless access is loaded and enabled. A 403 keeps the user on the screen so it
  can explain itself; the entry disappears from the Apps hub.
- **Account changes:** logout and account switch erase the cached snapshot,
  memory and disk, and re-check access for the selected workspace.
- **Access errors:** a failed access check hides the entry, so it is re-run when
  the app resumes and when the Apps hub is pulled to refresh; neither blinks a
  healthy entry while it checks.

## Access rule

Mastermind is restricted to one person, the platform owner account, through the dedicated workspace permission `manage_mastermind`.

- **Scope:** every Tuturuuu-owned surface that serves Mastermind data or
  actions: the mobile entry and its `/mastermind/**` routes, and
  `POST /api/v1/mastermind/push-events`. The mobile app reads snapshots and
  sends replies to the external hub Worker (`mastermind-hub.tutur3u.com`)
  directly; Tuturuuu serves no other Mastermind API.
- **Default:** deny. Migrations `20261030113000_manage_mastermind_enum` and
  `20261030113001_manage_mastermind_grants` add the permission with no grants; the owner grant is a separate, later
  change that needs an explicit GO (see Rollout). Unlike every other permission it is never
  implied by being the workspace creator, by `admin`, or by a default
  permission, and it counts only as membership of the one root role the grant
  procedure created. Database triggers reject enabling it as a default
  permission, in any other workspace or on any other role, and enabling it or
  adding a member to that role from an API session (anon, authenticated,
  service role). Re-saving an unchanged role and disabling or deleting grants
  stay allowed. The web and mobile role editors omit it from their catalogs,
  and every role write from either client (create, update, default
  permissions) strips it, even for the workspace creator. CMS external-project team role creation, role updates and default-permission writes apply the same filter; `team-access.test.ts` covers enabled, disabled and explicit-only payloads.
- **Granting:** for API sessions, only
  `private.grant_mastermind_access(user_id, reason)`, which the database owner
  alone may execute; a database-owner session is fully trusted and could also
  write the rows directly, without an audit row. The grantee must be a root
  `MEMBER` (not a guest). On first use the procedure creates its own root
  `Mastermind` role and records the id in `private.mastermind_access_role`;
  it never looks a role up by name, so renaming or creating another
  `Mastermind` role selects nothing. It refuses (raises) when the recorded role
  has a member other than the grantee or any permission row besides
  `manage_mastermind`, so at most one person holds it; revoke the current
  holder before granting another. API sessions cannot rename, re-date, move or
  delete the recorded role, add another permission to it, or add a member; the
  creator-grant guards still apply to it. It is idempotent and writes every call
  to `private.mastermind_access_audit`. `private.revoke_mastermind_access`
  (also database owner only) removes the user from the recorded role the same
  way. Running a grant in production is a production write that needs an
  explicit GO.
- **Enforcement points:** the flag switches the Web, push and mobile
  Mastermind gates. Database and Web-helper explicit-grant semantics always apply:
  - Database: `public.has_workspace_permission(ws, user, 'manage_mastermind')`
    is true only for an explicit root role grant.
  - Web helpers: `getPermissions().containsPermission('manage_mastermind')`
    (`packages/utils/src/workspace-helper.ts`) ignores creator, admin and
    default permissions for explicit-grant permissions
    (`packages/utils/src/explicit-grant-permissions.ts`).
  - Push events: each recipient must be in `MASTERMIND_PUSH_OWNER_IDS` (kept as
    defence in depth) and, with the flag on, hold root `manage_mastermind`; an
    unreadable answer skips the owner.
  - Hub: the external hub Worker enforces its own one-UUID owner allowlist on
    the requests the app sends it. That allowlist lives in the hub repository,
    is not changed here, and must name the same account.
  - Mobile: the access cubit shows the entry only when
    `GET /api/v1/mastermind/access` answers `enabled: true`; Web picks the
    rule, so a store build never decides it. Offline, the cubit reuses that
    user's last server answer. This hides the entry only; it is not
    authorization.
- **Exceptions:** none. Provisioning the recipient in the push allowlist and
  the hub allowlist is separate from the grant and must name the same user.

Migrations `20261030113000` and `20261030113001` grant the permission to
nobody. Separate migration `20261030120000_grant_mastermind_owner.sql` grants only root's creator through `private.grant_mastermind_access`. Missing root, null creator, missing auth account or root MEMBER membership produces NOTICE without a grant. After seed, the database owner may idempotently run `SELECT private.grant_mastermind_root_creator();`. Production writes require explicit approval. Before the production sync, an operator checks read-only that the creator exists in auth.users and is a root MEMBER, reporting names only. Rollback `20261030120000_grant_mastermind_owner.rollback.sql` uses audited revoke provenance, preserving later intentional operator grants. Missing provenance revokes nothing. Bootstrap coverage: `manage-mastermind-owner-grant.sql`; actual rollback coverage: `apps/database/scripts/mastermind-owner-rollback-test.py`.

- **Regression coverage:** `apps/database/supabase/tests/manage-mastermind-permission.sql`
  (no role, default permission, member or creator holds it after the
  migration; creator and admin do not imply it; every guard; the audited,
  idempotent grant and revoke),
  `apps/database/supabase/tests/manage-mastermind-role-binding.sql` (root and outside-root pre-seeded, renamed,
  older or staged `Mastermind`-named role is never selected; the recorded role
  is root-owned, holds only `manage_mastermind` and cannot be edited outside the

  refused),
  `packages/utils/src/__tests__/workspace-helper-explicit-grants.test.ts`,
  `packages/utils/src/__tests__/permissions.test.tsx` (absent from the web role
  catalog), `roles/route.creator-grant.test.ts`, `roles/[roleId]/route.test.ts`
  `roles/form/permission-payload.test.ts` and
  `workspace_role_permission_payload_test.dart` (every role write strips it,
  even for the creator; neither catalog lists it),
  `api/v1/mastermind/access/route.test.ts` (flag off and on),

Removing the member or disabling the role's `manage_mastermind` row removes
access immediately (fail closed); the recorded role itself cannot be deleted.
The migration rollback removes the role, its members and its record, so a
re-apply admits nobody. Restoring access requires the database owner to call
`private.grant_mastermind_access(user_id, reason)` again; ordinary role edits
cannot re-grant it. Role saves from web and mobile write permissions before the
name, so a rejected permission save leaves the name unchanged.

## Rollout

Production applies migrations only after the deployment marker, so Web and a
store build can be live before `manage_mastermind` exists there. Enforcement
therefore waits for a server-side switch that defaults to the earlier rule.

- **Scope:** `MASTERMIND_REQUIRE_EXPLICIT_GRANT` on Web, read by
  `apps/web/src/lib/mastermind/access.ts`. It drives
  `GET /api/v1/mastermind/access` (the mobile entry) and the push-events
  permission check.
- **Default:** off (unset or anything but `true`). The access answer is root
  `view_infrastructure` (creator and admin imply it), and push events go to
  every `MASTERMIND_PUSH_OWNER_IDS` owner without a permission lookup: the
  behaviour before `manage_mastermind`. On, the answer is root
  `manage_mastermind` and push recipients need it too.
- **Grant:** `20261030113001` grants nobody, so a local reset, CI pgTAP and
  staging apply unchanged and, with the flag off, nobody is locked out. The
  owner grant ships separately, after an explicit GO.
- **Exceptions:** none. The hub Worker's owner allowlist is separate and does
  not read the flag.

Flip procedure:

1. Merge and let the gated production migration workflow apply
   `20261030113000` and `20261030113001` for the exact SHA.
2. After the separately approved owner grant, read back exactly one holder, the
   owner, with this read-only query as the database owner. Any other result
   means do not flip; fix the cause and grant with
   `private.grant_mastermind_access` after an explicit GO. This query is the
   only way to see who holds the permission: the web role editor never lists
   it, and no RPC or route returns holders. `private` is revoked from anon,
   authenticated and service role, so run it only from a database-owner
   session (SQL editor or `psql`); `private.mastermind_access_audit` records
   every grant and revoke with its reason.

   ```sql
   select count(distinct wrm.user_id) as holders, array_agg(distinct u.email) as emails
   from private.mastermind_access_role mar
   join public.workspace_role_permissions wrp on wrp.role_id = mar.role_id
   join public.workspace_role_members wrm on wrm.role_id = mar.role_id
   join auth.users u on u.id = wrm.user_id
   where wrp.ws_id = '00000000-0000-0000-0000-000000000000'
     and wrp.permission::text = 'manage_mastermind'
     and wrp.enabled;
   ```

3. Set `MASTERMIND_REQUIRE_EXPLICIT_GRANT=true` on every runtime serving Web
   and redeploy. In new app builds, everyone else loses the entry on the next
   access sync. Older builds rely on the hub allowlist denial.

Rolling back is unsetting the flag (earlier rule again); the grant can stay.
## Data source

Fixture builds (development flavor with `MASTERMIND_FIXTURE`) read the bundled
synthetic sample. Staging reads `<hub-staging-host>.tutur3u.com`, production
reads `mastermind-hub.tutur3u.com`, and any build reads `MASTERMIND_HUB_URL`
when it is set; an explicit value always wins over the flavor host, and a bad
one never falls back to it. A build with neither (development without a
fixture, an unknown flavor) stays disconnected, as does any value that is not
a bare HTTPS origin: no credentials, path, query or fragment, so the bearer
token never leaves over cleartext or to a lookalike host. The app-level runtime owns
the source, the cache and the refresh scheduler and closes them with the app.
Each Mastermind screen only attaches to and detaches from the scheduler, so
refresh runs only while a screen is open and the app is in the foreground. It
also runs at once when the app returns from the background (`hidden` or
`paused`); a brief `inactive` blip such as Control Centre or a biometric prompt
is not a resume and fetches nothing. The scheduler follows device connectivity,
and the freshness line (Offline versus Couldn't refresh) updates when
connectivity alone changes.

## Tabs

Home, Inbox, Work, Ship and Insights share one mini-app shell: the top navbar
shows the destination title and no Back button, and the floating dock owns Back.
Every tab sits behind the same access gate and freshness strip. Work is planned
to become Threads (Home · Inbox · Threads · Ship · Insights); until the hub
serves threads it shows today's lane list.

In-screen views (Needs you | Decisions, Lanes | Backlog | Staff) use the compact
`MastermindSegmentedControl`: a 32 pt track whose segments each own a 44 pt hit
area, instead of the tall pill. When the segments cannot fit across at the
current text size they stack into full-width 44 pt rows with a check on the
selected one; the control never becomes a hidden horizontal scroller and labels
are never truncated. List search uses `MastermindCollapsibleSearch`:
hidden until the navbar search icon is tapped, kept
open while a query is applied, folded away once cleared and unfocused. Every
sheet opens on the root navigator so the floating dock never covers it.

## Freshness strip

Each tab starts with one short line inside the scroll view. Data age is
informational because publishing is manual at first; only a failed refresh or a
degraded source is a warning. The visible line carries an age or a short GMT+7
time (with the day once the data is 20 hours old); screen readers hear the full
sentence with the absolute GMT+7 date and time.

| Condition | Visible line |
|---|---|
| Published within 5 minutes | Updated `<HH:mm>`, on Home only |
| Older | Published `<age>` |
| Refresh failed and the device has no connection | Offline · showing `<time>` |
| Refresh failed while the device is online | Couldn't refresh · showing `<time>` |
| Hub schema newer than the app | Update the app to read the latest Mastermind data · showing `<time>` |
| Hub answered something unreadable | Couldn't read the latest update · showing `<time>` |
| Any source not ok | appended: `<n>` sources degraded |

Healthy, fresh data hides the strip on every tab but Home. A warning tints only
the glyph and a 3 pt leading bar; the text stays foreground so it keeps 4.5:1
contrast in light mode. The line ellipsizes at normal text sizes and wraps past
130%. It is a live region only while it is a warning. With degraded sources it
is a 44 dp row with a chevron that opens the "Sources" sheet: every source the
snapshot reports, degraded first, each as a glyph, a name and a state word.
Home also has a "Data sources" navbar action that opens the same sheet.

| State | Shown |

| Loading, nothing held | Skeleton cards, never a spinner alone |

### Catch-up

Scope: Mastermind mobile, top of Today. It renders only when the snapshot
carries a `catchup` object; no `/v1/catchup` route exists and the app calls
none. Everything is optional on the wire, unknown enum values are tolerated and
the parser never rejects the snapshot (`catchup/catchup_parser.dart`).

- **Contract.** `catchup { generated_at, window_start, coverage
  ok|partial|stale, products[{slug,name}], counts{needs_you,shipped,blocked,
  changed}, sections[{key, items[{id, kind, title (80), product|null, at,
  importance, link{label,url}|null, entity{kind,id}|null, neutral, reason?,
  owner_name?}]}] }`, at most 20 items per section and 100 in all, enforced
  again by the parser.
- **Window.** Default is since the last visit (rendered-time marker kept per
  device in local preferences); the first visit shows 24 hours. A visit ends
  after 30 minutes without a render, so tab switches keep the window. Items are
  filtered by `at` on the client. "Show N earlier" widens to 24 hours and draws
  a "New since your last visit" divider where the new rows end in each product
  group. Hub `counts` are used while nothing is filtered out; otherwise the
  counts line is computed from the visible rows.
- **Sections and groups.** Needs you, Shipped, Blocked, Changed, Usage & health,
  each grouped per product (hub name, else the slug) under collapsible headers
  whose state is remembered for the app session. Blocked rows show the reason
  and who is on it.
- **Taps.** `ask` opens `/mastermind/inbox/item/:id`, `lane` opens
  `/mastermind/work/lane/:id`, `env` and `release` open Ship, `usage` opens
  Usage. Otherwise the link opens in the system browser, only for `https`
  `tuturuuu.com` or `*.tuturuuu.com`; any other URL is dropped at parse time. A
  row with neither is not tappable.
- **Neutral items** render "Security update" with no product, title or link;
  the parser keeps only their kind, time and importance.
- **Times.** Relative with the clock glyph (`now`, `12m`, `2h 13m`, `3d`);
  long-press or a tap on the glyph shows the absolute time in
  Asia/Ho_Chi_Minh.
- **States.** First run, quiet, "Some updates may be missing" for partial or
  stale coverage (or a hub window that starts after the view's), offline or
  failed refresh from cache with the age line.
- **Catch me up** and pull-to-refresh refetch the snapshot (no LLM) with
  progress, an "up to date" confirmation and a failure message.
- **Morning catch-up** (Today navbar, Catch-up settings): a local toggle and
  time. The push body is the fixed line "Your catch-up is ready" with no
  content. There is no app quiet-hours setting yet; the server must apply

### Decisions

### Replies

Replies are gated at runtime by `GET /v1/capabilities` (`replies`, with schema
`1.4`), checked when an Inbox screen opens and at most every five minutes.
Where replies are off, or the hub cannot be asked, the detail shows the options
read-only and "Reply on your Mac"; there is no composer. The Worker owns the
switch, so it flips without a store release.

- **Gate in code:** submit, retry and flush all refuse to send unless the hub
  says replies are on, not only the composer's visibility. Entries queued while
  replies are off stay queued: neither sent nor dropped, until capabilities say
  `replies: true` again. Coming back online re-asks the hub before flushing.
- **Known answer kept offline:** a known "supported" answer survives a failed
  re-check. Going offline never flips it, so the outbox keeps working with no
  connection; only an answer from the hub turns replies off: `replies: false`
  from the capabilities check, or a 403 `replies_disabled` on a send (any other
  403 is a lost-access refusal, handled like a 403 on the snapshot).
- **One check at a time:** overlapping capability checks, forced or not, share a
  single request, and a reply sent during the first-ever check waits for its
  answer instead of being refused. Connectivity changes are de-duplicated, so
  several interfaces flipping together cause one re-check and flush.

- **Contract:** `POST /v1/replies` with exactly
  `{schema_version: "1.4", item_id, version_hash, option_index | text}`: one of
  an option index (into the item's own `options[]`) or free text of at most 500
  characters, counted in code points, and at most 10 lines (the hub's limit; the
  composer caps both as you type). An option sends its index after a five-second
  undo window (see Undo window below).
  The text field has a placeholder and a counter; free-text sending requires
  confirmation.
- **Idempotency:** the `Idempotency-Key` is a random v4 UUID from a secure
  generator, made once per reply and stored in the outbox before the first send.
  Every retry reuses it, so an unknown outcome never becomes a second reply. A
  200 replay is treated exactly like 201. One reply per question version.
- **Offline outbox:** a reply that cannot be delivered (offline, timeout, 5xx)
  stays queued on the device, per user, in the snapshot cache directory, and is
  sent again when an Inbox screen opens, when the app resumes and when the device
  comes back online. It can be retried or discarded. Entries expire after seven
  days and are dropped when a live snapshot no longer has the item open. Queued
  replies live in the OS cache directory, not the documents directory: that
  keeps them out of device backups, at the cost that the OS may purge the cache
  under storage pressure and silently lose a queued reply. We accept that
  trade-off, because a reply is short-lived and a lost one is re-asked; a reply
  already accepted by the hub is unaffected. Logout,
  account switch and lost access erase the outbox with the snapshot cache, behind
  the same generation fences, so an in-flight send cannot revive it.
- **409 `stale_item`:** refreshes the item; see the [answered elsewhere rules](/platform/features/mobile-mastermind-answered-elsewhere).
  Options always use the current question version. `idempotency_conflict` drops the queued entry with "Something went
  wrong with this reply. Review it and send it again."
- **Other answers:** 400 (`unsafe_text` explains the text policy) and 413 keep
  the words to edit; 429 waits out `Retry-After` and disables the retry until
  then; 403 `replies_disabled` hides the composer and 403 `forbidden` is lost
  access.
- **401:** the reply stays queued. The first failure offers "Try again"; only
  after a repeat does "Sign out and sign in again" appear, and it asks first,
  because signing out removes every saved account on the device.
- **Waiting rows:** the Inbox shows "N replies waiting to send" while replies
  are queued; with exactly one, the row opens that item. A queued reply binds to
  its item id and `version_hash`, so a reply to an older version of a question is
  never shown as the answer to the current one. A 429 counts down on its own and
  re-enables "Try again" when `Retry-After` has passed.
- **Search:** it never matches the "Reply on Mac" placeholder option.
- **Accessibility:** the reply status line is a live region, and the character
  counter has a spoken label ("12 of 500 characters used").

Delivery status beyond "Sent · waiting for Mastermind" (the item leaving the
next snapshot) is not polled yet.

## Work

The Work tab has three segments, a segmented control under the freshness
strip: **Lanes** (the default), **Backlog** and **Staff**. Lanes lists lanes
grouped by state, the one that needs attention first:
failed, waiting, running, queued, idle, stale, completed, cancelled, then the
rare open, answered, withdrawn and unknown. Each group shows its count and is
ordered oldest first, a lane with no age last. A row shows the title, role and
provider/model (display text, shown verbatim), "Running for 2 h" (or
"Running · age unknown"), "About 20 min left" only when there is an estimate,
and product, area and kind chips. State is always a glyph and a word.

- **Filters:** a search field ("Search lanes"), one chip per state, and product
  and area chips while two or more of each are present. A state chip's count
  follows the product, area and search filters, so it always matches its group
  header. A product or area filter resets when its value leaves the snapshot,
  because its chip would be gone.
- **Segment and filters in the URL:** the segment lives in the location as
  `?segment=backlog` or `?segment=staff` (Lanes is the bare tab, and an unknown
  value reads as Lanes), beside the lane filters `?state=`, `?product=` and
  `?area=`. Every segment or chip change rewrites the location with `go`, so
  Back never walks through segments. The lane filters stay in the URL on the
  other segments, so switching back to Lanes finds them. The Home lane chips
  open `/mastermind/work?state=<state>`. An unknown value is ignored and "All"
  clears the state. A lane opens by push, so Back from it (the dock included)
  pops to the same filtered list, search text and all; the shell pops a lane
  location instead of falling back to the bare tab root. External deep links
  open the tab root and never carry a segment, filter or lane id.
- **A filter that leaves the snapshot leaves the URL too:** when a product or
  area filter resets because its value is gone, the location is rewritten
  without it once the frame is built, so a later visit to that location does
  not bring a stale filter back. Filters that are still valid stay.
- **No matches:** a filter combination with no lanes (including a state with
  none) shows "No matching lanes" with a "Clear filters" row that resets state,
  product, area and search.
- **Backlog:** `backlog[]` grouped by product (the item count in each group's
  header), open before answered before withdrawn, in the publisher's order
  within a state. An item with no product sits last under "No product". Each row
  is a title and a state glyph and word; it has no tap target, and its opaque id
  is never shown. The search field ("Search backlog") matches the title and
  product and is local to the segment. An empty backlog reads "Backlog is
  clear" and hides the search; no match reads "No matching backlog items".
- **Staff:** `observability.staff[]`, which is `{role, title, state, model}`
  and nothing else. Rows sort by the Lanes state priority and then by role,
  case-insensitively, never by activity. A row shows the title, the role and
  model (display text; the literal `unknown` reads "Unknown model") and a state
  glyph and word. A summary caption reads "11 roles · 4 running". Staff has no
  search, filters or sort control. **Privacy rule:** the screen never shows or
  derives a last-active time, a runs-today count, an "active today" label or
  any activity ordering; the hub does not publish them, and a change that adds
  one must be reviewed as a privacy change. An empty list reads "No staff roles
  reported."
- **Security rows** keep the Home rule on Lanes and Backlog: one non-tappable
  line in a trailing "Security" group with no count, never counted, searched or
  filtered. Staff has none, because the hub omits security roles.
- **Detail:** `/mastermind/work/lane/:laneId` shows the same fields in full and
  has no action. The id is an opaque snapshot id and only ever a route
  parameter. An id that is not in the snapshot shows "This lane is no longer in
  Mastermind" (or "This lane finished or was removed" when it left while open)
  with a way back, never an error. A lane whose state changed while open shows
  "This lane was updated".

## Ship

`/mastermind/ship` is read-only. It lists, under the freshness strip:

- **Environments by product.** A product with a failing environment (deploy or
  CI `failure` or `error`) comes first, then the rest by most recent release,
  then by name. Each product is one compact card. Its header row carries the
  name, "Live 2 h ago" with the age basis (left out when the age is null, never
  "Unknown" or 0) and, when failing, a destructive glyph and a "Failing" badge.
  Production comes before staging. An environment row shows deploy and CI as a
  glyph and a word, and its own `freshness` as a chip only when it is not fresh
  (it never follows the snapshot's age). Then come the version and the commit id
  (monospace, with a 44-pt copy button; it is a public commit id), and one muted
  line with the subject, "Released 2 h ago" and "Checked 30 min ago" measured
  from the snapshot time. The absolute GMT+7 release and check times and the
  evidence label are in the row's semantics label. A reading the hub did not
  publish is left out, while one it could not read keeps its reason, for
  example "Deploy Not connected · Last checked 19:22". The publisher's stand-in
  subject for a commit it will not send is shown as the localized label
  "Withheld, open on Mac", muted with an info glyph and the tooltip "Details
  stay on the Mac". A failing environment on Home opens Ship on its product, and
  its row carries a chevron like the release rows.
- **Not tracked yet.** A product with no release age whose every environment has
  deploy, CI, freshness and evidence `unknown` and no release time, version or
  commit id gets no card. All such products share one final "Not tracked yet"
  row that names them ("Product A, Product B"). Tapping it lists each with the hub's
  reason ("Not connected · Last checked 19:22") or "No deployments observed".
  The row is hidden while a product filter is on, and these products get no
  filter pill.
- **CI now.** `observability.ci[]`, queued and running per repository. A null
  count reads "Unavailable", never 0.
- **Release cadence.** Most recent production release first; a product with none
  reads "No production release observed" and sits last. The caption carries the
  row count, and the list shows five rows with "Show all N" for the rest.
- **Pull requests and merges.** From `observability.delivery`: the latest open
  pull request count and merge-to-live median per product, and "At least N
  production releases observed" (a lower bound). A null count reads
  "Unavailable"; a delivery source with no coverage says so once and shows no
  numbers. Nothing on this tab opens a pull request, merges or syncs anything.
  The schema carries no separate sync record, so production sync is only
  visible as the release age and cadence above.
- **Product filter in the URL.** One horizontally scrolling pill bar (All, then
  the tracked products in list order, failing ones marked with a warning glyph)
  appears while two or more tracked products are present. It never wraps and
  writes `?product=<product>` with `go`. A product the snapshot lacks
  is shown unfiltered at once and removed from the URL after the frame, but
  only while Ship is the top route: a rewrite is a `go`, so one that fired under
  an open route would drop it. External deep links open the tab root.

Ship shows no security rows, ids or digests.

## Insights

`/mastermind/insights` is the Usage view (the Fleet, Models, Coordination and
Delivery sections arrive later and reuse the table route below).

- **Pools** come from `observability.usage.instances[]`, most urgent first:
  SHORT, then unknown pacing, then OK, then SURPLUS, then the least session
  budget left, then label. A pool's pacing is the worse of its session and
  weekly windows, so a weekly SHORT outranks a session that is fine. Pool labels
  are opaque display strings, shown verbatim and never summed or stacked.
- **Pool card.** One pacing verdict per pool, as a shape and a word: "Running
  short", "On pace", "Surplus", or "No pacing data" (a static hollow square, not
  the dashed outline that read as a spinner). The verdict is the worse of the
  windows that report pacing, so a window without pacing does not hide the
  other's. Under it, one muted line gives the burn and the signed projection at
  reset for the window the verdict comes from. An info button opens the
  "Reserve pacing (chart rule)" note saying it is not the routing decision.
  Then "Session left" and "Weekly left" each show a meter toned by that
  window's pacing, the percent and the reset ("Resets 17:10", with the day when
  it differs from the reading's). A window the hub did not read shows a dash
  and its reason ("Not connected · Last checked 19:22"), never 0.
- **Contradiction guard.** Scope: the pool card's burn line. Default: when the
  verdict window is SHORT and its burn is 0 pp/h or less, the line reads "Burn
  not measured yet" instead of "0 pp/h", because a pool that burns nothing
  cannot run short and the hub reading is partial. Exceptions: a zero burn on an
  OK or SURPLUS window is shown as measured. Coverage:
  `presentation/ship_usage_model_test.dart` ("a zero burn next to SHORT") and
  `mastermind_insights_compact_test.dart`.
- **Charts** use the shared chart kit: one panel per pool (session solid,
  weekly dashed, a fixed 0 to 100 percent axis, a reset marker when it falls in
  range), and for each Codex pool in `usage.credits[]` a balance panel and a
  burn-against-target panel. "Credits" is a unit of its own, never money or
  tokens; a null daily target reads "Target unavailable". Each panel's header
  holds its title and the Table action (a ghost button with an icon and a 44-pt
  target), so the action is never at the bottom of the card under the floating
  dock. A muted caption says what the plot leaves out ("Partial data: Weekly
  window not reported.", the gaps and their reasons). The plot's semantics label
  is the full text summary. The legend names only series with at least one
  reading, and a live readout follows. X-axis ticks show the GMT+7 time alone
  ("20:30"), adding the day ("Oct 28 05:45") only where the day changes and
  never on a chart within one day. With `usage.coverage` of `missing` or
  `unavailable` the plot is left out and the summary and coverage note stand
  in. With `partial` or `stale`, the caption and summary lead with the coverage
  word. A pool with no series shows the summary only.
- **Quota table** (`products.quotas[]`, including `Unknown account`), least left
  first and unknown last, with "as of N min ago" (left out when the read age is
  null). **Forecasts** (`quota_forecasts[]`): "Projected empty `<time>` GMT+7"
  soonest first, or "Not projected to run out before reset". Both captions carry
  the row count and show five rows with "Show all N" for the rest.
- **Chart table route.** `/mastermind/insights/:section/table/:chartId` is
  pushed over Insights and shows the same series rows the panel draws (a null
  cell reads "Unavailable"). The section is `usage` and the chart id is
  `budget:<pool>`, `credits:<pool>` or `burn:<pool>`; both are route parameters
  only. A chart the snapshot no longer has shows "This chart is no longer in
  Mastermind" with a way back, never an error. The shell pops this location on
  Back instead of falling back to the tab root.

## Product decisions

- **True activity counts.** Scope: Home tiles now; the lane list header and a
  Threads badge read the same `MastermindActivity` model. Default: running,
  waiting and idle come from the hub's `work.counts` only when its status is
  `ok` and `checked_at` is within 15 minutes of the snapshot; stale/down
  readings fall back to the latest `observability.fleet.series` point when
  coverage is ok or partial and it is at most 15 minutes older than
  `generated_at`, else from lane states, captioned "From lane reports". Queued
  and failed always come from lanes; unknown or stale lanes are a "not
  reporting" footnote, never a headline. "On you" counts open decisions and
  actions, never FYI. Coverage: `presentation/activity_model_test.dart`,
  `view/mastermind_home_v1_test.dart`.
- **Friendly names.** Scope: every row and detail title. Default: the hub's
  `[Name] Role` title shows verbatim; a redacted `Product · area · kind` title
  is never shown: a lane uses its standing role, or "`<Product>` `<area>`" for
  a child lane; an item uses its real title or first ask line. Models shorten
  to "Sonnet 5.5" or "GPT-6.1 sol"; an unknown model reads "Model not
  reported". Coverage: `presentation/display_names_test.dart`.
- **No bare unknown.** Scope: Home now, Ship and Insights next. Default: a
  missing, blank or "unknown" reading renders a muted `—` (`ReportedText`)
  announced as "Not reported" plus the hub's reason; the word "unknown" never
  stands alone. Coverage: `view/mastermind_home_v1_test.dart`,
  `view/forge_v1_fixture_test.dart`.

- **Resolved is the hub's word.** Scope: Inbox rows, the item detail, the
  Resolved segment. Default: an ask reads "Resolved" only once the hub
  lists it in `decisions_resolved`; a reply this device sent reads "Sent ·
  waiting for Mastermind" (with its GMT+7 queued time on the detail) until then,
  never Resolved. Exceptions: an ask that leaves the snapshot without a history
  row reads "This was answered or withdrawn". Coverage:
  `view/mastermind_inbox_v1_test.dart` ("a sent reply reads Sent · waiting until
  the hub resolves", "a resolved ask shows the hub outcome").
- **Decisions journal.** Scope: the Inbox Decisions segment, the decision
  detail and Home's recent-decisions card. Default: the Inbox segmented control
  ends with Decisions, its segment in the URL; Home rows open the
  detail and "See all decisions" opens the segment. Exceptions: the journal is
  history and is not answerable; search and risk/area filters are not offered
  yet. Coverage: `mastermind_decisions_test.dart`,
  `mastermind_decision_page_test.dart`, the "Back from a decision" cases in
  `shell_peer_section_checks.dart`.
- **Offline reply queuing.** Scope: replies from the item detail, on every app
  surface that shows the "N replies waiting to send" row (Home and Inbox).
  Default: a reply that cannot be delivered stays queued on the device and is
  sent later instead of being refused. This is safe because each queued reply is
  bound to its item id and `version_hash`, and carries one `Idempotency-Key`
  reused on every retry: if the question changed meanwhile the hub answers 409
  `stale_item`, the item is refreshed, the typed words are kept and the user
  reviews it again, so a stale answer is never accepted as the answer to a newer
  question. Exceptions: replies off at the hub keep entries queued without
  sending, an entry expires after seven days or when the item leaves the open
  list, and logout, account switch and lost access erase the outbox. Coverage:
  `mastermind_replies_cubit_test.dart`, `mastermind_replies_gate_test.dart`,
  `reply_outbox_store_test.dart`.

## Push notifications

The web route `POST /api/v1/mastermind/push-events` (see the
[API reference](/reference/api-reference/mastermind-push-events)) receives
signed hub events and sends a mobile push to Mastermind owners.

- **Scope:** `needs_you.new`, `decision.awaiting` and `pin_batch.new` only.
  Recipients are the owners in `MASTERMIND_PUSH_OWNER_IDS` who hold root
  `manage_mastermind` (once the rollout flag is on), with a registered device
  and the account push preference on.
- **Copy:** always "Open Mastermind" (vi "Mở Mastermind") under the title
  "Mastermind". The event carries no title, product or text, so no item content,
  including security items, can reach a lock screen.
- **Tap:** `openTarget: mastermind` with the tab root (`/mastermind/inbox`, or
  `/mastermind` for pins), held by the same access gate as any deep link. The
  app navigates only when `route` exactly matches one of those two roots; any
  other or missing route opens the notifications screen, and a route from the
  payload is never followed otherwise. An item id is never in the push.
- **Rate:** at most one push per type per owner per minute; a burst inside the
  window is dropped, not queued, because the next snapshot shows it.
- **Retries:** successful owners are skipped for 24 hours per event, including
  partial retries after the coalescing window. Token-owned claims prevent stale
  requests from releasing newer claims. Fan-out stops after 60 seconds and
  returns 502 for unreached owners. Observed FCM success gets a bounded,
  best-effort receipt write before the deadline is honoured; receipt failure
  warns and still counts as sent. A retry inside a pending coalescing window
  remains failed and retryable until the outcome is confirmed or the window
  expires, rather than completing the event. Unstored receipts can allow
  duplicates after the window expires if another owner failed. These rules
  apply to the web push endpoint; mobile tap behavior is unchanged.
- **Default:** off until Release Desk provisions `MASTERMIND_PUSH_HMAC_SECRET`
  and `MASTERMIND_PUSH_OWNER_IDS`; without the secret the route sends nothing.
- **Regression coverage:**
  `apps/web/src/app/api/v1/mastermind/push-events/route.test.ts`,
  `apps/web/src/app/api/v1/mastermind/push-events/route.race.test.ts`,
  `route.delivery.test.ts` and, for the tap,
  `apps/mobile/test/features/notifications/push/mastermind_push_destination_test.dart`.

## Decision and usage metadata

Mobile accepts legacy scalar fields alongside Forge v1 field envelopes. Missing
values display “Not published yet”; connection and source failures retain their
explicit status. An accepted reply remains sent until a live snapshot closes its
stable item ID. Resolved items leave Needs you and can appear in Recently resolved.
Full asks use `ask_text` (up to 2000 characters); an absent full ask is stated on
the detail page. No mobile action can infer that the hub processed a reply.

Usage charts annotate timestamp gaps with published reasons (source failure,
account switch or quota reset). Without metadata they say “No samples published”.
A reset timestamp within an inferred gap supplies the reset reason. Pools remain
separate. Adapter and classification regressions live in
`apps/mobile/test/features/mastermind/presentation/hub_contract_test.dart`.

Optional resolved history is parsed row by row: invalid entries are skipped,
repeated IDs use their latest resolved entry, and the last 20 valid entries are
shown. Additive lane and staff metadata does not invalidate the snapshot; known
fields still receive strict validation. Native open items may supply `status`
without the legacy `state`. Checked field timestamps and spoken chart gap bounds
use the same GMT+7 wall time as the rest of Mastermind.

Pages consume the shell's published bottom clearance through `AppPageScrollView`.
The Sources sheet opens on the root navigator, above the floating dock, so the
system safe area pads its end and no dock estimate is needed.

Forge v1 publishes field health beside the legacy arrays: `ship[]` supplies
`deploy`, `ci`, and `released_at`; `work.lanes[]` supplies age/ETA observations;
`insights[].weekly` supplies weekly budget and pacing observations. Mobile adapts
these companion paths and can show their reasons even when legacy environment
and usage-instance lists are empty. `work.counts` supplies Home's top-level
running, waiting, and idle counts. Unknown root keys, `asks_source`, and
`decisions_unknown` are safe to ignore. The exact redacted publisher fixture is
covered by `test/features/mastermind/view/forge_v1_fixture_test.dart`; it verifies
all five tabs, open asks, resolved history, source reasons, gaps, and counts.

Optional companions are validated field by field. Ship observations apply only to
production; null companions retain a published legacy value. Unknown enums,
invalid numeric values and unparseable timestamps retain the legacy value with
`not_published` status and an “Unrecognised value” reason. ISO timestamps with
`Z` or an explicit offset normalize to UTC. These rules apply to Ship, weekly
Insights and Work age/ETA fields. A malformed lane or unknown decision status
is skipped without hiding the remaining snapshot. Decisions marked resolved in
`decisions[]` also populate Recently resolved. Home keeps a queued chip when
`work.counts` is published, deriving queued from lanes when absent.
Regression coverage: `test/features/mastermind/presentation/companion_hardening_test.dart`.

An unreported pacing value retains its dashed status glyph beside the explicit
reason. The label wraps within the row's content area so checked timestamps do
not overflow narrow screens. `mastermind_insights_page_test.dart` preserves the
one-glyph-per-window assertion for reported and unreported values.

Truncated asks carry a visible Mac continuation notice. Recorded answers remain
available regardless of length, with an expandable preview. Failed replies say
"Not sent · tap to retry" while the reply is still queued and a retry can go
out (offline); tapping retries the existing reply and opens its recovery
details. A 429, a 401/403 (behind the auth-failure guard) or a dropped reply
reads "Couldn't send · open to review" and a tap only opens the details. Grouped open rows omit the repeated kind badge. Coverage:
`mastermind_inbox_v1_test.dart` (truncation, long answers, failed sends).

Ask cards on Home and Inbox share the same row. The A2 short title wins when
present; otherwise the publisher title wins;
a redacted title falls back to the first ask line. Cards preview two lines,
project, status and created-at age; detail keeps the full published ask. Only
unique open ids appear in Needs you; a hub-answered id always wins. Home's
See-all link opens Needs you. A redacted title is the first ask line, so the
preview starts on the second line; screen readers hear at most 200 characters
of the ask on a row. The recorded answer shows "Show full answer" whenever it
overflows four lines at the current width and text size.

**Undo window (decided 2026-10-28).** A Home or Inbox option is one tap; the item detail selects, then sends from the sticky Send ([decision detail](/platform/features/mobile-mastermind-decision-detail)). Either shows
"Sending “option” · Undo" for 5 seconds; the reply enters the outbox only then, through the same
`submit` and Idempotency-Key. One window per item; the other options lock
meanwhile. Leaving the screen inside the window still sends; logout or an
account switch cancels it, and so does a live snapshot where the ask changed or
left. Coverage: `mastermind_replies_undo_test.dart`, `mastermind_option_undo_test.dart`.

See [answered elsewhere and withdrawn](/platform/features/mobile-mastermind-answered-elsewhere) for cross-device answers, batch labels, undo cancellation and resolved rows.

## Read-only Threads preview

`MASTERMIND_THREADS` is a Dart define, default `false`. With it off, Work, Ship
and Insights retain their existing navigation. When enabled, Threads replaces
Work in the dock; Backlog and Staff remain segments, and Ship and Insights stay
separate. The flag is read through `mastermindThreadsEnabled`, which tests can
override with `debugOverrideMastermindThreads`, so the default `flutter test` run
covers both the flag-off and flag-on paths without a `--dart-define`.

P1a is Work's own page with a Threads segment control: it reads the same
accepted snapshot as Home and Work through the shared snapshot cubit and the
tolerant v1 parser, and never parses the hub payload on its own. The grouped
lane list, search, state, product and area filters, "Clear filters", Backlog and
Staff are Work's own components, so a Work or Home link keeps `?state=`,
`?product=` and `?area=` when it redirects to `/mastermind/threads`. The one
difference is the group and chip order: Waiting, Failed, Running (queued
follows), then Idle, each oldest first. The segment switch uses the compact
32 pt track with 44 pt hit areas. A row opens the existing lane detail under
`/mastermind/work/lane/:id`; the dock keeps Threads selected while it is open,
and a missing lane offers "Back to Threads". There is no send UI and no row
opens history. Loading, access loss, rate limits (the last snapshot stays) and a
404 with nothing published use the shared Mastermind section states.

Thread history is a separate P1b change, built to the design's mobile conditions
(app lock, screenshot protection, closed parsers, localized state words and
times). It is not part of P1a and has no flag here.

Regression coverage lives in `apps/mobile/test/features/mastermind/threads/`:
`threads_list_test.dart` covers the group order, filters, "Clear filters",
Backlog/Staff segments, 44 pt targets, dock clearance, rate-limit retention and
the 404 state with the flag on; `threads_flag_test.dart` keeps the flag-off
navigation unchanged and checks the flag-on dock selection, redirects with
filters kept, and the lane-gone copy. Enablement remains held for exact-commit
mobile CI and product acceptance.

### Inline decision cards

Scope: open asks on mobile Home and Inbox. Schema 1.4 remains the wire
version; the existing adapter accepts optional A2 `hub_title`, `hub_text`,
`hub_options`, `hub_recommended`, and `by`. Short title/text take precedence
on cards; absent, null or empty copy falls back to the canonical title/body.
The publisher's `text` and `recommended` aliases normalize to `body` and
`recommended_option`. Open asks still come from `now.needs_you` and the
item-identity rows in `decisions[]`; the journal is a separate history model.

Short option labels must preserve the canonical option order and count.
A mismatched list falls back to canonical labels; mobile always sends the
original `option_index`, item ID and version hash. Recommendation is marked
with localized text as well as a badge. Product and publisher chips wrap;
age appears only when `created_at` is published.

A tap optimistically replaces choices with the existing five-second
Sending/Undo window, then the existing version-bound, idempotent reply outbox
and `POST /v1/replies` transport. Undo restores choices without a send.
Acceptance remains “Sent · waiting for Mastermind”; only the hub may resolve
the ask. Offline, rejected and stale replies retain existing recovery behavior.
When capabilities do not permit replies, choices are disabled with the existing
capability explanation. No new endpoint or inferred backend capability is added.
Full detail continues to show canonical ask text and choices.

Regression coverage: `view/decision_cards_test.dart` (English/Vietnamese,
320px, text scale 2.0, short-copy fallback, recommendation, canonical indices,
Undo and delayed send) plus the existing reply cubit and Inbox/Home suites.

## Iris in the Inbox (M0)

The owner's inbox is a first-class part of the mobile Inbox,
behind a flag. Synthetic data only in fixtures and tests.

- **Flag:** `mastermindIrisEnabled` is on when the `MASTERMIND_IRIS` Dart define
  is set (dev, staging and tests) or when the hub's `GET /v1/capabilities`
  returns `"iris": true` (TestFlight and Play internal). The capabilities parser
  accepts that optional last key; a Worker without it, or a failed check, keeps
  Iris off. `iris` says only that the relay is on, never anything about
  enrolment. Tests use `debugOverrideMastermindIris`.
- **Inbox segments:** with Iris on, **Chat** is the first and default segment
  (`/mastermind/inbox`); Needs you is then written as `?segment=needs-you`, and
  `?segment=chat` deep-links Chat. With Iris off nothing changes. If the hub
  turns Iris off while Chat is open, the Inbox falls back to Needs you.
- **Chat feed:** `GET /v1/iris/feed` returns the `threads-1` page and message
  shape (oldest first, opaque `item-` thread ref and `m-` message refs, plus
  `next_after` on a forward `?after=` poll; `before` and `after` together is
  refused). The list is reversed so it opens at the newest message, newest
  last, and holds its place. Rows reuse the #7182 plain-text renderer: bidi and
  invisible characters stripped, redactions as neutral placeholders, and a
  withheld row (`withheld: true`, empty text) reads "Hidden message". The feed
  polls every 15 s with backoff, holds at most 500 rows in memory, is dropped
  when the app leaves the foreground, and resets to the latest page on a 404
  cursor. Author labels are display-only provenance: nothing owner-only
  (answers, enrolment, un-kill) is granted by who a message says wrote it.
- **Composer:** published into the shell's floating dock like Assistant, so
  there is no second dock or inner bar and the dock keeps its Back while idle.
  Text only in M0; voice is the OS keyboard's dictation. `POST /v1/iris/send`
  sends exactly `{"target":"atlas","text":…}` (1 to 16,000 characters) with a
  lowercase-UUID `Idempotency-Key`. Receipts from `GET /v1/iris/send/<id>` only
  move forward: received reads "Sending", delivered via `queue` reads "Queued",
  any other delivery reads "Sent", acked reads "Seen". Three failed attempts
  show "Not sent" with Retry, which reuses the same key.
- **Kill switch:** a 423 `killed` (or a 503 `iris_killed` from an older Worker)
  keeps the chat readable, shows a banner and turns sending off.
- **Signing:** every relay request carries the owner JWT plus `X-Iris-Device`,
  `X-Iris-Ts`, `X-Iris-Nonce` and `X-Iris-Sig` from an injected signer over
  method, path with query, sha256(body), timestamp, nonce, device id and the
  Idempotency-Key. Until the native device-key lane lands, a fake signer stands
  in; a real relay refuses it.
  Platform difference: iOS can drop the biometric read session early (`lock`),
  but on Android `lock` is a no-op and the Keystore's 300 s auth window stays
  open after any strong biometric. Writes stay disabled; a write-only second
  key (M1 gate) closes the gap. See `iris/device/SECURITY.md`.
- **Devices and enrolment:** `/mastermind/iris/devices` (Chat's navbar action)
  lists enrolled devices with their status, QA mark and key prefix, and revokes
  with a second tap on the same button, never a native dialog. Enrol shows the
  6-digit code and the key fingerprint prefix and says to confirm on the Iris
  enrol page with a passkey; the app then polls the device from pending to
  confirmed, or expired after 15 minutes. No typed T3 command or chat message
  confirms a device. Builds without a device key cannot enrol.
- **Ask cards:** asks keep the hub snapshot and `POST /v1/replies`; the relay
  never answers them. Inbox rows and detail share urgency badges ("Urgent",
  "High priority", each with a glyph) and deadline labels beside the age. A
  **What needs me** header (Needs you, Chat and the Home card) counts open asks
  once each as urgent, soon (high), FYI or other; in Chat it also shows the
  relay's role status and usage line. **Use recommendations** opens a confirm
  sheet listing each open ask with a recommended option, then queues one held
  reply per ask, each with its own Idempotency-Key and the existing durable
  undo on its card, and reports each result. The recommended option is a filled
  button beside its "Recommended" badge.
- **Fixture mode:** the development flavor with `MASTERMIND_FIXTURE=true` serves
  `assets/dev/mastermind/iris_fixture.json` (12 synthetic asks across
  urgent, soon and FYI, with and without options, one expired; 40 messages)
  through `FixtureIrisRelay`, with offline, 429, kill and slow-ack toggles.
- **Not in M0:** attachments, secure input, push deep links to Chat, typed-code
  approvals and the native device key. The summary and devices response shapes
  are provisional until the relay fixes them.

Regression coverage lives in `apps/mobile/test/features/mastermind/iris/`
(`data/http_iris_relay_test.dart` for routes, shapes, signed headers and
401/403/423/429 handling; `data/fixture_iris_relay_test.dart` for the fixture
and its faults; `cubit/iris_cubits_test.dart`; `view/iris_chat_view_test.dart`
for the feed, composer, receipts, retry, kill banner and dark mode;
`iris_integration_test.dart` for the flag, capabilities, Chat segment and
enrolment) and `view/what_needs_me_test.dart` for badges, counts and the
recommendations sheet.
