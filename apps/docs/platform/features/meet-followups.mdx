## From notes to action

Completed meeting notes show suggested next steps. Review an action item as a task,
review a suggested follow-up meeting as a calendar event, or choose **Reserve time
for this** to schedule work on a task. The original owner and scheduling wording
remain visible. Nothing is created when notes are generated or opened.

Calendar suggestions are included in newly generated notes. Older saved notes still
work and expose their existing action items. Dates resolve against the saved meeting start and supplied timezone. Unspecified dates, times, durations and owners
stay unspecified; incomplete transcripts remain visibly marked.

## Identity, destination and time

The review defaults to the signed-in user's personal workspace and saved calendar
timezone, falling back to the browser timezone for an automatic setting. The user
can choose another workspace where they are a full member. Tasks require a chosen
active board and list. Search destination members and select one or more assignees, use the suggested owner when uniquely matched, or leave the task unassigned. A suggested name alone never silently assigns a person. Priority, description and deadline are editable.
Events require a reviewed start and end and are saved to the selected enabled native calendar. Calendar and location are editable. The review checks overlap with saved
events in the selected workspace and reports when availability is unknown;
unsynced external calendars are outside that check. All created items include a source link
to the meeting notes; this does not grant recipients access to private notes.

The review shows local wall times and converts them to UTC before persistence.
Invalid dates, nonexistent DST times, repeated DST hours, invalid zones and reversed
event intervals are rejected. The user can select another local time or enter the
intended instant explicitly in UTC. Changing the timezone reinterprets the displayed
wall times, as explained in the form.

## Speaker attribution

New capture keeps microphone and shared-audio tracks separate in one audio context.
Each new segment carries a source kind and may carry a source account ID. The server verifies supplied accounts against
room admission before resolving the saved display name, falling back to email.
Segments display the source name and whether the source is a microphone or shared
audio. Historical mixed recordings remain unattributed. A source identifies a
device owner: it cannot distinguish several people speaking into the same microphone.
Notes must preserve that uncertainty rather than infer identity from voice.

Speaker clips are sent together in one upload window every ten seconds. One batch
uses one database reservation, retaining the existing sequence/rate contract and
three-hour session boundary. Capture stops 15 seconds before expiry to flush pending audio. Individual timestamps and source labels survive batching.
The provider returns one indexed transcript per file; missing or duplicate indices
fail validation rather than silently mixing speakers. Batches are bounded to 48 clips
and 12 MB, with at most 48 MB awaiting upload. These are explicit upload-capacity
limits; exceeding them marks the session incomplete. They do not multiply the
sequence counter by participant count.

Source metadata is stored alongside chunk usage without a schema migration. Notes
receive stable source IDs; generated owner IDs are checked against that roster.
The review matches those IDs against the chosen destination's actual members.
Changing workspace clears board, list, calendar and assignee selections.

## Server boundary

`/api/meet-ai/[wsId]/[meetingId]/followups` runs inside Meet. It verifies the Meet app
session and source-note sharing policy, then separately verifies full membership and
existing task/calendar permissions in the destination. Actor IDs come from the
verified session. A changed account invalidates an open review. Tasks call the shared Tasks creation handler with injectable Meet authentication, retaining task sorting, rich-text description formatting, relation writes, quotas and actor-aware access checks. Selected assignees must still be full destination members. Workspace member-name and email privacy settings are respected in the picker. Calendar writes resolve the selected enabled native calendar and use the existing encryption helper before inserting. Meet performs these authorized writes with its own verified session. Calendar encryption runs in strict mode: a key lookup, configuration or decryption failure rejects the write; only a workspace with no encryption key can store unencrypted fields.

A creation request has a UUID, timestamp and payload fingerprint. Existing private
room receipts prevent replaying the same request within the one-hour receipt window;
expired timestamps are rejected. The client also retains a per-user, per-suggestion
attempt marker and saved result URL, without storing note text. After an uncertain
write, check the destination before creating another copy. Confirmed pre-write failures release the matching pending room receipt and clear the local attempt marker so the user can correct the destination and retry. Receipt persistence can
fail after a successful write, so the server never automatically retries creation.

## Verification

Run the Meet meeting-ai tests, shared AI meeting-generation tests, internal API build,
`bun check`, and the actual Meet build. Use `NODE_ENV=test` for tests when the shell
inherits production mode. Verify authenticated task assignment, destination and
calendar timestamps in a dedicated test workspace before claiming production
end-to-end coverage. These changes require no database migration.

## Public meeting details and long calls

The host can enable **Public meeting details** from meeting details or call
settings. It is off by default. When enabled, the invitation page and its
Open Graph/Twitter metadata expose only the title, scheduled time and ended
status. Anonymous visitors can read that projection, then sign in to request
admission. Notes, recordings, calendar descriptions, host email and participant
identities never enter the public metadata. Private meetings keep generic,
non-indexable metadata. Policy failures also return the private projection.
Disabling visibility affects the next server request; external search/social
services may retain earlier previews. The sitemap contains only public Meet
landing pages and does not enumerate invitation codes.

Call duration follows the host's personal account subscription: Free has two
hours, Plus ten hours, and Pro/Enterprise twenty-four hours. The join-token route
resolves the host's active subscription on the server and signs the duration into
the token for every participant. The realtime room fixes its deadline on first
admission and retains it across reconnects and later tier changes. Existing rooms
keep their original deadline. Entitlement lookup failures do not silently turn a
paid host into a Free host. The UI displays the deadline with date and timezone.

These are call limits. Each transcription session still uses the existing
three-hour database reservation contract and ends just before expiry. Hosts can
start another transcription session during a longer call; each keeps its own
notes and usage. This change requires no production database migration. It does
not change participant capacity, AI credits or storage allowances.
