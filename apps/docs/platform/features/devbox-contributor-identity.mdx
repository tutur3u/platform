---
title: Contributor devbox identity
description: Disabled identity foundation for personal devbox access and labelled agent credentials.
---

Contributor grants bind to a user ID. An operator resolves the confirmed email at
creation only; acceptance and every later request use the revalidated signed-in
subject. A pending grant requires web acceptance with recent authentication and,
by default, MFA. Root workspace members cannot accept personal grants. Adding a
grantee to root membership suspends the grant and revokes its credentials.

`personal_pools_enabled` defaults to `false`. A missing settings row, unavailable
identity RPC, missing column or malformed result denies personal authorization.
S1 seeds no grants and provisions no runner or host. Existing fleet sessions keep
their root-member authorization. Infrastructure refuses agent and runner headers.

Agent credentials use the `tdba_` namespace, 256 random bits and SHA-256 storage.
Their labels identify agents; scopes cover `devbox:run`, `devbox:build` and
`devbox:read` only. The default life is seven days, the maximum is thirty days,
and the grant expiry is always the upper bound. Raw tokens appear only in a
`no-store` creation response. Lists omit hashes. A token cannot manage tokens or
become a fleet credential, including if its owner later joins the root workspace.
The token branch validates scope before any root-member lookup. Either run or
build scope permits same-owner stop, lease release and environment mutations.
S1 does not yet record per-use `last_used_at`.

Grant acceptance sets `sessions_not_before`. Every personal CLI and web session
must originate at or after both acceptance and this cutoff, including reads and
token list/revoke. CLI `auth_time` is signed at authentication and copied unchanged
into both tokens on every refresh. CLI handoff takes the signed primary proof
time, never its exchange time or caller-supplied session data. Handoffs without
a verified primary origin and legacy refresh chains without an origin receive
an origin of zero and require a fresh sign-in for devbox access. Web sessions use
the original primary authentication in verified Supabase `amr`, never refreshed
JWT `iat`. Minting also requires a recent primary proof and MFA by default. A web
user who accepted a grant must authenticate again after acceptance before using it.
Administrators may advance the cutoff through the service-only grant record.
All Web devbox mutations enforce CSRF regardless of the global mode.

Token revocation atomically revokes the credential, cancels its queued runs,
requests cancellation of its running work, and releases its attributed leases.
Any direct transition to revoked, suspended or expired runs the grant cascade in
the same transaction, including access/runner-token revocation, queued cancellation
with completion timestamps and lease release. Events record the acting user when
available, database/JWT role and old/new status. Previously revoked tokens retain
their revoking principal. The operator RPC accepts `p_operator_id`; direct SQL uses
the verified JWT actor or database role. Learner Judge/playground runs and their
tokenless pool leases remain allowed for past or inactive grantees; trusted
run/build work still requires an access token. Revocation permits no new
requests; stopping an untrusted running process still requires the future host
stop mechanism. Identity and scope triggers cover both INSERT and UPDATE.

S1 admits only token-scoped run/build mutations behind the default-OFF grant
switch. Runner registration remains fleet-only until reviewed enrollment exists. Enablement
requires Security Desk closure of SR-332/333/334, atomic S2 admission and claim
controls, enrollment and runner expiry enforcement, S3 private observability and
secret handling, host isolation evidence, and the named human approval gates.
Pinned `runnerId` ownership depends on #7130 (SR-334) and its database triggers;
S1 alone must never be enabled. Merge the shared predicate prerequisite after
#7121, then #7130, then S1. #7130 delegates its grant check to the service-only
`private.devbox_identity_grant_active(p_user_id uuid)` function, keyed by `user_id`.

The Worker deploy config explicitly enables the existing agent API so fleet
heartbeat/poll/connect survive deployment. This does not enable personal pools.
Its expiry Cron runs every five minutes with a separate
`TUTURUUU_DEVBOX_EXPIRY_SWEEP_ENABLED=false` durable stop fence. OFF performs zero
database requests. ON makes at most one database request per invocation, with a
10-second fetch bound, no retries and a 25-grant transactional batch. Terminal
grants are excluded; interrupted or failed invocations resume on the next Cron.
Disabling the fence stops database work; removing the Cron also stops invocations.
This change does not deploy the Worker or enable personal pools.

Regression coverage lives in `devbox-contributor-identity.sql`,
`devbox-identity-lifecycle.sql`, `devbox-identity-ownership-composed.sql`, `session-cutoff.test.ts`, `expiry-sweep.test.ts`, the framework-free
`actor.test.ts`, Web `authorization.test.ts` and `entry-point-matrix.test.ts`, and
the control Worker tests. The entry-point matrix inventories all active devbox
routes and executes denial checks on every listed HTTP method.

## Server quotas (S2, disabled draft)

The grant defaults to two boxes, four vCPUs, 8192 MiB and 60 GiB per box,
two admitted runs, 480 CPU-minutes and 10 GiB egress per Vietnam calendar day,
a 30-minute default and two-hour maximum run time, five agent tokens and a
30-day maximum grant. Pending and running runs both reserve a slot; there is
no extra queue allowance in this stage. This conservative rule closes admission
and claim races without changing Security's claim RPC.

Personal creation uses `create_personal_devbox_run`: a grant row lock, lease,
run and CPU reservation commit together. The insert trigger also enforces limits
on direct writes. Reservations span midnight until settled. Billing uses server
start/end timestamps and the recorded allocation, split at midnight in
`Asia/Ho_Chi_Minh`; runner resource reports never supply billing data.

The soft CPU cap blocks new admissions. It does not cancel in-flight work.
The host must stop a VM at cap plus 25 percent or maximum runtime, whichever
comes first, and after more than 10 percent CPU for five idle minutes.
Persistent stop requests are audited and retain an alert obligation. S2 does not
implement VM stops, alerts or automatic restart. Host-side F2, F3, F9 and F10
remain enablement blockers, including daily golden-disk resets, fail-closed
watchdogs and continuous tunnel byte limits.

`POST /api/v1/devboxes/usage/ingest` is an authenticated 501 stub. It accepts
only an operator collector credential (`X-Devbox-Collector-Token`, `tdbc_` plus
64 hex digits, SHA-256 stored privately). Runner and agent credentials are
rejected. No collector credential or grant is seeded. The future collector
contract needs idempotent sample IDs, server receipt timestamps, per-day host
CPU and egress counters, idle CPU and duration, and stop acknowledgements;
runner telemetry cannot call this contract.

The Cloudflare scheduled handler makes one bounded RPC with no retries. Both
`TUTURUUU_DEVBOX_QUOTA_REAPER_ENABLED` and the database progress row are OFF;
no cron trigger is installed by S2. The global personal-pool switch is another
stop fence. A tick records its minute and count transactionally, so a duplicate
or unknown HTTP outcome can be reconciled without replaying work. A batch
examines at most 25 grants and four overdue runs per grant. Revoked, suspended
and expired grants remain the identity lifecycle owner's responsibility.

Agents may request bounded raises, never approve their own requests. The
Infrastructure route requires the root administrator gate; decisions are audited.
Raises expire within seven days and before grant expiry. Effective limits return
to the base grant when a raise expires. Hard ceilings are four boxes/runs,
1920 CPU-minutes, 40 GiB egress, 16 GiB memory and 120 GiB disk.

Migration approval, Security's claim-side acceptance, host acceptance and exact
commit CI remain required before enablement. Regression entrypoints are
`devbox-quota.sql`, `quota-errors.test.ts` and `quota-reaper.test.ts`.
