## Phase boundary

Phase 1 delivers the [standard](/platform/data-protection-standard), [inventory](/platform/data-protection/inventory) and source appendices. It does not implement retention, apply migrations, access production data, change processor settings or authorize phase 2. The integration owner reviews this packet and obtains the user's go-ahead. Every migration, including D1 or the memory sidecar schema, requires explicit user approval through that owner before implementation or execution.

The findings below are source-backed compliance and data-lifecycle risks. They are not claims of an exploited vulnerability, production data exposure or complete absence of other safeguards. Severity describes the consequence if the observed gap remains in the applicable processing flow. Owners and acceptance are proposed work allocations, not claims that those owners have accepted delivery.

## Top five risks

| ID and priority | Trigger and consequence | Source evidence and existing protection | Smallest useful next change |
| --- | --- | --- | --- |
| DP-01, high | A subject or workspace is considered deleted while profile details, embeddings, files or processor copies remain. The platform cannot demonstrate full erasure by its deadline. | Account deletion removes the Auth identity but the trigger soft-deletes private details. Memory sidecar forget retains content/embeddings. Workspace deletion deletes a DB row with best-effort subscription cleanup. These are real product paths, but no cross-store completion ledger was established. See Identity, AI and memory, and the sidecar in the inventory. | Define subject discovery and one request/adapter receipt contract. Implement physical memory purge and account/workspace adapters as separately reviewed changes. Preserve legally justified records explicitly. |
| DP-02, high | A delayed queue consumer, provider sync, backfill, offline client or backup restore republishes data after withdrawal or deletion. | Per-feature claims/retries and memory consent checks exist. This review did not establish a platform deletion generation checked by every writer, or a backup restore barrier. See asynchronous state, calendar, chat and backups in the inventory. | Add durable fences and exercise write-versus-delete races before connecting purge workers. Preserve original identities for unknown provider writes. |
| DP-03, high | Ordinary security events or development email sending place raw personal values into long-lived logs outside the erasure graph. | Abuse protection logs a sanitized IP, and email DEV_MODE logs recipient lists and subject. `sanitizeLogValue` removes control characters and bounds length; it does not redact PII. See the precise links below. | Replace raw values with allowlisted diagnostic fields at these callers, preserve native `console.*` severity, then expand in small product scopes. Set sink retention and artifact hygiene separately. |
| DP-04, high | Raw events or person-linked metadata outlive their purpose or the 90-day ceiling. | `link_analytics` and `email_audit` have raw IP/UA fields. Studio metadata defaults to 365 days and can be configured longer. Cleanup RPCs and short-lived Redis counters protect some stores but do not establish the platform schedule. | Classify raw versus necessary accounting metadata. Add approved TTL/index changes and bounded Cloudflare purge adapters, and verify PII-free aggregate output. |
| DP-05, high | A rights request is scheduled for 30 days even when an earlier legal deadline applies, or is declared complete before a processor/backup answers. | Product-specific exports exist, and legal acceptance versions are recorded. A unified request/deadline/processor receipt path was not established. Provider registries differ. Decree 13's historical shorter deadlines require legal triage; current successor-law applicability is unresolved. | Legal owner confirms current-law mapping and processor roles. Add deadline-aware intake and truthful partial-state reporting, then verify processor and backup expiry/restore evidence. |

DP-03 source examples are [abuse IP logging](https://github.com/tutur3u/platform/blob/8d6a13e58762aedff6b1ea5eabb6de474a257e99/packages/utils/src/abuse-protection/index.ts#L465), [email development logging](https://github.com/tutur3u/platform/blob/8d6a13e58762aedff6b1ea5eabb6de474a257e99/packages/email-service/src/email-service.ts#L386), and [log-injection sanitization](https://github.com/tutur3u/platform/blob/8d6a13e58762aedff6b1ea5eabb6de474a257e99/packages/utils/src/log-sanitizer.ts). This distinction prevents treating a log-injection fix as PII redaction.

## Small PR sequence

Use native GitHub stacks for actual dependencies. Keep independent documentation, log fixes and processor evidence on separate branches. Each row is a review boundary and can split further by product or store. No row authorizes a migration or a production cutover.

`Yes` means explicit user approval is required for the proposed schema migration. `No` means the proposed scope avoids schema changes, not that deployment or processor writes are already authorized. If implementation discovers a schema change in a `No` row, stop that part and obtain approval through the integration owner.

The first useful enforcement stack is C → D → E1/E2 or F1/F2. Storage and Worker stacks depend on the same fence contract. Event TTLs and logging can advance independently once their approved scopes are clear. Integrate a verified contiguous stack prefix only through the integration owner. Do not merge a later layer as implied approval for an unapproved migration below it.

## Verification and release evidence

Phase 1 uses documentation navigation/link/frontmatter checks, a source-count reconciliation, a focused secret scan of the diff and `bun check:changed` before push. No build, `bun validate`, DB reset, production data query or provider write belongs in this phase. If the M4 disk gate refuses the required pre-push check, retain the exact local commit and report the blocker. Do not bypass the gate.

Later implementation uses focused non-build tests locally and admitted isolated environments for database/runtime tests. Offload builds and broad suites according to current host/resource policy. Each migration needs explicit approval, isolated reset/upgrade evidence, exact-SHA staging application and the gated production migration result after an authorized release. Documentation alone never authorizes migration execution.

Before rollout, the integration owner records exact source, CI, security review, deployed identity, approved migration receipts, processor evidence and a subject/workspace fixture whose purge is complete across every in-scope store. Maintain the hard release hold for open critical/high security findings under the repository security policy. The source-risk register does not replace independent security review of implementation changes.

Completion of a rights request requires all required store receipts, or a precise lawful retained subset and expiry communicated under the applicable rules. Any missing provider response, unconfirmed delete, inaccessible backup expiry or unresolved unknown write remains visible. Metrics report deadline misses and partial completion without customer content or raw identifiers.
