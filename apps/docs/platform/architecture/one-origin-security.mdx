The [one-origin super-app](/platform/architecture/one-origin-super-app) is a proposed design. This page describes its intended behavior, not a completed deployment.

Browsers isolate origins rather than application paths. Apps sharing an origin therefore share a browser security boundary. Moving an app onto that origin requires security review and acceptance; a common URL layout alone provides no isolation guarantee.

## Session cookies

The recorded design uses one shared session across apps on the main origin. Sign-in and logout are intended to apply across those apps. Per-app sessions are not the intended design. The shared-session implementation and each app's admission need separate verification before cutover.

See the [security overview](/platform/architecture/system-design/security-architecture) and [authentication overview](/platform/architecture/authentication).

## Drive, Chat, CMS and Forms mounts

Drive, Chat, CMS and Forms admit their matching `tuturuuu.com/<app>` prefix
alongside their subdomain root. Drive admits the apex only in its production
profile; its staging profile retains separate host and environment fences.

On these mounts, `NEXT_LOCALE`, `sidebar-collapsed`, `sidebar-behavior` and
`sidebar-behavior-updated-at` are app-owned preferences. The bridge filters
incoming cookies and writes owned preferences host-only with `Path=/<app>` and
`Secure`. Session cookies are never app-owned. Subdomain cookie handling retains
its existing policy. Mounted login routes send users to the central `/login`
with a return URL inside the app's mount. Offline providers do not register a
service worker on these surfaces.

Each app's `src/start-bridge/apex-mount.test.ts` covers host admission, cookie
isolation, mounted assets and API dispatch, central login return URLs and root
behavior. Drive's `src/start-candidate/apex-worker.test.ts` additionally covers
production bindings on the apex. Emitted Worker and deployed acceptance remain
required before routing production traffic.

## WebAssembly in Meet

The in-browser code formatters are WebAssembly modules: Ruff (Python),
clang-format (C and C++), gofmt (Go), shfmt (shell) and the tree-sitter parser
behind Prettier Java. Compiling WebAssembly needs `'wasm-unsafe-eval'` in
`script-src`. Prettier for JavaScript and TypeScript is plain JavaScript and
needs nothing.

Meet has two policies, and this change adds the keyword to both:

- **Enforced today.** On mounted `/meet` HTML, `apps/meet/src/runtime/handler.ts`
  already sends a `Content-Security-Policy` built by the Start bridge: a nonce and
  `'strict-dynamic'` in `script-src`, plus `object-src 'none'`, `base-uri 'self'`
  and `frame-ancestors 'none'`. Meet now builds it with
  `contentSecurityPolicy(nonce, { extraScriptSources: [WASM_COMPILE_SOURCE] })`
  from `packages/start-bridge/src/core/csp.ts`, so its `script-src` is exactly
  `'nonce-…' 'strict-dynamic' 'wasm-unsafe-eval'`. Policies intersect, so without
  the keyword the enforced policy blocks the formatters whatever the
  report-only policy says.
- **Report-only.** The profile in `apps/meet/cloudflare/security-profile.ts` adds
  the same source through `WASM_COMPILE_SOURCE` in
  `packages/utils/src/security-headers.ts`.

Scope and limits:

- **Meet only.** `defaultContentSecurityPolicy(nonce)`, which every other app
  uses, is byte-identical to before. `contentSecurityPolicy` accepts exactly
  `'wasm-unsafe-eval'` as an extra script source and throws on anything else,
  every other `unsafe-*` keyword and every host included. The report-only builder
  throws for the same sources, and for the wasm source on any mount other than
  `/meet`. Both throw when the header is built, which is at request time for a
  document, not at build time; header unit tests
  (`packages/start-bridge/src/core/csp.test.ts`,
  `packages/utils/src/__tests__/security-headers.test.ts`,
  `apps/meet/cloudflare/security-profile.test.ts` and
  `apps/meet/src/runtime/handler-server-timing.test.ts`) pin the exact strings.
  Parley has no CSP profile of its own; it becomes a Meet activity and inherits
  Meet's.
- **What it does not allow.** `'wasm-unsafe-eval'` lets the page compile
  WebAssembly. It does not enable JavaScript `eval`, `new Function` or string
  timers, and adds no host to `script-src`. `connect-src` is unchanged because
  the formatter binaries are fetched from Meet's own origin.
- **What loads.** The formatters are lazily loaded first-party packages at exact
  versions under permissive licenses (MIT or Apache-2.0), bundled with the app.
  The page fetches no formatter code from a third-party host.

What was verified in a browser: a loopback page in Chromium (Playwright) was
served with the exact header Meet sends, a nonced module script, and the
formatter bundle with its `.wasm` files next to it. With `'wasm-unsafe-eval'`,
JavaScript, Java, Python, C++, Go and shell formatted; with the previous header
(no keyword), the five WebAssembly formatters failed with a `CompileError` that
names the Content Security Policy, and JavaScript still formatted. This proves the
CSP semantics for these modules. It does not exercise the built Worker handler,
which a preview or staging smoke has to confirm.

## Mounted app Trusted Types rollout

Tasks, Learn, Nova, Tools, Teach, LMS, Finance, Drive, Chat, CMS, Forms,
Git, AI and Apps register the shared Start bridge default Trusted Types policy
before application scripts. Script CSP uses a response nonce and `strict-dynamic`.
The custom LMS and Apps renderers propagate that nonce through the bridge request
context and TanStack Router SSR options.

`TTR_TRUSTED_TYPES_<APP>=enforce` selects enforcement in the app Worker binding;
the default sends Trusted Types in `Content-Security-Policy-Report-Only`.
Tasks additionally requires `TTR_CSP_TASKS=enforce` for its existing script rollout.
Learn and Teach use their own variables on `/lms/learn` and `/lms/teach`;
`TTR_TRUSTED_TYPES_LMS` controls the launcher only. LMS has no subdomain route.

Every report endpoint is relative to the resolved app base at `/api/csp-report`.
The collector caps bodies at 16 KiB and logs only bounded directive/disposition
categories, with at most 50 entries per minute per isolate. It never records URLs,
script samples, cookies or report bodies. It returns an empty 204 for POST reports.
This isolate budget bounds diagnostic output, not incoming request volume.

The named policies include `default` and `dompurify`; Learn also names its Monaco
editor policies. Monaco's initial stale-realm replacement `domSanitize0` is listed;
further stale-realm recoveries must be assessed from the report window. Neither
wildcard names nor `allow-duplicates` are granted. Tiptap/ProseMirror create no
additional named policies in the installed source. Forms lists its exact Turnstile loader URL (including callback/render query parameters)
in the generic bootstrap's script URL allowlist; other external script URLs remain
refused. Forms' Turnstile flow and
Learn's coding/editor/worker flows need explicit runtime coverage before enforcement.

An app may enforce only after a clean window of a few hours of traffic, or a
headless crawl of its key pages with zero violations. Header unit tests establish
configuration and mode selection; they do not establish that clean window.
The release owner flips each app's binding after acceptance and retains the
report-only binding value as the immediate Trusted Types rollback.
Meet and Roadmap follow their release owners' separate rollout.

Regression coverage lives in `packages/start-bridge/src/core/document-security.test.ts`,
`apps/learn/security-configs.test.ts`, the bridge nonce
and bootstrap suites, and Tasks' Worker request suite.
