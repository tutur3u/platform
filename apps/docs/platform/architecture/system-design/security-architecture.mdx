Tuturuuu uses authentication, workspace permissions and scoped access to protect customer data. Security reviews and verification accompany changes to these boundaries. An architecture description does not certify deployed controls or legal compliance.

Read the [authentication overview](/platform/architecture/authentication), [one-origin design](/platform/architecture/one-origin-security) and [personal data protection standard](/platform/data-protection-standard) for their scope and limitations.

## Vulnerability disclosure

Report suspected vulnerabilities privately to [security@tuturuuu.com](mailto:security@tuturuuu.com). Follow the [Security Policy and responsible disclosure guidelines](https://github.com/tutur3u/platform/blob/main/SECURITY.md), including its testing limits, reporting process and response commitments.

## Employee public-consumer proof

Employee account workflows need compatible application consumers as well as database verification. A type check alone does not establish successful account creation or recovery. Detailed qualification procedures are maintained privately.

## Opt-in chat initial-settings qualification

Optional chat settings are qualified separately from employee account workflows. Passing an isolated settings check does not establish production activation or consent for additional processing.

## Original CREATE response recovery

When an employee account creation response is lost, the application observes the original operation before confirming success. An uncertain response must not be treated as a confirmed account or trigger an unrelated recovery operation.

## Personal journal schema qualification

Database qualification for personal journals does not by itself establish provider readiness, user consent or production activation. Those require separate acceptance.
