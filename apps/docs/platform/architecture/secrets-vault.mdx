ships before that review approves. Every rule below is **Planned** until its
slice lands with the listed regression coverage.

The vault stores workspace secrets and environment variables so that people,
fleet machines, agents and CI can use them from any machine without copying
files. Values are encrypted and signed on clients. The Tuturuuu server stores
ciphertext, wraps, signatures and metadata.

**Scope:** Web, the `ttr` CLI, CI and deploy runners, fleet agents and
Cloudflare workloads. **Out of scope:** `public.workspace_secrets`, which
remains a plaintext feature-flag and configuration table.
`private.mobile_deployment_*` and the other server-held vaults keep their
custodial model until they are migrated onto this vault.

## Guarantees

1. **End-to-end environments.** For an environment with no workload grant and
   no unattended service credential, the Tuturuuu server, including a full
   database dump and every Tuturuuu server secret, cannot decrypt a value and
   cannot make a client accept a value, key or recipient it did not get from
   an authorised signer.
2. **Custodial environments are labelled.** An environment granted to a
   [workload](#workload-principals) is **server-readable**: whoever controls
   that Worker's secrets or code can decrypt it. An environment granted to an
   [unattended CI credential](#unattended-ci-credential) is readable by
   whoever controls that CI secret store. The UI, CLI and audit show these
   labels, and guarantee 1 does not apply to them.
3. A person unlocks with a vault passkey or a recovery key on any machine with
   no local state. MFA plus PIN unlock is a separate, weaker tier with its own
   identity, off by default (see [MFA unlock](#mfa-unlock-tier)).
4. Machines and agents receive short-lived, scoped, device-bound grants that an
   environment admin approves. Nothing durable is written to the machine.
5. Every reveal, copy, run, pull, sync, grant and key change is audited by
   name, never by value. Audit is server-trusted (see [Audit](#audit)).

## Explicit limits

- **Web E2EE trusts the served code.** Malicious JavaScript delivered to an
  unlocked vault page can read what that page decrypts. The vault runs on an
  isolated origin with a strict CSP; the signed CLI is the stronger client.
- **A decrypting client can always exfiltrate.** A machine that receives the
  sensitive key can reveal sensitive values locally. "Sensitive" is
  cryptographic for members without that key and policy for everyone else.
- **Scope is per environment.** Every grant decrypts the whole environment at
  the granted level. Finer scopes use separate environments.
- **Metadata is plaintext.** Workspace, project, environment and variable
  names, types, flags, timestamps, expiry, version numbers, sizes and audit
  events. Values, descriptions and notes are encrypted.
- **Freshness depends on the witness.** A party that controls both the vault
  API and the [witness](#witness) can present a stale or forked view.
- **Removal cannot unsee.** A removed principal keeps whatever plaintext or
  keys it already holds. Removal fences future access and lists values to
  rotate at their source.
- **Losing every strong unlock method loses the data.** There is no escrow.

## Primitives

Only standard constructions with published test vectors. No custom
cryptography.

| Use | Construction | Implementation |
| --- | --- | --- |
| Value encryption | AES-256-GCM, 96-bit random nonce, per-version subkey | WebCrypto |
| Subkeys | HKDF-SHA256 (RFC 5869) | WebCrypto |
| Public-key wraps | HPKE base mode (RFC 9180), `DHKEM(X25519, HKDF-SHA256)`, `HKDF-SHA256`, `AES-256-GCM` | `@hpke/core`, `@hpke/dhkem-x25519` |
| Deterministic key pairs | HPKE `DeriveKeyPair` (RFC 9180 §7.1.3) | same |
| Signatures | Ed25519 (RFC 8032) | WebCrypto, `@noble/curves` fallback |
| PIN gating | OPRF (RFC 9497, `ristretto255-SHA512`), then Argon2id (RFC 9106) | `@cloudflare/voprf-ts`, `hash-wasm` |
| Canonical encoding | Deterministic CBOR (RFC 8949 §4.2) | `cborg` |
| WebAuthn verification | WebAuthn Level 3 | `@simplewebauthn/server` |

Library choices are confirmed in the slice 1 review; formats below do not
depend on them. Versions are pinned, and CI runs the RFC test vectors.

### Encoding and suites

Every stored object is a deterministic CBOR map with `v` (format version) and
`suite`. Version 1 has exactly one suite, `1`: the primitives above. A client
rejects an unknown `v` or `suite`, a missing field, an extra field, or a
non-canonical encoding. There is no negotiation and no fallback.

### Context binding

Every AEAD `aad`, HPKE `info` and `aad`, HKDF `info` and signature input starts
with a domain label (`tuturuuu/vault/<purpose>/v1`) followed by the canonical
CBOR of its context:

| Purpose | Context |
| --- | --- |
| `value` | `ws, env, variable_id, version, epoch, sensitive` |
| `wrap` | `ws, scope_id, epoch, key_kind (edk, esk, identity, history), recipient_kind, recipient_id, recipient_key_fingerprint` |
| `unlock` | `user_id, identity_tier, method, method_id, params_version` |
| `grant` | `ws, grant_id, recipient key fingerprints, scope, not_after, transcript_hash` |

A fingerprint is `SHA-256` of the canonical public key, shown as the first 128
bits in base32 when people compare it.

### Value encryption

`value_key = HKDF(EDK_epoch, salt = nil, info = "tuturuuu/vault/value/v1" ‖ ctx)`
gives every version its own key, so the AES-GCM random-nonce limit applies per
version, not per environment. Sensitive values are HPKE-sealed to the ESK public
key with the same context as `info`.

### Writer signatures

HPKE base mode does not authenticate the sender, and anyone holding a public
key can create a sensitive ciphertext. Every value version therefore carries a
**version record** signed by its writer's Ed25519 key:

`{ws, env, variable_id, name, type, sensitive, version, epoch, prev_record_hash, ciphertext_hash, writer_id, written_at}`

A consumer accepts a value only if the record verifies, the writer held
`writer` or higher on that environment at that point in the
[key log](#key-log), `ciphertext_hash` matches, and the chain from the
environment's signed head reaches it. The server cannot replace, move, rename
or roll back a value without a signature failure. Verification ships in the
same slice as the first client that reads values.

## Trust anchors

### Workspace root

Creating a vault generates a **workspace root key** (Ed25519) on the owner's
client. The root key signs the genesis of the key log and every admin set
change. Its private key is wrapped to each workspace owner's strong identity.

The root fingerprint is the vault's identity. Clients never accept a root from
the API alone:

- Each user's **keyring** (below) pins the roots of the workspaces they
  belong to. The keyring is encrypted and authenticated under the user's strong
  identity, so the server cannot add or swap a pin.
- A user joins only through an invite that carries the root fingerprint out of
  band (below), or by comparing the fingerprint with an existing member.

### Keyring

The keyring is a per-user object, encrypted with AES-GCM under a key derived
from the strong identity, holding pinned workspace roots, the last verified
key-log head per workspace, the last verified witness checkpoint and a
monotonic counter. It is stored on the server, so it follows the user across
machines. A client rejects a keyring older than one it has already seen in the
same session, and rejects a key log or checkpoint older than the keyring
records.

### Recipient binding

Before any client wraps a key to a public key, that key must be bound by an
independent channel:

| Recipient | Binding |
| --- | --- |
| New member | Invite secret (below) |
| Machine or agent | [Pairing](#pairing) |
| CI credential, workload | Generated by the admin's own client, which registers the public key in a signed key-log entry |
| Existing member, new device | Nothing new: devices are unlock methods of the same identity |

**Invites.** An admin's client creates a 256-bit invite secret and an invite
link whose fragment carries the secret and the root fingerprint. The fragment
never reaches the server. The admin sends the link through a channel they
choose; the server's invite email carries no secret and only says an invite
exists. The invitee's client publishes their identity public keys with
`HMAC-SHA256(invite_secret, "tuturuuu/vault/invite/v1" ‖ ctx ‖ keys)`. The
admin's client verifies the HMAC before signing the member entry and wrapping.
An invite expires after 7 days or one use.

### Key log

Each workspace has an append-only, hash-chained key log. An entry holds
`{seq, prev_hash, kind, subject, public keys or digest, epoch, issued_at}` and
a signature by the root (admin set changes) or by an admin valid at `seq - 1`
(members, roles, machines, credentials, workloads, epochs). Clients verify from
genesis against the pinned root on every unlock.

### Witness

A **witness** is a Cloudflare Worker deployed from a separate Cloudflare
account with separate deploy credentials and its own signing key, not readable
by the vault API. It cosigns a key-log checkpoint `(ws, seq, head_hash)` only if
it extends the last checkpoint it cosigned for that workspace, and it keeps the
latest cosigned checkpoint per workspace.

- Clients fetch the latest cosigned checkpoint directly from the witness.
  Before **wrapping, granting, approving or rotating**, a client requires a
  cosigned checkpoint at most 10 minutes old that matches the head it verified.
  Otherwise the operation fails closed.
- Reading values with already-held keys does not need the witness, so a witness
  outage blocks key changes but not use.
- The witness public key is pinned in the client build and in the keyring.
- Later work can mirror checkpoints to a public transparency log for
  independence beyond Tuturuuu operations.

## Key hierarchy

```text
strong unlock ─KEK─▶ strong identity (X25519 + Ed25519) ─▶ keyring, root (owners)
                        │ HPKE                         └─▶ PIN identity private keys
PIN unlock ────KEK─▶ PIN identity (X25519 + Ed25519)
                        │ HPKE (only environments that allow PIN)
                        ▼
              environment epoch keys: EDK (AES-256) + ESK (X25519)
                        │
     normal values: AES-GCM(value_key)      sensitive values: HPKE(ESK public)
```

- **Identities.** Each user has a strong identity and, if enabled, a separate
  PIN identity. Environments are wrapped to the PIN identity only when their
  policy allows PIN unlock, so disabling it on an environment removes that
  path completely.
- **Epochs.** The EDK, the ESK and the intake key pair exist per environment
  and epoch. A new epoch is
  created on any removal, downgrade, grant revocation or suspected compromise.
  The new epoch's EDK wraps the previous epoch's EDK and ESK as **history**
  wraps, so current principals can read retained versions.
- **Projects** group environments and carry RBAC defaults; they hold no keys.

## Unlock methods

### Vault passkey (WebAuthn PRF)

A passkey with `rpId` `tuturuuu.com` can be exercised from every
`*.tuturuuu.com` origin, so the vault never uses login passkeys for PRF.
It registers a **vault passkey** with `rpId` `vault.tuturuuu.com`, usable only
from that origin, with the `prf` extension and `userVerification: "required"`.

- PRF input: the constant `SHA-256("tuturuuu/vault/prf/v1")`. It contains no
  user ID, so a change of identity provider or user ID does not change it.
- `KEK = HKDF(prf.first, salt = wrap_salt, info = "tuturuuu/vault/kek/passkey/v1" ‖ unlock_ctx)`.
- The vault server stores the credential public key and verifies each
  assertion (challenge, origin `https://vault.tuturuuu.com`, RP ID, UV flag,
  credential ID belonging to this user, signature counter where present) before
  releasing the wrap, using `@simplewebauthn/server`.
- Enrolment fails if the authenticator returns no PRF result at registration
  or first assertion. Slice 3 records a PRF continuity matrix per provider
  (iCloud Keychain, Google Password Manager, Windows Hello, security keys),
  browser and transport, including cross-device (hybrid) use.
- Synced passkeys carry the PRF secret across a user's devices, which is what
  makes unlock work on a new machine.

### Recovery key

At enrolment the client generates a 256-bit recovery key, shows it once in
base32 groups, and requires the user to re-enter one group.
`KEK = HKDF(recovery, wrap_salt, "tuturuuu/vault/kek/recovery/v1" ‖ unlock_ctx)`.
It unlocks the strong identity.

### MFA unlock tier

TOTP is a secret the server also holds, so TOTP alone would give the server
custody. This tier combines a fresh MFA step-up with a PIN gated by an
**OPRF**, so every PIN guess needs one online evaluation by the share service.
It is off by default and **deferred to slice 7**, after a separate protocol
review.

- **Share service:** a Cloudflare Worker and Durable Object holding a
  per-user OPRF key `k_u`. It never sees the PIN.
- **Enrolment:** the client blinds the PIN (`NFKC`, UTF-8, at least 8
  characters), the service evaluates with `k_u`, the client unblinds to `y`
  and derives `rwd = Argon2id(y, salt = pin_salt (16 random bytes), m = 64 MiB,
  t = 3, p = 1, len = 32)`, then `KEK = HKDF(rwd, wrap_salt, "tuturuuu/vault/kek/pin/v1" ‖ unlock_ctx)`.
  Parameters are stored in the wrap as `params_version`.
- **Each evaluation** requires a central-session step-up proof
  (`typ: ttr+stepup`, ES256) with `iss` and `env` pinned to this deployment,
  `aud: service:vault-share`, `act: vault.pin-eval`, `sub` this user, and
  `exp` at most 5 minutes after `iat`. The step-up grant's parameters hash
  binds the service's single-use challenge, the unlock wrap version and the
  client's ephemeral HPKE public key; the service encrypts its response to that
  key. The service consumes `jti`, `nonce` and challenge atomically in its
  Durable Object.
- Evaluations are capped at 5 per user per 24 hours and 20 per 30 days. After
  the cap, the PIN identity locks until the user unlocks with a strong method.

| Attacker holds | Strong identity | PIN identity |
| --- | --- | --- |
| Database dump | Nothing | Nothing (missing `k_u`) |
| Database + share service (or its key) | Nothing | Offline Argon2id search over the PIN |
| Password + TOTP, or a compromised step-up issuer | Nothing | Online guesses only, at most 5 per day |
| Malicious code on an unlocked vault page | What that page decrypts | Same, plus the PIN |

The PIN identity receives only environments whose policy allows it, so its
compromise never exposes the strong identity, the keyring or the workspace
root.

## Principals and grants

| Principal | Recipient keys | Lifetime | Custodial |
| --- | --- | --- | --- |
| Member | Strong identity (and PIN identity where allowed) | Membership | No |
| Machine or agent | Ephemeral X25519 + Ed25519 in process memory | Default 8 h, max 24 h | No |
| Attended CI job | Ephemeral per-job keys | One job | No |
| Unattended CI credential | Derived from a stored credential | Max 90 days | Yes, the CI secret store |
| Workload | Worker secrets | Until revoked | Yes, the Worker operator |

### Pairing

A machine or agent grant binds the device's keys through one of two
authenticated channels; the server relays messages but cannot complete either
without detection.

1. **Fragment link (default).** `ttr secrets login` generates its keys in
   memory and prints an approval URL whose fragment carries the full device
   fingerprints. The owner opens it from the machine's own output (terminal,
   T3 thread). The approval page wraps only to keys matching the fragment.
2. **Fleet card with numeric comparison.** When the owner approves from the
   Mastermind fleet card, which the server delivers, the parties run a
   commitment-based short authentication string: the device publishes
   `C = SHA-256("tuturuuu/vault/pair/v1" ‖ device_keys ‖ N_d)`; the approver
   sends its ephemeral key and `N_a`; the device reveals `N_d`; both show the
   6-digit `SAS = trunc(HKDF(N_d ‖ N_a, info = transcript))`. Because the device
   commits before seeing `N_a`, an attacker gets one guess per pairing
   (probability 10^-6), and a mismatch ends the request. The card carries only
   the approval link (`flow: "link"`, no user code); a `tuturuuu` service with
   hosts `tuturuuu.com` and `vault.tuturuuu.com` is added to the fleet login
   allowlist.

The approver signs the **transcript** (device keys, scope, environments,
level, `not_after`, machine label, pairing mode, central-session `sid`) and the
exact wraps. Redemption requires a fresh Ed25519 signature by the device key
over a server challenge, and the central-session `sid` must still be live; the
server stops serving wraps when it is not. Nothing is derived from the central
session's device secret.

**No durable machine state.** `ttr secrets agent` holds the device keys, its
own central `cli` session and decrypted environment keys in process memory,
and serves the same user's `ttr` invocations over a Unix socket (mode 0600,
peer UID checked; a named pipe with an owner-only ACL on Windows). It does not
read or write the persistent CLI configuration. It never uses a keychain.
Leases end on agent exit, `not_after` or revocation; renewal needs approval.

On a hostile host, memory-only storage, TTL and revocation limit only future
access: anything decrypted during the lease may already be copied.

### Attended CI jobs

The preferred path has no stored decryption key. A job generates ephemeral
keys, authenticates with its GitHub OIDC token, and an environment admin (or a
workload acting as an approver, which makes the environment custodial) wraps
the granted keys to the job's keys after checking the verified OIDC claims.

### Unattended CI credential

For jobs without an online approver, an admin's client creates a 256-bit
credential `cred`, stored by the operator as a GitHub environment secret.

- `auth = HKDF(cred, "tuturuuu/vault/svc/auth/v1")`; the server stores
  `HMAC-SHA256(server_pepper, auth)`.
- `(svc_sk, svc_pk) = DeriveKeyPair(HKDF(cred, "tuturuuu/vault/svc/key/v1"))`.
  The admin's client wraps the granted keys to `svc_pk` and registers it in the
  key log.
- Delivery needs `auth` **and** a GitHub OIDC token whose signature, `iss`,
  `aud` (`tuturuuu-vault:<ws>`), `exp`, `repository_id`, `repository_owner_id`,
  `job_workflow_ref`, `ref`, `environment` and `event_name` match the binding.
  `jti` is single use until `exp`. Non-GitHub runners are not supported in
  version 1.
- **Exposure:** anyone holding `cred` and a delivered wrap can decrypt. A
  15-minute delivery lease does not expire keys already delivered. The
  environment is labelled custodial to the CI secret store, credentials expire
  within 90 days, and rotation creates a new epoch.

`ttr secrets pull --stdout --format dotenv|json` prints to stdout only.

### Workload principals

An admin's client generates a workload's X25519 and Ed25519 keys, installs the
private keys as secrets of one named Worker, and registers the public keys in
a signed key-log entry. Only environments created for workloads can be granted
to one, and they are labelled server-readable.

- Every request names the workspace and is signed with the workload key over
  method, path, body hash, timestamp (±60 s) and a nonce kept until expiry.
- A lease lasts 1 hour, is bound to `(workload, workspace, environment)` and is
  rejected for any other workspace. One version-poll call returns current
  versions for a list of names; the workload refetches changed values at most
  once per lease renewal. A Durable Object may keep plaintext in memory for the
  lease.
- A workload granted `writer` on specific variables writes signed version
  records with compare-and-swap on the previous version.
- Ending custody revokes leases, removes the key-log entry, starts a new epoch
  for every granted environment and lists values to rotate at their source.

## Values, sensitivity and versions

- A variable has a name (`^[A-Z_][A-Z0-9_]{0,127}$`), a type (`secret` or
  `variable`), a sensitivity flag, optional expiry and rotation interval, and
  signed versions.
- **Variables** and **secrets** are encrypted under the EDK. Secrets need a
  confirmation to reveal, and each reveal and copy is audited.
- **Sensitive** secrets are sealed to the ESK. Members without the ESK
  (`viewer`, `reader`, `writer`) can set them but cannot decrypt them.
  Environment admins hold the ESK because they approve machines; their reveals
  are audited by first-party clients only.
- **Marking a variable sensitive** re-seals its retained versions under the ESK
  in the same client operation and deletes the EDK ciphertexts. Readers may
  already hold earlier plaintext, so the UI suggests rotating at the source.
  Clearing the flag re-encrypts under the EDK.
- The newest 20 versions or 90 days are retained, whichever is more. Restoring
  writes a new signed version. Deletion writes a signed tombstone and purges
  ciphertext after 30 days.

## RBAC

| Role | Names | Decrypt normal | Decrypt sensitive | Set values | Manage |
| --- | --- | --- | --- | --- | --- |
| `viewer` | Yes | No | No | No | No |
| `writer` | Yes | No | No | Yes | No |
| `reader` | Yes | Yes | No | No | No |
| `editor` | Yes | Yes | No | Yes | No |
| `admin` | Yes | Yes | Yes | Yes | Members, grants, rotation |

`writer` holds no EDK. It seals sensitive values to the ESK public key and
normal values to a per-epoch HPKE **intake key**, whose private key is wrapped
with the EDK to every principal that decrypts normal values. Readers therefore
decrypt intake ciphertext directly, and the writer cannot read it back. A workspace permission
`manage_secrets_vault` allows creating projects and environments. Server checks
decide who fetches which ciphertext; cryptography decides who decrypts.

## Membership and epochs

- **Add:** an invite binds the member's keys; an admin signs the member entry
  and wraps the current epoch keys at the granted level.
- **Remove, downgrade or revoke:** the admin's client performs the change in
  one request together with the next epoch: new EDK and ESK, wraps to every
  remaining principal, history wraps, a signed epoch entry and witness
  checkpoint. The server applies it atomically; from then on it rejects writes
  under the old epoch and stops serving old-epoch wraps to the removed
  principal. Dependent machine leases and CI deliveries are revoked.
- **Re-encryption** of retained versions into the new epoch runs on authorised
  clients in bounded batches with a per-variable idempotent marker, and resumes
  after interruption. Until it finishes, old versions stay readable through
  history wraps.
- **Rotation list:** the removal shows every value the principal could decrypt
  so admins can rotate them at their source.
- **Unlock method loss:** deleting a passkey or recovery wrap stops its future
  use but cannot revoke copies. If a method may be compromised, the user
  rotates the identity: new keys, a signed key-log entry, re-wraps, and a new
  epoch on every environment the old identity could read.

## Audit

`private.vault_audit_events` records actor kind (`user`, `machine`, `ci`,
`workload`, `sync`), actor ID, event, resource IDs and names, a truncated IP
prefix (/24 or /48), user-agent family, grant or lease ID and result. It never
records values, ciphertext, wraps, PINs, OPRF material or tokens. Workspace
admins can read it; events are kept for 400 days.

Audit is **server-trusted**: the operator could rewrite or drop events. The
per-workspace hash chain detects accidental damage, and its head is included
in each witness checkpoint, so rewriting history before a checkpoint is
detectable. Reveal and copy events come from first-party clients; a modified
client can skip them.

## Sync targets

Sync decrypts, so it runs only in a principal that already decrypts: an
unlocked browser, `ttr secrets sync` with a machine grant, or a CI job. The
server never syncs on its own.

| Target | Direction | Notes |
| --- | --- | --- |
| Cloudflare Worker secrets | Push | Per Worker and environment |
| GitHub environment secrets | Push | Sealed box to the repository public key, as GitHub requires |
| Vercel | Import and archive | Vercel `sensitive` values cannot be read back; they are listed by name for re-entry |

Idempotency uses the signed version record ID: a target is up to date when its
recorded version ID matches. No value digest is stored or logged. Provider
tokens are sensitive vault values. A run is bounded (at most 500 writes, 3
retries with backoff), records a terminal state and stops on a durable cancel
flag.

## CLI

| Command | Behaviour |
| --- | --- |
| `ttr secrets login` | Starts the agent and requests a machine grant |
| `ttr secrets unlock` | Renews or widens the lease through a new approval |
| `ttr secrets list [--env]` | Names and metadata |
| `ttr secrets get NAME [--env]` | Prints one value to stdout; refuses a TTY for secrets without `--reveal` |
| `ttr secrets set NAME [--env] [--sensitive]` | Reads the value from stdin only |
| `ttr secrets run [--env] -- <cmd>` | Spawns `cmd` with the environment injected; writes nothing to disk |
| `ttr secrets pull --stdout [--format]` | Prints only |
| `ttr secrets sync <target>` | Runs a configured sync |
| `ttr secrets logout` | Revokes the lease and stops the agent |

No command accepts a value on argv. Debug output is redacted by value match.
Same-user processes can read a process environment on most systems; that is
the accepted boundary for `run`.

## Web delivery hardening

- The vault UI is served from `vault.tuturuuu.com` with a nonce-based CSP, no
  third-party scripts, Trusted Types, `frame-ancestors 'none'` and
  `Cross-Origin-Opener-Policy: same-origin`.
- It uses a host-only child session (`__Host-` cookie) from the satellite
  handoff and same-origin vault APIs. No long-lived bearer token is readable by
  page script, per [Shared session](/platform/architecture/shared-session).
- Plaintext lives only in component memory, never in TanStack Query caches,
  Web Storage, IndexedDB or logs. Unlocked state ends on tab close, 15 minutes
  of inactivity, or lock. The keyring head cache in `sessionStorage` holds no
  key material.

## Storage and runtime

Ciphertext, wraps, records, the key log, keyrings and audit live in Postgres in
the `private` schema, reached only through server routes and
`packages/internal-api`. No Supabase-only features are used, so the tables move
to Hyperdrive with the platform. The API lives under
`apps/web/src/app/api/v1/workspaces/[wsId]/vault/**`.

New backend work runs on Cloudflare: the share service, the witness, reminder
scheduling (a Cron Trigger Worker sending expiry and rotation reminders 14, 3
and 0 days ahead from plaintext metadata, with bounded retries, an idempotent
per-reminder key and a durable stop flag), and workload leases. Plaintext
re-encryption always runs on authorised clients.

## Package boundaries

- `packages/vault-crypto`: formats, context binding, wraps, signatures, key
  log and manifest verification, pairing, recovery encoding. Its portable
  entrypoint imports no Next.js, React, Cloudflare or request globals.
- `packages/internal-api/src/vault/*`: data access and authorisation.
- `packages/sdk/src/cli/secrets/*`: CLI commands and the agent.
- `apps/vault-share`, `apps/vault-witness`: Cloudflare Workers.

## Threat model

| ID | Threat | Mitigation | Residual |
| --- | --- | --- | --- |
| T1 | Database dump | Ciphertext, wraps and signatures only | Metadata |
| T2 | Compromised vault API and database | Pinned root, invite binding, signed key log and records, witness | Denial of service, metadata |
| T3 | API + witness compromise | Keyring pins and counters detect rollback below the user's last state | Stale view for key changes |
| T4 | API + share service | Strong identity unaffected | PIN identity: offline Argon2id |
| T5 | Malicious code on the vault origin | Isolated origin, CSP, Trusted Types, no third parties | Inherent to web E2EE |
| T6 | Sibling-origin script | Vault passkeys scoped to `vault.tuturuuu.com`; host-only session | — |
| T7 | Stolen session or password + TOTP | Strong unlock needs the vault passkey or recovery key; PIN guesses online, capped | Weak PIN within the cap |
| T8 | Rogue machine approval | Fragment link or committed SAS, signed transcript, scope and TTL | Owner approving without reading |
| T9 | Server substitutes a recipient key | Recipient binding table; fail closed without witness | First invite channel trust |
| T10 | Server injects or swaps values | Writer signatures, chained records, epoch fencing | — |
| T11 | Removed principal | Atomic epoch change, write fence, lease revocation, rotation list | Already-seen plaintext |
| T12 | Leaked CI credential | OIDC binding, custodial label, 90-day expiry | Delivered wraps |
| T13 | Compromised machine during lease | Memory-only, scope, TTL, revocation | Values used during the lease |
| T14 | Workload or Worker secret disclosure | Separate labelled environments, signed requests, re-key on custody end | Custodial by design |
| T15 | Nonce reuse | Per-version subkeys with random nonces | — |
| T16 | Leaks via argv, logs, caches, crash dumps | stdin input, redaction, no plaintext caches, names-only logs | OS memory inspection |
| T17 | Audit tampering | Hash chain, witness checkpoints | Server-trusted between checkpoints |
| T18 | Library vulnerabilities | Pinned versions, RFC vectors, advisory review per change | — |
| T19 | Identity-provider migration | PRF input independent of user ID, vault-owned credentials | — |

## Dependencies on the central session

Reused from the central provider-agnostic session model:

1. The `ttr+stepup` proof for the share service, verified offline with `iss`,
   `env`, `typ`, `aud` and `act` pinned, `jti` and `nonce` single use.
   MFA unlock stays off until it ships.
2. The `cli` device session (`dev`, `sid`, approval with `stepUpGrantId`) that
   machine grants bind to; a proof is not a liveness check, so redemption
   checks the `sid` separately.
3. The host-only child session for `vault.tuturuuu.com` (design gate G9).
   Slice 3a is blocked on G9.

Login passkeys and their credential list are not used for vault unlock.
