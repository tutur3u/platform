Status: **Design, pending independent cryptography and security review.** No
code ships before that review is recorded. Every rule below is **Planned**
until its slice lands with the listed regression coverage.

The vault stores workspace secrets and environment variables so that people,
fleet machines, agents and CI can use them from any machine without copying
files. Values are encrypted on the client. The Tuturuuu server stores
ciphertext, wrapped keys and metadata only, and cannot decrypt a value on its
own in any unlock mode described here.

**Scope:** Web (`tuturuuu.com`), the `ttr` CLI, CI and deploy runners, and fleet
agents. **Out of scope:** `public.workspace_secrets`, which remains a plaintext
feature-flag and configuration table and is not a secret store.
`private.mobile_deployment_*` and other server-held vaults keep their existing
custodial model until they are migrated onto this vault in a later slice.

## Goals

1. The server alone, including a full database dump plus every Tuturuuu server
   secret, cannot decrypt a secret value.
2. A person unlocks with a Tuturuuu passkey, or with Tuturuuu MFA plus a vault
   PIN, on any machine with no local state.
3. Machines and agents receive short-lived, scoped, device-bound grants that an
   owner approves from a phone or browser. Nothing durable is written to the
   machine; a wiped machine loses only its lease.
4. CI and Cloudflare deploys use scoped, short-lived, OIDC-bound service access.
5. Sensitive values are write-only for people by default.
6. Every reveal, copy, run, pull, sync, grant and key change is audited by
   name, never by value.

## Non-goals and explicit limits

- **Web E2EE trusts the served code.** A server that ships malicious
  JavaScript to an unlocked browser can read what that browser decrypts. The
  vault page runs on an isolated origin with a strict CSP (see
  [Web delivery](#web-delivery-hardening)), and the signed CLI is the stronger
  client. This limit is inherent to browser E2EE and is stated in the product.
- **A decrypting client can always exfiltrate.** "Sensitive" and "not
  revealable" are enforced by key distribution and first-party clients, not by
  making a decrypted value unreadable to the process that uses it.
- **Metadata is not encrypted.** Workspace, project, environment and variable
  names, timestamps, expiry, version numbers, sizes and audit events are
  plaintext so the server can authorise, remind, sync and audit. Values,
  descriptions and notes are encrypted.
- **Losing every unlock method loses the data.** There is no server-side
  escrow. Workspace owners always hold a wrap of every environment key, and
  each user has a recovery key.

## Primitives

Only standard, reviewed constructions are used. No custom cryptography.

| Use | Construction | Implementation |
| --- | --- | --- |
| Value encryption | AES-256-GCM, 96-bit random nonce, 128-bit tag | WebCrypto (browser, Bun, Node) |
| Key wrapping to a public key | HPKE base mode, RFC 9180, `DHKEM(X25519, HKDF-SHA256)`, `HKDF-SHA256`, `AES-256-GCM` | `@hpke/core` with `@hpke/dhkem-x25519` over WebCrypto; RFC 9180 test vectors in CI |
| Key wrapping to a symmetric KEK | AES-256-GCM with a fresh random nonce and AAD binding | WebCrypto |
| Key derivation | HKDF-SHA256 with explicit `info` labels | WebCrypto |
| Signatures (key log, approvals) | Ed25519 | WebCrypto Ed25519, `@noble/curves` fallback where WebCrypto lacks it |
| PIN hardening | Argon2id, `m=64 MiB, t=3, p=1` minimum | `hash-wasm` (browser), same parameters in the CLI |
| Recovery key encoding | 256 random bits, Crockford base32 in 4-character groups, CRC-free; correctness is checked by unwrapping | — |
| Randomness | `crypto.getRandomValues` only | — |

Every ciphertext carries a `suite` byte and a key version so primitives can be
replaced. The review gate for slice 1 confirms the HPKE and Argon2id library
choices; replacing a library does not change the formats below.

### AAD binding

Every AEAD operation binds its context so a ciphertext cannot be moved between
rows, environments or versions by the server. The AAD is the canonical JSON
(RFC 8785) of:

- values: `{t:"value", ws, project, env, variable_id, version, key_version, suite}`
- key wraps: `{t:"wrap", ws, scope_id, key_version, recipient_kind, recipient_id, suite}`
- unlock wraps: `{t:"unlock", user_id, method, method_id, suite}`

The variable name is bound through `variable_id`, and the name-to-id mapping is
covered by the signed environment manifest (see [Integrity](#integrity-and-the-key-log)).

## Key hierarchy

```text
user unlock method ─KEK─▶ user identity (X25519 enc key, Ed25519 sign key)
                                   │ HPKE
                                   ▼
               environment keys: EDK (AES-256) + ESK (X25519 key pair)
                                   │
            ┌──────────────────────┴──────────────────────┐
     AES-GCM(EDK): normal values          HPKE(ESK public): sensitive values
```

- **User identity keys.** Each user has one X25519 encryption key pair and one
  Ed25519 signing key pair, generated on the client at enrolment. Public keys
  are published in the key log. Private keys exist on the server only as unlock
  wraps.
- **Environment data key (EDK).** A random AES-256 key per environment and key
  version. Normal values are AES-GCM ciphertext under the EDK. The EDK is
  HPKE-wrapped to each principal allowed to read normal values.
- **Environment sensitive key (ESK).** An X25519 key pair per environment and
  key version. Sensitive values are HPKE-sealed to the ESK public key, so any
  writer can set a sensitive value without being able to read one. The ESK
  private key is wrapped only to consumer principals (machine grants, service
  access, sync runners) and to workspace owners for audited break-glass.
- **Projects** group environments and carry RBAC defaults. They hold no key of
  their own; every key is per environment so revocation stays local.

Per-environment keys bound AES-GCM nonce use: an EDK version is rotated before
2^28 encryptions, far inside the random-nonce limit, and on every member
removal.

## Unlock methods

An unlock method produces a key-encryption key (KEK) that unwraps the user's
identity private keys. A user may enrol several; each is a separate wrap.

### Passkey (WebAuthn PRF)

The vault performs its own `navigator.credentials.get()` with the `prf`
extension against the user's Tuturuuu passkeys (`rpId` `tuturuuu.com`,
`userVerification: "required"`).

- PRF input: `SHA-256("tuturuuu/vault/prf/v1" ‖ user_id)`.
- `KEK = HKDF-SHA256(ikm = prf.first, salt = wrap_salt, info = "tuturuuu/vault/kek/passkey/v1" ‖ credential_id ‖ user_id)`.
- The server stores, per credential: `credential_id`, `wrap_salt`, and the
  AES-GCM wrap of the identity private keys. The PRF output never leaves the
  client.
- A passkey without PRF support (for example an authenticator that did not
  enable `hmac-secret`) is reported in enrolment and the user is offered a new
  PRF-capable passkey. PRF availability per platform is verified in slice 3.
- Synced passkeys (iCloud Keychain, Google Password Manager) carry the PRF
  secret across a user's devices, which is what makes passkey unlock work on a
  new machine without local state.

**Trade-off:** confidentiality rests on the authenticator's PRF secret. The
server cannot derive it. Releasing the wrap needs only a signed-in session
because the wrap alone is useless; this is pure E2EE.

### Tuturuuu MFA plus vault PIN (split key)

TOTP is a shared secret that the server also holds, so a design that unlocks on
TOTP alone would let the server unlock. MFA unlock is therefore a two-share
design: one share from something only the user knows, one released by a
separate service after fresh MFA.

- **Client share:** `S_c = Argon2id(PIN, salt = pin_salt, m=64 MiB, t=3, p=1)`.
  The PIN is at least 8 characters; the UI recommends a passphrase.
- **Server share:** `S_s`, 32 random bytes generated by the client at
  enrolment and sent once to the **share service**, a Cloudflare Worker with
  its own Durable Object storage and an encryption key held only as a Worker
  secret. `S_s` is never stored in the Tuturuuu database.
- `KEK = HKDF-SHA256(ikm = S_c ‖ S_s, salt = wrap_salt, info = "tuturuuu/vault/kek/mfa-pin/v1" ‖ user_id)`.
- **Release:** the share service returns `S_s` only for a request carrying a
  step-up proof from the central session (TOTP or passkey user verification
  within 5 minutes, bound to this user and to a single-use release nonce). Each
  release consumes one step-up. Releases are limited to 10 per user per 24
  hours and are audited.

**Exact security trade-off versus pure E2EE:**

| Attacker holds | Passkey unlock | MFA + PIN unlock |
| --- | --- | --- |
| Database dump only | Nothing | Nothing (missing `S_s`) |
| Database + share service storage and its key | Nothing | Offline Argon2id search over the PIN. Strength equals PIN entropy |
| Account password + TOTP device, no PIN | Nothing | Online guessing, each guess costs one fresh TOTP step-up and is capped at 10 per day |
| Malicious server code delivered to an unlocked browser | Values that browser decrypts | Same, plus the PIN as it is typed |

So MFA + PIN is **not** pure E2EE against an attacker who controls both the
database and the share service: it degrades to a password-hardened secret.
Passkey unlock does not degrade. Workspaces can set the policy
`unlock.allow_mfa_pin = false` to require passkeys or recovery keys only.
OPAQUE (RFC 9807) for the PIN is a candidate for a later revision so the share
service never sees PIN-derived material and offline search needs the share
service's OPRF key; it does not change the table above.

MFA-only unlock without a PIN is not offered, because it is server custody.

### Recovery key

At first enrolment the client generates a 256-bit recovery key, shows it once
as grouped base32, and requires the user to confirm a group from it.
`KEK = HKDF-SHA256(recovery, wrap_salt, "tuturuuu/vault/kek/recovery/v1" ‖ user_id)`.
The user can regenerate it while unlocked, which replaces the wrap. The server
never sees it.

## Principals and grants

| Principal | Holds | Lifetime | Can read normal | Can read sensitive |
| --- | --- | --- | --- | --- |
| Member (person) | Identity keys via unlock methods | Membership | With `reader` role | Only workspace owners, break-glass, audited |
| Machine grant (CLI, fleet agent) | Ephemeral device key in memory | Default 8 h, max 24 h | If granted | If granted |
| Service access (CI, deploy) | Service credential plus OIDC | Lease 15 min; credential max 90 days | If granted | If granted |
| Sync runner | A machine grant or service access | Same as its carrier | If granted | If granted |
| Workload (Cloudflare Worker, Durable Object) | Workload key held as a Worker secret | Lease 1 h, renewable | If granted | If granted |

### Workload principals (server-readable environments)

Some values must be usable by an always-on server workload with no person
present, for example channel connector tokens and per-workspace model API
keys. A workload principal is an X25519 key pair whose private key is a
Cloudflare Worker secret for one named Worker. An unlocked environment admin
grants it by HPKE-wrapping the environment keys to its public key, exactly as
for a machine grant.

- **This is custodial by construction.** Whoever can read that Worker secret
  and the vault ciphertext can decrypt every environment granted to the
  workload. An environment with any workload grant is labelled
  **server-readable** in the UI, CLI and audit, and goal 1 does not hold for
  it. Workspaces put workload-consumed values in their own environments so
  that other environments stay end-to-end encrypted.
- The workload authenticates with its Worker identity (a signed request using
  a separate Ed25519 workload signing key, also a Worker secret) and receives a
  1-hour lease listing the current key version and value versions. A Durable
  Object may keep decrypted values in memory for the lease and refetches when
  the lease ends or when a version-change notification arrives.
- A workload granted `writer` on specific variables can write new versions,
  for example a refreshed session blob. Writes are sealed client-side in the
  Worker under the current EDK or ESK, carry the expected previous version for
  compare-and-swap, and are audited with actor kind `workload`.
- Workload grants can be revoked instantly; revocation triggers the normal
  re-key flow for that environment.

### Machine and agent grants

1. `ttr secrets login` (or the first `get`/`run` without a lease) generates an
   **ephemeral X25519 device key pair in memory** and a request with the public
   key, requested scope (environments, `read`/`run`, TTL) and a machine label.
2. The CLI prints a 10-character base32 **safety code**,
   `base32(SHA-256("tuturuuu/vault/sas/v1" ‖ device_pub ‖ request_id))[0..10]`
   (50 bits), and publishes a fleet login request (`flow: "link"`, the vault
   approval URL on `tuturuuu.com`, the safety code as its user code). The
   request appears as a login card in the Mastermind fleet view on mobile and on
   the Web approval page.
3. The owner opens the card, unlocks (passkey or MFA + PIN), compares the
   safety code, narrows scope and TTL, and approves. The approving client
   HPKE-wraps the granted EDKs and, if granted, ESK private keys to
   `device_pub`, signs the grant with the owner's Ed25519 key, and uploads it.
4. The CLI fetches the signed grant with a lease token, verifies the signature
   against the key log, and unwraps in memory.

The server cannot substitute its own device key without changing the safety
code; doing so within the approval window would need about 2^50 X25519 key
generations online.

**No durable machine state.** `ttr secrets agent` holds the device private key
and decrypted environment keys in process memory and serves the same user's
`ttr` invocations over a Unix socket (mode 0600, peer UID checked;
a named pipe with an owner-only ACL on Windows). When the agent exits, the
lease expires or the owner revokes it, the material is gone. The optional
`--keychain` flag caches only the device private key in the OS keychain until
lease expiry, for long agent sessions; it is off by default and the cache is
disposable. Leases are renewable by the owner from the card without a new
device key.

Agents receive grants through the same flow. An agent brief carries the grant
request ID, never a secret or a file path.

### Service access for CI and deploys

A service credential is a 256-bit random secret shown once, stored by the
operator as a CI secret (for example a GitHub environment secret).

- `auth = HKDF(cred, "tuturuuu/vault/svc/auth/v1")`; the server stores
  `SHA-256(auth)` for lookup and an HMAC for comparison.
- `(svc_priv, svc_pub) = X25519 from HKDF(cred, "tuturuuu/vault/svc/key/v1")`;
  the server stores `svc_pub`. Granted environment keys are HPKE-wrapped to
  `svc_pub` by an unlocked owner when the credential is created.
- **OIDC binding is required for CI.** A request must present the credential's
  `auth` and an OIDC token matching the bound issuer, repository, ref and
  environment claims. The server then issues a 15-minute lease that releases
  the wrapped keys. A leaked credential alone fails the OIDC check; a leaked
  OIDC token alone has no decryption key.
- Cloudflare deploys use the same path from CI. Credentials without OIDC
  (non-GitHub runners) are allowed only with a TTL of at most 7 days and are
  marked in the UI.
- `ttr secrets pull --stdout --format dotenv|json` prints to stdout only, for
  piping into a deploy step. It never writes a file.

## Values, sensitivity and versions

- A variable has a name (`^[A-Z_][A-Z0-9_]{0,127}$`), a type (`secret`,
  `variable`), a sensitivity flag, optional expiry and rotation interval, and
  versions.
- **Variables** (non-secret configuration) are still encrypted; they are
  revealable to readers by default.
- **Secrets** are revealable to readers with a confirmation step, and each
  reveal and copy is audited.
- **Sensitive** secrets are HPKE-sealed to the ESK. Members can set and
  replace them but cannot reveal them. They reach processes only through
  machine grants, service access and sync. Workspace owners can break-glass
  reveal with step-up; it is audited and notifies other owners.
- Each write creates an immutable version. The newest 20 versions or 90 days
  are kept, whichever is more; restoring creates a new version. Deleting a
  variable tombstones it and purges ciphertext after 30 days.
- Reminders: the server sends expiry and rotation reminders 14, 3 and 0 days
  ahead to environment admins, using plaintext metadata only.

## RBAC

Workspace permissions gate the vault; environment roles gate key distribution.

| Role | Names and metadata | Reveal normal | Set values | Run/pull | Manage members, grants, rotation |
| --- | --- | --- | --- | --- | --- |
| `viewer` | Yes | No | No | No | No |
| `consumer` | Yes | No | No | Through a grant | No |
| `reader` | Yes | Yes | No | Yes | No |
| `writer` | Yes | Yes | Yes | Yes | No |
| `admin` | Yes | Yes | Yes | Yes | Yes |

A new workspace permission `manage_secrets_vault` lets a member create vault
projects and environments. Server checks decide who may fetch which ciphertext
and wraps; cryptography decides who can decrypt. A server RBAC bypass leaks
ciphertext only; a key distribution mistake is a confidentiality bug and is
covered by tests in slice 2.

## Membership and re-keying

- **Add:** a new member enrols identity keys. The server lists them as
  pending. An unlocked environment admin approves, which HPKE-wraps the EDK
  (and nothing sensitive) to the member's key from the key log and signs a
  key-log entry. The server cannot complete this step.
- **Remove or downgrade:** the server immediately stops serving wraps and
  ciphertext to the member. The next admin unlock is prompted to rotate: a new
  EDK and ESK version is generated, wrapped to remaining principals, and values
  are re-encrypted client-side in bounded batches with an idempotent progress
  marker per variable. Reads use the newest key version a value is encrypted
  under. Removal also lists the values the member could reveal so admins can
  rotate the underlying credentials, because a removed member may have kept
  plaintext.
- **Device or passkey loss:** delete that unlock wrap; no environment re-key is
  needed because environment keys were never wrapped to an unlock method.
- **Identity key compromise:** the user rotates identity keys, which re-wraps
  every environment key addressed to them and triggers environment rotation.

## Integrity and the key log

The server could try to substitute a public key so an admin wraps to the
attacker. Each workspace vault keeps an append-only, hash-chained **key log**:

- Entry `n` holds `{prev_hash, kind, subject, public keys or grant digest, issued_at}`
  and an Ed25519 signature by an admin key that is valid at `n-1`.
- The genesis entry is signed by the creating owner. Clients verify the chain
  from genesis on every unlock and cache the last verified head in browser
  storage as a convenience, so a later rollback or fork on that browser is
  detected. The cache is not required for correctness.
- Each environment has a signed **manifest** (`variable_id → name, type,
  sensitive, current version`) so the server cannot rename or swap values
  between variables without a signature failure.
- Members can compare a 12-word key fingerprint out of band; the UI shows it on
  the member page.

Residual risk: the first enrolment is trust-on-first-use, and a server can
withhold entries (freeze) but cannot forge them without an admin signing key.

## Audit

`private.vault_audit_events` is append-only (no update or delete grant),
hash-chained per workspace, and records actor kind (`user`, `machine`,
`service`, `sync`), actor ID, event, resource IDs and names, IP prefix, user
agent family, grant or lease ID, and result. It never records a value,
ciphertext, wrap, PIN, share or token.

Server-observed events (ciphertext fetch, wrap fetch, lease issue, share
release) are authoritative. Client-reported events (reveal, copy) are recorded
by first-party clients before the value is shown; a modified client can skip
them, which the audit page states.

## Sync targets

Sync decrypts, so it runs only where a decrypting principal already exists: in
an unlocked browser, a `ttr secrets sync` process holding a machine grant, or a
CI job with service access. The server never syncs on its own.

| Target | Direction | Notes |
| --- | --- | --- |
| Cloudflare Worker secrets | Push | Per Worker and environment, through the Cloudflare API; bounded batches, idempotent by name and value digest |
| GitHub environment secrets | Push | Libsodium sealed box to the repository public key, as GitHub requires |
| Vercel | Import and archive | Imports values Vercel returns; Vercel `sensitive` values cannot be read back, so they are listed by name for manual re-entry |

Provider tokens are themselves sensitive vault values. Sync logs carry names,
target identifiers, value digests truncated to 8 hex characters (HMAC under the
EDK, not a plain hash) and results. Every sync run is bounded (at most 500
writes, 3 retries with backoff) and records terminal state.

## CLI

| Command | Behaviour |
| --- | --- |
| `ttr secrets login` | Requests a machine grant and starts `ttr secrets agent` |
| `ttr secrets unlock` | Renews or widens the lease through a new approval |
| `ttr secrets list [--env]` | Names and metadata only |
| `ttr secrets get NAME [--env]` | Prints one non-sensitive value to stdout; refuses a TTY for secrets unless `--reveal` is passed |
| `ttr secrets set NAME [--env] [--sensitive]` | Reads the value from stdin only, never from argv |
| `ttr secrets run [--env] -- <cmd>` | Spawns `cmd` with the environment injected; writes nothing to disk |
| `ttr secrets pull --stdout [--format]` | For CI; prints only |
| `ttr secrets sync <target>` | Runs a configured sync |
| `ttr secrets logout` | Revokes the lease and stops the agent |

`run` passes values only through the child environment. Same-user processes
can read a process environment on most systems; this is the accepted boundary
for `run`. No command accepts a value on argv, and `--debug` output is
redacted by value match.

## Web delivery hardening

- The vault UI is served from `vault.tuturuuu.com` with a nonce-based CSP, no
  third-party scripts, Trusted Types, `frame-ancestors 'none'` and
  `Cross-Origin-Opener-Policy: same-origin`. Passkeys still use `rpId`
  `tuturuuu.com`.
- Decrypted values live only in component memory, never in TanStack Query
  caches, Web Storage, IndexedDB or logs. Unlocked state ends on tab close,
  15 minutes of inactivity, or lock.
- The vault API is bearer-authenticated per the
  [shared session](/platform/architecture/shared-session) rules and same-origin
  for cookie requests.

## Storage

Ciphertext, wraps, manifests, the key log and audit live in Postgres tables in
the `private` schema, reached only through server routes and
`packages/internal-api` with service credentials. There are no Supabase-only
features (no client RLS path, no Edge Functions), so the tables move to
Hyperdrive with the rest of the platform. The share service is a Cloudflare
Worker and Durable Object. The API stays under
`apps/web/src/app/api/v1/workspaces/[wsId]/vault/**`.

## Package boundaries

- `packages/vault-crypto`: framework-agnostic core (formats, AAD, HPKE wraps,
  KEK derivations, recovery encoding, safety codes, key-log verification). Its
  portable entrypoint imports no Next.js, React, Cloudflare or request globals.
- `packages/internal-api/src/vault/*`: data access and authorisation.
- `packages/sdk/src/cli/secrets/*`: CLI commands and the agent.
- `apps/share-service` (Cloudflare Worker): MFA share custody.

## Threat model

| ID | Threat | Mitigation | Residual |
| --- | --- | --- | --- |
| T1 | Database dump or backup leak | Ciphertext and wraps only; `S_s` stored elsewhere | Metadata exposure |
| T2 | Compromised Tuturuuu server (DB + API) | Cannot decrypt; key log and AAD detect substitution | Can deny service, withhold key-log entries, observe metadata |
| T3 | Server + share service compromise | Passkey and recovery wraps unaffected | MFA + PIN wraps reduce to PIN strength (Argon2id) |
| T4 | Malicious JavaScript on the vault origin | Isolated origin, CSP, Trusted Types, SRI, no third parties | Inherent web E2EE limit; CLI is the stronger client |
| T5 | XSS on another `tuturuuu.com` app | Separate origin; no vault state in shared storage | — |
| T6 | Stolen session cookie or token | Ciphertext without keys; MFA share needs fresh step-up | Metadata read |
| T7 | Stolen password + TOTP | Needs PIN or passkey; online PIN guessing capped at 10 per day | Weak PIN |
| T8 | Phished approval of a rogue machine | Safety code, machine label, scope and TTL on the card; signed grants; revocation | User approving without comparing |
| T9 | Server swaps a device or member public key | Safety code (50 bits online); signed key log | First-use trust |
| T10 | Removed member | Wraps and ciphertext stop; re-key; credential rotation list | Plaintext already seen |
| T11 | Leaked CI service credential | OIDC binding, 15-min leases, scope, max 90 days | Non-OIDC credentials up to 7 days |
| T12 | Compromised fleet machine | Lease scope and TTL; in-memory only; revocation | Values used during the lease |
| T13 | Replay or row swapping by server | AAD binding, signed manifest, versioned keys | — |
| T14 | Nonce reuse | Random nonces, per-environment keys, rotation before 2^28 | — |
| T15 | Value leakage through logs, argv, crash dumps, caches | stdin-only input, redaction, no cache of plaintext, names-only logs | OS-level memory inspection |
| T16 | Audit tampering | Append-only grants, hash chain | A malicious server can stop writing new events |
| T17 | Brute force of the share service | Fresh step-up per release, per-user daily cap, audit and owner notification | — |
| T18 | Supply chain (crypto libraries) | Pinned versions, RFC test vectors, advisory review per change | — |
| T19 | Workload key or Worker secret disclosure | Server-readable label, separate environments, per-Worker keys, revocation and re-key | Custodial by design for granted environments |

## Dependencies on the central session

Step-up proofs, passkey user-verification recency and device identity reuse the
central provider-agnostic session model (see
[Shared session](/platform/architecture/shared-session#credentials-minted-from-a-signed-in-session)).
The vault needs:

1. A signed, audience-bound step-up proof (`sub`, `amr`, `auth_time`, `nonce`,
   `aud = "vault-share"`, `exp ≤ 5 min`) that the share service can verify
   offline.
2. Passkey credential IDs for the current user, to build `allowCredentials`.
3. A device and lease identity shape compatible with CLI device approval and
   the fleet login card.

Until (1) exists, MFA + PIN unlock stays disabled; passkey and recovery unlock
do not depend on it.
