Every Tuturuuu web app, whether on its own subdomain or mounted at
`tuturuuu.com/<app>`, uses one signed-in session. These are the customer-facing
rules for that session. The implementation and rollout live in
[Start bridge](/build/devops/start-bridge#shared-session-on-the-apex-decision-b-server-held-session).

**Scope:** Web and every satellite app in a browser. **Exceptions:** the mobile
app and the CLI hold bearer tokens in native secure storage and keep their own
sign-in flows; see [Authentication](/platform/architecture/authentication#raw-session-tokens-are-native-only).

Status: **Enforced** means the rule is live in code with the listed regression
coverage. **Planned** means it is approved and scheduled in the shared-session
plan, with its owner PR not yet merged.

## Who can read the session

| Rule | Default | Status |
| --- | --- | --- |
| The session cookie is `HttpOnly`, `Secure`, `SameSite=Lax`; page script cannot read it | Applies to every browser session | Planned (Stage A) |
| No auth endpoint returns a raw access or refresh token to a browser request; only native clients (no `Origin`, no Fetch Metadata) receive token pairs | Always | Enforced: `lib/auth/password.test.ts`, `lib/auth/otp.test.ts`, `__tests__/mobile-session-browser-fence-route.test.ts` |
| No endpoint exports the session or its cookies as JSON | Always | Enforced (`/api/auth/me/session` removed) |
| Browser code never holds a session token in Web Storage, IndexedDB or the Cache API | Always | Planned (browser-surface guard) |

## Logout

| Rule | Default | Status |
| --- | --- | --- |
| Logout asks before changing sessions; app-only is the primary satellite choice, and central logout ends the current account in this browser | Explicit choice | See Logout confirmation and app scope below |
| **Log out everywhere** ends every session of the account on every device | Explicit second action | Planned |
| Logout preserves other saved accounts and does not purge every site cookie with `Clear-Site-Data` | Current-account scope | See Logout confirmation and app scope below |
| Logout never clears local app data (`"storage"` is not sent), so unsent drafts survive | Always | Planned |
| Logout and a password change revoke outstanding cross-app handoff tokens | Always | Enforced |
| After logout, another app on a subdomain stops accepting the session within 15 minutes | 15 min bound | Planned (app access-token lifetime 8 h to 15 min) |
| A signed-out session's access token stops working within 15 minutes | 15 min bound | Planned (hosted access-token lifetime 60 min to 15 min) |

## Logout confirmation and app scope

The logout menu opens the central confirmation page before clearing any session.
Opening `/logout`, going back, and a GET to an app logout endpoint do not sign
anyone out. The page displays the verified current account when available and offers these choices:

- **This app only** is the primary choice for a registered satellite on its own
  host. Its POST clears only host-scoped app cookies. Web and other app hosts
  keep their sessions. A secure, HttpOnly, host-only signed-out marker prevents
  shared-cookie fallback and automatic refresh from restoring that app's actor.
  A signed-out app redirects through central login with an explicit account-confirmation step before a new app token is minted. Ordinary internal SSO remains automatic when the app has not been signed out. A fresh explicit app sign-in clears the marker. App-only logout keeps the central Web session and is not a security boundary against someone who can use that session. A direct central login return link without the confirmation request can issue a fresh app token. The confirmation stays on Web after success so it does
  not immediately re-enter the signed-out app.
- **All of Tuturuuu** means the **current account in this browser**, using the
  existing local sign-out operation. It does not sign out other saved accounts
  or other devices. It does not call the all-accounts logout endpoint.
- **Go back** returns to the registered app without changing a session.

If the central session has expired while an app session remains, a registered
app can still be logged out without signing into Web first. The central-account
choice is omitted in that state. Central logout uses the server local-scope
endpoint followed by a full document navigation, so no new browser Supabase
client surface is needed.

App-only logout is not offered for an unknown origin, an app without this logout
endpoint, an origin outside the central site's configured shared-cookie domain,
an HTTP origin, or apps sharing the central hostname (including localhost ports and
same-origin mounts), whose cookie scopes cannot be isolated by host. The display
name and return origin come from the first-party registry; a `from` label or
arbitrary return URL does not become a redirect destination.

Satellite logout accepts POST from its own origin and, for the confirmation
flow only, the exact configured central origin with same-site browser metadata.
Other sibling origins, cross-site requests, missing or opaque origins are rejected
without setting cookies. CORS credentials are allowed only for that accepted
origin. GET returns 405 except legacy Hive and Teach entries, which redirect to the
confirmation page without clearing cookies; OPTIONS never clears a session. This narrow endpoint
exception does not change general cookie-authenticated mutation rules.

Regression coverage: `packages/auth/src/app-only-logout.test.ts` checks cookie
scope and origin rejection; `packages/utils/src/logout-target.test.ts` rejects
hostile and non-isolated destinations; the logout page component tests cover
EN/VI, ask-first behavior, failure recovery and current-account local scope.
`packages/satellite/src/components/user-nav-client-settings.test.tsx` verifies
that the menu navigates without calling logout. These are fixture-based checks,
not signed-in production acceptance. `packages/auth/src/proxy/logout-fence-integration.test.ts` and the login form logout-confirmation test cover the explicit click before re-entry; the transport test drives the actual logout handler over loopback HTTP.

## Credentials minted from a signed-in session

| Credential | Rule | Status |
| --- | --- | --- |
| Cross-app handoff token | Lasts at most 60 s (300 s for CLI copy-paste), is single use, and is only for a known app or an enabled registered external app | Pending (#6840) |
| CLI login token | Issued only to a top-level browser navigation; the copy page renders in an isolated origin | Enforced: `app/api/cli/auth/start/route.test.ts`, `apps/web/next.config.test.ts` |
| Realtime join ticket | Lasts 60 s, covers one topic, cannot become a session | Enforced (existing) |
| Storage download/upload link | One object; private links last at most 15 minutes | Planned clamp |
| API keys, CLI device approval, QR-login approval, external-app exchange, passkey registration, MFA changes, email or password change, account deletion | Require a recent step-up (passkey user verification, or password plus second factor, within 5 minutes) on a Web page | Planned |

## Cross-site protection

Cookie-authenticated changes are accepted only from the same origin. Requests
from other sites and from sibling `*.tuturuuu.com` subdomains are rejected.
Bearer (mobile, CLI) requests are unaffected. Status: Planned (report mode
first, then enforce).

## Local browser verification

With `TUTURUUU_LOCAL_E2E_AUTH_BYPASS=1` and an HTTP loopback
`NEXT_PUBLIC_SUPABASE_URL`, satellite cookie cleanup preserves the configured
Supabase session cookie on `localhost` and `127.0.0.1`. Cookies are shared across
ports, so expiring that cookie from Tasks also signs the browser out of Web.
This applies to local verification across Web and satellites; the default
without the bypass continues to clear unsupported cookies. Unrelated hosts and
cloud Supabase configuration do not enable this exception. Production shared
domain behavior is unchanged. Regression coverage lives in
`packages/auth/src/app-session-local-cookies.test.ts`; the browser lifecycle spec
covers signup, workspace creation, invitations and task CRUD.

## Account switch serialization

Web account switches use server-only service-role Supabase REST against the
existing private vault tables. The signed device cookie and derived secret hash
bind every switch to its saved-account set. The target update compares its
composite device/user key and observed `updated_at`; the device update compares
its ID, secret hash, observed active user (including null), observed `last_seen_at`
and unrevoked state. Both updates must return exactly one row. Version timestamps
advance beyond the observed value even under a frozen millisecond clock.

Outgoing rotated tokens are read from cookies without a provider refresh. Target
session validation uses a detached client with one refresh HTTP attempt and no
retry. Browser cookie writes remain buffered until both updates succeed. A CAS
loss returns generic HTTP 409 and emits no session cookies. The session row can
remain updated if the following device CAS fails; these REST writes are not an
atomic transaction. Independent revocation, target removal after admission, and
cross-origin cookie ordering remain concurrency limitations. Other device touches
can cause a safe conflict. Switching requires no direct database connection URL.

Removing the active account deletes its stored row first. A failed fallback
switch clears browser auth cookies and returns a login redirect target. An invalid target
session returns `requiresReauth` with a generic error and retains its saved entry
for explicit removal or reauthentication; provider error text is never returned.

The Web client shares switch admission across modal lifetimes, retains only the
latest queued intent, and suppresses stale navigation after query invalidation.
Web Locks serializes participating tabs on the same origin; a metadata-only
local-storage intent token suppresses superseded callbacks across those tabs.
Browsers without Web Locks retain per-document serialization only.

**GAP-01 partial: cross-origin Set-Cookie ordering OPEN.** Satellite direct
requests, response-cookie delivery and competing session refresh writers are
outside this switch-only guarantee. A database commit and a stale callback check
cannot order browser cookie application. Canonical coordination and cookie
finalization remain a proposal; this change does not establish full session
ordering or exactly-once provider effects.

Regression coverage: `switch-intent.test.ts` covers latest-intent admission,
asynchronous callback fencing and transport failure without replay.
`rest-cas.test.ts` covers concurrent admission, revocation, removal, actor/device
binding and fail-closed active logout. `rest-transport.test.ts` exercises real
PostgREST and auth SDK clients with synthetic HTTP responses, exact CAS predicates,
version advancement and actual response Set-Cookie absence on failed CAS.
`account-switch-auth.test.ts` covers pure expired-cookie reads, bounded refresh,
and buffered installation. These fixtures do not establish deployed provider behavior.
