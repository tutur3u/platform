Tuturuuu authenticates users before granting access to protected features. Workspace membership and permissions determine what an authenticated user may do; successful sign-in alone is not access to every workspace.

## IEEAI free invitation exchange proposal

The central app-token exchange proposal automatically accepts a pending MEMBER
invitation only for `ieeai-stats` and workspace
`a65cebd7-3a8c-4883-a3d9-82f9703d652f`, also present in the verified app's
`allowedWorkspaceIds`. It requires a confirmed Auth identity after the existing
app-secret, token, PKCE and MFA checks. User-id invitations match that actor;
email invitations match only the case-normalized confirmed Auth email. Multiple
matches, GUEST invitations and uninvited actors remain pending or denied.

The default is fail closed. Positive server subscription/product records must
prove FREE, zero-cost, non-seat entitlement; missing records, paid products,
unknown state and read failures do not qualify. Locked billing state prevents an
upgrade from racing acceptance. The canonical membership finalizer retains the
invited role set, and membership, selected-invite removal and ids-only audit
commit together. Existing members retain ordinary `workspace:session` access;
refresh never accepts an invitation. Other apps and paid-workspace paths keep
their existing behavior. No Polar API call is part of this proposal.

Regression coverage is in `ieeai-free-invite.sql`, the database verifier and
concurrency harness, `ieeai-free-invite.test.ts`, and the exchange integration
tests. Run the disposable verifier through resource admission; it exercises
rollback/reapply, audit failure rollback and competing acceptance/upgrade
transactions. Local proof does not establish deployment readiness. Release
requires central Web deployment and the separately approved additive migration;
the external IEEAI server is not a deployment dependency for this platform rule.

## OAuth Sign In

Customer sign-in supports configured OAuth providers. Staff sign-in has a separately restricted Microsoft entry. Provider identities and account linking must be verified; an email address or domain alone is not sufficient authority to link accounts or grant staff access.

## Raw session tokens are native-only

Browser sign-in uses the browser session flow. Raw access and refresh tokens are reserved for supported native-client authentication flows; browser requests to those native token flows are refused. Native-client compatibility and browser session behavior require separate verification.

## Mobile App Lock

An elapsed App Lock timeout applies to the device's signed-in content even when
the app resumes into an authentication route. Add Account stays available, and
returning to protected content requires local authentication. The unlock action
is visible on the first resumed Flutter frame. App-owned foreground refreshes
wait for the gate to clear.

The Flutter boundary hides protected routes during lifecycle transitions.
App Lock hides account toasts even on Add Account. Lock and account changes
discard queued toasts from the former UI session. On iOS the window cover attaches when the scene starts to deactivate.
The app submits a safe frame for the current activation, then the native cover
stays in place through the next display interval. Android 13 and later suppress
the Overview thumbnail. Android 12 and earlier keep the entire window secure
while App Lock is enabled and an account is signed in. A policy or account
change requires its own Flutter frame acknowledgment and a native display
interval before Android clears the secure flag. Both bridges retry transient
failures within the current transition. If retries fail, privacy stays in
place and the next activation starts a fresh handshake.

The mobile lifecycle tests exercise first-frame privacy, deferred refresh and
stale prompts. The registered destinations tests drive Add Account cancellation
and a platform deep link through the production router.

### Verify device snapshot ordering

Use the same candidate build on an iPhone with a device passcode and on an
Android 12 device with a PIN. Sign into a test account, set App Lock to
**Immediately**, and open a workspace or mailbox with recognizable test text.
Use an external camera in slow motion to record the screen and inspect the
recording frame by frame. Repeat with light and dark appearance.

1. **iOS.** Open the app switcher directly from the protected page. Check that its
   preview contains no test text. Reopen the app, cancel authentication, and
   confirm that the first frame after the native cover is the lock screen.
   Rapidly repeat the switch twice and return to the app. Confirm that neither
   a stale page nor a stuck cover appears. Unlock using Face ID or Touch ID, then
   repeat using the device passcode. Repeat after terminating the app from the
   switcher and launching it directly.
2. **Android 12.** While the protected page is visible, press Power and Volume
   Down. Confirm the OS rejects the screenshot or captures a blank app window.
   Open Overview without leaving the page first and check that the thumbnail
   contains no test text. Return and unlock using the device PIN. Repeat the
   screenshot on the restored page. Switch to a second test account and
   verify screenshots stay blocked across the transition. Sign out and verify
   screenshots work after the sign-in screen replaces the signed-in content.
   Sign in again, disable App Lock, and confirm screenshots work on the
   current page. On Android 13 or later, repeat the Overview check.
3. **Both.** Open Add Account, background the app, return, and tap its cancel
   button. Verify that the lock screen precedes Home, including any workspace
   toast. Repeat by tapping `https://tuturuuu.com/apps` from another app.
   Start disabling App Lock from Settings, background during authentication,
   then return. Confirm that a
   new unlock works and the stale prompt cannot disable App Lock.
4. **Both.** Leave Mail open when backgrounding. Return and cancel the unlock.
   Confirm the mailbox fetch logs show zero resume refreshes. Unlock and
   confirm the refresh fires after authentication.

## Web CSRF and forwarded workspace requests

Web's CSRF rollout is controlled by `TTR_CSRF_MODE`: unset or invalid values
leave it off, `report` logs rejected checks without blocking, and `enforce`
returns 403. Cookie-bearing mutations from same-site sibling origins are denied
unless the Web adapter explicitly trusts the exact serialized origin. The sole
satellite entry is `https://workspace.tuturuuu.com`, whose API requests forward
to Web. Same-origin mounts need no satellite entry. Other subdomains, alternate
schemes or ports, userinfo, paths, and missing or opaque origins do not qualify
for the same-site exception. Cross-site, `none`, and unknown Fetch Metadata
remain rejected even with that trusted origin.

Saved-account endpoints use exact registered first-party origins for
credentialed CORS. Their mutation handlers require an allowed `Origin` and an
`application/json` content type even when the global guard is off. Account JSON
responses use `Cache-Control: private, no-store`. The account route tests cover
allowed Web and satellite callers, rejected origins and media types, and cache
headers.

Before moving Web to `enforce`, have Release Operations read back the current
production mode. Follow the [CSRF rollout runbook](/build/devops/workspace-start-void#csrf-mode-and-origins)
and run `report` first. Review `CSRF check failed` logs for legitimate traffic
while exercising sign-in, saved-account mutations, and logout through the apex
mounts, Workspace forwarding, and supported satellite origins. Resolve any
legitimate denials and rerun the affected checks before approving `enforce`.
After the change, repeat those checks and restore `report` if legitimate
requests begin failing.

A bearer string cannot exempt a mutation carrying a session cookie. Cookie-less
bearer clients retain their existing exemption; ordinary cookie-less mutations
remain admitted. The three session-clearing logout endpoints still require
origin proof without a session cookie. Shared CSRF callers reject same-site
requests by default; only an explicit adapter opt-in enables this exception.

Regression coverage lives in `apps/web/src/lib/security/csrf.test.ts` and
`packages/auth/src/csrf.test.ts`. The dispatch probe in
`apps/web/src/lib/security/csrf-dispatch.test.ts` exercises the installed Next
production filesystem and render matchers with synthetic logout manifests. A
decoded filesystem hit is not a handler dispatch: route metadata and the render
match must also select the endpoint. This probe does not replace a built Web
artifact or hosting-provider routing acceptance check.

## Saved-account vault key rollout

The vault requires a dedicated `WEB_MULTI_ACCOUNT_SESSION_SECRET` of at least
32 bytes. If the setting is missing or too short, saved-account operations are
disabled and ordinary sign-out remains available. The Web vault writes v2
entries. Legacy entries and entries that cannot be decrypted are treated as
absent. Users sign in again once to save those accounts. The vault never tries
the service key for decryption.

Before deploying this change, provision the dedicated secret in production
under the approved secret-custody process. The predecessor uses the dedicated
secret as soon as it receives it, so coordinate its activation with the
approved re-link window. After deployment, verify an existing device can sign
in again, save an account and switch successfully. Verify a new device can
also save an account. Keep the rollout open for seven days of monitoring.
Source regression coverage lives in the multi-account `crypto.test.ts` and
`vault-switch.test.ts` suites.

## Reserved fleet QA identities

The auth-ops helper creates only two reserved normal-user aliases after exact
source and one-use execution review. It checks for existing Auth identities and
pending email roles before creating either user, and it grants no platform roles.
A1 creates one dedicated shared test workspace through the product UI; A2 has no
shared membership. Trigger-created personal workspaces remain during QA.

Cleanup verifies both identity and workspace inventories, deletes the recorded
shared workspace before its creator, deletes Auth users to revoke sessions, and
then confirms personal-workspace cascade deletion or performs the fenced fallback.
Auth absence and exact filtered alias lookups are required; alias-only tombstones
are counted. Access JWT lifetime is recorded as UNKNOWN without reading auth
configuration. See `scripts/auth-ops/fleet-qa-contract.md` for the exact CLI,
source/ACK binding, one-shot browser consumer, restricted surfaces and mock limits.
