Tuturuuu authenticates users before granting access to protected features. Workspace membership and permissions determine what an authenticated user may do; successful sign-in alone is not access to every workspace.

## IEEAI free invitation exchange proposal

The central app-token exchange proposal automatically accepts a pending MEMBER
invitation only for `ieeai-stats` and workspace
`a65cebd7-3a8c-4883-a3d9-82f9703d652f`, also present in the verified app's
`allowedWorkspaceIds`. It requires a confirmed Auth identity after the existing
app-secret, token, PKCE and MFA checks. User-id invitations match that actor;
email invitations match only the case-normalized confirmed Auth email. Multiple
matches, GUEST invitations and uninvited actors remain pending or denied.

The default is fail closed. Positive server subscription/product records must
prove FREE, zero-cost, non-seat entitlement; missing records, paid products,
unknown state and read failures do not qualify. Locked billing state prevents an
upgrade from racing acceptance. The canonical membership finalizer retains the
invited role set, and membership, selected-invite removal and ids-only audit
commit together. Existing members retain ordinary `workspace:session` access;
refresh never accepts an invitation. Other apps and paid-workspace paths keep
their existing behavior. No Polar API call is part of this proposal.

Regression coverage is in `ieeai-free-invite.sql`, the database verifier and
concurrency harness, `ieeai-free-invite.test.ts`, and the exchange integration
tests. Run the disposable verifier through resource admission; it exercises
rollback/reapply, audit failure rollback and competing acceptance/upgrade
transactions. Local proof does not establish deployment readiness. Release
requires central Web deployment and the separately approved additive migration;
the external IEEAI server is not a deployment dependency for this platform rule.

## OAuth Sign In

Customer sign-in supports configured OAuth providers. Staff sign-in has a separately restricted Microsoft entry. Provider identities and account linking must be verified; an email address or domain alone is not sufficient authority to link accounts or grant staff access.

### Provider hints, saved accounts and cross-app returns

Scope: the Web `/login` page, including requests from registered external
apps and internal satellites (`/login?provider=google&returnUrl=…`).

- The login and add-account HTML is a shared CDN shell only for requests
  without a session cookie; a request with a Supabase or Web app session
  cookie gets `private, no-store`, because the locale layout renders the
  session user into its providers. When a request has a provider hint or an absolute `returnUrl`,
  the page reads its view from `GET /api/v1/auth/login-view` (private,
  `no-store`): whether a session exists with only its name and avatar, the
  device's saved accounts (id, email, name and avatar only). Listing saved
  accounts never touches the device row, whose `last_seen_at` is the account
  switch's compare-and-set version, an allowed hint (`google`, `apple`, `github`)
  and the return app, named only when the external-app registry matches its
  origin and callback path.
- **Focused external sign-in.** A hint plus a registered external return app
  shows one fixed-size card with one decision per step and no other
  providers or email form:
  - a session: "Continue to <app>" as that account, or "Use another
    account", which signs out locally and starts the hinted provider.
    Continue is enabled only when the browser session is the account the
    card names, and it sends that account's id with the mint; the
    cross-app return route answers `409 ACCOUNT_CHANGED` instead of minting
    for any other session (for example after a switch in another tab). A
    different browser account falls back to the regular account
    confirmation;
  - saved accounts and no session: one-tap saved accounts, or "Use another
    account";
  - neither: the hinted provider starts at once, with a manual button only
    as a fallback.
  The header reads "Sign in to continue to <app>". While the view loads, a
  skeleton of the same size holds the card and header.
- Elsewhere a hint is advisory: it starts the provider automatically only
  with no session and a device known to have no saved account. With saved
  accounts, a hint or a cross-app return shows the saved-account chooser
  first. Unknown saved accounts (view pending or failed) never auto-start.
- The return target survives the provider round trip: `returnUrl` and a
  well-formed S256 `code_challenge` pair travel through `/api/auth/callback`
  only for a registry-validated return target. An unregistered target falls
  back to the default destination with no challenge and no token.
- When the cross-app token mint answers `MFA_REQUIRED`, the login page runs
  the MFA step-up once and mints again. A second refusal, a mint failure,
  unavailable assurance or a stalled step shows the retry card instead of the
  home page.
- Google sign-in asks with `prompt=select_account`, so a returning user
  picks an account in one tap and sees consent only when Google needs it.
- The login form loads with the shell rather than as a lazy chunk, and the
  entry animations stop under `prefers-reduced-motion`.
- The `/login` and `/add-account` CDN policy is set both by the proxy and by
  the `headers()` rules in `apps/web/next-config.web.ts`; config headers win,
  so the public rule there is conditioned on a missing session cookie and a
  private rule follows it.
- Turnstile renders in a fixed 300 by 65 slot, and every focused step uses
  one fixed-height frame (a long saved-account list scrolls inside it), so
  nothing shifts as the widget or the view loads.

Exceptions: `multiAccount=true` (add-account) never shows the chooser and
never starts a provider without a click, and "Use another account" applies
only to the provider and return it was chosen for. Microsoft (`azure`) is
never started from a hint.

## Raw session tokens are native-only

Browser sign-in uses the browser session flow. Raw access and refresh tokens are reserved for supported native-client authentication flows; browser requests to those native token flows are refused. Native-client compatibility and browser session behavior require separate verification.

## Mobile App Lock

App Lock is off by default and opt-in from Settings. While it is off, nothing
covers or blanks the app: switching away, system prompts, Control Center and
the notification shade leave the live UI and its input untouched, and the
operating system keeps its normal app-switcher preview and screenshots.

With App Lock on:

- An elapsed timeout locks the device's signed-in content even when the app
  resumes into an authentication route. Add Account stays available, and
  returning to protected content requires local authentication.
- The lock screen shows its guidance and the Unlock action on its first frame
  and asks for biometrics automatically. A cancelled or failed attempt says so
  and keeps Unlock available; an attempt in progress disables it.
- The app-switcher preview stays private natively, because Flutter draws no
  frames once the app is in the background. iOS adds a non-interactive blur
  only after the scene enters the background and removes it 0.3 seconds after
  the scene becomes active. Android 13 and later hide the Recents thumbnail;
  Android 12 and earlier have no thumbnail control, so App Lock secures the
  window, which also blocks screenshots there. A failed native update is
  retried on the next lock or account change.
- Control Center, the notification shade and system prompts never blur or
  cover the app; with a delay other than Immediately, staying in them longer
  than the delay locks on return. An elapsed lock engages on the first lifecycle event back
  from the background, before the resumed frame, and the time spent returning
  still counts toward the delay.
- Signing into or switching to an account locks at once when App Lock is
  known to be on, before the settings read completes.
- App-owned foreground refreshes wait for the lock to clear. Lock and account
  changes discard toasts from the former UI session.

The first App Lock settings read after sign-in shows a splash with a progress
indicator so a locked device never flashes content. A settings reload keeps the
last known state on screen. Turning App Lock on or off records the choice as a
device preference before the secure write, and fails visibly if the record
cannot be saved; each successful read refreshes the record, and the secure
value always wins over it; when secure storage fails or times out, App Lock follows
that record, so it fails closed. A device with no record and an unreadable keychain
shows the lock screen when it can authenticate locally, since App Lock cannot
have been turned on otherwise, and stays unlocked only when it cannot. Either
way the splash never holds. A failed
delay read keeps a confirmed opt-in with its last delay.

(lock on account change, read-failure fallbacks, unlock failure feedback),
`app_lock_settings_store_test.dart` (fail-closed opt-in record),
`apps/mobile/test/features/security/view/app_lock_boundary_test.dart`
(no cover while off, system prompts stay responsive, first-load progress,

refresh, stale prompts, lock before the resumed frame, return time counted

never holds the UI) and `app_lock_splash_timing_test.dart` (Unlock and

drive Add Account cancellation and a platform deep link through the production

### Verify on device

Use the same candidate build on an iPhone with a device passcode and an Android
device with a PIN, in light and dark appearance.

1. **App Lock off.** Pull down Control Center and the notification shade,
   trigger a system permission prompt, and switch apps. The live page stays
   visible and responsive throughout; no black or blank screen appears.
2. **App Lock on, Immediately.** Open the app switcher from a page with
   recognizable test text and check that its preview is blurred (iOS) or
   hidden (Android). Pull down Control Center and confirm nothing blurs. Return,
   cancel authentication, and confirm the lock screen shows the cancellation
   message and Unlock. Unlock with biometrics, then with the device passcode.
3. **Both.** Open Add Account, background the app, return, and tap its cancel
   button. Verify that the lock screen precedes Home. Start disabling App Lock
   from Settings, background during authentication, then return. Confirm that
   a new unlock works and the stale prompt cannot disable App Lock.
4. **Both.** Leave Mail open when backgrounding. Return and cancel the unlock.
   Confirm the mailbox fetch logs show zero resume refreshes, then unlock and
   confirm the refresh fires after authentication.

## Mobile approval keys

Signed phone approval uses an installation-local P-256 key scoped to the
account and enrollment. The operating system verifies the user for each
signature and derives the prompt from the signed action and number.
Explicit sign-out and account removal delete that account's approval keys.
A device-wide sign-out deletes all approval keys. Switching between saved
accounts retains their separate keys.

iOS uses a Secure Enclave key with a passcode-set, device-only accessibility
class and a fresh user-presence check. Adding or replacing a biometric can
still leave the key usable through the current passcode. Removing the
passcode invalidates the device-only Keychain item. App Attest binds the
approval public key and one-time enrollment challenge to a production app
installation. The Secure Enclave user-presence policy is enforced locally.

Android 11 and later require secure hardware to enforce authentication for
each ECDSA operation. StrongBox is preferred when the Keystore can create an
attested key there. The server can require StrongBox or accept an attested
Trusted Execution Environment. Allowing the device credential means
Android's biometric-only enrollment invalidation rule does not apply.
Resetting the secure lock can invalidate the Android key and require
registration again. Android 11 exposes a hardware boolean to the app. The
server distinguishes StrongBox from TEE using the verified certificate chain.

Before enabling enrollment, run the following checks with a synthetic
account and the exact signed build on physical devices.

1. On Android 11 and a newer device, enroll and confirm the hardware level
   in the verified attestation. Check that the Keystore reports
   `userAuthenticationValidityDurationSeconds == -1` for the signing key.
2. On iOS, enroll with a production App Attest identity and confirm approval
   and denial each request system verification. Repeat on Android, including
   with the device credential.
3. Enter `03` and verify that the system prompt includes both digits.
   Cancel the prompt and verify that the peer login remains pending.
4. Change biometric enrollment and remove the secure lock separately.
   Check the behavior for the applicable platform and register again if
   the operating system invalidates the key.
5. Sign out one account and confirm that its old key can no longer sign.
   Switch between two saved accounts and verify each retains its own key.
   Sign out all accounts and check that their signing keys are removed.

The [mobile signing tests](https://github.com/tutur3u/platform/blob/main/apps/mobile/test/features/security/device_mfa/mobile_approval_key_test.dart)
cover exact signing bytes and platform cancellation. The [account lifecycle tests](https://github.com/tutur3u/platform/blob/main/apps/mobile/test/features/auth/cubit/auth_workspace_recents_cleanup_test.dart)
cover account-specific and device-wide key removal requests.

## Web CSRF and forwarded workspace requests

Web's CSRF rollout is controlled by `TTR_CSRF_MODE`: unset or invalid values
leave it off, `report` logs rejected checks without blocking, and `enforce`
returns 403. Cookie-bearing mutations from same-site sibling origins are denied
unless the Web adapter explicitly trusts the exact serialized origin. The sole
satellite entry is `https://workspace.tuturuuu.com`, whose API requests forward
to Web. Same-origin mounts need no satellite entry. Other subdomains, alternate
schemes or ports, userinfo, paths, and missing or opaque origins do not qualify
for the same-site exception. Cross-site, `none`, and unknown Fetch Metadata
remain rejected even with that trusted origin.

Saved-account endpoints use exact registered first-party origins for
credentialed CORS. Their mutation handlers require an allowed `Origin` and an
`application/json` content type even when the global guard is off. Account JSON
responses use `Cache-Control: private, no-store`. The account route tests cover
allowed Web and satellite callers, rejected origins and media types, and cache
headers.

Before moving Web to `enforce`, have Release Operations read back the current
production mode. Follow the [CSRF rollout runbook](/build/devops/workspace-start-void#csrf-mode-and-origins)
and run `report` first. Review `CSRF check failed` logs for legitimate traffic
while exercising sign-in, saved-account mutations, and logout through the apex
mounts, Workspace forwarding, and supported satellite origins. Resolve any
legitimate denials and rerun the affected checks before approving `enforce`.
After the change, repeat those checks and restore `report` if legitimate
requests begin failing.

A bearer string cannot exempt a mutation carrying a session cookie. Cookie-less
bearer clients retain their existing exemption; ordinary cookie-less mutations
remain admitted. The three session-clearing logout endpoints still require
origin proof without a session cookie. Shared CSRF callers reject same-site
requests by default; only an explicit adapter opt-in enables this exception.

Regression coverage lives in `apps/web/src/lib/security/csrf.test.ts` and
`packages/auth/src/csrf.test.ts`. The dispatch probe in
`apps/web/src/lib/security/csrf-dispatch.test.ts` exercises the installed Next
production filesystem and render matchers with synthetic logout manifests. A
decoded filesystem hit is not a handler dispatch: route metadata and the render
match must also select the endpoint. This probe does not replace a built Web
artifact or hosting-provider routing acceptance check.

## Saved-account vault key rollout

The vault requires a dedicated `WEB_MULTI_ACCOUNT_SESSION_SECRET` of at least
32 bytes. If the setting is missing or too short, saved-account operations are
disabled and ordinary sign-out remains available. The Web vault writes v2
entries. Legacy entries and entries that cannot be decrypted are treated as
absent. Users sign in again once to save those accounts. The vault never tries
the service key for decryption.

Before deploying this change, provision the dedicated secret in production
under the approved secret-custody process. The predecessor uses the dedicated
secret as soon as it receives it, so coordinate its activation with the
approved re-link window. After deployment, verify an existing device can sign
in again, save an account and switch successfully. Verify a new device can
also save an account. Keep the rollout open for seven days of monitoring.
Source regression coverage lives in the multi-account `crypto.test.ts` and
`vault-switch.test.ts` suites.

## Reserved fleet QA identities

The auth-ops helper creates only two reserved normal-user aliases after exact
source and one-use execution review. It checks for existing Auth identities and
pending email roles before creating either user, and it grants no platform roles.
A1 creates one dedicated shared test workspace through the product UI; A2 has no
shared membership. Trigger-created personal workspaces remain during QA.

Cleanup verifies both identity and workspace inventories, deletes the recorded
shared workspace before its creator, deletes Auth users to revoke sessions, and
then confirms personal-workspace cascade deletion or performs the fenced fallback.
Auth absence and exact filtered alias lookups are required; alias-only tombstones
are counted. Access JWT lifetime is recorded as UNKNOWN without reading auth
configuration. See `scripts/auth-ops/fleet-qa-contract.md` for the exact CLI,
source/ACK binding, one-shot browser consumer, restricted surfaces and mock limits.
