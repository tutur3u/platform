# Tuturuuu SDK

Official TypeScript/JavaScript SDK for interacting with the Tuturuuu platform. Provides type-safe access to workspace storage, files, documents, and agent-friendly task workflows.

## Installation

<CodeGroup>

```bash npm
npm install tuturuuu
```

```bash yarn
yarn add tuturuuu
```

```bash pnpm
pnpm add tuturuuu
```

```bash bun
bun add tuturuuu
```

</CodeGroup>

## Quick Start

```typescript
import { TuturuuuClient } from 'tuturuuu';

// Initialize the client with your API key
const client = new TuturuuuClient('ttr_your_api_key');

// List files in workspace
const files = await client.storage.list({
  path: 'documents',
  limit: 50
});

// Upload a file
const file = new File(['content'], 'example.txt');
const result = await client.storage.upload(file, {
  path: 'documents'
});

// Create a document
const doc = await client.documents.create({
  name: 'My Document',
  content: { text: 'Hello World' }
});
```

## Features

Source previews support native `ttr backlog search help --lang en|vi --json`
and `ttr backlog search model-status --json` before login. Lexical queries require
an explicit `--db`.
Model status without `--runtime-dir` loads or downloads no model. These source
commands do not establish published npm availability or model admission. See
[local operational state](/reference/packages/cli-operational-state).

Search indexing reads the full current projection and rebuilds every lexical
document with complete member content and provenance. Under the same source UUID,
projection version, and authenticated runtime fingerprint, it can reuse a vector
for an identical record ID and versioned full-record content hash. Canonical
membership, provenance, content, or runtime recipe changes invalidate affected
vectors. Deleted records are omitted. An absent or revoked runtime removes all
semantic vectors. An older content policy requires one rebuild.

Index output reports `strategy: snapshot-reconciled-vector-reuse-v1`,
`reuseEligible`, `reused`, `computed`, `removed`, and `invalidated`. `embedded`
counts committed vectors, with a maximum corpus of eight documents. `incremental`
means reuse eligibility. `projectionScan` and `lexicalRebuild` remain full-snapshot
operations; indexing does not consume an event delta feed. A newer cached revision
or equal-revision snapshot drift denies reuse.

`modelLoaded` reports a successful non-injected embedding return in this command.
A command that computes no new vectors authenticates the runtime without loading
the model. `embeddingAttemptsThisCommand` and
`successfulEmbeddingsThisCommand` also describe this command. A later
embedding failure can leave `modelLoaded: true` while the committed lexical
fallback has zero vectors. Partial semantic caches are never published.

Structural cache, projection, and source conflicts propagate as errors. Runtime
embedding failures and capacity failures use lexical fallback. Before publication,
the index rereads source UUID, revision, snapshot, version, and cache permission.
Queries require the current snapshot and exact document IDs and content keys.
An older content policy produces `stale-content-policy` and lexical fallback.
Similarity candidates remain uncertain and never authorize closure or merge.
Source tests and review qualify this reuse behavior separately from real engine
execution, installed CLI availability, and hosted SDK packaging.

SDK package qualification drains each owned process group after termination. On Darwin, a group containing only exiting or zombie members can briefly return `EPERM` to a signal-zero probe. The drain keeps polling within its existing 1500 ms budget and succeeds only after `ESRCH`; persistent permission errors remain `PROCESS_GROUP_UNDRAINED` with the last probe error as `cause`, while other probe errors are rethrown unchanged. The post-leader-close `SIGKILL` alone may continue to drain after `EPERM`; other termination failures remain errors. Regression coverage lives in `scripts/ci/sdk-package-process.test.js` and the unchanged real-descendant assertions in `qualify-sdk-package.test.js`. Apple’s [process-group implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c) filters zombies and can return `EPERM` when no eligible member remains.

## Type-check and declaration output

The SDK `type-check` command uses `tsconfig.typecheck.json`, which extends the
public build configuration to retain its source files and semantic checking options.
It disables emit, composite output and incremental state, so it owns no `dist`
files even when the CI task graph also schedules the SDK build. The portable
`build` remains responsible for JavaScript and public declarations; its configuration
remains separate from the no-emit check. `sdk-typecheck-boundary.test.ts` checks resolved compiler
coverage/options and exercises a disposable type error and successful check without
output files. Exact-head CI must verify both type-check and the real portable build.
This structural boundary does not identify the writer behind a historical
`ENOTEMPTY` failure.

Portable staging excludes test/spec/acceptance modules and the shared
`resources-test-fixtures.ts` helper. Test-only imports such as Vitest's fixture
hooks must not enter the public runtime closure. The actual-source control in
`packages/sdk/scripts/portable-build.test.cjs` verifies this before compilation.

## CLI

For offline request ledgers and separate operational notes, see
[Local operational state](/reference/packages/cli-operational-state). These groups
run before authentication and update checks and do not access platform data.

The SDK package includes a native Bun-powered CLI. `ttr` is the primary command,
and `tuturuuu` plus `tutur3u` are aliases for the same binary.

```bash

ttr upgrade
ttr --version
ttr whoami
ttr host current
ttr host use local --port 7803
ttr workspaces
ttr workspaces use
ttr boards
ttr boards use
ttr lists use
ttr tasks use
ttr tasks --board <board-id>
ttr tasks --compact
ttr tasks search "deadline review"
ttr tasks search "deadline review" --mode text
ttr tasks search "deadline review" --mode semantic
ttr tasks create "Add Tuturuuu CLI"
ttr tasks create --list <list-id> --name "Write release notes"
ttr tasks done <task-id>
ttr tasks close <task-id>
ttr tasks update <task-id> --json-payload '{"completed":true}'
ttr finance wallets

ttr finance transactions --page-size 10
ttr finance transactions create --amount 150000 --wallet <wallet-id> --taken-at 2026-05-09

ttr calendar schedule preview --window-days 14 --timezone Asia/Ho_Chi_Minh
```

`ttr login` opens the browser and creates a Tuturuuu-managed CLI app-session
JWT pair through `apps/web`. The terminal and browser confirmation page show the
signed-in account email when the web session exposes it. The CLI stores that
session and selected workspace, board, list, task, label, and project in the OS
app config directory. `personal` is the default workspace after login and when
no workspace has been selected:

Use `ttr host use` to switch between Tuturuuu origins. `production` and `prod`
resolve to `https://tuturuuu.com`; `local` and `localhost` prefer safe local
environment URLs from `TUTURUUU_LOCAL_BASE_URL`, `PORTLESS_URL`, `WEB_APP_URL`,
`NEXT_PUBLIC_WEB_APP_URL`, or `NEXT_PUBLIC_APP_URL`, then fall back to
`https://tuturuuu.localhost`. Pass `--port <port>` for
`http://localhost:<port>`, or `--portless --port <port>` for
`https://tuturuuu.localhost:<port>`. Changing origins clears the saved session
and selected workspace context because both are origin-specific.

`ttr config set-base-url <url>` remains available for compatibility and uses the
same host normalization and context-clearing behavior. The CLI normalizes
`0.0.0.0` and unspecified IPv6 origins to `localhost` so the browser login flow
does not open a blocked address.

On Dockerized production deployments, the web auth start route also rewrites
wildcard bind origins such as `0.0.0.0:7803` to the forwarded public host or the
configured app URL (`WEB_APP_URL`, `NEXT_PUBLIC_WEB_APP_URL`,
`NEXT_PUBLIC_APP_URL`, `COOLIFY_URL`, or `COOLIFY_FQDN`) before sending users to
`/login`. If those environment values are unset and no public forwarded host is
available, `https://tuturuuu.com` is the default fallback.

- macOS: `~/Library/Application Support/Tuturuuu/config.json`
- Linux: `$XDG_CONFIG_HOME/tuturuuu/config.json` or `~/.config/tuturuuu/config.json`
- Windows: `%APPDATA%\Tuturuuu\config.json`

For headless agent environments, use copy-token mode:

```bash
ttr login --copy
```

Open the printed URL in an authenticated browser, copy the returned CLI token,
and paste it into the terminal. Set `TUTURUUU_CONFIG` to use a custom config
file, or use `ttr host use <target>` to target a local, production, or explicit
URL origin.

The CLI checks the npm registry at most once per hour and writes a notice to
stderr when a newer `tuturuuu` version is available. JSON invocations suppress
this notice on both output streams while retaining the update check and cache.
This covers `--json` and explicit JSON format/output flags; non-JSON commands
retain the notice. The CLI entrypoint regression tests in
`packages/sdk/src/cli/update-entry.test.ts` cover JSON success, feedback JSON
errors, and non-JSON notices. Use `ttr upgrade` to run `bun i -g tuturuuu`. Use
`--no-update-check` on a single command, or set `TUTURUUU_DISABLE_UPDATE_CHECK=1`,
to disable the check.

CLI sessions are dedicated Tuturuuu gateway JWTs, separate from normal browser
and Supabase Auth sessions. The CLI stores a short-lived app-session access JWT
plus a longer-lived refresh JWT, refreshes shortly before access-token expiry,
updates the saved config with the rotated refresh token, and retries once after a
`401` response. Refresh JWTs only carry the CLI refresh scope, so they cannot be
used directly as API bearer tokens. If refresh fails because the user no longer
exists or the refresh JWT has expired, run `ttr login` again.

The SDK fetch wrapper must attach CLI bearer tokens, refresh sessions, and retry
`401` responses only for relative Tuturuuu API paths or absolute URLs whose
origin exactly matches the configured CLI base URL. Cross-origin absolute URLs
must be delegated without `Authorization` headers.

API routes used by `ttr` must accept the CLI app-session access JWT from the
`Authorization: Bearer ...` header. For `apps/web` routes, prefer
`withSessionAuth` with `targetApp: 'platform'` and
`requiredScope: 'cli:access'` when the route is CLI-only; shared user profile
routes can include the platform target alongside satellite app targets. Shared
API routes should verify the CLI app-session token before falling back to
Supabase session auth and then keep workspace membership checks explicit.
When a handler lives in `packages/apis` and is reused by multiple apps, keep
`@tuturuuu/auth` imports in the app-owned route wrapper and pass a
pre-authenticated context into the shared handler so package builds do not form
an auth/UI/API cycle.

SDK version and changelog PRs are generated by
`.github/workflows/release-please.yaml` from Conventional Commits on
`production`. Release Please tracks the SDK in `release-please-config.json` as
the `sdk` component, records the current version in
`.release-please-manifest.json`, and updates `packages/sdk/package.json` in the
combined monorepo release PR. SDK releases are then published automatically from
`.github/workflows/release-sdk-package.yaml` when that version bump lands on
`production` or when the release workflow itself changes. The same publish
workflow can be dispatched manually to catch up a version that already landed on
`production`. Manual dispatches from any other ref are rejected before
dependency installation, packaging, or npm trusted publishing can run. The
workflow runs the SDK tests, skips publication if the exact package version
already exists on npm, waits for publishable Tuturuuu workspace dependencies to
be visible on npm, prepares a tarball with `npm pack` outside the
trusted-publish job, and then publishes that tarball through
[npm trusted publishing](https://docs.npmjs.com/trusted-publishers). Only the
final `publish-npm` job requests `id-token: write`, so GitHub Actions mints the
short-lived OIDC token after dependency installation, package builds, and version
checks have already finished. That job downloads the prepared artifact, verifies
its package `name` and `version`, confirms the bundled `npm` CLI supports trusted
publishing, runs `npm publish ./<tarball> --ignore-scripts`, and polls `npm view`
until the exact SDK version is visible without using an `NPM_TOKEN`. npm treats
the downloaded artifact as a local file path. The job
targets the GitHub environment `sdk-release-production`; keep that environment
restricted to the `production` branch in repository settings, and keep the npm
trusted publisher bound to the same environment name so a branch-selected
workflow cannot mint a matching npm publish identity. Do not add `bun install`,
`npm install -g`, package builds, package lifecycle scripts, or repository
secrets to the SDK release workflow. Because the `tuturuuu` package is public
and `tutur3u/platform` is a public repository, npm also generates and attaches
build provenance attestations automatically. The package manifest inside the
tarball must keep repository metadata aligned with the provenance repository:
`repository.url` is `https://github.com/tutur3u/platform`, and
`repository.directory` points at the package directory.

`.github/workflows/sdk-version-bump.yaml` is retired and no longer generates
patch-version PRs. Do not restore checksum or package-only bump automation for
the SDK; release-please must remain the version/changelog source of truth.

The SDK imports `@tuturuuu/devbox`, `@tuturuuu/types`, and
`@tuturuuu/internal-api` through package exports that point at their git-ignored
`dist/` directories. The release workflow must build those workspace packages in
the non-OIDC build and prepare jobs before running SDK tests or creating the
`npm pack` tarball; otherwise a clean Actions checkout cannot resolve the SDK
imports. The workflow then runs
`node scripts/ci/prepare-npm-package-manifest.js packages/sdk` before
`npm pack` so the published manifest contains concrete npm versions instead of
local `workspace:` protocol ranges. Keep matching npm release workflows for the
SDK runtime workspace dependencies so consumers can install the published SDK.
When release-please bumps the SDK and one of those dependencies in the same
production push, the SDK workflow waits for the dependency versions before it
packs and publishes. If a dependency release workflow for the same SHA fails,
the SDK wait fails immediately instead of waiting for npm visibility until
timeout.

The matching npm-side trusted publisher must stay configured at
`https://www.npmjs.com/package/tuturuuu/access` with these exact values:

- **Provider**: GitHub Actions
- **Organization or user**: `tutur3u`
- **Repository**: `platform`
- **Workflow filename**: `release-sdk-package.yaml`
- **Environment name**: `sdk-release-production`

If the npm-side configuration drifts (for example after a repo rename, missing
first-publish setup, package access drift, or after moving the publish step into
another workflow file), `npm publish` can fail with `ENEEDAUTH`, `E404`, or
permission text. Update the npm package access or trusted publisher entry first;
do not paper over the failure by reintroducing a long-lived `NPM_TOKEN`. After
confirming a trusted-publisher release works end to end, the npm package
settings should keep `Require two-factor authentication and disallow tokens`
enabled so the package cannot be published with classic tokens.

### Dev channel and private previews

The stable channel remains Release Please plus the production release workflow.
The dev channel builds each SDK change on `main`, or a manual dispatch of
`release-sdk-dev.yaml` on `main`. It qualifies the portable package, publishes
`X.Y.(Z+1)-dev.<run-number>.<sha7>` under npm's `dev` tag with provenance, and uploads
the tarball, qualification receipt and `manifest.json`. It never updates `latest`.
The manifest records the version, full source SHA, SHA-256, npm integrity and
shasum. `ttr --version` prints only the bare version for machine consumers.
`ttr resources status --json` reports the installed version, channel and source SHA. Older stable packages without build metadata report an
unknown source; do not infer a source SHA from their version.

Branch Actions builds are deliberately refused. This repository is public, so
Actions artifacts are not a private distribution boundary. For premerge work,
build a clean committed checkout privately on an admitted build host, then transfer the tarball
and manifest over SSH. Do not upload unmerged previews to public Actions artifacts
or publish them to npm. Checksums establish byte identity, not code approval.

#### Cut a build

For the main channel, dispatch the workflow after its operator setup below:

```sh
gh workflow run release-sdk-dev.yaml --ref main
```

For a private premerge preview, use a clean checkout in an admitted build root.
Use Node 24.21.0 and Bun 1.4.4, matching public package qualification. Do not build
on a workstation while a resource hold applies.

```sh
# On the build host, inside the admitted clean checkout:
~/.bun/bin/ttr resources run -- bun sdk:dev-pack
```

The command prints JSON containing the output directory and checksum manifest.
Its default version uses a timestamp as the dev run number outside Actions.
The patch is one above the stable base, so prereleases sort above that base
and below the next stable patch.
Keep the `internalOnly: true` manifest and tarball private. The command builds the
portable SDK and dependencies, then runs the same public consumer/compiled-CLI
qualification and receipt verification as the official release. Missing registry
dependencies stop qualification; they are not replaced with workspace links.

The pack lock records its owner PID and gated child process groups atomically.
A later pack reclaims the lock after a crash or `SIGKILL` only when the owner and
every recorded process group have ended. Live builders are never evicted by age. If owner metadata is malformed or a reclaim guard
was interrupted, inspect `packages/sdk/.dev-pack.lock` and its `.reclaim/owner.json`
first. Only after confirming every recorded PID and process group has ended, remove those exact
lock/guard paths and retry. Do not delete a live owner's lock or partial package
outputs from another job. These coordination files are ignored by Git.

#### Roll out and recover

The rollout tool is a repository command, so it can update an older global CLI.
Run it outside an admitted job: its cutover needs an idle queue. Each target uses
its existing home, global Bun installation, queue, roots and limits. Hosts run
sequentially; the first failed or unknown result stops the fleet operation and
lists never-attempted hosts as skipped. SSH receives the requested drain time
plus a 30-minute operation budget. A disconnected attempt is reconciled from a
private terminal report when available; otherwise retain its `reportFile` and
staging paths for inspection. Do not replay an unknown installation.

```sh
bun sdk:rollout --channel dev --host <host-a> --host <host-b>
bun sdk:rollout --channel latest --wait-drain 120 --host <host-a>
bun sdk:rollout --tarball /private/path/tuturuuu-preview.tgz --sha256 <manifest-sha256> --host <host-a>
```

Review the JSON report and retain its backup directory. The command verifies
bytes before installation, backs up the previous supplier and scheduler files,
previews setup, applies setup, and qualifies the global CLI and launchers. It
holds admission during cutover, never kills owners, and restores the backup on
failure. Without `--wait-drain`, an occupied queue refuses immediately. A bounded
wait does not authorize interrupting another job.

Automatic rollout targets must advertise `tuturuuuBuild.rolloutProtocol: 1`.
The existing 0.28.0 package predates that protocol and is refused before install;
use the reviewed manual drain/backup procedure for that older target, or wait for
a maintenance-capable stable release. Newly qualified dev and stable packs carry
the protocol marker. Every rollout target requires Python 3, preflighted before
installation, for its OS-released recovery lock. The tool qualifies project root/package metadata, not each
project's test suite.

Use the generated rollback command in the report to restore the saved supplier
without downloading it again. Rollback also requires an idle queue. Preserve the
backup until the host passes qualification; reconcile a failed or interrupted
rollback before attempting another rollout. Do not change `TTR_RESOURCES_HOME`,
link a workspace `dist`, or run concurrent global package-manager operations.
Global installation is required by the same-install trust fence.

A later rollback compares the current global install, configuration and launchers
with the recorded post-rollout hashes. **Rollback refuses after another global
package or a root/limit change.** Do not force a whole-install restore over newer
state; inspect and reconcile that state first. An interrupted rollback retains
its same-operation recovery fence so it can resume safely.

Candidates install from the stable content-addressed cache at
`~/.tuturuuu/resources/suppliers/<sha256>.tgz`, separate from backups. Completed
rollouts prune old completed backups, retaining five recent backups plus the
current/protected backup. Failed or unknown recovery evidence stays retained.
Cache pruning preserves archives referenced by the current installation and
retained backups.

#### Recover a stale admission fence

A dead preparation owner with no `admission/mutation.json` has not changed the
installation. Preparation has no retained reclaim fence; ordinary admission
reclaims a dead preparation owner. If a legacy or malformed fence still blocks
admission, stop new submissions and inspect
`~/.tuturuuu/resources/admission/owner.json`. Verify the recorded owner PID and
child PID/process group have ended, the token is unchanged, and `mutation.json`
is absent. Preserve the owner record and move only that confirmed stale
`admission/` directory into a private backup before admitting new work. Never
move a live owner's directory or remove slots, queue tickets or legacy locks.

When `mutation.json` exists, keep admission closed and use the backup path
recorded there to run its `rollback.sh`. A missing, malformed or ambiguous record
requires operator investigation; do not clear the fence to bypass it.


Promote code by merging the reviewed change and following the existing
production/Release Please process. Do not promote a dev tarball by moving
`latest`: stable releases are separately versioned, qualified and published.

#### Operator setup and threat model

Before enabling publication, create GitHub environment `sdk-release-dev` with
an explicit deployment branch restriction allowing only `main`. Add an additive
npm trusted publisher for `tuturuuu`: GitHub Actions, owner `tutur3u`, repository
`platform`, workflow `release-sdk-dev.yaml`, environment `sdk-release-dev`.
Keep the existing production publisher unchanged. Use GitHub-hosted publish
runners; do not add a registry token or secrets to artifacts. See
[npm trusted publishers](https://docs.npmjs.com/trusted-publishers/).

The trust boundary is reviewed main source, a nonprivileged build/qualification
job, and an isolated OIDC publish job that treats artifacts only as data. The
publish job has no checkout, builds, dependency installation or lifecycle scripts.
The environment restriction prevents a modified branch workflow from obtaining
matching publish authority. A checksum prevents corrupt or substituted bytes
when its expected value arrives through a trusted channel; it does not make
unreviewed code safe. Installing a private preview grants that code the host
user's authority. Backups may contain private scheduler configuration: keep them
on the target with private permissions and never commit or upload them.

### Devbox Setup

Use `ttr box setup` on self-hosted runner machines before offloading expensive
checks, Supabase workflows, or E2E suites. The command clones or reuses
`https://github.com/tutur3u/platform.git` at `~/Documents/tuturuuu`, runs
`bun install --frozen-lockfile`, starts the local Supabase stack with
`bun sb:start`, reads `supabase status -o json`, and upserts local Supabase
connection values into ignored `apps/*/.env.local` files with secret values
redacted from CLI output.

```bash
ttr box doctor
ttr box setup
ttr box setup --dir .
ttr box repair --dir .
ttr box repair --dir . --dry-run
```

`ttr box doctor` stays read-only. Use `ttr box setup --yes` only when the host
should install detected missing prerequisites through its package manager.
Use `ttr box repair --dir .` after a CLI upgrade to repair an existing runner
service without registering a new runner token.

### Agent-Friendly Discovery

For autonomous engineering workflows, start by discovering the current account
and selected context:

```bash
ttr whoami
ttr whoami --json
ttr workspaces --json --no-update-check
ttr tasks --json --no-update-check
```

`ttr whoami` shows login state, account email, current workspace, selected
board/list/task/label/project ids, base URL, config path, and the `Tuturuuu CLI`
session label. Use `--json` when another agent is going to parse stdout;
`--no-update-check` is optional and skips the registry check entirely.

The v1 task surface covers workspaces, boards, lists, tasks, labels, projects,
relationships, moves, and bulk task updates. Read-oriented groups list by
default, so `ttr tasks` and `ttr workspaces` are equivalent to their explicit
`list` forms. `ttr boards` shows active, unarchived boards by default; use
`ttr boards --archived`, `ttr boards --deleted`, or `ttr boards --all` when an
agent needs archived or deleted board inventory. Unscoped `ttr tasks` starts
from the personal workspace and lists personal tasks plus open tasks assigned to
the user in other accessible workspaces; selecting a board/list or passing
`--workspace` scopes the result back to that context. `ttr tasks` shows open
tasks by default by excluding rows with `completed_at` or `closed_at` and by
limiting task-list statuses to `not_started` and `active`. That default hides
tasks in `documents`, `review`, `done`, and `closed` lists, and tasks from
archived boards; use `--all`, `--include-archived`, `--documents`, `--review`,
`--done`, `--closed`, `--include-documents`, `--include-review`,
`--include-done`, or `--include-closed` to adjust that filter. Results are
paginated at 50 tasks by default; use
`--page`/`--page-size` or `--limit`/`--offset` to page through larger task sets.
Human-readable task lists show a footer with the total task count and current
page/max page. Add `--compact` to task lists when an agent only needs the task
title, task list name, and per-task workspace name. Task lists are ordered by
priority and due date, with prettier due dates and configured task-list colors
in table output. Human-readable tables use smooth box borders, respect the
terminal width, and wrap long cell content so task titles stay readable instead
of overflowing narrow panes. Add `--json`
when another agent or script needs machine-readable output.

Use `ttr tasks search <query>` for ranked task search. Search defaults to
`--mode hybrid`, accepts `--mode text` for PostgreSQL full-text search only and
`--mode semantic` for embedding similarity only, and supports
`--query`/`--q`, `--limit`/`--match-count`, `--threshold`/`--match-threshold`,
`--workspace`/`--ws`, `--compact`, and `--json`. Search output preserves API
relevance order and shows the score when available. Existing list filtering
with `ttr tasks --q <query>` is unchanged and remains the lightweight list text
filter.

`tasks create`, `boards create`, and `lists create` accept a quoted positional name as
a shorthand for `--name`. Task CRUD accepts either the task UUID or the board
identifier shown in the UI, such as `VHP-12`; prefixed identifiers resolve
within the selected workspace even when another list is selected, and matching
human-readable output keeps that prefixed identifier visible. Marking a task
completed stamps `completed_at` so Tuturuuu moves it to the first `done` list;
pass `--list <done-list-id>` or include `list_id` in `--json-payload` to choose
another done destination. Use `ttr tasks done [task-id]` as the quick shortcut.
Use `ttr tasks close [task-id]` to stamp `closed_at`; pass `--list
<closed-list-id>` to choose a specific closed destination.

Task templates are single-task starters, separate from board templates.
Workspace templates are managed with
`ttr task-templates list/show/create/update/delete/use` and can be imported
from or exported to local markdown files. Local templates live under
`.tuturuuu/task-templates/*.md`, use YAML frontmatter for fields such as `key`,
`name`, `task_name`, `priority`, `label_ids`, `assignee_ids`, and
`project_ids`, and use the markdown body as the task description. Markdown
descriptions from `--description-format markdown` and local template bodies
support GFM pipe tables and are stored as TipTap/Yjs table content for the web
editor. `ttr tasks create --template <key-or-path>` resolves workspace keys or
local markdown paths; explicit flags such as `--name`, `--list`, `--priority`,
`--labels`, and `--projects` override template defaults.

```markdown
---
key: qa-handoff
name: QA handoff
task_name: Verify release handoff
priority: high
---

| Field | Value |
| --- | --- |
| Owner | Platform |
| Environment | Staging |
```

### Finance CLI

Finance commands use the selected workspace and the same authenticated internal
APIs as the web app. Use `--workspace` or `--ws` to target a different
workspace, and use `--json-payload` when a script needs to send fields that do
not have dedicated flags yet. Finance list output is paginated by default; use
`--page`/`--page-size` or `--limit`/`--offset` to move through larger result
sets.

Finance API routes that back `ttr finance` should resolve access through
`getFinanceRouteContext` from `@tuturuuu/apis/finance/request-access`, with
app-owned routes passing `resolveFinanceRouteAuthContext(request)` from

does not depend on `@tuturuuu/auth`; `getFinanceRouteContext` still keeps the
pre-authenticated actor, browser Supabase sessions, `personal` workspace
resolution, and finance permission checks on the same path.

### Calendar CLI

Calendar commands use the selected workspace and the same authenticated calendar
APIs as the web app. Use `--workspace` or `--ws` to target a different
workspace, and use `--json` when scripts need the raw structured response.
Human output renders resource-specific tables for events, calendars, categories,
accounts, provider calendars, connections, sources, and schedulable tasks.

Event time input is exact ISO datetime only. `events create` requires `--start`
and exactly one of `--end` or `--duration-minutes`; `events update
--duration-minutes` also requires `--start`. Source flags map to provider
payloads: use `--source-provider tuturuuu --calendar <workspace-calendar-id>`
for workspace calendars, or `--source-provider google|microsoft --connection
<connection-id>` for connected provider calendars. `calendar calendars reset`
is destructive and requires `--yes`.

```bash
ttr calendar sources list
ttr calendar sources use --source-provider tuturuuu --calendar <calendar-id>
ttr calendar calendars create "Team" --color BLUE
ttr calendar calendars update <calendar-id> --name "Team Calendar"
ttr calendar calendars reset --yes

# Categories and provider connections.
ttr calendar categories create "Focus" --color BLUE
ttr calendar categories reorder --json-payload '{"categories":[{"id":"...","position":0}]}'
ttr calendar accounts list
ttr calendar auth google
ttr calendar auth microsoft
ttr calendar provider-calendars list --account <account-id>
ttr calendar connections create --calendar-id primary --calendar-name "Primary" --account <account-id>

# Scheduling.
ttr calendar schedule status
ttr calendar schedule tasks --q roadmap
ttr calendar schedule preview --window-days 14 --timezone Asia/Ho_Chi_Minh
ttr calendar schedule apply --mode safe-apply --scope impacted-only --window-days 14 --timezone Asia/Ho_Chi_Minh
```

Common task workflows:

```bash

ttr tasks

# List active boards only; pass --archived, --deleted, or --all for other states.
ttr boards

# Compact human output: task title, task list, and workspace.
```

For terminal workflows, omit an id from `use`, `get`, `update`, `delete`, or
`move` commands to pick a workspace, board, list, task, label, or project with
the keyboard. The interactive picker shows one-based indexes, colored badges
such as `[FREE] Tuturuuu` and `[PRO] Personal`, task-list color swatches, the
selected row, and muted metadata. Use up/down or `j`/`k` to move, space/enter to
select, and escape/`q` to cancel. Interactive selection is disabled for `--json`
output. Picker labels, descriptions, badges, and color names derived from
platform data must visibly escape terminal control characters before rendering.
Use `ttr -v` or `ttr --version` to print the installed CLI version.

Uploads a file to the workspace drive.


### Download File

Downloads a file as a Blob.

```typescript
const blob = await client.storage.download('documents/report.pdf');

const a = document.createElement('a');
```


### Public Folder Asset Sync

### Register and configure an external site from the CLI

Root operators can manage registered apps, approve scopes, create templates,
and bind workspaces without opening Infrastructure or CMS. Existing root and
workspace permission checks remain mandatory; the CLI does not grant access.

```bash
ttr external apps list --json
ttr external apps save --file app.json --dry-run
ttr external apps save --file app.json --confirm CONFIGURE_EXTERNAL_APP
ttr external apps scopes rennu --scopes external-projects:read,external-projects:manage,external-projects:publish --dry-run
ttr external apps scopes rennu --scopes external-projects:read,external-projects:manage,external-projects:publish --confirm APPROVE_EXTERNAL_APP_SCOPES
ttr external templates create --file template.json --confirm CREATE_SITE_TEMPLATE
ttr external binding set --workspace <workspace-id> --template rennu --confirm LINK_SITE_TEMPLATE
ttr external binding get --workspace <workspace-id> --json
```

App JSON requires `id`, `displayName`, `enabled`, `origins`, `allowedScopes`,
and `allowedWorkspaceIds` (explicit UUID allowlist). Do not include secrets or
audit fields. Save updates these fields without rotating credentials. Scope
changes replace the whole approved list; `--clear-scopes` revokes all scopes.
Custom template JSON can be
`{"id":"rennu","display_name":"Ren Everheart","adapter":"custom"}`;
the template ID must match the registered app ID. Run `projects setup`, `diff`,
and confirmed `apply` after binding to configure and populate the workspace.

```bash
ttr external apps rotate-secret rennu --secret-out /private/secure/ren-app-secret --confirm ROTATE_EXTERNAL_APP_SECRET
```

This explicitly issues or rotates the secret and immediately invalidates the
previous value. The destination must not exist; its parent must exist. The CLI
writes an owner-only (`0600`) file, never the secret to stdout. Transfer it to
the app's server environment and securely remove the local file; never commit
it. A failed request may leave an empty file, which is not overwritten on retry.
The SDK equivalent lives at `TuturuuuUserClient.external.admin`.

External apps can keep seed media in their local `public/` folder and still publish it through Tuturuuu Drive. Mark each manifest asset with `metadata.publicPath`, `metadata.localAssetPath`, `metadata.sourcePublicPath`, or a relative `sourceUrl`.

```typescript
import { linkExternalProjectPublicFolderAssets } from 'tuturuuu';
import { uploadExternalProjectPublicFolderAssets } from 'tuturuuu/external-projects/public-assets';

const linkedManifest = linkExternalProjectPublicFolderAssets(manifest);

const sync = await uploadExternalProjectPublicFolderAssets(
  client.externalProjects,
  'workspace-id',
  manifest,
  { publicDir: './public' }
);

console.log(sync.uploaded.length);
console.log(linkedManifest.content.entries[0]?.assets?.[0]?.storagePath);
```

The linker writes deterministic storage paths under `external-projects/{adapter}/{collectionSlug}/{entrySlug}/{filename}`. External apps can upload those assets through signed upload URLs, or through the external-project asset multipart route when they need the app server to stream the file with a server-owned bearer token. Production Supabase keys are not needed in external apps.

## Error Handling

The SDK provides specific error classes for different scenarios:

```typescript
import {
  AuthenticationError,
  AuthorizationError,
  NotFoundError,
  ConflictError,
  RateLimitError,
  NetworkError,
  ValidationError
} from 'tuturuuu';

try {
  await client.storage.upload(file);
} catch (error) {
  if (error instanceof AuthenticationError) {
    // Invalid or expired API key
    console.error('Authentication failed:', error.message);
  } else if (error instanceof AuthorizationError) {
    // Insufficient permissions
    console.error('Forbidden:', error.message);
  } else if (error instanceof NotFoundError) {
    // Resource not found
    console.error('Not found:', error.message);
  } else if (error instanceof ConflictError) {
    // Resource already exists
    console.error('Conflict:', error.message);
  } else if (error instanceof RateLimitError) {
    // Rate limit exceeded
    console.error('Rate limited:', error.message);
  } else if (error instanceof NetworkError) {
    // Network or timeout error
    console.error('Network error:', error.message);
  } else if (error instanceof ValidationError) {
    // Invalid input
    console.error('Validation error:', error.message);
  }
}
```

### Error Properties

All error classes include:

- `message` - Human-readable error description
- `code` - Machine-readable error code
- `statusCode` - HTTP status code
- `name` - Error class name

```typescript
try {
  await client.storage.delete([]);
} catch (error) {
  if (error instanceof ValidationError) {
    console.log(error.message); // "At least one path is required"
    console.log(error.code); // "VALIDATION_ERROR"
    console.log(error.statusCode); // 400
    console.log(error.name); // "ValidationError"
  }
}
```

## API Key Management

### Creating an API Key

1. Log in to your Tuturuuu workspace
2. Navigate to **Settings** → **API Keys**
3. Click **"Create API Key"**
4. Set a descriptive name
5. Assign a **Workspace Role** (determines permissions)
6. Optionally set an expiration date
7. Copy the generated key (starts with `ttr_`)
8. Store securely (you won't see it again)

### Best Practices

<Warning>
  **Never commit API keys to version control!** Use environment variables or
  secret management services.
</Warning>

```bash
# .env
TUTURUUU_API_KEY=ttr_your_api_key_here
```

```typescript
// app.ts
const client = new TuturuuuClient(process.env.TUTURUUU_API_KEY!);
```

### Permissions

API keys inherit permissions from their assigned **Workspace Role**. The role determines what operations the key can perform.

**Required Permissions:**

| Operation                                                                      | Required Role Permission             |
| ------------------------------------------------------------------------------ | ------------------------------------ |
| Storage Operations (list, upload, download, delete, folders, share, analytics) | `manage_drive`                       |
| Document Operations (list, create, get, update, delete, search)                | `manage_documents`                   |
| API Key Management                                                             | `manage_api_keys` (Owner/Admin only) |

**Note:** Permissions are managed through workspace roles, not individual API keys. To modify what an API key can do, update its assigned role's permissions in **Settings** → **Roles**.

## Security Best Practices

<Warning>
  **CRITICAL: Never expose API keys in client-side code!** API keys must remain
  server-side only.
</Warning>

### ❌ Insecure (NEVER do this)

```typescript
// BAD: Exposes API key to browser!
'use client'; // Client component

const client = new TuturuuuClient(process.env.NEXT_PUBLIC_API_KEY);
// ❌ Anyone can inspect network requests and steal your key!
```

### ✅ Secure (Recommended patterns)

#### Next.js App Router (Recommended)

Create server-side API routes that proxy SDK calls:

```typescript
// app/api/storage/list/route.ts (SERVER-SIDE)
import { TuturuuuClient } from 'tuturuuu';
import { NextResponse } from 'next/server';

const client = new TuturuuuClient(process.env.TUTURUUU_API_KEY);

export async function GET(request: Request) {
  const { searchParams } = new URL(request.url);
  const path = searchParams.get('path') || '';

  const files = await client.storage.list({ path, limit: 50 });
  return NextResponse.json(files);
}
```

Then call from your client component:

```typescript
// app/components/FileList.tsx (CLIENT COMPONENT - SAFE)
'use client';

export function FileList() {
  const [files, setFiles] = useState([]);

  useEffect(() => {
    fetch('/api/storage/list?path=documents')
      .then(res => res.json())
      .then(setFiles);
  }, []);

  return <div>{/* Render files */}</div>;
}
```

```typescript
// server.js
import { TuturuuuClient } from 'tuturuuu';

const client = new TuturuuuClient(process.env.TUTURUUU_API_KEY);
const app = express();
```

```typescript
// netlify/functions/storage.ts
import { TuturuuuClient } from 'tuturuuu';

export const handler = async (event) => {
```

## Rate Limiting

The API enforces rate limits per API key to ensure fair usage and system stability:

### Rate Limits by Operation

| Operation            | Limit        | Window     |
| -------------------- | ------------ | ---------- |
| Storage Upload       | 20 requests  | per minute |
| Storage Download     | 50 requests  | per minute |
| Signed Upload URLs   | 30 requests  | per minute |
| All Other Operations | 100 requests | per minute |

### Rate Limit Headers

Every API response includes rate limit information in the headers:

- `X-RateLimit-Limit` - Maximum requests allowed in the time window
- `X-RateLimit-Remaining` - Number of requests remaining in current window
- `X-RateLimit-Reset` - Unix timestamp when the rate limit resets

```typescript
const result = await client.storage.list();

// Access rate limit info from headers (if using direct API calls)
console.log('Limit:', result.headers.get('X-RateLimit-Limit'));
console.log('Remaining:', result.headers.get('X-RateLimit-Remaining'));
console.log(
  'Resets at:',
  new Date(Number.parseInt(result.headers.get('X-RateLimit-Reset')) * 1000)
);
```

### Handling Rate Limits

When you exceed the rate limit, the API returns a `429 Too Many Requests` response:

```typescript
try {
  await client.storage.upload(file);
} catch (error) {
  if (error instanceof RateLimitError) {
    console.error('Rate limited! Try again later.');
    console.error('Retry after:', error.retryAfter, 'seconds');

    // Implement exponential backoff
    await new Promise((resolve) =>
      setTimeout(resolve, error.retryAfter * 1000)
    );
  }
}
```

### Best Practices

<Tip>
  **Implement exponential backoff** when handling rate limits to avoid hammering
  the API with retries.
</Tip>

```typescript
async function uploadWithRetry(file: File, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    try {
      return await client.storage.upload(file);
    } catch (error) {
      if (error instanceof RateLimitError && attempt < maxRetries - 1) {
        // Exponential backoff: 1s, 2s, 4s
        const delay = Math.pow(2, attempt) * 1000;
        await new Promise((resolve) => setTimeout(resolve, delay));
        continue;
      }
      throw error;
    }
  }
}
```

<Tip>
  **Monitor rate limit headers** to track your usage and avoid hitting limits:
  ```typescript
  // Check remaining requests after each call
  const response = await fetch('https://tuturuuu.com/api/v1/storage/list', {
    headers: { 'Authorization': `Bearer ${apiKey}` }
  });

const remaining = response.headers.get('X-RateLimit-Remaining');
const limit = response.headers.get('X-RateLimit-Limit');

console.log(`API calls remaining: ${remaining}/${limit}`);

// Slow down if close to limit
if (Number(remaining) < Number(limit) \* 0.1) {
await new Promise(resolve => setTimeout(resolve, 1000));
}

```
</Tip>

## Local resource control

Use `ttr resources` to keep coding sessions responsive with bounded validation on the same machine. This opt-in feature supports macOS/Linux without login or a background daemon.

```bash
ttr resources setup --root ~/code/project-a --root ~/code/project-b --shell zsh
ttr resources status
ttr resources run -- bun run test
ttr resources monitor --seconds 60 > resource-samples.jsonl
```

Explicit `run` requires setup-provisioned executable shims matching the current runtime and resource entry. It only reads and validates those launchers; it never installs, rewrites, chmods, or activates them. Missing, stale, malformed, or nonexecutable shims fail before queue admission and workload launch, with an explicit `ttr resources setup --shell none` instruction. Inspect occupancy and obtain installation authority before setup; a source update does not authorize replacing an installed scheduler. Resource commands dispatch before general authenticated CLI imports. This avoids those eager imports but does not establish the cause or repair of any host-specific startup hang. Regression coverage lives in `resources-provisioning.test.ts` and `entry-dispatch.test.ts`; existing lane tests retain FIFO, pressure, and owned cancellation/drain coverage.

Setup includes linked Git worktrees. One canonical per-user FIFO queue defaults to one lane; missing `validationLanes` in version-1 configurations means one. `validationLanes` is the base lane count, an integer from `1` to `8`, configured with `setup --lanes`. `--workers` sets the aggregate Vitest/Cargo total. Configurations split that total across lanes with rounding down, but every lane receives at least one worker. Turbo runs one task per lane, and explicit Vitest/Cargo flags are capped. `--dry-run` inspects changes without writing.

Admission is reentrant. An admitted job exports `TTR_RESOURCES_ADMITTED=<owner token>` (and the legacy `TTR_RESOURCE_OWNER`). A nested `ttr resources run` or shim-admitted heavy command inside that job runs immediately with the owner's caps instead of queueing behind its own ancestor. The marker counts only while it names a live owner inside that owner's process tree (an ancestor PID or the owned launcher's process group). When `ps` ancestry is unavailable, the marker cannot be verified, so it is ignored with a warning and the command queues. On Linux without a trusted `ps`, lineage falls back to the kernel's `/proc/<pid>/stat`, which is not PATH-controlled. Where no ancestry evidence exists at all, a waiter whose marker names a live owner fails after 60 seconds with an actionable error (install `ps`, or use `TTR_RESOURCES_BYPASS=1`) instead of waiting forever behind its own ancestor (`resources-ancestry.test.ts`). Ancestry and process-group liveness come only from `/bin/ps` or `/usr/bin/ps`, run with an empty environment; `ps` is never resolved through the caller's PATH, so a fake `ps` cannot fabricate ancestry. Without a trusted `ps` there is no evidence and the command queues. Stale or copied markers are likewise ignored with a warning and queue normally. Children whose environment is filtered, such as under Turbo strict env, are matched by ancestry alone. Successful ancestry snapshots are cached per process, and failed `ps` probes are retried. A waiter also rechecks ancestry about once per second, so a transient probe failure cannot deadlock it behind its own ancestor. Regression coverage lives in `resources-reentrancy.test.ts`.

Explicit `run` skips the queue only for a few read-only coreutils (`echo`, `pwd`, `true`, `false`, `whoami`, `uname`, `date`, `printenv`, `cat`, `head`, `tail`, `wc`). `ls` always queues because recursion hides in bundled flags (`-1R`) and GNU long-option abbreviations (`--rec`). The exemption is decided on the executable that would actually run: the first PATH match (or the given path) must resolve to the same-named binary directly inside `/bin`, `/usr/bin` or Ubuntu's rust-coreutils applet directory `/usr/lib/cargo/bin/coreutils` (exact directories, no subdirectories; the same basename keeps a multicall binary on the intended applet, so busybox-style targets queue), and that file and every directory above it must be root-owned and not writable by group or others, so an impostor script named `cat` or `/any/path/node` queues. On Ubuntu 26.04 (skr-linux-lan, verified 2026-10-23) `/bin` links to `usr/bin`, and `/usr/bin/{cat,echo,head,tail,wc,pwd,date,uname,printenv,whoami,false}` link to root-owned 755 applets in `/usr/lib/cargo/bin/coreutils`, with every directory up to `/` root:755. Those tools are trusted there; `true` links to `/usr/bin/gnutrue`, a different basename, so it queues. The host-gated test in `resources-trusted-path.test.ts` rechecks this on any such host. The CLI then spawns exactly that canonical path, never the original name or symlink, so swapping a symlink after classification cannot run a payload (`resources-race.test.ts`; Linux and macOS layouts in `resources-trusted-path.test.ts`). It is also refused while `LD_*`, `DYLD_*`, `GCONV_PATH` or `LOCPATH` is set. Runtimes and package managers queue even for `--version`/`--help`, because `NODE_OPTIONS=--require`, `npm_config_*` and preload settings load code before any flag is read. Every git command queues, because `status`/`ls-files` run `core.fsmonitor` (also injectable through `GIT_CONFIG_COUNT`), `branch` runs the `reference-transaction` hook and a pager, and `diff|log|show` run textconv or external diff drivers. Regression coverage lives in `resources-hardening.test.ts` and the occupied-slot dispatcher test in `resources-bypass.test.ts`. Shims already pass non-heavy commands straight through.

Node shim classification consumes known runtime option values, including `--diagnostic-dir /tmp`, before identifying a tool entrypoint. Unknown or incomplete Node options queue conservatively, even when later arguments include `--help`. Recognized Vitest entrypoints retain their worker cap after runtime options and the Node `--` separator. Arguments after an ordinary script path remain that script's arguments. The Node 26.4 bare forms of `--experimental-config-file` and `--experimental-specifier-resolution` do not consume the next argv; only their `=` forms are accepted as value options. Any separate option value that itself identifies a tool, ttr launcher, or heavy script makes classification ambiguous and queues conservatively.

The adaptive design requires a CLI release before activation. Optional `maxValidationLanes` accepts an integer from the base count through `8` and defaults to the base count. After release and a full idle drain, `ttr resources setup --max-lanes N` explicitly opts into a higher ceiling. Host capacity never changes the default automatically. Changing base lanes, maximum lanes, or aggregate worker budgets requires idle owners and zero waiters. Use `--workers` only for a justified aggregate budget. A maximum is a ceiling, not a promise of concurrent jobs.

Burst admission above the base requires a load-to-CPU ratio below `0.7` and sufficient memory. macOS requires normal memory pressure, reported as `1`. Linux requires at least 25% available memory and enough available memory for the estimated per-lane need. Missing telemetry refuses burst admission while preserving base admission behavior. Burst memory checks still apply with `--ignore-pressure`. FIFO order remains unchanged, and running jobs are never interrupted to shrink occupancy.

Shims classify only the program for `node`, `bun`, `bunx` and `npx`: the first positional argument after the runtime's own flags. Its later arguments belong to that program, so `bun /path/ttr resources run -- bunx vitest` is `ttr`, not vitest. The `ttr` CLI is a `#!/usr/bin/env bun` launcher and starts through the bun shim whenever the shims are on PATH (for example from a `~/.zshenv` that adds them for every zsh, including `ssh host 'cmd'` and `zsh -c`). Shims never admit it: `ttr` performs its own admission, and a shim admitting it first would hold the only lane while `ttr run` queued behind its own parent. Inside an admitted job, nested shims (`bunx` → a `#!/usr/bin/env node` vitest entry → the node shim) pass through under the owner once ancestry is verified. `resources-shim-chain.test.ts` reproduces that chain with one lane.

The effective lane count is `max(1, min(maxValidationLanes, host lane ceiling))`, so base lanes above the host ceiling (for example a config copied from a larger machine) are capped as well, where the host lane ceiling is `max(1, min(8, floor(memory GiB / 4), CPUs - 2))` (6 on a 24 GiB / 10 CPU host). Worker totals no longer cap the lane count. Admission subtracts recorded running allocations from each budget. Once the aggregate budget is spent, each further pressure-gated burst lane receives exactly one worker, so the overcommit is bounded to one worker per burst lane. For multi-lane or adaptive configurations, the aggregate worker total is clamped with a warning to the host worker ceiling, `min(8, floor(memory GiB / 8), floor(CPUs / 2))` when that exceeds the legacy budget. Configured totals are never raised automatically.

Before replacing the installed scheduler, fully drain old brokers, shim processes, and FIFO waiters. An old scheduler encountering `slots/2` fails closed. Never rewrite tickets, remove live locks, or run mixed versions. Source tests/review do not authorize installation or activation, and this design does not change any installed scheduler. Reconcile every legacy `status.owner` consumer first. Status retains `owner`, `owners`, `laneCount`, `waiting`, and `limits`, and adds `baseLanes`, `maxLanes`, `effectiveLanes`, `occupied`, `burst: { eligible, reason }`, `ownerDetails` (PID, child PID, command, cwd, elapsed seconds, current CPU percent, cumulative CPU seconds, idle seconds), `waitingDetails` (command and wait time), and `warnings`. Brokers sample their owned process tree's cumulative CPU every 30 seconds into the slot's `activity.json`. Status warns when an owner has been idle at 0% CPU for more than 10 minutes. It never signals or kills owners. The compatibility `owner` stays populated whenever any owner exists; initializing occupancy is reported separately.

Admission publishes complete owner metadata exclusively and serializes pressure checks, FIFO selection, and atomic slot claims, re-caps the original arguments to the admitted policy, and rejects policy changes during pressure probing. A live legacy owner, surviving child group, or old waiter excludes all slots. Malformed/unknown state fails closed. Initialization has a 30-second grace followed by a state recheck; time never expires a live owner. An abandoned mutex removal marker requires operator recovery review. Cancellation removes only its own ticket/slot after its owned child group drains. Workload execution waits for a durable child-PID receipt.

Cross-machine offload goes through `ttr box`. `ttr resources run --offload auto -- <command>` offloads only when every effective local lane is occupied or local waiters exist; `--offload <runner-id>` always targets that runner and fails instead of falling back. Offload requires a `ttr login` session and a clean tree whose `HEAD` is contained in an `origin/*` remote-tracking branch (a commit only on a fork or other remote is refused). Only the SHA, the relative directory and the argv travel, inside a typed commit-run envelope; no local environment is sent. The runner fetches that exact commit into a temporary worktree and removes it afterwards. Logs stream while the run polls, paging forward by the per-run event sequence cursor so long runs are neither truncated nor refetched, and lines that commit late are never skipped, the remote exit code is propagated, and `--timeout` (default `30m`) or Ctrl-C (handled from before the run is created) requests a remote stop (exit `124` or `130`). Each create carries a fresh operation ID as `idempotencyKey`. If the acknowledgement is lost, the CLI stops the run by that key within a bounded retry, or prints the key when cancellation cannot be confirmed. Once a remote run exists, the command never falls back to a local run in either mode: if the control plane stays unreachable while following it, the CLI requests a remote stop and exits `1`. `--offload auto` queues locally only when no run was created: offload was unavailable, no runner was eligible, or the server rejected the run with a `4xx`. An ambiguous creation failure (network error or `5xx`) exits `1` instead, because the run may exist.

A runner is eligible only when its heartbeat is fresh (under 60 seconds by the server clock from the snapshot's `Date` header, never the local clock; a list `status` of `online` alone is not freshness), it is not draining, `run` is enabled, it holds no Judge or playground role, it attests `executionMode: trusted`, and it advertises `protocols.commitRun` containing the client's envelope version (`capability_missing` otherwise). Otherwise the diagnostic names a `blockedBy` reason: `local_saturated`, `no_eligible_runner`, `offline`, `stale_heartbeat`, `draining`, `capability_missing` or `trust_cap`. When no runner is eligible, the closest actionable blocker is reported first (`stale_heartbeat`, `offline`, `draining`, `capability_missing`), then `trust_cap`. Queue messages print `blockedBy=local_saturated` with an `--offload auto` hint. `ttr resources offload [--runner <id>] [--json]` shows local saturation, every runner's eligibility and the selected target. `ttr box runners --json` adds the same `trustedWork` verdict per runner. Root admins can use `ttr box feature --runner <id> --feature <name> --enable|--disable` and `ttr box drain --runner <id> [--undo]`. Regression coverage lives in `resources-box-offload.test.ts`, `resources-box-offload-safety.test.ts` and `devbox-fleet.test.ts`.

Elevated memory pressure holds new admission while existing jobs continue. Blocked waiters back off outside admission, remain cancellable, and probe pressure afresh before launch. This is cooperative scheduling; scripts can still fan out within a slot. Sequence lint, tests and browser QA when memory is limited.

Shell setup preserves existing content and original backups through marked Zsh/Bash blocks. Open a new shell to activate hooks, or use `--shell none` for explicit queue usage. Absolute paths, custom PATH replacement and existing processes can bypass shims; wrap unrecognized scripts explicitly.

Out-of-range numeric configuration values (lanes `1`–`8`, workers and Turbo `1`–`64`, `maxValidationLanes` below the base) are clamped with a stderr warning that names the field and allowed range. Invalid JSON or wrongly typed fields produce an `Invalid resource configuration: <field> <expectation>` error that never discloses field values. Explicit `run` and `setup` fail on that error. `status` still prints its report with `config.state: invalid` and the error as a warning, then exits `1`; it also reports `disabled` admission and base lanes (or, failing that, `maxValidationLanes`) above the host lane ceiling as warnings. Shims print it and run the command without admission, so one bad value cannot brick every tool on the machine. `disable`/`enable` toggle future automatic admission. All configuration mutations, including uninstall, serialize with admission and read the latest policy inside the mutex. Disabled, out-of-scope and deliberate bypass commands retain their arguments/environment without admission-cap validation. `TTR_RESOURCES_BYPASS=1` is a deliberate one-command bypass. Once owners and waiters drain, `uninstall` removes owned hooks/shims and preserves shell content, configuration and backups. Keep the default `TTR_RESOURCES_HOME` across projects; private temporary homes are for lightweight synthetic tests, not parallel heavy work. Resource fixtures mock host capacity in Vitest parents and disposable Bun loaders/shims. Read exit diagnostics after subprocess pipes close; use a separate exit barrier when testing surviving descendants. Parent Vitest coverage is not evidence of coverage inside Bun subprocesses.

The bounded monitor emits JSONL memory-pressure, T3-tree resident-memory and top-process samples without arguments or environment values. RSS differs from Activity Monitor's footprint and can count shared pages multiple times.
Offload full validation with `ttr box run --runner <remote-id> -- <command>` only after verifying a different machine and intended checkout. Same-machine runners/containers consume local RAM; resource setup does not configure runners, transmit credentials, or restart Docker.

### Multi-host weighted admission

`ttr resources run --hosts -- COMMAND` admits a job across the hosts in `<resources home>/hosts.json`. Without that file, `--hosts` refuses to run and admission stays the single-host lane FIFO. The CLI never writes or activates `hosts.json`; an operator installs it after a reviewed release. The registry decides where code runs, so it is trusted only from the canonical per-user home `~/.tuturuuu/resources`. That directory must be a real 0700 directory owned by you, `hosts.json` a real 0600 file owned by you, and every parent a non-symlink directory writable only by root or you (a root-owned sticky directory such as `/tmp` is allowed). The file is opened with `O_NOFOLLOW` and re-verified through the descriptor. A home inside an opted-in repository root (`roots`, or a `repositories` checkout) is refused too, as is an invalid `config.json`. When `TTR_RESOURCES_HOME` points anywhere else, or any check fails, the registry is ignored and `--hosts` is disabled (`resources-hosts-trust.test.ts`). `ttr resources hosts [--json]` shows each host's budget, reservations and waiters (or the proposed registry when none is installed). `ttr resources hosts --simulate [--json]` is an offline dry run of the measured queue through the same planner.

- **Classes and weights.** Explicit `--hosts` jobs are `heavy` unless `--class light` is given; trivial commands never queue. Local light work also passes the dequeue disk gate, and the CLI tells a nested `run --hosts` which reservation it runs under through `TTR_RESOURCES_HOST_RESERVATION`. That nested job then runs under the ancestor's reservation, but only while that reservation is live and its broker or owned child group is a verified process ancestor; otherwise it would deadlock behind its own ancestor. No registered host that could ever hold the job (counting `remoteOk`) means it fails fast instead of queueing. Each host has separate `slots.light` and `slots.heavy`, per-class CPU/memory `weights`, and per-class worker caps (`workers`). A job is admitted only if its class slot is free and the weighted sum fits `capacity - reserved`.
- **Reserved headroom.** `reserved.cpus`, `reserved.memoryGiB` and `reserved.diskGiB` are per host, for co-tenants such as production containers, CI runners, Judge workers and the desktop.
- **Hosts.** The single `local` host uses the lane FIFO for heavy work. Lane owners count as local heavy load, a heavy `--hosts` job takes a local lane only while no lane waiter is ahead, and light local work holds a ledger reservation. `runner` hosts dispatch the exact pushed commit through the devbox offload transport (`runBoxOffload`, unchanged). Immediately before remote creation the runner is re-validated against a fresh snapshot that carries the server's timestamp. If it is stale, draining or missing, its disk is unknown or low, or the snapshot has no server time, the reservation is released and the job requeues without dispatching. Admission also refuses runners in snapshots without a server timestamp, and runners without activity telemetry (other clients' runs would be invisible). The commit plan is recomputed at dispatch; if it changed, the job falls back to local hosts. SIGHUP is forwarded to the offload transport's cancellation as SIGTERM, so a closed terminal also stops the remote run. Runs that other clients start on that runner count as heavy load. A runner that refuses creation means no remote run exists, so the job is requeued for local hosts; an ambiguous failure is never repeated locally.
- **Admission.** Admission requires a fresh trusted runner (`evaluateTrustedRunner` plus `telemetryTtlSeconds`) and known free disk at or above `reserved.diskGiB`. Unreachable fleets, stale heartbeats, draining runners and unknown disk are never admitted. Dirty or unpushed trees are local-only.
- **Canonical reservations.** Tickets and reservations live in `<home>/hosts-state/` and are created only inside the host-wide admission mutex. Concurrent requesters on this machine therefore cannot double-assign a slot. Each reservation is tied to its broker PID (or owned child group). Cancellation (SIGINT/SIGTERM/SIGHUP) releases it, and a dead owner is pruned on the next round. A malformed entry closes admission. Only `scope: "host"` reservations claim capacity: a project-only lock never stands in for host-wide admission.
- **Fairness.** Waiters are ordered by their project's live share, then age. A project is the repository's common Git directory, so all Upskii worktrees share one identity. A waiter overtaken `fairness.maxBypass` times (default 4) holds every host that could ever fit it until it is placed. This backpressure is what prevents starvation.
- **Disk at dequeue (REV-6480-1/2).** Every lane-queued job re-checks free disk inside admission, immediately before claim and spawn, using a local `statfs` probe (`resources-disk-gate.ts`).
  - It uses Lane ST's thresholds: `TTR_STORAGE_MIN_FREE` (default 15 GiB) and `TTR_STORAGE_MIN_FREE_PERCENT` (default 5%).
  - Below the floor, or when free disk is unknown, the job keeps waiting (fail closed).
  - Block reasons name only the job volume, the free/floor figures and an errno code, never the working path or raw filesystem errors, and status labels them `blockedBy=disk`.
  - The probe runs before taking the admission mutex, only for the FIFO head. It is bounded (2 s) and never stacked on a pending probe, so a hung volume counts as unknown and stalls no other admission.
  - `TTR_RESOURCES_IGNORE_DISK=1` overrides it for one command.
  - Once Lane ST's `storage-headroom` lands, the probe can delegate to it without changing this hook.

### Docker metadata lifecycle diagnostic

The SDK metadata subprocess is silent by default. Disposable CI can opt in with
`CI=true` and `TTR_DOCKER_METADATA_DIAGNOSTIC=1`. Each invocation emits one JSON
record (`schema: ttr-docker-metadata-v1`) at its existing settlement boundary.
It records a process-local ordinal, Node/Bun runtime versions, monotonic elapsed
milliseconds, spawn/first stdout/error/exit/close times, first and total stdout
byte counts, deadline time and callback lateness, kill return value, fixed spawn
classification, numeric exit code and an allowlisted signal. Numeric counters
saturate at 2,147,483,647; versions are validated and bounded; records stay below
1024 bytes. No arguments, paths, environment values, Docker host/context, metadata,
output or exception text are included.

A null event time means it was not observed before settlement. In particular,
settlement still follows error or exit and never waits for close. The stdout
consumer continues draining with the existing 65,536-character retained cap;
diagnostics add no timers, subprocesses, probes or retries. The 4000ms deadline
and fail-closed capacity behavior remain unchanged. Focused pure mocks in
`devbox-docker-metadata-diagnostic.test.ts` cover opt-in gating, bounded fields,
event order, deadline/kill outcomes, errors, close timing, overflow and redaction.

### Launcher mismatch incident recovery

Symptom: the global CLI rejects missing, stale or malformed launchers. A stale workspace SDK dist can write its own entry into shared launchers before admission, and its nested run can block the queue. Never run operational commands through workspace or ancestor `node_modules/.bin/ttr` or stale `packages/sdk/dist`.

Repository admission uses the verified global `~/.bun/bin/ttr` (stable >= 0.28.0). `check:changed` and `node scripts/ttr-run.js -- COMMAND` run directly when the inherited `TTR_RESOURCES_ADMITTED` or `TTR_RESOURCE_OWNER` marker is present. When the global install is absent, `check:changed` warns and runs sequentially with its existing worker limits. The operational wrappers still require a global CLI, and an invalid/old installed global fails with `bun add -g tuturuuu` recovery guidance. None falls back to a workspace binary. Refresh declared workspace bin links after adopting the source wrapper. `bun install` alone can leave orphan aliases unchanged; use the explicit orphan inspection/removal procedure below. This does not rebuild dist. The shipped bin works in installed packages; workspace aliases refuse to execute dist, including from `bunx`.

An operator with installation authority must identify and drain the offending jobs, preserve the existing resource configuration, then restore canonical launchers through the trusted global CLI with the **same existing roots and shell settings**:

```sh
~/.bun/bin/ttr resources setup --root <existing-root-1> --root <existing-root-2> --shell <existing-shell>
~/.bun/bin/ttr resources status --json
```

Fence-enabled CLI versions refuse a different installation by default. Inspect `setup --force --dry-run` before an intentional cross-install restore, then use `setup --force` with the same roots after the queue drains. The plan reports each old/new launcher. Force never overwrites unmanaged files. Version changes within one Bun global installation are allowed; versioned cache paths normalise to its stable global link. Run/shim never write launchers. Review status for enabled installation and an empty queue before resuming work. Source changes do not repair already-installed links or prove historical writer attribution.

Regression coverage: `scripts/trusted-ttr.test.js`, `scripts/workspace-ttr-bin.test.js`, and `resources-provisioning.test.ts` exercise ancestor lookup, inherited admission, minimum version, stale bins, same-install upgrades, refusal and forced replacement with disposable homes.

#### Orphan workspace aliases

A refusal can also mean stale workspace bin links in an ancestor checkout that still has a legitimate SDK dependency. Inspect that ancestor's package.json and links first. For a declared dependency, run `~/.bun/bin/ttr resources run -- bun install --force` there to regenerate aliases pointing to `bin/ttr.cjs`; retain its legitimate package link. `--no-ttr` does not bypass unsafe ancestor links. The removal procedure below applies only to confirmed undeclared orphan symlinks.

If the root manifest has no `tuturuuu` dependency, old symlinks can remain: `node_modules/tuturuuu -> ../packages/sdk` and `node_modules/.bin/{ttr,tuturuuu,tutur3u} -> ../tuturuuu/dist/cli/index.js`. Bun may report no changes and keep them. The trusted repo wrapper and `check:changed` refuse such ancestor aliases, even inside an admitted lane; they never execute or remove them silently. A healthy global CLI does not make those bare aliases safe.

From the affected ancestor checkout, inspect the manifest and every link first. Only after confirming these are the orphan symlinks above, remove those links explicitly and reinstall under admission:

```sh
ls -l node_modules/tuturuuu node_modules/.bin/ttr node_modules/.bin/tuturuuu node_modules/.bin/tutur3u
# Confirm the root has no tuturuuu dependency and each path is a symlink.
for alias in ttr tuturuuu tutur3u; do
  file="node_modules/.bin/$alias"
  if [ -L "$file" ] && [ "$(readlink "$file")" = '../tuturuuu/dist/cli/index.js' ]; then
    rm -- "$file"
  fi
done
if [ -L node_modules/tuturuuu ] && [ "$(readlink node_modules/tuturuuu)" = '../packages/sdk' ]; then
  rm -- node_modules/tuturuuu
fi
~/.bun/bin/ttr resources run -- bun install
```

Do not remove `packages/sdk` or its dist. A declared dependency can recreate aliases pointing to the new `bin/ttr.cjs` wrapper; an undeclared orphan can remain absent. Inspect the resulting links before resuming. Native temp-directory and symlinked-home tests use physical paths, so macOS `/var/folders` aliases do not change installation identity. Resolve HOME and the Bun install base independently: a symlinked `.bun` or `.bun/install` is supported, while entries outside that resolved install base are still refused.
