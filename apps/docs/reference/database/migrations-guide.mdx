The Tuturuuu platform uses Supabase migrations to manage database schema changes with version control and reproducibility.

## Declarative adoption preparation

Declarative schemas are opt-in preparation. Existing migrations remain the
source of truth; this foundation does not enable an engine, export a baseline,
change deployment gates, or regenerate database types.

```sh
node apps/database/scripts/declarative-schema-readiness.js --json
```

Run after workspace dependency setup. The checker prints migration/schema
filename and byte-hash inventories, config/lock identities, the PostgreSQL major,
and bounded help probes of the installed bundled Supabase CLI. It installs
nothing and makes no database connections. It rejects linked targets, database
URLs, apply/overwrite/experimental flags, and unknown arguments before inspection.
Exit 2 means adoption is held; exit 1 means inspection failed; `--help` exits 0.
A schema tree plus supported commands cannot produce a ready result. Keep the
report in ignored task evidence.

The [current Supabase guide](https://supabase.com/docs/guides/local-development/declarative-database-schemas)
distinguishes pg-delta `db schema declarative generate`/`sync` from legacy migra
`db diff` and ordered `schema_paths`. Check exact installed help first. Root owns
any CLI upgrade choice. Do not use a pg-delta export with legacy diffing, add a
partial tree, or silently change the engine/config or existing `sb:diff` command.

Baseline approval requires a fresh source/config/lock/version binding, explicit
reconciliation of pending migration owners, complete disposable Linux replay,
and full ledger comparison. Export DDL only from that task-owned database,
review for embedded secrets, then prove a no-op declarative diff against the
complete history and catalog/security parity from a second disposable replay.
A production dump can omit pending migrations and is not an approved baseline.
Never reset foreign databases or rewrite deployed history.

Keep DML/backfills, environment operations, and diff-engine unsupported objects
in reviewed imperative migrations with an explicit exception inventory. Verify
RLS, public/private grants and default privileges, service-role functions,
security-definer search paths, extension versions, Storage policies, and
application customizations of managed auth/storage/realtime schemas separately.
A no-op diff cannot prove objects the engine excludes. Keep declarations below
the authored 700-LOC ceiling, use the shared resource queue, and prove closure of
all task-owned containers, volumes, ports, and scopes.

The detailed repository procedure is
`plugins/tuturuuu/skills/tuturuuu-database/references/declarative-schema-adoption.md`.
Until those independently reviewed receipts exist, adoption remains preparation.
After approval, use the qualified engine to propose forward migrations, review
all generated SQL, replay and test security, then run typegen on the applied
schema. Production application remains separately authorized.

## Creating Migrations

### Method 1: Generate from Studio Changes

**Best for:** Visual schema editing, quick table creation

1. **Make changes in Supabase Studio:**
   ```bash
   bun sb:start
   # Open http://localhost:8003
   # Make changes in Table Editor
   ```

2. **Generate migration:**
   ```bash
   bun sb:diff
   ```

3. **Review generated file:**
   ```bash
   # apps/database/supabase/migrations/20250101120000_add_new_table.sql
   ```

### Method 2: Manual SQL Migration

**Best for:** Complex changes, custom functions, data migrations

1. **Create blank migration:**
   ```bash
   bun sb:new add_custom_function
   ```

2. **Edit migration file:**
   ```sql
   -- apps/database/supabase/migrations/20250101120000_add_custom_function.sql

   -- Create custom function
   CREATE OR REPLACE FUNCTION get_user_task_count(user_uuid uuid)
   RETURNS integer AS $$
     SELECT COUNT(*)::integer
     FROM workspace_tasks
     WHERE created_by = user_uuid;
   $$ LANGUAGE sql SECURITY DEFINER;
   ```

## Migration File Structure

### Naming Convention

```
[timestamp]_[descriptive_name].sql
```

Examples:
```
20250101120000_create_tasks_table.sql
20250101130000_add_task_priority_column.sql
20250101140000_update_task_rls_policies.sql
```

Keep new migration timestamps ahead of the latest migration already on `main`,
`staging`, and `production`. Supabase refuses to apply a local migration that
sorts before the last remote migration unless the operator passes
`--include-all`. Staging and production CI intentionally run
`supabase db push --include-all` so each project can converge after migration
history changes, but ordinary forward deploys should still keep timestamps
monotonic. After a rebase, merge, or hotfix, re-list
`apps/database/supabase/migrations` and rename any still-unapplied local
migration forward instead of treating `--include-all` as permission to edit or
replay old migration history.

PR CI enforces this: `scripts/check-migration-timestamps.js` fails when any
migration a pull request adds or renames sorts at or before the newest
migration on its base branch, and names the offending files and the base
timestamp. Run it locally (or through `bun check:changed`) to compare against
your local `origin/main`.

### File Template

```sql
-- Migration: [Description]
-- Created: [Date]
-- Author: [Name]

-- Create table
CREATE TABLE IF NOT EXISTS table_name (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  created_at timestamptz DEFAULT now()
);

-- Add indexes
CREATE INDEX idx_table_name_column ON table_name(column);

-- Enable RLS
ALTER TABLE table_name ENABLE ROW LEVEL SECURITY;

-- Add RLS policies
CREATE POLICY "policy_name"
ON table_name
FOR SELECT
USING (true);

-- Add comments
COMMENT ON TABLE table_name IS 'Description of table';
COMMENT ON COLUMN table_name.column IS 'Description of column';
```

## Common Migration Patterns

### Creating Tables

```sql
-- Create workspace-scoped table
CREATE TABLE workspace_resources (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  ws_id text NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  name text NOT NULL,
  description text,
  created_by uuid REFERENCES workspace_users(id) ON DELETE SET NULL,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);

-- Add indexes
CREATE INDEX idx_workspace_resources_ws_id ON workspace_resources(ws_id);
CREATE INDEX idx_workspace_resources_created_by ON workspace_resources(created_by);

-- Enable RLS
ALTER TABLE workspace_resources ENABLE ROW LEVEL SECURITY;

-- Add policies
CREATE POLICY "workspace_members_can_view"
ON workspace_resources FOR SELECT
USING (
  ws_id IN (
    SELECT ws_id FROM workspace_members WHERE user_id = auth.uid()
  )
);

CREATE POLICY "permission_required_to_modify"
ON workspace_resources FOR ALL
USING (
  ws_id IN (
    SELECT wm.ws_id FROM workspace_members wm
    JOIN workspace_role_permissions wrp
      ON wrp.ws_id = wm.ws_id AND wrp.role_id = wm.role
    WHERE wm.user_id = auth.uid()
      AND wrp.permission = 'manage_resources'
  )
);
```

### Adding Columns

```sql
-- Add nullable column
ALTER TABLE workspace_tasks
ADD COLUMN priority integer;

-- Add column with default
ALTER TABLE workspace_tasks
ADD COLUMN status text DEFAULT 'pending';

-- Add NOT NULL column (requires default or backfill)
ALTER TABLE workspace_tasks
ADD COLUMN category text DEFAULT 'general' NOT NULL;

-- Update existing rows (if needed)
UPDATE workspace_tasks
SET category = 'important'
WHERE priority >= 4;
```

### Modifying Columns

```sql
-- Rename column
ALTER TABLE workspace_tasks
RENAME COLUMN old_name TO new_name;

-- Change column type
ALTER TABLE workspace_tasks
ALTER COLUMN priority TYPE smallint USING priority::smallint;

-- Add constraint
ALTER TABLE workspace_tasks
ADD CONSTRAINT priority_range CHECK (priority BETWEEN 0 AND 5);

-- Drop constraint
ALTER TABLE workspace_tasks
DROP CONSTRAINT priority_range;
```

### Creating Indexes

```sql
-- Standard index
CREATE INDEX idx_tasks_ws_id ON workspace_tasks(ws_id);

-- Composite index
CREATE INDEX idx_tasks_ws_list ON workspace_tasks(ws_id, list_id);

-- Partial index
CREATE INDEX idx_incomplete_tasks
ON workspace_tasks(ws_id)
WHERE completed = false;

-- Unique index
CREATE UNIQUE INDEX idx_unique_task_name
ON workspace_tasks(ws_id, name);

-- GIN index for JSONB
CREATE INDEX idx_metadata_gin ON workspace_tasks USING GIN (metadata);

-- Text search index
CREATE INDEX idx_tasks_search
ON workspace_tasks USING GIN (to_tsvector('english', name || ' ' || COALESCE(description, '')));
```

### Creating Functions

```sql
-- Simple function
CREATE OR REPLACE FUNCTION get_workspace_task_count(workspace_id text)
RETURNS integer AS $$
  SELECT COUNT(*)::integer
  FROM workspace_tasks
  WHERE ws_id = workspace_id;
$$ LANGUAGE sql SECURITY DEFINER;

-- Function with complex logic
CREATE OR REPLACE FUNCTION complete_task_with_notification(task_uuid uuid)
RETURNS void AS $$
DECLARE
  task_name text;
  task_ws_id text;
BEGIN
  -- Update task
  UPDATE workspace_tasks
  SET completed = true, completed_at = now()
  WHERE id = task_uuid
  RETURNING name, ws_id INTO task_name, task_ws_id;

  -- Create notification (example)
  INSERT INTO notifications (ws_id, message, type)
  VALUES (task_ws_id, format('Task "%s" completed', task_name), 'success');
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

### Creating Triggers

```sql
-- Update updated_at timestamp trigger
CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS trigger AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trigger_update_workspace_tasks_updated_at
  BEFORE UPDATE ON workspace_tasks
  FOR EACH ROW
  EXECUTE FUNCTION update_updated_at();
```

### Creating Enums

```sql
-- Create enum
CREATE TYPE task_status AS ENUM ('pending', 'in_progress', 'completed', 'cancelled');

-- Add enum column
ALTER TABLE workspace_tasks
ADD COLUMN status task_status DEFAULT 'pending';

-- Modify enum (add value)
ALTER TYPE task_status ADD VALUE 'on_hold';

-- Cannot remove enum values - requires recreation
```

## Data Migrations

### Safe Data Migration Pattern

```sql
-- 1. Add new column
ALTER TABLE workspace_tasks
ADD COLUMN new_priority integer;

-- 2. Backfill data
UPDATE workspace_tasks
SET new_priority = CASE
  WHEN old_priority = 'high' THEN 5
  WHEN old_priority = 'medium' THEN 3
  WHEN old_priority = 'low' THEN 1
  ELSE 0
END;

-- 3. Make NOT NULL (if needed)
ALTER TABLE workspace_tasks
ALTER COLUMN new_priority SET NOT NULL;

-- 4. Drop old column (in separate migration after verification)
-- ALTER TABLE workspace_tasks DROP COLUMN old_priority;
```

### Batch Processing Large Migrations

```sql
-- For tables with millions of rows, batch the updates
DO $$
DECLARE
  batch_size integer := 1000;
  rows_updated integer;
BEGIN
  LOOP
    UPDATE workspace_tasks
    SET new_column = calculate_value(old_column)
    WHERE id IN (
      SELECT id FROM workspace_tasks
      WHERE new_column IS NULL
      LIMIT batch_size
    );

    GET DIAGNOSTICS rows_updated = ROW_COUNT;
    EXIT WHEN rows_updated = 0;

    -- Commit after each batch
    COMMIT;
  END LOOP;
END $$;
```

## Testing Migrations

### Local Testing

```bash
# Reset to clean state
bun sb:reset

# Verify schema
bun sb:status

# Check migration list
ls apps/database/supabase/migrations/

# Test specific queries
psql -h localhost -U postgres -d postgres -c "SELECT * FROM workspace_tasks LIMIT 5;"
```

### Test RLS Policies

```sql
-- Set user context for testing
SET request.jwt.claim.sub = 'user-uuid-here';

-- Test query with RLS
SELECT * FROM workspace_tasks WHERE ws_id = 'workspace-123';

-- Reset context
RESET request.jwt.claim.sub;
```

### Verify Indexes

```sql
-- Check if index is being used
EXPLAIN ANALYZE
SELECT * FROM workspace_tasks WHERE ws_id = 'workspace-123';

-- List all indexes on table
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'workspace_tasks';
```

## SQL grant guard

The guard checks all migrations, rollbacks and schema SQL against the
[declarative grant policy](#declarative-grant-guard-p2-2). Historical findings
are digest-bound debt, not safe exceptions; there is no date cutoff.
Dynamic SQL requires statement-adjacent security review. Settings of
`standard_conforming_strings` are forbidden, and `set_config('search_path', …)`
fails closed. Dollar-quoted bodies cannot supply review markers.

## Migration Checklist

Before committing a migration:

- [ ] Migration file has descriptive name
- [ ] All tables have RLS enabled
- [ ] No `public`/`anon` grants and every `SECURITY DEFINER` function revoked from `public, anon` ([SQL grant guard](#sql-grant-guard))
- [ ] RLS policies are tested
- [ ] Indexes added for foreign keys
- [ ] Indexes added for frequently queried columns
- [ ] Comments added for complex logic
- [ ] Data migration is idempotent
- [ ] Migration tested with `bun sb:reset`
- [ ] Type generation updated (`bun sb:typegen`)
- [ ] Breaking changes documented

## Deploying Migrations

### ⚠️ AGENTS: NEVER RUN THESE COMMANDS

Agents should prepare migrations but NEVER deploy them. Only users should run:

```bash
# Link to remote project (one-time setup)
bun sb:link

# Push migrations to production
bun sb:push
```

### Agent Workflow

**Agents should:**
1. Create migration file
2. Test locally with `bun sb:reset`
3. Run `bun sb:typegen`
4. Commit files
5. **Instruct user to run `bun sb:push`**

**Agents should NEVER:**
- Run `bun sb:push`
- Run `bun sb:linkpush`
- Deploy to production

## Rollback Strategy

See the [manual incident rollback runbook](/reference/database/migration-incident-rollbacks)
for the per-migration inventory, reverse run order, timeout/transaction rules and
forward-only cross-app token containment. These manual files do not alter the
hosted migration ledger.

### Simple Rollback

```sql
-- Create reverse migration
-- apps/database/supabase/migrations/20250101150000_rollback_add_priority.sql

ALTER TABLE workspace_tasks DROP COLUMN priority;
```

### Complex Rollback

```sql
-- apps/database/supabase/migrations/20250101150000_rollback_task_status_enum.sql

-- 1. Add back old column
ALTER TABLE workspace_tasks ADD COLUMN old_status text;

-- 2. Convert data
UPDATE workspace_tasks
SET old_status = CASE
  WHEN status = 'pending' THEN 'todo'
  WHEN status = 'in_progress' THEN 'doing'
  WHEN status = 'completed' THEN 'done'
END;

-- 3. Drop new column
ALTER TABLE workspace_tasks DROP COLUMN status;

-- 4. Rename old column
ALTER TABLE workspace_tasks RENAME COLUMN old_status TO status;

-- 5. Drop enum type
DROP TYPE task_status;
```

## Common Issues

### Issue: Migration Fails on Production

**Cause:** Local Supabase version differs from production

**Solution:**
```bash
# Check Supabase version
bun sb:status

# Update Supabase CLI
bun add -g supabase

# Recreate local instance
bun sb:stop
bun sb:start
```

### Issue: Type Generation Fails

**Cause:** Migration has syntax errors

**Solution:**
```bash
# Reset database
bun sb:reset

# Check migration syntax
cat apps/database/supabase/migrations/[migration-file].sql

# Fix errors and retry
bun sb:typegen
```

### Issue: RLS Policy Conflicts

**Cause:** Multiple policies on same table/operation

**Solution:**
```sql
-- List all policies
SELECT policyname, permissive, roles, cmd, qual
FROM pg_policies
WHERE tablename = 'workspace_tasks';

-- Drop conflicting policy
DROP POLICY "old_policy" ON workspace_tasks;
```

## Best Practices

### ✅ DO

1. **Use descriptive names**
   ```sql
   20250101_add_task_priority_with_validation.sql
   ```

2. **Add indexes for foreign keys**
   ```sql
   CREATE INDEX idx_tasks_ws_id ON workspace_tasks(ws_id);
   ```

3. **Enable RLS on all tables**
   ```sql
   ALTER TABLE table_name ENABLE ROW LEVEL SECURITY;
   ```

4. **Add comments for clarity**
   ```sql
   COMMENT ON TABLE workspace_tasks IS 'User tasks within workspaces';
   ```

5. **Test migrations locally first**
   ```bash
   bun sb:reset
   ```

6. **Materialize replacement-table rows before rewiring child foreign keys**
   ```sql
   -- When replacing a parent table, copy or upsert the source rows first.
   INSERT INTO workspace_user_groups (id, ws_id, name)
   SELECT id, ws_id, name
   FROM workspace_courses
   ON CONFLICT (id) DO UPDATE
   SET name = EXCLUDED.name;

   -- Then backfill the child FK, validate it, and only afterwards drop the legacy column/table.
   ALTER TABLE workspace_course_modules ADD COLUMN group_id uuid;

   UPDATE workspace_course_modules
   SET group_id = course_id
   WHERE group_id IS NULL;

   -- Verify the backfill before dropping or rewiring the legacy FK in a follow-up migration.
   -- SELECT COUNT(*) FILTER (WHERE group_id IS NULL) AS unmigrated
   -- FROM workspace_course_modules;
   ```

### ❌ DON'T

1. **Don't skip RLS**
   ```sql
   -- ❌ Bad: No RLS
   CREATE TABLE table_name (...);
   ```

2. **Don't use DROP without backup**
   ```sql
   -- ❌ Dangerous
   DROP TABLE important_data;
   ```

3. **Don't modify old migrations**
   ```sql
   -- ❌ Bad: Modifying committed migration
   ```

4. **Don't deploy without testing**
   ```bash
   # ❌ Bad: Skip local testing
   bun sb:push
   ```

### Declarative grant guard (P2-2)

The SQL grant guard checks all migrations, schemas and rollbacks, including on
main. `scripts/ci/sql-grant-guard.baseline.json` records **historical debt, not
safe**: one entry per existing diagnostic, with path, rule and SHA-256 of the
statement or block. Shared file digests bind each entry to the complete file.
The baseline needs independent review; it never declares historical SQL safe.

A new diagnostic fails. Any change to a baselined file fails until its diagnostics
are fixed and its debt entries removed. Entries that no longer match also fail
and must be removed. The baseline can only shrink; additions, digest rewrites and
stale metadata fail. CI resolves shallow history explicitly and checks main
pushes against the pre-push commit. An unresolved base fails loudly.

For the initial reviewed bootstrap, generate from a pinned main SHA with
`node scripts/ci/sql-grant-guard-baseline.js --generate <full-main-SHA>`.
The guard independently checks bootstrap entries against that source snapshot.
Routine fixes remove debt entries rather than regenerating or growing the list.
Use `node scripts/ci/sql-grant-guard.js --report` to inspect debt and new findings.

Created functions and procedures require a subsequent matching-signature `REVOKE
ALL` from `PUBLIC, anon, authenticated`, plus a grant to `service_role` or a
same-file `-- tuturuuu: no-grant (internal)` or `-- tuturuuu: no-grant (trigger)`
comment. The grant policy applies in every file, including later standalone
migrations and schemas:

- Grants without an explicit parseable argument list fail.
- Schema-wide grants (`ON ALL ... IN SCHEMA`) and `ALTER DEFAULT PRIVILEGES`
  grants to `PUBLIC`, `anon`, or `authenticated` always fail, even with a marker.
- A grant to `authenticated` requires its own statement-adjacent review marker
  naming the exact canonical signature.
- A grant to `anon` or `PUBLIC` additionally requires `anon-required` in that
  marker. The legacy `allow-anon-grant` marker cannot satisfy this routine fence.

```sql
-- tuturuuu: reviewed(function-grant): public.example(integer) review=<reference>
GRANT EXECUTE ON FUNCTION public.example(integer) TO authenticated;

-- tuturuuu: reviewed(function-grant): public.example(integer) anon-required review=<reference>
GRANT EXECUTE ON FUNCTION public.example(integer) TO anon;
```

Use canonical signatures (`public` is explicit, argument names are omitted, and
aliases such as `int` normalize to `integer`). Each target in a multi-target grant
needs its own signature marker. A marker applies only on the statement's lines or
its immediately preceding line. A reviewed client grant satisfies intended access
for a CREATE, but the subsequent matching `REVOKE ALL` is still required.
Definers require `pg_catalog` first and `pg_temp` last, with no duplicate settings,
empty paths, user-dependent schemas or explicit temporary namespaces. Quoted
identifier case is significant. The live pgTAP gate remains authoritative for
schema CREATE privileges.

ALTER routine security/configuration/owner mutations, DO/EXECUTE statements,
complex routine/ACL/SET identifiers, role-membership grants and grant options
require security review. Policy names containing spaces are accepted. Separate
plain schema literals such as `'pg_catalog', 'pg_temp'` are accepted for
`search_path`; Unicode-escaped SET identifiers fail closed.

Record reviewed statements with a real line comment on the statement or its
immediately preceding line:

```sql
-- tuturuuu: reviewed(dynamic-sql-review): <review-reference>
DO $$ BEGIN EXECUTE 'SELECT 1'; END $$;

-- tuturuuu: reviewed(alter-routine-review): <review-reference>
ALTER FUNCTION public.example(integer) SET search_path = pg_catalog, pg_temp;
```

`reviewed(dynamic-sql-review)` also applies to EXECUTE and routine bodies; it
never waives required ACLs. `reviewed(quoted-identifier-review)` waives only the
complex-identifier review diagnostic. Strings, dollar bodies, block comments,
unrelated statements, and other files cannot supply markers. Migration, rollback,
and schema SQL are covered by CODEOWNERS. Rollbacks also reject public/anonymous grants, TRUNCATE, MAINTAIN and
default-grant restoration; their names must match a migration and an approved
suffix. Run the `sql-grant-guard*.test.js` suites with `node --test` for parser, baseline and
shallow-checkout regression coverage.


The single historical-debt baseline is retained, including path/rule/block digest,
occurrence, complete-file pins, stale-entry checks, and main's pre-push comparison.
The following seven real debt items carry a `class` field. Multiple diagnostics
for one statement receive the same class. These tags describe historical debt;
forward fixes do not alter applied migration bytes or automatically clear entries.

| File suffix | Statement lines | Class |
| --- | --- | --- |
| `20261029012300_tighten_legacy_table_grants.rollback.sql` | 2 | `latent-rollback-grant` |
| `20261029030500_align_cross_app_token_grant_and_private_fence.rollback.sql` | 6 | `latent-rollback-grant` |
| `20261029030600_pin_workspace_membership_rls.rollback.sql` | 43 | `latent-rollback-grant` |
| `20261029050430_merge_batch_null_guards.sql` | 9, 120 | `definer-path-hygiene` |
| `20261029100000_chat_first_message_creation_receipts.sql` | 39, 380 | `definer-path-hygiene` |

Regression evidence is in `sql-grant-guard-security.test.js` for signature review,
escaped GUCs, reviewed statements and false positives, and in the repository suite
for synthetic shallow history and the pre-push baseline fence.
